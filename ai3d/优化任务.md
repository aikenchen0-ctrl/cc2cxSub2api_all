# AI3D 优化任务

> 项目：`ai3d/`（卫星应用）。基线：2026-11-14。
> 全局约束见根目录 `评估报告.md`、`优化任务-总调度.md`；本文件只负责 `ai3d/` 内落地。

## 1. 项目定位与边界

- 卫星应用，图片/草图/GLB 的 3D 生成、查看与资源管理；服务端代调主站模型。
- SSO 建立 3 天 HttpOnly Session；浏览器不得接触 SuperKey、应用凭据或 SSO 密钥。
- 本项目只改 `ai3d/`，不改主站协议、根 Compose 或其他卫星。

## 2. 结论与商用判定

MIT 许可证相对清晰，但**票据消费是 JSON 文件、非事务，且 Compose 无健康检查**。当前适合内部验证，公开商用前须完成身份/票据持久化、上传生命周期和部署门禁。

4. 记录失败基线与独立任务卡。

### AI3-02 SSO 与模型代调（P0/P1）

**现象与证据**
- `server/auth-sso.mjs:33` 将 `consumed` 状态写入 JSON 文件；多进程/并发写可能丢失或覆盖。
- Compose 已用 `${VAR:?}` 强制 `SUB2API_APP_CREDENTIAL` 与 `SUB2API_SSO_SECRET`；健康检查仍缺失。
- 当前调用使用裸 `X-Sub2API-On-Behalf-Of`；主站 S2A-07 后改为短期用户断言。

**实施步骤**
1. 校验 SSO `iss/aud/sub/iat/exp/jti`，TTL ≤ 2 分钟，`aud=ai3d` 精确匹配。
2. 将消费状态升级为 SQLite 唯一键或 Redis 原子操作；禁止 JSON 文件作为生产唯一防线。
3. 补并发、重启、多副本重放测试；消费与 Session 建立应在同一事务边界内。
4. 验证 3 天 Session、生产 Cookie `Secure + HttpOnly`、注销可撤销。
5. 服务端调用主站只使用本应用凭据、slug 和用户断言；缺失一律 401/503。
6. 主站 S2A-01/06/07 完成后改用专属凭据/派生密钥，测试跨 slug 被拒。
7. 计费只走主站 `ai3d` slug 配置或当前用户余额；不得发送或接受 `X-Sub2API-Payer`、`X-Sub2API-Commission-Rate`。
8. **按 S2A-08 实现受理与别名契约**：调用上游前先提交 `accepted`；本地拒绝先提交 `rejected_before_upstream` 与真实 `funds_effect/quota_effect`，只有双零且 `dispatch_state=not_started` 才可标记可重发；同一请求只建一条 admission（先以临时键建行，最终键只一次 CAS 写入 `final_request_id`；dispatch 前拒绝可保持空，不得伪造），临时键经 `request_admission_alias` 单跳、双向唯一并外键归属该 admission；改绑、二次归属或引用未升级最终键均冲突。usage/反查必须返回完整 `admission_source/funds_effect/quota_effect/dispatch_state/state_version/query_request_id/final_request_id`，`query_request_id` 逐字等于查询键；别名缺失不得返回 `settled`。最终键升级、别名与权威 usage 同事务或同事务 outbox，任一步失败不得确认成功或换键重发；临时键查询别名缺失不得 `settled`，最终键查询唯一 usage 存在须 `settled`。

**验收**
```powershell
cd ai3d
npm test
```
- 同 ticket 并发仅一次成功；重启后重放失败；缺凭据/错 slug 失败关闭。
- 当前仓库未找到覆盖 ai3d/server/auth-sso.mjs 的 SSO 并发消费/重启重放测试；须新增“两并发仅一条成功、重启后同 jti 拒绝”的可执行测试，不能只靠代码阅读判定通过。
- 现有 JSON 持久化只用进程内 Promise 串行化；多副本并发仍需数据库/分布式锁或唯一约束，不能把单进程测试当作多副本验收。
- 普通卫星携带付款/抽成头被主站 403；生成任务、资源与 usage 均归属当前用户。
- 只带 `X-Sub2API-Commission-Rate`、不带 `X-Sub2API-Payer` 同样被拒绝；非数字、负数、`>=1`、`NaN`、`±Inf` 不得被静默忽略或转成普通用户请求。
- 主站不得静默钳制合法费率：`0.9501`、`0.99`、`0.999` 要么按显式上界计算，要么在扣款前明确 4xx 拒绝；不得“接受 0.99 却按 0.95 扣款”。同一 request_id 重放必须复用首次付款人与费率快照。 Payer 存在时佣金头缺失/为 0 的语义必须两端一致：若 0 表示平台不抽成（Payer 承担 `actual_cost` 全额），必须在接口契约中写死并允许省略头；若不允许省略，Payer 存在而费率缺失/非法时必须 4xx。无论选哪种，不得把 0 解释为 `PayerCost=0`；零扣款只允许来自订阅成功行（`billing_subject=subscription`，含 `ActualCost=0` 的零成本订阅）、`ActualCost=0` 且 `TotalCost=0` 的 `free` 成功行、客户报价 0 但上游 `TotalCost>0` 的余额/订阅免费策略行（不得写 `free`，账号配额仍按 `TotalCost * AccountRateMultiplier` 累计），或未来显式开放的 100% 抽成余额行；必须同时看 `billing_subject` 与 `total_cost`，不能单凭 0 猜来源。当前 `rate>=1` 被拒绝，不得把佣金 0 当成零扣款。
- 用稳定 `request_id` 调 `GET /v1/sub2api/usage?request_id=<id>`：`actual_cost` 等于该 slug 配置的报价（未配置自定义价时等于模型 `actual_cost`；因报价先舍入 6 位、命令再量化 8 位，允许不超过 `5e-7` 的舍入差），`total_cost` 仍是模型/渠道成本；模型/渠道成本不可得时必须显式阻断或标记未归类，不得让 `total_cost=0` 的成功权威行参与统计或对账；命中自定义价时 `rate_multiplier = 1` 且 `billing_mode` 与规则单位一致（`token` / `image` / `video` / `per_request`），不得把按量规则误写为 `per_request`；未命中自定义价且主站为空 setting 键/显式 `mode=model` 时，`rate_multiplier` 才可等于该 Key 的实际倍率；`custom/request/points` 的 `rules=[]` 属配置误用，必须失败关闭，不能靠清空规则回模型价；其他模式未命中必须失败关闭。 另须验证：卫星 SuperKey 未绑组时，主站必须按“用户全部有效订阅”判定：`ListActiveUserSubscriptions(userID)` 返回 0 条走余额，1 条走订阅，2 条及以上请求前显式拒绝，且不写 usage/余额/Key 配额；拒绝码固定为 `MULTIPLE_ACTIVE_SUBSCRIPTIONS`（未映射时至少 403 `billing_error`），不得以订阅 + Payer 错误或任意一条订阅替代多订阅拒绝；请求前预检与后扣必须复用同一请求内订阅快照（不得各自重查；预检后新增/失效订阅不得改变本次账本分支），不得按请求头组、实际调度账号组或订阅 ID 排序任选一条。订阅已命中时 `isSubscriptionBill` 必须为真，且必须由显式账本分支字段表达“未解析/确认无订阅/唯一订阅”，不能继续用 `Subscription=nil` 兼表三态，不得仅因 `apiKey.Group == nil` 或 `apiKey.Group` 非订阅组而落到余额。SuperKey 会跨启用组选号，实际账号组不等于请求组，不能直接套用。平台配额只适用于余额模式：余额模式下按资金主体 `(PayerUserID 或 UserID, 解析出的请求平台)` 与本次 `charged_cost` 累计（余额自付等于 `ActualCost`，代付等于 `PayerCost`）；`Payer == User` 时即为 `(UserID, ActualCost)`。订阅模式走订阅账本，不写 `user_platform_quotas`；不得按 `UserID + ActualCost` 默认记账而让 Payer 额度漏计。平台解析失败时必须显式阻断或记录可对账的未归类消费，不得静默跳过。命中卫星报价时 `api_keys.quota_used`、Key 限流必须按报价（`actual_cost`）累计。另须断言 `/v1/sub2api/usage` 返回本次 typed 额度快照与精确金额，包括 `api_key_id`、`billing_subject`、`payer_user_id`、`charged_cost`、`api_key_quota_cost`、`api_key_rate_limit_cost`、`account_quota_cost`、`platform_quota_subject_user_id/platform_quota_platform/platform_quota_cost`、`subscription_cost` 及 `*_usd_nanos`/定点十进制：余额模式自付时 `payer_user_id=user_id` 且 `charged_cost=actual_cost`；订阅模式必须返回 `billing_subject=subscription` 且 `charged_cost=0`，不得把订阅未扣资金误判为余额零扣款；若主站对本项目启用代付，则 `payer_user_id` 必须为实际付款人、`charged_cost` 为实际扣款额。字段缺失或历史 `NULL` 不得被解释为自付；`charged_cost=0` 必须能与历史 `NULL` 区分。佣金为 0 表示 Payer 承担全额成本（`charged_cost=actual_cost`），不得误写成 0。余额模式下解析出平台后 `user_platform_quotas` 必须按同一资金主体与 `charged_cost` 累计。不得用泛化 `quota_subject_user_id` 或 JSON 浮点代替；金额验收比较 nanos/定点，不得先把主站 8 位金额四舍五入到分。  另须断言零扣款来源：`billing_subject=subscription` 且 `charged_cost=0` 只表示订阅账本，不得当作余额零扣款；`free` 仅 `ActualCost=0` 且 `TotalCost=0`，五类额度均为 0；其余成功行一律不得以 `charged_cost=0` 作为免扣款理由。另须覆盖失败尝试：后扣失败后，`usage_logs` 不得出现该 `(request_id, api_key_id)` 的零金额成功行，必须写独立 `billing_attempts`（含 `attempt_no/failure_stage/error_code/actual_cost/charged_cost/total_cost/用量/video_duration_seconds/duration_source`）；同键重试成功后才形成唯一真实金额权威行，资金只变化一次。 自有 Provider 路径不得用主站 `/v1/sub2api/usage` 缺失或余额不变证明未重复建单/未重复计费；必须以 Provider 创建次数、Provider 回执 ID 与本地 `(owner, idempotency_key)` 唯一行共同验收。若该路径改走主站 relay，则删除 Provider 侧证明并改用 `X-Client-Request-ID` + 主站权威 usage，不得双轨。
- **usage 命中不是结算证据**：查询必须按 `request_id + 主站 api_key_id`（或主站等价精确过滤）判定；0 行只表示主站暂时不可见/未写入，多行或主站 `api_key_id` 缺失 `NULL` 一律视为不可唯一确认。以上任一情况都不得把任务标为已结算、不得扣本地钱包/额度、不得重试生成新键、不得改用余额差或本地报价补猜，只能保持 `pending`/待对账；只有唯一权威行且 `request_id`、主站 `api_key_id`、付款主体与金额逐项一致时才允许确认。0 行必须结合主站 `request_admission`：仅 `settled` 可确认；只有 `rejected_before_upstream`、`dispatch_state=not_started`（须由写出点事件证明，不得仅凭时间戳为空）且 `funds_effect=none`、`quota_effect=none` 才可重发；`not_seen`/`accepted`/`unknown` 均不得解释为未受理或未扣款，`quota_effect=changed` 也不得作为本站钱包拒释依据。
- **订阅行主体必须完整且不得回退余额**：命中行 `billing_subject=subscription` 时，`subscription_id` 必须非空，`subscription_cost` 必须存在且等于该行 `actual_cost`（零成本订阅写 `0`，不得为 `NULL`），`charged_cost=0`；`balance_cost` 必须为 0 且不得同时出现余额实扣或非本人 Payer 实扣。缺主体、缺金额或与余额证据冲突时，只能 `pending`/人工复核，不得按 `charged_cost=0` 确认“未扣款”。`billing_subject=free` 仅限 `actual_cost=0` 且 `total_cost=0`，不得替代缺失的订阅主体。
- **配额主体必须与资金主体一致**：本项目不发送 Payer/抽成头，普通请求 `Payer == User`，但验收仍须能证明余额、Key 配额、Key 限流、账号配额与平台配额由同一计费快照复算：Key 配额/限流记在发起请求的 APIKey、金额为 `ActualCost`；账号配额仅对 `APIKey`/`Bedrock` 类型账号按实际 `account_id` 与 `TotalCost * AccountRateMultiplier` 累计（`usage_billing_repo.go:212`），其他账号类型 `account_quota_cost=0` 且不写账号配额；平台配额仅在余额模式按资金主体 `(PayerUserID 或 UserID, 请求平台)` 与 `charged_cost` 累计，订阅模式不写 `user_platform_quotas`。若主站将来对本项目启用代付，须按 S2A-09 冻结的账本事实与 Payer 互斥切换为 Payer 资金主体，并按 S2A-08 落 usage 金额与配额字段；Key 配额主键不变，不得出现“余额按 Payer、额度按 User”的分叉。**实现状态**：`UsageBillingCommand` 尚无平台配额字段，service 层仍按 `p.User.ID + cost.ActualCost` 另写；本条平台配额口径修复前验收必须标记未通过，不得把 Redis/DB 另写当作已满足。**PayerCost 同精度**：代付金额 `PayerCost=ActualCost×(1-rate)` 必须在任何仓储扣款、usage `charged_cost` 与平台配额累计之前按 8 位 half-away-from-zero 量化，三者使用同一量化值；当前 `quantizeMonetaryFields` 未覆盖 `PayerCost`（`usage_billing.go:85-91`），第 9 位为 5 的边界（如 `0.000078125×(1-rate)`）修复前必须标失败，不得只在仓储或 usage 单侧补舍入。
- `/v1/sub2api/usage` 当前实现缺口是不返回 `api_key_id` 或 `group_id`，同用户多把 Key 用同一 `request_id` 只能靠行 `id` 区分；这不是接口契约，S2A-08 落地后必须返回 `api_key_id` 并支持按 Key 过滤。在该字段落地前，响应中缺少 `api_key_id` 不得被解释为“当前用户只有一把 Key”或“可以按行 `id` 猜结算”；验收须显式标记为未满足并按 `pending`/人工复核处理。查询固定 `PageSize=20`，同用户大量 Key 可能截断，验收须给出上限/分页语义。
- 本项目当前只有图片/文本输入，代码中未发现视频生成入口；验收须显式写“无视频上游任务”并给出路由/调用证据。即使无视频路径，也必须断言：若上游或代理误传 `VideoCount > 0`，主站不得静默落到 `token`/`request` 规则，必须按 S2A-08 fail closed。
- **误传视频字段的时长语义**：本项目不生成视频，但若上游误传 `VideoCount>0` 与 `VideoDurationSeconds=0`，不得套用 xAI 默认 8 秒或按次数收费；必须显式拒绝/待对账，并记录 `duration_source=unknown`，不得把 `0` 静默补成 8。
- **纯文本 token 缺失不得按次**：本项目若为主站 `custom` 模式配置了 `millionTokens` 规则，纯文本调用必须取得可信 token 合计后按 `token` 计价；上游未返回 usage、解析失败或仅有图片 token 时，不得静默落到 `request` 或模型价，必须失败关闭/进入待对账；同目标同时有 `token` 与 `request` 规则时固定优先 `token`。上游明确返回 0 token 可按 `millionTokens` 得到 0 金额，但 `billing_mode` 仍须为 `token`，并与“用量未知”分开断言。 **当前实现未满足该零用量分支**：`quoteSatelliteBilling` 仍以 token 合计 `>0` 才尝试 `millionTokens`，0 用量会落到 `request`/模型价；修复前该用例只能标为失败/待实现，不得按现网行为验收通过。
- **只读余额/状态查询不进入计费账本**：本项目存在经 `/api/sub2api/balance` 转发到主站 `GET /v1/sub2api/balance` 的展示/预检调用；该接口只能读取余额，不得生成 usage、占用计费键、扣余额/配额或作为“请求已成功结算”的证据。验收须断言余额查询前后 `usage_logs`/`billing_attempts` 行数、余额、Key/账号/平台额度均不变，且查询失败不得触发重试计费或改变本次模型请求的账本分支。若某次余额查询同时携带了模型结算键，仍只能按只读处理，不得复用该键产生 usage。
- 同一 Key、同一 `request_id` 的**已成功结算**请求重放：`/v1/sub2api/usage` 只返回首次权威记录（first-write-wins），不追加第二行；失败尝试走独立失败审计、不占结算键，成功重试后才形成唯一权威行；同一账本下余额、Key 配额、订阅用量与 usage 行均只变化一次。去重键是 `(request_id, api_key_id)`；同一用户换 Key 使用同一 request_id 会生成第二条记录，不得写成全局“一个 request_id 只一条”。重放命中时不得用本次模型、token、金额、`billing_mode`、订阅或付款人覆盖首次 usage；付款人或费率与首次不一致时，必须返回明确冲突或既有结果并写审计，不得静默换人扣款。
- **媒体请求缺数量不得按次/按 token 成功**：本项目若存在生图或图片编辑路径，主站 `quoteSatelliteBilling` 只在 `ImageCount>0` 时尝试 `image` 规则；请求已明确为生图但张数为 0 时会落到 `token`/`request`。验收必须覆盖 `ImageCount=0` 的明确生图请求，断言失败关闭/待对账而不是按次成功；视频同理覆盖 `VideoCount=0`、`VideoDurationSeconds>0`。若本项目确无该媒体路径，须在卡内显式写“无此路径”并给出路由/调用证据，不得默认跳过。
- 若主站对该 slug 启用 `custom/request/points` 规则：本卫星实际使用的目标/单位必须在规则中命中；未命中时请求必须失败关闭并返回可定位错误，不得静默按模型价扣费。`points` 模式只允许整数点数，金额按 `点数 × 0.01` 换算；`request` 单位得到 `billing_mode=per_request` 且 `actual_cost = 点数 × 0.01`，`image`/`videoSecond` 分别按图片数/秒数乘点数，`millionTokens` 必须被配置校验拒绝（`satellite_billing.go:114-122/356-359`）。不得把 `per_request` 一律当作固定 1 次请求而不乘 0.01，也不得把 `points` 的 `request` 规则误判为 `custom` 的 token 兜底。
- 本项目若存在异步上游任务/轮询/回调（视频、导出、批处理、WebSocket 结果等），必须用服务端可复用的稳定业务键派生 `request_id`：优先取上游任务 ID，或调用方在提交时已验明的业务幂等键；创建、多次轮询、完成回调只能产生一个结算键。服务端随机生成的本地 `jobId`/`taskId` 若每次重提都会变化，不得当作结算键；若仅在创建后才取得上游任务 ID，必须先持久化创建意图，不能等拿到 ID 再补键。**主站已按 S2A-02 接收并校验 `X-Client-Request-ID` 后**，才可断言最终恰有一条权威 usage / 只扣一次；未落地前必须标记“结果不确定/需对账”，不得每次轮询新生成 `request_id` 或据本地键默认成功。补“同一任务轮询 N 次 + 回调 1 次”只产生一条权威 usage、`/v1/sub2api/usage` 只一条的端到端测试；若本项目无此类路径，须在验收中显式写“无异步上游任务”并给出路由/调用证据。

### AI3-05 生成/分析付费调用幂等与归属登记（P1 商用阻断）

**现象与证据**
- `/api/3d/analyze` 是同步付费入口而非免费预览：`server.mjs:145-166` 读取图片并调用 `analyzeAssetImage`；`server/providers/vision.mjs:118-176` 在非 managed 模式直接使用站长自有 `OPENAI_API_KEY`，managed 模式虽改走 relay，但 `satelliteHeaders`（`server/auth-sso.mjs:203-213`）只发 `Authorization`、`X-Sub2API-On-Behalf-Of`、`X-Sub2API-Satellite`，没有稳定 `X-Client-Request-ID`。
- 该调用没有幂等键、调用前意图或结果行：客户端超时/刷新后重试会再次上传图片并再次消耗视觉模型 tokens；`readJsonBody` 后的日志只记录请求摘要（`server.mjs:148-153`），不能作为“已分析”的事实源。若上游已返回但响应丢失，本地既无法按原图回查，也无法证明没有重复计费。
- 视觉分析结果可安全缓存：同一用户、同一图片内容哈希、同一模型与提示词版本的重复请求应返回首次结果或明确冲突，不得重复调用 Provider；缓存键必须包含 owner，避免用户 A 的分析结果或错误详情泄露给用户 B。
- `/api/3d/generate` 先调用 Provider 创建上游任务，拿到 `taskId` 后才写 `taskOwners` 与 JSON 归属表；归属写失败时响应已包含有效上游任务，但本地没有归属，后续状态查询会被 403。证据：`ai3d/server.mjs:168-193`、`ai3d/server/auth-sso.mjs:158-188`。
- 创建请求没有客户端幂等键或持久创建意图；请求超时、连接中断、上游已建单但响应未到达时，用户重试会再次调用 Provider，产生第二条上游任务和第二次额度消耗。证据：`ai3d/server.mjs:168-184`、`server/providers/hunyuan-cloud.mjs:129-159`、`fal.mjs:67-88`、`rodin.mjs:46-71`、`tripo.mjs:195-211`。
- 任务状态本身由上游 `taskId` 派生，可跨进程查询；但仅当客户端已拿到 `taskId`。响应丢失时没有本地记录可用于恢复或对账。
- 本地 Hunyuan 模式在响应缺少 ID 时用 `hunyuan-${Date.now()}` 自造 `taskId`，该 ID 无法向上游回查；状态轮询会失败，且每次重试生成不同 ID。证据：`ai3d/server/providers/hunyuan.mjs:59-82/84-120`。
- 3D 生成使用项目自有 Provider Key（`TRIPO_API_KEY`/`RODIN_API_KEY`/`FAL_API_KEY`/`HUNYUAN_CLOUD_API_KEY`），不经过主站 usage；因此不能靠主站 `/v1/sub2api/usage` 发现丢失任务，必须由卫星自身持久记录。
- **Provider 执行成功与本地模型缓存失败必须分离，且各 Provider 语义一致**：`hunyuan-cloud.mjs:196-205` 在上游 `success` 后缓存下载失败时把 `status` 改为 `failed`，并把缓存异常塞进 `error`；`tripo.mjs:56-71`、`rodin.mjs:105-122` 保留 `success` 但同样把缓存错误写进 `error`，`fal.mjs:118-142` 在缓存失败时回退到远程代理 URL 也仍带 `error`。结果是同一“上游已完成并可能已计费”的事实，在 Hunyuan 表现为任务失败、在其他 Provider 表现为成功但带错误，客户端/运营无法判断是否该重试或退款。统一任务事实至少拆分 `provider_status`（`accepted`/`running`/`succeeded`/`failed`/`cancelled`/`unknown`）、`model_status`（`pending`/`cached`/`remote_only`/`failed`）、`upstream_task_id`、`asset_error_code`；缓存失败不得改写 `provider_status`，`error` 字段不得同时承载 Provider 失败与本地缓存失败。若 Provider 已 `succeeded` 但没有可持久化结果引用，任务进入 `unknown/需人工对账`，不得自动重新生成或按失败退款；仅可重试下载/缓存，且必须复用同一 `upstream_task_id`。验收对 Hunyuan/Tripo/Rodin/FAL 分别注入缓存失败：断言上游任务 ID 不变、Provider 查询次数不增加、任务不显示为 Provider `failed`、`model_status=failed` 且可重试落盘；若远端 URL 仍可用，`model_status=remote_only` 并可标记待本地化，不得据此再建上游任务。

**风险**
- 双建单导致站长自有 Provider 额度重复消耗，且没有可对账的本地任务行。
- 归属登记失败会把已计费任务变成不可查询的孤儿任务；多副本部署时 JSON 归属册也不是原子共享存储。
- 自造 `taskId` 使“queued”任务永远无法完成，用户看到长期无结果。

**实施步骤**
1. 接收并持久化客户端幂等键（或由服务端按用户 + 请求体摘要派生）；创建上游任务前先写 `creating` 意图行，记录 `user_id`、幂等键、Provider、请求摘要和创建租约。
2. 上游返回后在同一逻辑边界写入 `task_id` 与归属；响应丢失后的重试先按幂等键/创建意图查 `task_id`，不得再次建单。
3. 创建意图超过租约仍无 `task_id` 时标记 `unknown` 并要求人工/Provider 对账；不得自动重提，除非能证明上游未建单。
4. Provider 响应缺少可回查 ID 时必须失败关闭，不得用本地时间戳伪造任务 ID。
5. 归属存储改为数据库唯一约束（`task_id` 唯一）或至少原子共享存储；多副本读同一记录。
6. **计费主体独立**：本项目 Provider Key 由站长自有、不经过主站 usage；上述“只建单一次/只消耗一次”以 Provider 侧对账为准，不得套用主站 `(request_id, api_key_id)` 口径。若将来改走主站代调，必须接入 S2A-02 稳定计费键并在主站校验后才可宣称只扣一次。
7. 视觉分析在调用 Provider 前先写 `analyzing` 意图：`(owner_user_id, image_sha256, model, prompt_version)` 唯一，保存请求 ID、租约与 Provider 可核对 ID（若有）；命中既有成功结果直接返回，命中进行中返回真实状态/冲突，不得再调 Provider。 `prompt_version` 必须是显式持久版本，而不是代码内联文案的隐含常量：当前系统提示散落在 `server/providers/vision.mjs:139-159`，用户消息还带 `fileName`；只要任一文本、模型标识或输出 schema 变化，就必须升版本，否则旧缓存会被错误复用。缓存键至少包含规范化 `owner + image_sha256 + provider + model + prompt_version + 输出 schema 版本`，不得只按用户或文件名去重；同一图片不同提示版本是不同分析事实，可并存。读取缓存前必须先验证所有权与版本，命中旧版本不得返回给新请求，也不得覆盖旧行。验收：修改提示词但不升版本必须测试失败；升版本后同一图片产生新分析行且 Provider 调用 1 次；跨用户相同图片/文件名不命中；旧版本结果不得被新请求读到。
8. 自有 `OPENAI_API_KEY` 路径与 managed relay 路径分别登记：前者以 Provider 用量/账单核对，后者在 S2A-02 落地后发送稳定用户断言 + `X-Client-Request-ID`；两条路径都不得因主站 usage 缺失就宣称“未计费”。
9. 读超时/连接中断且无法证明未提交时进入 `unknown/需对账`，不得自动重发；提供按 `(owner, image_sha256)` 查询/重放已存结果的能力。

**验收**
- 模拟“上游已建单、响应丢失”：同一幂等键重试只返回原 `task_id`，Provider 创建次数为 1，归属可查询。
- 模拟归属写入失败：不得向客户端返回一个无法查询的 `taskId`；要么回滚/标记孤儿并告警，要么在上游创建前完成可恢复意图。
- 重启或多副本轮询同一 `taskId`：归属一致，非所有者 403，所有者可查询。
- 本地 Hunyuan 缺少上游 ID：返回明确错误，不产生 `hunyuan-<timestamp>` 任务。
- 运行 `cd ai3d; npm test`，新增重复创建、响应丢失、归属写失败与未知任务恢复用例。
- 若存在主站代调分支，另断言稳定 `X-Client-Request-ID` 被主站接收/校验且同一业务键只有一条 usage；自有 Provider Key 路径不得用主站 usage 缺失推断“未计费”，须按 Provider 建单/额度记录对账。
- 同一用户重复提交同一图片（相同 `image_sha256`、模型与提示词版本）：Provider 视觉调用为 1 次，本地分析行只有一行；首次响应丢失后重提能返回原结果或明确状态，不得再次上传/计费。
- 模拟视觉 Provider 读超时/断连：不得自动重提，必须进入 `unknown/需对账` 并保留请求摘要、尝试次数与可核对字段；不得把“没拿到响应”当成未计费。
- 用户 B 用相同图片或相同请求摘要不得读取用户 A 的结果、错误详情或缓存键；非 managed 模式缺 `OPENAI_API_KEY` 返回 `unavailable` 而不是匿名成功。
- `cd ai3d; npm test` 新增重复分析、响应丢失、跨用户隔离与 Provider 未知状态用例。

## 6. 全链路验收

- 从主站菜单进入，SSO 成功、Session 3 天、注销可撤销。
- 主站 usage/反查必须返回 `request_admission` 六态（`not_seen`/`accepted`/`rejected_before_upstream`/`settled`/`conflict`/`unknown`）及真实最终键、`admission_source/funds_effect/quota_effect/dispatch_state/state_version/query_request_id/final_request_id`；0 行、`not_seen`、`accepted`、`conflict`、`unknown` 均不得触发自动重发、免费释放或重复扣款，只有 `rejected_before_upstream` 且 `dispatch_state=not_started`（须由写出点事件证明，不能靠时间戳为空、4xx 状态码或本地异常推断）才可重试。自动重发/免费处理还必须 `funds_effect=none`（余额、欠款、订阅用量无资金变化）且 `quota_effect=none`（Key/限流、账号、平台、订阅额度均未写）；本站钱包释放只按本地预留与主站资金效果判断；`quota_effect` 既不是释放前提，也不是拒释前提，不得因主站额度变化改扣本站钱包。`accepted`/`unknown` 表示可能已调上游，必须待对账；已读到唯一成功 usage 必须为 `settled`，不得因冲突态降级为未结算。同一请求只能有一条 admission（先以临时键建行，最终键只一次 CAS 写入 `final_request_id`），临时键与最终键必须经 `request_admission_alias(alias_request_id, api_key_id, admission_id, final_request_id)` 单跳反查同一受理事实，alias 行以外键绑定该 admission，禁止引用尚未升级最终键的行；同一临时键改绑、同一最终键归属第二条 admission、别名引用未升级最终键的 admission、别名缺失或 CAS 失败时不得确认。调用上游前必须先提交 `accepted`（临时键仅作 `admission_key`，最终键未定时不得写可解析别名），提交失败不得调用上游；本地拒绝先提交零效果受理，提交失败只能返回 `unknown`/不可重试；最终键、别名与权威 usage 同事务或同事务 outbox，任一步失败不得确认成功，不得自动换键重发。
- **受理与别名验收必须可执行**：同一临时键并发绑定两个最终键时恰一条成功、另一条 `conflict`；同一请求由临时键建 admission 后改用最终键查询，不得产生第二条 admission，最终键只能一次 CAS 写入；同一最终键被两个临时键/两条 admission 指向时恰一条成功；临时键别名缺失而最终 usage 已存在时，查询必须返回 `unknown`/待对账，不得返回 `settled`；直接查询最终键且唯一 usage 存在时必须返回 `settled`（`admission_source=usage`），不得因别名未写降级；所有查询（含 `usage_count=0`）必须回传完整 `admission_source/funds_effect/quota_effect/dispatch_state/state_version/query_request_id/final_request_id`，且 `query_request_id` 逐字等于查询键；临时键与最终键反查必须命中同一 `state_version`。注入受理写入失败时上游调用计数必须为 0；注入别名或 usage 写入失败时不得返回成功或自动换键重发。
- 图片/草图/GLB 生成成功，资源归属当前用户，余额不足有提示。
- 重放、跨用户、超大文件、模型失败均被正确处理。
- 浏览器、日志、构建产物无 SuperKey/应用凭据/SSO 密钥。
