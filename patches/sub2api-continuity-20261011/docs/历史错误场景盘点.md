# Sub2API 历史错误场景盘点

采集时间：2026-10-11 05:50–06:23（香港时间）。服务器只读查询，未改账号、未重启、未发推理请求。本次补充仅合并已完成的旧内部网关扫描结果，未重新连接服务器。真实聚合材料只在 F 盘保存，不提交 Git。

## 核心发现

1. 现存错误库包含 61,515 条记录，但其中 8,099 条明确标为已恢复的上游/认证错误，989 条记录客户端取消；不能把整个错误库当作客户失败数。
2. 最大未恢复类别是网关无可用候选（21,647 条）、通用服务故障（10,628 条）、上游余额不足（6,798 条）。快速切换只有在存在协议、模型、权限均兼容的健康备用时才有用。
3. 工具密文解密失败有 132 条错误记录，另 1 条明确恢复记录；按请求ID关联网关HTTP完成日志后，133个请求全部HTTP200。请求过大另66个请求同样HTTP200。错误库的400是语义错误状态，不能当成实际HTTP状态。普通推理/消息密文验证失败有71条，清理reasoning不能处理所有密文故障。
4. 1,079 条“原会话协议没有兼容账号”来自上游，不能认定是当前本地源码产生。错误集中在 9 月 27 日至 10 月 4 日，全部 group32 的 OpenAI APIKey 上游；也有 Responses 转 Chat 路径。
5. 6 条历史错误说明某些结构要求 encrypted_content 必填。现存材料无法确认原 item 类型或字段是否曾被清理，不能据此推断当前 reasoning 清理必然错误。
6. 旧内部网关现存四份日志已完整读取，共 1,273,340 行，覆盖 10 月 2 日至 11 日。新增盘点包含支付回调、邮件、验证码设置读取、Grok 计费、令牌刷新及模型能力探测场景；这些不能混算为推理调用失败。关键词原标为“审计失败”的 5 行实际来自邮件队列，已纠正；23 行持久化/队列相关记录同时带上下文取消，不能据此认定数据库故障。

## 当前设计必须控制的连锁副作用

| 触发 | 非预期后果 | 应对 |
|---|---|---|
| 网关只改本轮副本，客户端仍重发旧密文 | 下一轮再次报错或反复切号，缓存持续失效 | 按下游Key/组隔离记录密文归属与已确认失效摘要；逐轮确定性变换；限制TTL/容量，不修改用户原历史 |
| 按用户/session全局硬钉账号 | 单号耗尽时整个会话不可用，其他健康账号无法分担 | 普通请求软亲和；仅确实不可移植状态硬约束；健康失败与上下文约束分开统计 |
| 将工具调用/结果转普通文本 | 丢失call_id配对、工具角色信任、并行调用、错误标志、多媒体及客户端执行协议；可能重复执行 | 仅用于有明文证据的历史解释降级，不伪造本轮工具成功；新输出继续使用原工具协议 |
| HTTP200或usage当成功 | 错误流被写入成功粘性，账单和成功率失真 | 以协议终止事件与语义完成判定，失败尝试与最终结果分账 |
| 读到未知EOF/5xx就整轮重放 | 上游服务端工具可能已执行，产生重复写入/支付/作业 | 不确定执行状态停止整轮自动重放；明确拒绝且未执行才安全切换 |
| 长推理等待按固定短超时切号 | 浪费计算和缓存，重试越多越慢 | 动态首输出预算；首输出前后、客户端工具执行间隔分别计时 |
| 全号429/5xx都重试多遍 | 并发放大、成本放大、冷却同步雪崩 | 每请求总尝试预算、抖动、小规模半开探测；冷却按账号/模型/错误原因范围 |
| 上游429其实客户端准入限制 | 无意义等待重试直到客户超时 | 语义分类；能力不兼容，不当作短期限流 |
| 备用账号共享同一供应商池 | 表面多号，实际单一故障域 | 保留供应商/凭证故障域信息，择不同健康域；不能凭账号数量承诺冗余 |
| 日志扫描/审计阻塞转发 | 排查或可观测性本身拖累用户 | 本次只读限时聚合；审计异步有界；失败不阻塞客户服务 |

初次采集时的审计机制及不可隐藏的约束（后续上线状态以对应部署记录为准）：

1. `cc2-audit-route.timer` 是每次执行结束30秒后再运行，脚本还要执行串行健康检查、数据库查询、磁盘检查和队列标记检查；每次HTTP检查最多4秒，命令最多15秒。故故障切走窗口不能简单承诺最多30秒。
2. Nginx审计入口为单一`proxy_pass`，连接超时3秒、读写3600秒、请求/响应缓冲关闭、`proxy_next_upstream off`。连接建立失败不会在同一个客户请求内自动直连28080；只在下一次健康同步后让新请求绕过审计。
3. 当前`forward-client-authorization=true`在存档补丁中走独立直接转发分支，`.send().await`一次。没有调用下面通用SDK重试函数；不会与Sub2API调度自动叠加重试。
4. 审计上传与业务转发分离；捕获名额/内存/响应队列使用try-acquire/try-send，资源不足跳过审计继续转发。真实日志10-10 15:04:08香港出现一次`response_queue_full_or_closed`，说明“所有请求永久完整审计”与“审计绝不拖慢转发”存在可观测取舍。
5. 异步审计解决上传阻塞，不消除前置代理进程和套接字故障。已开始的响应流断开后，定时改Nginx路由无法修复原客户端连接；盲重放可能重复工具副作用。只能在明确尚未向网关发送业务请求的连接失败阶段考虑安全回退；中途失败必须保留不确定执行状态。
