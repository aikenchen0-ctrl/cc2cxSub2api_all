# Canvas 优化任务

> 项目：`canvas/`（卫星应用）。基线：2026-11-14。
> 全局约束见根目录 `评估报告.md`、`优化任务-总调度.md`；本文件只负责 `canvas/` 内落地。

## 1. 项目定位与边界

- 卫星应用，Go + Gin + GORM 后端，Next.js 前端，已有 Sub2API 对接。
- 本项目 `AGENTS.md` 要求：先读现有代码、最少修改、不兼容旧数据、任何文件修改前必须得到用户明确同意、不要执行构建。
- **并行 Agent 特别约束**：领取任务后先向用户说明将改哪些文件并获得同意；不要因为本任务书存在就视为已授权修改。
- 本项目只改 `canvas/`；主站协议、根 Compose 由协调 Agent 处理。

## 2. 结论与商用判定

**当前为发布阻断，不适合公开商用。**
历史记录称全量 `go test ./...` 失败、文本/图片/视频链路 503、路由契约测试失败；本轮未重新运行，**必须按当前版本复测后再判定是否仍存在**。另有 AGPL-3.0 网络服务义务，商用需法务确认。

### CAN-03 SSO 与计费（P0/P1）

**现象与证据（异步与自有额度补查 2026-11-14）**
- 图片/音频任务只有“先落 `queued` 行、再 `go runCanvas*Task`”的执行路径：`handler/canvas_task.go:57-80/210-231` 创建后立刻用无租约 goroutine 执行；`runCanvasImageTask`/`runCanvasAudioTask`（`:253-353`）在进程内推进状态。启动入口没有扫描 `queued/processing` 的恢复器，进程重启后这些行会永久停在中间态，用户看到“处理中”但没有执行者。
- 图片/音频任务的可恢复事实源不足：模型 `model/canvas_image_task.go:3-35`、`canvas_audio_task.go:3-31` 只保存请求快照与结果，没有 `idempotency_key`、租约、`provider_task_id`、`attempt_no`、`request_id`；当未传 `X-Client-Task-ID` 时 `service/canvas_image_task.go:32`（及音频 `:30`）每次都生成新的 `canvas_*_task_<uuid>`，响应丢失后的重提一定是新任务。
- 这两条路由还会再走一次本地扣费：`runCanvasImageTask`/`runCanvasAudioTask` 的 `executeCanvasAIRequest`（`:355-372`）构造内部 `/images/*` 或 `/audio/speech` 请求并调用 `proxyAIRequest`，后者在 `handler/ai.go:204-226` 按模型价格 `ConsumeUserCredits`，失败再 `RefundUserCredits`。因此缺少 `X-Client-*` 幂等键时，重提既新建任务、又再次扣本地 credits、又可能再次调用上游。
- 当 `Sub2APIRelayEnabled()` 为真时，普通用户请求被强制走主站 relay（`handler/ai.go:22-32`），`canvas` 自身不再直接使用 `kie/apimart/autodl` 的站长 Key；但 `userChannelID` 非空、或 relay 未启用、或管理员/本地渠道路径仍可能直接使用渠道 `APIKey`（`service/model_protocol.go:38-44/55-56/90-95`、`service/user_data.go:54-108`）。这些分支的重复创建/超时对账不能被“默认走 relay”一句带过。
- 同步代理路径没有稳定计费键：`proxyAIRequest` 直接构造上游请求（`handler/ai.go:149-246`），不转发 `X-Client-Request-ID`；`copyAIResponse` 读超时或客户端断连时只能退款或留日志（`handler/ai.go:248-291`），无法按同一键查回主站是否已受理。仅 `video_task.go:451` 把上游返回的 `request_id` 当任务 ID 读取，不能替代提交前的业务键。
- 视频任务已有持久 `video_tasks` 与 poller，但图片/音频没有同等恢复；`refundVideoCredits` 的本地补偿也只覆盖视频。本卡新增验收不得把视频 poller 的结论外推到图片/音频。

**现象与证据**
- `service/sub2api_sso.go` 有数据库持久化路径，但本轮未验证并发/重启/多副本。
- Compose 的应用凭据/SSO 密钥均为 `:-}` 可空，这是当前缺陷。
- 当前调用使用裸 `X-Sub2API-On-Behalf-Of`；主站 S2A-07 后改为短期用户断言。

**实施步骤**
1. 校验 SSO `iss/aud/sub/iat/exp/jti`，TTL ≤ 2 分钟，`aud=canvas` 精确匹配。
2. 验证票据消费数据库唯一键；补并发、重启、多副本测试。
3. 验证 3 天 Session、生产 Cookie `Secure + HttpOnly`、注销可撤销。
4. 服务端代调带 `canvas` slug 和当前用户断言；缺凭据不得回退。
5. 验证文本/图片/视频计费、余额不足、usage 归属。
6. 主站 S2A-01/06/07 完成后改用专属凭据/派生密钥并测试跨 slug 被拒。
7. 计费只走主站 `canvas` slug 配置或当前用户余额；不得发送或接受 `X-Sub2API-Payer`、`X-Sub2API-Commission-Rate`。
8. 文本/图片/视频 usage 必须记录当前用户、任务 ID 和可复算的 `request_id`；同一任务重试只有在主站已接收并校验稳定 `X-Client-Request-ID`（或按同一业务键可查重）时才可断言不重复扣款，否则必须标记“结果不确定/需对账”。
9. 同步代理入口（`/api/v1/chat/completions`、`/responses`、`/images/*`、`/audio/speech`）在扣费前写持久意图并发送稳定 `X-Client-Request-ID`；`/api/ai/direct-request` 保持无状态参数转译，只返回 URL/body/uploads，不得接受或返回服务端凭据、不得作为计费或无幂等提交入口。

10. **退款前必须先证明“本请求确实扣过款”，且不得在扣款前调用退款**：`proxyAIVideoTaskRequest` 在 `handler/video_task.go:102-108` 的 `SetModelChannelAuthHeader` 失败分支调用 `refundVideoCredits(user.ID, modelName, credits, upstreamPath)`，但扣款发生在 `:124-128`；因此该分支会直接给用户余额加钱，可被“带合法请求体但缺少渠道凭据”的请求重复触发，形成任意增发 credits。所有退款/补偿入口必须先按 `(user_id, business_key/attempt)` 读取本请求的 `consumed` 事实（或要求传入已持久化的预扣订单 ID），只有状态为已扣且未退过才可退；禁止只凭请求上下文里的 `credits>0` 就退款。补测试：鉴权失败、上游 4xx、建单前失败各调用一次，断言余额不变、`credit_logs` 无 `ai_refund`；同一请求重复失败不得累计加钱。
11. **本地 credits 扣款与流水、退款与流水必须同事务，且退款必须唯一**：`service/auth.go:341-365` 先 `repository.ConsumeUserCredits` 更新余额，再单独 `SaveCreditLog`；后者失败时余额已扣但无流水，日志里 `Balance` 还是旧值（先读后写也非原子）。`RefundUserCredits`（`:367-391`）同样先加余额后写流水，失败会形成“余额已退、无退款记录”，重试还会再次退款。`repository/user.go:82-120` 的加减余额与 `SaveCreditLog` 没有共同事务边界，也没有按业务键唯一约束。必须让余额变更、`credit_logs`、退款唯一键（`billing_key`/`refund_key`）在同一数据库事务提交；`ai_consume` 与 `ai_refund` 必须成对且各自至多一次，余额不足时不写流水。补测试：在写流水处注入失败，断言余额回滚、无半条流水；并发重复退款仅一次生效；重复请求命中已退款键返回原状态而非再次加钱。
12. **上游已受理但本地任务落库失败不得只留“失败”**：`proxyAIVideoTaskRequest` 在拿到上游任务 ID 后调用 `service.CreateVideoTask`（`handler/video_task.go:166-192`），落库失败只记日志并返回 500，本地 credits 已扣且无任务行、无对账键；用户重试会再次调用上游并再次扣费。发布/回包失败与“上游未受理”必须区分：上游返回 2xx 且含任务 ID 时，若本地落库失败，必须保留 `unknown/需对账` 事实（可先写意图行或失败 outbox，含上游任务 ID、响应摘要和计费键），不得直接退款或允许无提示重提；只有确认上游未创建任务才可退。补测试：注入 `SaveVideoTask` 失败后，断言存在可查询的对账记录、credits 不被自动退回、同一业务键重提先查回该记录而非再次 create。
13. **视频轮询进入 `failed` 必须有明确的退款或对账分支，不能静默留扣款**：`UpdateVideoTaskFromPoll`（`service/video_task.go:263-304`）只把状态改为 `failed`，全仓没有任何 poll 失败退款调用；用户在创建时已被扣 credits，上游最终失败后余额不会恢复，也没有人工处理标记。必须区分“上游已受理并完成但业务失败”“上游受理失败/明确未生成”“轮询结果不确定”三类：前两类按产品策略退款或按约定收费，并记录 `refund_key` 与原因；超时/5xx/429/解析失败只更新 `unknown/需对账`，不得把一次瞬时轮询错误直接当终态，也不得重复退款。补测试：创建成功后轮询明确 `failed` → 退款至多一次且流水成对；轮询 5xx/超时 → 任务保持可重试/待对账，余额与退款次数不变；重复 poll 同一失败结果不重复加钱。
14. **同一业务键的扣款、退款、任务行必须共用唯一键，不能靠本地随机 ID 拼出“新请求”**：当前 `CreateVideoTask` 用 `firstVideoTaskValue(input.ClientTaskID, UpstreamTaskID, UpstreamVideoID, "video-task-"+uuid)` 作主键（`service/video_task.go:71-72`），`ConsumeUserCredits`/`RefundUserCredits` 都没有业务键参数，`credit_logs` 也没有唯一约束。因此响应丢失后重提既可能新建任务行，又可能再次扣 credits；并发或人工重试还可能产生两条退款。必须接收并持久化客户端/服务端稳定业务键（`X-Client-Task-ID` 或按 `user_id + 规范化请求摘要` 派生），以 `(user_id, idempotency_key)` 唯一约束绑定任务、预扣和退款；命中已有键时只返回既有任务或冲突，不得再次 `ConsumeUserCredits`，也不得再次调用上游。补测试：同键并发两次仅一行任务、一次扣款、最多一次退款；不同用户同键互不串账；已有失败任务重试不得产生第二笔扣款除非旧单已明确关闭。

**跨账退款边界（根 7.3.1 第 23 条）**：本地 `credit_logs`/`ai_refund` 只撤销 canvas 已扣 credits，不得写成主站 usage `reversed`，也不得要求主站按本地任务失败退款；主站 usage 冲正同样不得自动给本地余额加款。视频/图片/音频任务进入 `failed` 时，仅 Provider 返回显式“未受理/未创建”证据（如 4xx 且无 task ID、`prediction.created=false`/等价查询结果）或本地扣款前失败可自动退；本地异常、`null` 响应、解析失败、5xx/超时、已有 task ID 或仅有本地 `failed` 状态均不得视为未受理；已有 Provider task ID、已发生上游费用或轮询超时/5xx/解析失败只能 `unknown/需对账` 或人工复核，不得因状态为 `failed` 自动退款。验收断言：鉴权前失败余额与 `credit_logs` 不变；本地已扣且 Provider 已计费后失败两侧均不自动退；重复/并发退款至多一次；主站冲正与本地退款各自独立 CAS。

**本地退款必须消费同一业务键的已扣凭证（2026-11-15 补充）**：`RefundUserCredits`（`service/auth.go:367-391`）只按 `(user_id, credits, model, path)` 加余额并写 `ai_refund`，不能证明该金额来自本请求已确认的 `ai_consume`；在并发重试、任务重提或上游已受理时，不能仅凭调用方传入的 `credits` 退款。必须引入持久 `consume_key/refund_key`：扣款成功写 `ai_consume` 行（含业务键、任务/请求 ID、金额、递增尝试序号与状态 `consumed`），退款只能以同一 `consume_key` 的条件更新 `consumed→refunding→refunded`，累计退款不超过原扣款且每个 `refund_key` 至多一次；0 行或状态不符时返回既有结果/冲突，不得加款。重复任务、请求重放或“任务已失败”都不构成可退款凭证；只有 Provider 明确未受理/未创建，或本地扣款在事务内回滚，才允许自动退款。补测试：同键并发扣款仅一条 `consumed`；无 `consumed` 行调用退款 → 余额/流水不变；`consumed` 行重复退款仅一次；本地已扣且 Provider 已受理 → 进入 `unknown/需对账`；`refunding` 期间不得再次扣同一键。

**收到上游 2xx 后不得凭本地解析失败退款（2026-11-15 补充）**：`proxyAIVideoTaskRequest` 在 `doAIRequest` 返回 2xx 后，仍会在 `video_task.go:139-164` 对错误体、缺少任务 ID、解析失败调用 `refundVideoCredits`；`workflow_agent.go:144-146` 在收到 2xx 后 `normalizeWorkflowDraft` 失败也直接退款。只要 HTTP 2xx 已返回且请求体已被 Provider 接收，空内容、字段缺失、结构不合法、`error` 字段或本地 normalize 失败都不能证明 Provider 未计费；这些分支只能记 `unknown/需对账`，保留上游响应摘要与业务键，不得自动加本地 credits。仅 `SetModelChannelAuthHeader` 失败、请求尚未发出、明确 401/403 且可证明未受理等“未提交”分支可退款，并仍须携带同一 `consume_key` 的 `consumed` 凭证。`429`/`5xx` 同样不得直接退款：`copyAIResponse`（`ai.go:261-273`）与视频创建（`video_task.go:139-146`）把非 2xx 一律交给 `onFailure`/`refundVideoCredits`，但 429/502/503 可能已被上游受理或计费；必须按“是否收到 Provider 回执/是否可证明零计费”分类，未知则待对账。补测试：2xx 空体、2xx 解析失败、2xx 缺任务 ID、429、500、流中途断开各一次，断言本地 `ai_refund` 不增加或进入 `unknown`（按产品选择其一并写死），`consume_key` 不能被重复退款；Provider 明确未受理时同一键仅退一次。
15. **按 S2A-08 实现受理与别名契约**：调用上游前先提交 `accepted`；本地拒绝先提交 `rejected_before_upstream` 与真实 `funds_effect/quota_effect`，只有双零且 `dispatch_state=not_started` 才可标记可重发；同一请求只建一条 admission（先以临时键建行，最终键只一次 CAS 写入 `final_request_id`；dispatch 前拒绝可保持空，不得伪造），临时键经 `request_admission_alias` 单跳、双向唯一并外键归属该 admission；改绑、二次归属或引用未升级最终键均冲突。usage/反查必须返回完整 `admission_source/funds_effect/quota_effect/dispatch_state/state_version/query_request_id/final_request_id`，`query_request_id` 逐字等于查询键；别名缺失不得返回 `settled`。最终键升级、别名与权威 usage 同事务或同事务 outbox，任一步失败不得确认成功或换键重发；临时键查询别名缺失不得 `settled`，最终键查询唯一 usage 存在须 `settled`。

- **纯文本 token 缺失不得按次**：本项目若为主站 `custom` 模式配置了 `millionTokens` 规则，纯文本调用必须取得可信 token 合计后按 `token` 计价；上游未返回 usage、解析失败或仅有图片 token 时，不得静默落到 `request` 或模型价，必须失败关闭/进入待对账；同目标同时有 `token` 与 `request` 规则时固定优先 `token`。上游明确返回 0 token 可按 `millionTokens` 得到 0 金额，但 `billing_mode` 仍须为 `token`，并与“用量未知”分开断言。 **当前实现未满足该零用量分支**：`quoteSatelliteBilling` 仍以 token 合计 `>0` 才尝试 `millionTokens`，0 用量会落到 `request`/模型价；修复前该用例只能标为失败/待实现，不得按现网行为验收通过。
- **只读余额/状态查询不进入计费账本**：本项目存在经 `/api/sub2api/balance` 转发到主站 `GET /v1/sub2api/balance` 的展示/预检调用；该接口只能读取余额，不得生成 usage、占用计费键、扣余额/配额或作为“请求已成功结算”的证据。验收须断言余额查询前后 `usage_logs`/`billing_attempts` 行数、余额、Key/账号/平台额度均不变，且查询失败不得触发重试计费或改变本次模型请求的账本分支。若某次余额查询同时携带了模型结算键，仍只能按只读处理，不得复用该键产生 usage。
- 同一 Key、同一 `request_id` 的**已成功结算**请求重放：`/v1/sub2api/usage` 只返回首次权威记录（first-write-wins），不追加第二行；失败尝试走独立 `billing_attempts`（含 `attempt_no/failure_stage/error_code/actual_cost/charged_cost/total_cost/用量/video_duration_seconds/duration_source`），不占结算键，成功重试后才形成唯一权威行；同一账本下余额、Key 配额、订阅用量与 usage 行均只变化一次；平台配额仅在余额模式按资金主体 `(PayerUserID 或 UserID)` 与 `charged_cost` 累计一次，订阅模式不写 `user_platform_quotas`。去重键是 `(request_id, api_key_id)`；同一用户换 Key 使用同一 request_id 会生成第二条记录，不得写成全局“一个 request_id 只一条”。重放命中时不得用本次模型、token、金额、`billing_mode`、订阅或付款人覆盖首次 usage；付款人或费率与首次不一致时，必须返回明确冲突或既有结果并写审计，不得静默换人扣款。
- **媒体请求缺数量不得按次/按 token 成功**：本项目若存在生图或图片编辑路径，主站 `quoteSatelliteBilling` 只在 `ImageCount>0` 时尝试 `image` 规则；请求已明确为生图但张数为 0 时会落到 `token`/`request`。验收必须覆盖 `ImageCount=0` 的明确生图请求，断言失败关闭/待对账而不是按次成功；视频同理覆盖 `VideoCount=0`、`VideoDurationSeconds>0`。若本项目确无该媒体路径，须在卡内显式写“无此路径”并给出路由/调用证据，不得默认跳过。
- 若主站对该 slug 启用 `custom/request/points` 规则：本卫星实际使用的目标/单位必须在规则中命中；未命中时请求必须失败关闭并返回可定位错误，不得静默按模型价扣费。`points` 模式只允许整数点数，金额按 `点数 × 0.01` 换算；`request` 单位得到 `billing_mode=per_request` 且 `actual_cost = 点数 × 0.01`，`image`/`videoSecond` 分别按图片数/秒数乘点数，`millionTokens` 必须被配置校验拒绝（`satellite_billing.go:114-122/356-359`）。不得把 `per_request` 一律当作固定 1 次请求而不乘 0.01，也不得把 `points` 的 `request` 规则误判为 `custom` 的 token 兜底。
- 本项目若存在异步上游任务/轮询/回调（视频、导出、批处理、WebSocket 结果等），必须用服务端可复用的稳定业务键派生 `request_id`：优先取上游任务 ID，或调用方在提交时已验明的业务幂等键；创建、多次轮询、完成回调只能产生一个结算键。服务端随机生成的本地 `jobId`/`taskId` 若每次重提都会变化，不得当作结算键；若仅在创建后才取得上游任务 ID，必须先持久化创建意图，不能等拿到 ID 再补键。**主站已按 S2A-02 接收并校验 `X-Client-Request-ID` 后**，才可断言最终恰有一条权威 usage / 只扣一次；未落地前必须标记“结果不确定/需对账”，不得每次轮询新生成 `request_id` 或据本地键默认成功。补“同一任务轮询 N 次 + 回调 1 次”只产生一条权威 usage、`/v1/sub2api/usage` 只一条的端到端测试；若本项目无此类路径，须在验收中显式写“无异步上游任务”并给出路由/调用证据。
- 本项目确有异步视频任务：`handler/video_task.go:18-19,157-195` 创建任务并落库，`service/video_task.go:105-107,200-248` 的 poller 从 `ListDueVideoTasks` 恢复轮询，`repository/video_task.go:5-10,72-88` 使用数据库 `Save`/due 查询。本卡验收必须进一步证明：创建 `VideoTask` 成功后重启服务，poller 能按持久 `upstream_task_id` 继续轮询并收敛到终态；`SaveVideoTask` 失败时不得向上游返回可计费成功，也不得只在内存保留任务。同一任务多次轮询、手动查询与完成回调只产生一条 usage、扣款一次；重启前后不得更换 `request_id`。
- 补“同 client task ID 响应丢失后重提”：断言 credits 只扣一次、上游 create 只调用一次、`video_tasks` 只有一行；若进程在上游已建单、本地行未写时中断，必须按 client task ID 进入待对账，不得退款后静默重提。
- 当前创建顺序是“先扣本地 credits → 调上游 → `CreateVideoTask` 落库”，`:166-193` 的落库失败分支只记录日志并返回 500，既不退款也不写待对账任务；此时用户已被扣费、上游已有 `UpstreamTaskID`，但 poller 没有行可轮询，形成不可对账窗口。`refundVideoCredits` 本身只在日志失败时告警（`:610-614`），也不能证明退款成功。验收必须覆盖落库失败与退款失败两种注入。
- 本地 credits 扣减与流水不是同一事务：`service/auth.go:341-364` 先 `repository.ConsumeUserCredits` 改余额（`repository/user.go:82-100`），再单独 `SaveCreditLog`；后者失败时返回错误，但余额已扣且没有扣费流水。退款同理（`:367-390`），额度和流水仍分两步。必须把余额 CAS、流水与关联任务 ID 放在同一事务，或先写持久意图再由可重试 worker 完成两阶段；失败不得只返回错误了事。
- 退款不幂等：`RefundUserCredits` 只按用户加余额（`repository/user.go:102-120`），`CreditLog.RelatedID` 从未赋值（`model/user.go:88-97`），没有 `(billing_order_id, type)` 唯一键。上游失败重试、handler 重入或落库失败再加补偿时会被重复退款。必须用持久 `refund_intent` + 唯一键保证每笔扣费至多退款一次，并让流水能回指原扣费行。
- 当前 handler 只在 `doAIRequest` 失败、上游 4xx、响应缺任务 ID 时退款；`CreateVideoTask` 失败（`:189-193`）未退款。必须在落库失败时保留 `UpstreamTaskID` 与扣费关联，先写待对账/补偿行，再决定退款；不得让“上游已建单 + 本地无任务 + 已扣费”成为无记录终态。 **4xx 也不得直接视为“未受理”**：Provider 返回 400/401/403/404/409/422 时，必须先从响应/Provider 查询/本地 `provider_task_id` 证明未建单且未产生费用；不能证明时写入 `unknown/需对账` 并保留扣费关联，不得自动 `RefundUserCredits` 后让用户重提。只有明确未受理的失败才可释放意图并退款，且退款仍需 `refund_intent` 唯一键。
- **同一 client task ID 重提仍会二次扣款/建单**：`X-Client-Video-Task-ID` 只用于最终 `CreateVideoTask` 的本地主键，提交入口在扣款与上游调用前不查询既有任务（`handler/video_task.go:125-188/198-216`）。因此同键重提会再次 `ConsumeUserCredits`、再次调用上游 video create，最后才用 `db.Save` 覆盖既有行；即使最终一行，也已产生两次真实上游成本和两次 credits 流水。必须在扣款前以 `(user_id, client_task_id)` 唯一键写入 `creating` 意图并复用既有任务/`UpstreamTaskID`；同一键不得再次扣款或再次上游 create。
- 本地任务主键直接取客户端可控的 `X-Client-Video-Task-ID`，且只校验 `client_video_task_` 前缀（`handler/video_task.go:198-216`、`service/video_task.go:65-77`）。`VideoTask.ID` 是全局主键（`model/video_task.go:3-5`），`SaveVideoTask` 是 `db.Save(&task)` 全字段写入（`repository/video_task.go:5-11`）：同一 `ID` 由另一用户提交时会更新既有行，覆盖 `user_id/upstream_task_id/status/credits`，把他人任务移走或把终态改回 `queued`。必须改为服务端生成主键 + `(user_id, client_task_id)` 唯一键，或保存前按 owner/终态做条件更新；验收须包含“用户 B 复用用户 A 的 client task ID 不得改写 A 的任务、不得接管上游任务”。
- **图片/音频任务必须是可恢复的持久任务，而非进程内 goroutine**：创建入口先以 `(user_id, idempotency_key)` 唯一约束写 `queued/creating` 意图并返回既有任务；worker 以租约领取 `queued`，执行中续租，完成后条件更新为终态。启动或定时扫描必须能重新领取未完成行；`X-Client-Task-ID` 缺失时不得用随机 UUID 冒充可重提键，缺失幂等键应 400/409 或由服务端按用户 + 规范化请求摘要派生并写唯一约束。
- **图片/音频重提不得二次扣本地 credits 或二次调用上游**：`proxyAIRequest` 只能在同一内部任务/同一 `request_id` 下扣一次；任务命中既有行时直接返回真实状态或结果，不得先扣款再判断。若上游已提交但响应未知，必须保存 `provider_task_id`/可核对请求 ID 并进入 `unknown/需对账`，不得自动重发或无条件退款后重提。补“同一键 + 响应丢失”“同一键 + 重启”“落库失败”三组注入测试。
- **同步代理入口也必须先落幂等意图，不得只靠视频/图片任务表**：非 relay 的 `proxyAIRequest` 在调用上游前就 `ConsumeUserCredits`（`handler/ai.go:146-226`），请求失败才 `RefundUserCredits`；它没有任务行、没有幂等键、没有 `request_id` 持久化。即使路径不创建 `canvas_image_task`/`video_tasks`，同一用户刷新或重提仍会先扣款再调用 `kie/apimart/autodl` 等自有渠道；若上游已受理但响应丢失，退款可能发生而 Provider 已计费，形成“本地退款、站长额度仍被消耗”的不可对账窗口。`/api/ai/direct-request`（`router/router.go:46`、`handler/ai_direct_request.go:46-66`）只是准备/翻译请求，不负责提交与计费；不得把它当成幂等入口。此类同步付费调用必须：以服务端验明的业务键（客户端键经 owner 绑定，或 `owner + 规范化请求摘要`）先写 `creating` 意图与唯一约束，提交前扣款与意图同事务/同补偿单元；响应丢失、超时、5xx、524 进入 `unknown/需对账`，不得自动退款后重提；命中既有键返回真实结果或冲突，不得再次扣款或再次 create。`userChannelID`（用户自带 Key）不消耗站长额度，但跨用户隔离与任务归属仍需覆盖。
- **工作流 Agent 草稿入口也不得先扣后退**：`service/workflow_agent.go:52-63` 在调用上游前 `ConsumeUserCredits`，`:82-100` 仅在本地构造请求或 `client.Do` 返回错误时 `RefundUserCredits`；读超时、连接重置或上游已受理但响应丢失都走同一退款分支，形成“本地 credits 已退、上游已计费”的不可对账窗口。`/workflows/agent-draft` 必须与同步代理入口共用同一 `creating` 意图与稳定业务键：调用前持久化意图，超时/5xx/524 进入 `unknown/需对账`，不得自动退款或重提；退款只能在持久证据证明上游未受理且按 `refund_intent` 唯一键执行。补“上游已受理但客户端读超时”“进程在扣费后崩溃”“同键重提”三组测试，断言 credits 只恢复一次、上游只调用一次。
- **自有渠道 Key 路径另算**：在 `userChannelID` 或非 relay 分支下，图片/音频/视频若直接使用 `kie/apimart/autodl` 等站长自有 `APIKey`，必须登记 Provider、是否计费、是否幂等、`provider_task_id` 持久化与账单核对；不得因主站 usage 缺失就认定未计费。`X-Client-Task-ID` 只允许服务端校验后的业务键，用户可控值不得覆盖他人任务或跨用户复用。
- **浏览器直连只做参数转译，不得成为第二套计费入口**：`POST /api/ai/direct-request` 位于未加 `UserAuth` 的 `/api` 组（`router/router.go:46`），接收浏览器传入的 `channel.baseUrl` 后只校验协议/主机格式并返回 `directAIRequestPlan`（`handler/ai_direct_request.go:46-125/136-142`），由前端携带用户自己的 Key 直接 `fetch` 上游（`web/src/services/api/direct-ai.ts:115-135/313-330`）。它不是服务端提交入口，不消耗站长额度，也不得读取 `SUB2API_APP_CREDENTIAL`/渠道 `APIKey`、不得接受 `X-Client-Request-ID` 作为计费键；服务端返回的计划只能包含转译后的 URL/body/uploads，不得注入服务端凭据。登录用户选择本地渠道时仍走 `/api/v1` 代理（`web/src/services/api/image.ts:519-528`、`video.ts:39-48`），该代理按 `userChannelID` 跳过本地 credits 但仍受用户配置归属校验（`service/user_data.go:54-108`）；两种模式不得混用计费口径。

## 6. 全链路验收

- 从主站菜单进入，SSO 成功、Session 3 天、注销可撤销。
- 主站 usage/反查必须返回 `request_admission` 六态（`not_seen`/`accepted`/`rejected_before_upstream`/`settled`/`conflict`/`unknown`）及真实最终键、`admission_source/funds_effect/quota_effect/dispatch_state/state_version/query_request_id/final_request_id`；0 行、`not_seen`、`accepted`、`conflict`、`unknown` 均不得触发自动重发、免费释放或重复扣款，只有 `rejected_before_upstream` 且 `dispatch_state=not_started`（须由写出点事件证明，不能靠时间戳为空、4xx 状态码或本地异常推断）才可重试。自动重发/免费处理还必须 `funds_effect=none`（余额、欠款、订阅用量无资金变化）且 `quota_effect=none`（Key/限流、账号、平台、订阅额度均未写）；本站钱包释放只按本地预留与主站资金效果判断；`quota_effect` 既不是释放前提，也不是拒释前提，不得因主站额度变化改扣本站钱包。`accepted`/`unknown` 表示可能已调上游，必须待对账；已读到唯一成功 usage 必须为 `settled`，不得因冲突态降级为未结算。同一请求只能有一条 admission（先以临时键建行，最终键只一次 CAS 写入 `final_request_id`），临时键与最终键必须经 `request_admission_alias(alias_request_id, api_key_id, admission_id, final_request_id)` 单跳反查同一受理事实，alias 行以外键绑定该 admission，禁止引用尚未升级最终键的行；同一临时键改绑、同一最终键归属第二条 admission、别名引用未升级最终键的 admission、别名缺失或 CAS 失败时不得确认。调用上游前必须先提交 `accepted`（临时键仅作 `admission_key`，最终键未定时不得写可解析别名），提交失败不得调用上游；本地拒绝先提交零效果受理，提交失败只能返回 `unknown`/不可重试；最终键、别名与权威 usage 同事务或同事务 outbox，任一步失败不得确认成功，不得自动换键重发。
- **受理与别名验收必须可执行**：同一临时键并发绑定两个最终键时恰一条成功、另一条 `conflict`；同一请求由临时键建 admission 后改用最终键查询，不得产生第二条 admission，最终键只能一次 CAS 写入；同一最终键被两个临时键/两条 admission 指向时恰一条成功；临时键别名缺失而最终 usage 已存在时，查询必须返回 `unknown`/待对账，不得返回 `settled`；直接查询最终键且唯一 usage 存在时必须返回 `settled`（`admission_source=usage`），不得因别名未写降级；所有查询（含 `usage_count=0`）必须回传完整 `admission_source/funds_effect/quota_effect/dispatch_state/state_version/query_request_id/final_request_id`，且 `query_request_id` 逐字等于查询键；临时键与最终键反查必须命中同一 `state_version`。注入受理写入失败时上游调用计数必须为 0；注入别名或 usage 写入失败时不得返回成功或自动换键重发。
- 文本/图片/视频链路按当前版本复测并记录结果；失败项有证据。
- 计费归属当前用户；余额不足有明确提示。
- 跨用户、重放、缺凭据、错 slug 均被拒绝。
