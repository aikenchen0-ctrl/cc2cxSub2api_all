# 图片与视频上游切换方案

状态：方案确认稿  
日期：2026-11-07  
范围：Sub2API 的图片、视频、Grok 媒体，以及 `/v1/responses` 中生图工具请求的调度与故障转移  
不包含：卫星应用自身的生成逻辑、Batch Image 队列的作业语义、参考项目 `sub2api-cost-console/`

## 1. 目标与边界

### 1.1 目标

1. 客户只使用 Sub2API 的 API Key，不感知上游账号切换。
2. 上游账号硬故障时，立即切换到同一分组下的其他可用账号。
3. 客户端不需要重新开会话，不需要手工输入“继续”。
4. 软性、短时、请求级故障优先在同一账号上修复，避免为了稳定性频繁切号，减少上游缓存和会话粘性损失。
5. 图片、视频任务不产生重复创建、重复计费、任务所有权丢失。
6. OpenAI 推理密文和 Claude thinking 签名只在必要时做最小清理，优先保留上下文。

### 1.2 不可控边界

- 客户端可能是 Codex、OpenCode、Claude Code 或其他兼容客户端，Sub2API 不能要求客户端改协议。
- 上游的账号、模型容量、密文密钥、签名校验规则不可控。
- OpenAI 的 `encrypted_content` 无法解密；Claude 的 thinking 签名是否可跨账号复用由上游验证决定。
- 服务端没有保存原始明文历史时，不可能同时做到“跨账号”和“完整恢复依赖远端状态的上下文”。
- 上游已经执行但响应丢失的媒体创建，不能通过本地逻辑证明其没有执行。

### 1.3 核心原则

- **先修复，再换号**：只有硬故障或修复预算耗尽才切换账号。
- **硬故障快切**：认证失效、账号禁用、额度耗尽、上游账号状态异常立即切换。
- **软故障不惩罚账号**：请求级容量、客户端参数、短时 5xx/429 不应导致账号被摘除。
- **已写出不切换**：一旦向下游写出语义字节，停止故障转移，避免客户端看到拼接响应。
- **任务所有权优先**：视频查询固定创建账号，不跨账号查询。
- **结果不确定就停止**：视频创建已发出但响应不确定时，不重放。
- **密文最小删除**：只删除被明确拒绝的密文或签名，优先保留 summary、可见文本、工具调用和工具结果。
- **上下文优先于盲目成功**：无法重建历史时，宁可返回明确错误，也不静默删除客户上下文。

### 2.2 主要问题

1. 文本、图片、视频各自维护一套循环，状态码判断、同号重试、切号计数和错误文案分散。
2. 媒体同号重试只有 1 次，5xx 被直接当成请求级瞬时故障；部分场景修复预算不足，另一些场景又可能过度切号。
3. 视频创建已有“结果不确定不重放”的保护，但缺乏统一的策略类型和端到端验收约束。
4. 视频任务账号绑定目前依赖会话缓存 TTL；如果绑定丢失，查询侧可能无法稳定找到创建账号。
5. OpenAI 密文清理主要覆盖 WebSocket/续链场景，HTTP 和媒体场景尚未完全统一。
6. Claude thinking 签名处理偏“400 后整流”，与切号策略、上下文损失统计没有形成统一闭环。
7. 缺少统一的指标：同号修复成功率、切号原因、密文删除量、上下文损失量、任务所有权丢失、结果不确定停止次数。

## 3. 总体设计

### 3.1 三层决策

所有上游尝试统一按以下顺序决策：

1. **发送前检查**
   - 客户端是否已断开。
   - 请求是否需要视频任务所有权存储；存储不可用时，视频创建在发送前直接返回 503。
   - 当前账号是否可用、是否在冷却期、视频查询是否与创建账号一致。

2. **发送后分类**
   - 根据端点类型、HTTP 状态、错误体、响应头、是否已发出、是否已写出语义字节、是否可能已产生媒体任务，生成统一失败分类。
   - 不能用单一状态码直接决定切号。

3. **执行动作**
   - `repair_same_account`：同账号修复并重试。
   - `switch_account`：排除当前账号，同分组选择下一个。
   - `stop_request`：请求本身不可恢复，直接返回。
   - `stop_ambiguous`：上游可能已执行，禁止重放。
   - `cancel`：客户端已断开，静默终止。

### 3.2 统一失败分类

建议新增纯策略层，输入尽量为值类型，避免依赖 handler 或 service 具体实现：

```go
type EndpointKind string

const (
	EndpointText               EndpointKind = "text"
	EndpointResponsesImageTool EndpointKind = "responses_image_tool"
	EndpointImageSync          EndpointKind = "image_sync"
	EndpointImageAsync         EndpointKind = "image_async"
	EndpointVideoCreate        EndpointKind = "video_create"
	EndpointVideoLookup        EndpointKind = "video_lookup"
	EndpointVideoContent       EndpointKind = "video_content"
)

type FailureClass string

const (
	FailureRequestInvalid       FailureClass = "request_invalid"
	FailureAccountAuth          FailureClass = "account_auth"
	FailureAccountQuota         FailureClass = "account_quota"
	FailureAccountState         FailureClass = "account_state"
	FailureTransientSameAccount FailureClass = "transient_same_account"
	FailureCapacityRequestScope FailureClass = "capacity_request_scoped"
	FailureTransportBeforeSend  FailureClass = "transport_before_send"
	FailureTransportAfterSend   FailureClass = "transport_after_send"
	FailureCipherOrSignature    FailureClass = "cipher_or_signature"
	FailureResponseStarted      FailureClass = "response_started"
	FailureAmbiguousMediaCreate FailureClass = "ambiguous_media_create"
)

type AttemptAction string

const (
	ActionRepairSameAccount AttemptAction = "repair_same_account"
	ActionSwitchAccount     AttemptAction = "switch_account"
	ActionStopRequest       AttemptAction = "stop_request"
	ActionStopAmbiguous     AttemptAction = "stop_ambiguous"
	ActionStopCancel        AttemptAction = "cancel"
)
```

分类结果需要携带：

- `Reason`：稳定、可检索的原因码。
- `PenalizeAccount`：是否将失败归因到账号健康。
- `Cooldown`：账号冷却时长；请求级故障必须为 0。
- `SameAccountRetryMax`：本错误允许的同号修复次数。
- `RetryDelay`：本次重试延迟。
- `ClientStatusCode` / `ClientMessage`：最终对客户端的响应。
- `ContextLoss`：本次尝试是否发生上下文删减，以及删减项数量。

### 3.3 默认判定表

| 上游情况 | 默认分类 | 默认动作 | 惩罚账号 |
| --- | --- | --- | --- |
| 400/422 客户端参数错误、内容策略、上下文窗口 | `request_invalid` | `stop_request`；可本地修复则先修复 | 否 |
| `previous_response_not_found`，且本地历史可完整重建 | `request_invalid` | 先本地重建，再同号重试 | 否 |
| 401/403/402、账号禁用、密钥失效、组织/工作区不可用 | `account_auth` / `account_state` | `switch_account` | 是，冷却 60 秒 |
| 配额型 429、重置时间较远 | `account_quota` | `switch_account` | 是，按下一次可用时间冷却，封顶 60 秒 |
| 429，`Retry-After` 很短、可在请求内等待 | `transient_same_account` | `repair_same_account` | 否 |
| 单次 5xx、502 空包、503/529 容量不足、504、流空闲 | `transient_same_account` / `capacity_request_scoped` | 先同号修复 | 否或轻量 |
| 同一账号 60 秒内第 2 次 5xx/超时 | `transient_same_account` | `switch_account` | 是，冷却 30-60 秒 |
| 连接失败、请求尚未发出 | `transport_before_send` | 同号重试 1 次，仍失败再切号 | 视情况 |
| 连接失败、请求已发出但无响应 | `transport_after_send` | 媒体创建为 `stop_ambiguous`；文本按是否可重放决定 | 否 |
| 已向下游写出语义字节 | `response_started` | `stop_request` | 否 |
| 密文/签名校验失败，且历史可重建 | `cipher_or_signature` | 先最小清理并同号重试 | 否 |
| 密文/签名校验失败，且依赖不可重建的远端历史 | `request_invalid` | `stop_request` 或保持原账号 | 否 |
| 视频创建已发出但响应不确定 | `ambiguous_media_create` | `stop_ambiguous` | 否 |
| 视频查询账号不可用 | `account_state` | 保持创建账号，短退避；不跨账号 | 否 |

### 3.4 发送状态

每次尝试必须显式记录：

- `RequestPrepared`：已构造请求。
- `BytesSent`：至少部分请求字节已写入网络。
- `ResponseHeaders`：已收到上游响应头。
- `SemanticBytesWritten`：已向客户端写出语义字节。
- `AmbiguousPossible`：该端点存在“上游已执行但本地不知道结果”的可能。

故障转移判断必须建立在上述状态上，不能只看 `err != nil`。

实现约定：`UpstreamFailoverError.RequestPhase` 显式记录本地传输阶段
（`not_sent` / `sent` / `unknown`）。handler 只在阶段未知时使用自身观测，
不能把“账号已选好”当成“请求已发出”。图片同步、异步图片、Grok 图片/视频
创建与查询、AutoDL 视频都按这一约定进入策略。

## 4. 重试与成本控制

### 4.1 同号修复预算

| 场景 | 默认同号修复次数 | 重试间隔 | 总等待上限 |
| --- | --- | --- | --- |
| 同步图片 | 1 | 250ms 起，最多 2s | 2s |
| 异步图片执行 | 1 | 250ms 起，最多 2s | 2s |
| Grok 图片 | 1 | 250ms 起，最多 2s | 2s |
| 视频创建 | 0 | 不重试 | 0 |
| 视频查询/内容 | 2 | 300ms、800ms | 2s |
| 文本 Responses/Chat | 3（沿用账号池配置） | 250ms、750ms、1500ms，带 ±20% 抖动 | 8s |

说明：

- 视频创建为 0 次同号重试，是因为无法证明上一次创建没有成功。
- 同号修复只适用于可安全重放的请求。
- 一旦已向上游写出请求且无法确认结果，媒体创建直接进入 `stop_ambiguous`。
- 重试延迟必须带抖动，避免多个请求同时重试打爆同一账号。
- 异步图片任务使用独立端点 `image_async`，但执行预算与同步图片一致；
  worker 在派生 context 上带 `openai_async_images_endpoint` 标记。
- 同号修复预算与共享策略必须一致：图片 1 次、视频查询 2 次、
  视频创建 0 次、文本 3 次。service 层只负责给出候选延迟和上限，
  handler 再按统一动作执行。

### 4.2 换号预算

- 图片、视频默认最多切换 3 个账号。
- 文本沿用现有配置，但每个请求必须有明确上限，不能无限循环。
- 已经尝试过的账号在当前请求内不重复选择。
- 同一账号连续失败达到阈值后进入冷却；请求级故障不推进账号级失败计数。
- 所有候选账号都不可用时，返回明确的上游容量/账号不可用错误，不继续空转。

### 4.3 账号冷却

建议与现有 `账号切换策略-260926.md` 对齐：

- 失败统计窗口：60 秒。
- 硬故障：首次即进入冷却 60 秒。
- 软故障：同一账号 60 秒内第 2 次失败进入冷却 30-60 秒。
- 冷却结束先半开放行一次；成功则恢复，失败则重新冷却。
- 请求级瞬时故障不写账号不可调度状态。
- 客户端主动断开不计入账号失败。

### 4.4 粘性与缓存

- 账号健康时优先保持粘性，不为单次软故障切号。
- 同号修复不刷新、不重建上游 prompt cache 身份。
- 只有实际切换账号时才触发缓存失效统计和必要的缓存计费口径。
- 切换后记录 `cache_affinity_lost`，用于评估成本影响。

## 5. 图片场景

### 5.1 同步图片

端点：

- `/v1/images/generations`
- `/v1/images/edits`
- 对应无 `/v1` 前缀别名

规则：

1. 请求未发出：可同号重试，也可换号。
2. 上游明确返回 5xx 且未写出响应：同号修复 1 次，仍失败再换号。
3. 上游返回 429：
   - `Retry-After` 很短且可在 2 秒内等待：同号等待重试。
   - 配额型或重置时间较远：立即换号并冷却账号。
4. 连接中断且无法确认上游是否已生成：
   - 不跨账号重放，避免重复生成和重复计费。
   - 返回明确的“结果不确定”错误。
5. 已开始流式写出图片字节：不再切换账号。
6. 生图能力必须匹配：不能切到只能 Chat Completions、无法执行生图的账号。

### 5.2 异步图片

端点：

- `/v1/images/generations/async`
- `/v1/images/edits/async`
- `/v1/images/tasks/{task_id}`

规则：

1. 提交阶段返回 `202` 后，任务与客户端连接解耦。
2. 任务执行仍使用统一失败分类，不复制同步图片循环。
3. 任务记录至少保存：
   - 当前状态。
   - 已尝试账号 ID。
   - 每个账号的失败分类。
   - 是否发生同号修复。
   - 是否停止于结果不确定。
4. 轮询只读本地任务记录和对象存储结果，不重新访问上游。
5. 任务失败时保留结构化错误，客户端不需要重开任务。
6. 结果上传对象存储失败时，任务标记失败，不在 Redis 保存大体积 base64。

### 5.3 `/v1/responses` 生图工具

这不是纯图片端点，而是“文本 + 生图工具”的混合请求。

- 失败分类与文本 Responses 一致。
- 必须调度到同时支持 Responses 和生图能力的账号。
- OpenAI 密文规则适用于整个请求，不能因为存在生图工具就整段删除历史。
- 生图工具能力的判定复用现有 `image_generation` 意图识别，不能只按模型名猜测。
- 如果切换后账号不支持生图，应视为能力不匹配，不把上游错误归因到账号健康。

### 5.4 Batch Image

Batch Image 是独立作业队列，本方案第一阶段不改变其排队、重试和结算语义。

- 如果批处理内部调用网关，则复用统一失败分类。
- 如果批处理直接调用供应商 API，则只做观测，不强行接入网关故障转移。

## 6. 视频场景

### 6.1 视频创建

规则：

1. 发送前检查任务所有权存储；存储不可用时返回 503，不向上游发送。
2. 请求未发出：可以换号。
3. 请求已发出但无响应：`stop_ambiguous`，不换号、不重放。
4. 上游明确返回可重试 5xx：仅在确认请求未产生任务时允许换号；否则按结果不确定处理。
5. 创建成功后立即持久化：

```text
task_id -> {
  user_id,
  api_key_id,
  group_id,
  account_id,
  platform,
  model,
  created_at,
  expires_at,
  billing_snapshot,
  ownership_version
}
```

6. 绑定写入失败时：
   - 不触发重放。
   - 记录 P0 告警。
   - 进入重试队列，避免产生孤儿任务。
7. 对客户端返回创建成功前，至少完成一次同步绑定尝试；绑定存储必须在发送前可用。

### 6.2 视频查询/内容

规则：

1. 只允许查询创建账号。
2. 创建账号短时不可用：同号退避重试，不跨账号。
3. 创建账号永久失效：返回“任务所有权不可用”类错误，不伪装成任务不存在。
4. 不允许通过通用粘性回退覆盖任务所有权记录。
5. 查询请求不刷新、不修改创建账号绑定。
6. 视频内容下载如果使用签名 URL，可不带账号凭据；但签名 URL 的来源校验必须保留。

### 6.3 视频任务所有权存储

建议双层：

- 主存储：Redis，低延迟，带 TTL 和版本号。
- 兜底存储：PostgreSQL 或任务账本表，用于 Redis 故障恢复和审计。

建议 Redis Key：

```text
media:video:owner:v1:{task_id}
media:video:create:intent:v1:{local_request_id}
```

要求：

- 写入使用 `SET NX` 或版本比较，防止并发覆盖。
- 创建前写入 intent，成功后将 intent 转为 owner。
- owner TTL 不短于计费和轮询所需时间，默认 7 天，可配置。
- 查询时先读 owner，再读旧会话缓存兼容；owner 不存在时才使用旧缓存。
- owner 与旧缓存冲突时以 owner 为准，并记录 `video_owner_conflict`。

## 7. 密文与签名处理

### 7.1 原则

密文处理不是“切号时统一删掉”，而是按协议、失败原因和历史可重建性分级处理。

必须区分：

- 普通 reasoning 密文。
- 压缩历史/opaque compaction。
- `previous_response_id` 远端引用。
- `item_reference`。
- 工具调用与工具结果配对。
- Claude `thinking` 签名。
- Claude `redacted_thinking`。
- 第三方 Anthropic 兼容上游要求的 thinking 原样回传。

### 7.2 OpenAI Responses

新增 `ContinuationPlan`，每个尝试只生成一次：

| 级别 | 条件 | 动作 |
| --- | --- | --- |
| `ReplayExact` | 无跨账号密文风险 | 原文重放 |
| `StripRejectedCipherOnly` | 同账号被明确拒绝，且只有部分密文失效 | 只删被拒绝摘要命中的 `encrypted_content` |
| `StripProviderCipherKeepPortable` | 跨账号，但请求可独立重放，工具链完整 | 删除 provider 密文和 provider id，保留 summary/content/tools |
| `RebuildFromLocalHistory` | 有 `previous_response_id`/`item_reference`，且本地保存了完整父轮 | 用本地历史替换远端锚点后重放 |
| `UnsafeAcrossAccount` | opaque compaction、远端引用、工具链不完整、本地历史缺失 | 不跨账号；保持原账号或明确报错 |

约束：

1. 不修改 canonical 客户端请求体；所有清理都从 canonical body 派生 attempt body。
2. 同一请求内每种密文修复最多执行一次，避免反复删改。
3. 只删除被上游明确拒绝的密文摘要，不因为“可能不兼容”就全量删除。
4. 保留 `summary`、可见文本、工具调用、工具结果和 `call_id` 配对。
5. 删除项数量、保留项数量、上下文损失量写入日志和指标。
6. 失效密文摘要按会话记录 lineage，后续轮次直接跳过，避免重复“拒绝→剥离→重试”。
7. lineage 不能替代本地历史重建；它只解决重复失效密文。
8. 无明文输入、无摘要、无父轮锚点的纯密文请求，不能假装可以恢复。
9. HTTP 与 WebSocket 共用同一恢复计划：`PlanOpenAIContinuationRecovery`
   先判定 `replay_exact` / `strip_rejected_cipher_only` /
   `strip_provider_cipher_keep_portable` / `rebuild_from_local_history` /
   `unsafe_across_account`，再执行对应 body 派生。
10. 收到 `invalid_encrypted_content` 时，只剥离本轮进场正文中已收集摘要
    命中的 reasoning 密文；没有命中就不盲删。压缩历史始终保留。

### 7.3 本地历史重建

仅在以下条件同时满足时启用：

- 客户端有稳定会话标识。
- 服务端完整观察到父轮请求和响应。
- 工具调用与工具结果配对完整。
- 历史大小未超过配置上限。

建议存储：

```text
media:continuation:history:v1:{group_id}:{session_hash}
```

内容为规范化后的父轮 transcript，包含：

- response id。
- input 中的可见消息。
- reasoning summary（不保存无法解密的 opaque 内容）。
- tool calls 与 tool outputs。
- 生成时间、模型、账号、过期时间。

限制：

- 默认关闭，先做 dry-run 和容量评估。
- 有 TTL、单会话大小上限、全局容量上限。
- 不保存原始密钥、Authorization、完整 base64 图片。
- 只保存重建上下文所需的最小字段。

### 7.4 Claude thinking

按协议族分流：

- `AnthropicStrict`：有效签名保留；缺失/非法签名才清理。
- `PassbackRequired`：保留 thinking block 原样；不能预剥离。
- `Unknown`：保守保留，不主动变形。

同账号签名失败：

1. 只移除缺失/非法签名的 thinking block。
2. 保留 thinking 文本时，可降级为普通 text block。
3. `redacted_thinking` 无法还原，最后才删除。
4. 不允许为了绕过错误而整段删除历史 thinking。

跨账号：

1. 先判断请求是否可独立重放。
2. 可重放时，有效签名尽量保留；无法保留的 thinking 内容降级为 text。
3. `PassbackRequired` 上游不跨账号做 thinking 变形；无法安全重放时停止。
4. 所有降级和删除记录上下文损失。

### 7.5 结果不确定与上下文损失

以下情况必须返回明确错误，而不是静默成功：

- 视频创建已发出但结果不确定。
- 压缩历史/远端引用无法重建，且原账号不可用。
- 纯密文历史无法恢复，且不能保持原账号。
- 密文清理后会导致工具调用链断裂。

错误信息应包含稳定原因码，例如：

```text
media_result_ambiguous
continuation_context_unrecoverable
video_owner_unavailable
ciphertext_history_unrecoverable
```

## 10. 落地顺序

### 阶段 0：文档与基线

- 本文档确认。
- 收集当前文本、图片、视频的切号率、同号重试成功率、视频查询失败率。
- 定义 dry-run 日志格式。

### 阶段 1：统一策略骨架

- 新增纯策略包和失败分类类型。
- `UpstreamFailoverError` 增加分类、动作、惩罚、冷却、结果不确定等字段。
- 文本、图片、Grok 媒体先接入分类，但 `dry_run` 下保持原行为。
- 增加指标和日志。

验收：

- 现有测试全部通过。
- dry-run 日志能解释每一次“为什么切/为什么没切”。
- 线上行为无变化。

### 阶段 2：软故障同号修复

- 图片同步、异步图片、Grok 图片接入 1 次同号修复。
- 视频查询接入 2 次同号退避。
- 请求级故障不惩罚账号。
- 硬故障立即切号。

验收：

- 单次 5xx、短 429、流空闲不再立即切号。
- 认证/额度/账号失效仍然立即切号。
- 媒体切号率相比基线下降，缓存命中率不下降。

### 阶段 3：视频所有权

- 新增视频任务所有权账本。
- 创建前检查存储可用性。
- 创建成功同步写入 owner。
- 查询只认 owner。
- 旧会话缓存作为兼容兜底，不能覆盖 owner。

验收：

- 连接中断场景不产生重复视频任务。
- owner 丢失率、绑定失败率可观测。
- 查询不会跨账号。

### 阶段 4：密文/签名统一

- OpenAI 接入 `ContinuationPlan`。
- 失效密文 lineage 从 WebSocket 扩展到 HTTP 和媒体。
- Claude thinking 严格按协议族处理。
- 增加上下文损失指标。

验收：

- 同账号失效密文只删除命中项。
- 可独立重放请求跨账号时保留 summary/content/tools。
- 不可重建历史不静默删除。
- 现有密文/签名测试通过。

### 阶段 5：本地历史重建（可选）

- 默认关闭。
- 先做容量评估和隐私评估。
- 只在明确会话、完整工具链、受限 TTL 下启用。

### 阶段 6：清理重复循环

- 删除图片/Grok 媒体中重复的重试和切号分支。
- 全部走统一策略层。
- 稳定后移除 dry-run 开关，保留紧急回滚开关。

## 11. 测试与验收

### 11.1 单元测试

必须覆盖判定矩阵：

- 401/402/403 -> 立即切号，账号冷却。
- 短 `Retry-After` 429 -> 同号修复，不惩罚账号。
- 长重置 429 -> 切号，账号冷却。
- 单次 500/502/503/504 -> 同号修复。
- 60 秒内第 2 次 5xx -> 切号。
- 400 参数错误 -> 不切号。
- 已写语义字节 -> 不切号。
- 视频创建发送后连接中断 -> `stop_ambiguous`，上游调用次数为 1。
- 视频查询账号不可用 -> 不跨账号。
- owner 存储不可用 -> 视频创建发送前 503，上游调用次数为 0。
- 密文同号失效 -> 只删命中项，保留 summary。
- 压缩历史/`previous_response_id` -> 不跨账号盲目剥离。
- Claude strict 非法签名 -> 最小清理或文本降级。
- Claude passback-required -> 不预剥离。

### 11.2 集成测试

使用模拟上游验证：

1. 同分组多账号，第一个账号 503，第二个成功；断言只发生 1 次同号修复后切号。
2. 第一个账号 401，断言不重试同号，直接切号。
3. 视频创建第一次连接中断，断言没有第二次创建请求。
4. 视频创建成功后查询走创建账号，即使其他账号更健康。
5. 异步图片任务在后台切换账号后仍能完成并写入对象存储。
6. 密文清理后工具调用链完整，`call_id` 配对不丢失。
7. 并发同会话请求不覆盖 owner，不产生错误粘性绑定。
8. 客户端断开后不再发起新的上游尝试。

### 11.3 回归命令

实现阶段至少执行：

```powershell
cd sub2api/backend
go test ./internal/handler/...
go test ./internal/service/...
go test ./internal/pkg/apicompat/...
```

如果仓库有统一测试脚本，以仓库脚本为准。

### 11.4 上线验收指标

- 视频重复创建：混沌测试和线上告警均为 0。
- 视频查询跨账号：0。
- 已写出响应后仍切号：0。
- 请求级软故障导致的账号冷却：0。
- 同号修复新增时延：图片 p95 不超过 2 秒，文本 p95 不超过 8 秒。
- 媒体切号率：相对 dry-run 基线下降，具体目标在拿到基线后确定。
- 缓存亲和命中率：不因软故障策略下降。
- 密文上下文损失：每次删除都有指标和日志，无法重建时返回明确错误。

## 12. 风险与回滚

### 12.1 风险

1. 同号修复可能增加单次请求时延；必须设置总预算和抖动。
2. 视频所有权存储增加一次依赖；存储故障时视频创建会 fail-closed，需要在运维上保证 Redis/DB 可用性。
3. 密文清理逻辑复杂，错误删除可能降低模型能力；必须 dry-run、最小删除和上下文损失指标。
4. 本地历史重建涉及隐私和存储成本；默认关闭。
5. 不同上游对 thinking/密文的校验规则可能变化；协议分类需要版本化和可配置。

### 12.2 回滚

- `gateway.media_failover.enabled=false`：回到现有行为。
- `dry_run=true`：只观测不改变动作。
- `video_ownership.required_before_send=false`：仅作为紧急回滚，不建议长期开启。
- `continuation.cross_account_strip=false`：禁止跨账号密文清理。
- `continuation.local_history_rebuild=false`：关闭历史重建。

回滚不能删除已写入的 owner 记录；查询侧必须保持向后兼容。

## 14. 已确认的产品取舍

以下取舍按本方案执行，不再在实现阶段反复变更：

1. **视频创建已发出但无响应：不重放。** 宁可返回结果不确定，也不产生重复任务和重复计费。
2. **视频查询只认创建账号。** 账号不可用时同号退避，不跨账号查询。
3. **密文无法重建时：保上下文优先。** 不静默删除历史；必要时返回明确错误。
4. **软故障先同号修复。** 单次 5xx、短 429、流空闲不立即切号。
5. **硬故障立即切号。** 认证、额度、账号状态异常不消耗同号修复预算。
6. **请求级故障不惩罚账号。** 只有账号级失败才进入冷却。
7. **已写语义字节不切换。** 客户端看到的响应流不拼接、不重放。
8. **第一版先 dry-run。** 先观测分类和动作，再逐步开启行为变更。
