# 前端技术栈与架构分析

## 分析目标

基于 `frontend/` 的实际代码和配置，说明项目的技术选型、运行时分层、模块边界、数据流、构建测试方式，并评估当前架构的优势与风险。

## 结论摘要

这是一个面向 AI API 网关的中大型 Vue 单页应用，业务同时覆盖公开页、用户控制台、管理后台、认证回调和多支付渠道。它的工程基础比较扎实：类型严格、路由懒加载、请求层统一、中英文包按需加载、测试面较广，生产交付也与 Go 后端形成了清晰的单二进制部署模式。

当前的主要阻力不是技术栈老化，而是业务增长速度超过了模块边界的演进速度：路由、大型 SFC、全局类型和部分 store 已承担过多职责。因此推荐保留现有栈，按业务域渐进迁移到 `features/*` 垂直切片，而不是重写。

## 整体架构

```text
浏览器
  -> main.ts 启动编排
     -> Pinia 和注入的公开配置
     -> Vue I18n 异步语言包
     -> Vue Router 首次导航与权限/功能开关守卫
  -> App.vue 跨页编排
     -> RouterView
        -> View
           -> AppLayout / AuthLayout / TablePageLayout
           -> 业务组件 + common 组件 + composables
           -> Pinia Store 或域 API 模块
              -> Axios 统一客户端
                 -> /api/v1 -> Go 后端

生产交付：Vite dist -> backend/internal/web/dist -> Go embed -> 单个后端进程
```

### 启动与公开配置

`main.ts` 先恢复主题和移动端视口，再创建 Pinia，从 `window.__APP_CONFIG__` 读取后端注入的站点名、Logo 和功能开关，然后加载当前语言包和路由。等待 `router.isReady()` 后才挂载，可以避免首航重定向与页面渲染竞态。

开发期由 Vite 插件调用 `/api/v1/settings/public` 并注入同样的全局配置；生产期由 Go HTML 缓存层完成。这使开发与生产使用同一启动协议，也避免品牌信息二次请求导致的闪烁。

### 路由与权限

所有页面组件均采用动态导入。路由 meta 的核心策略是默认需要登录，显式 `requiresAuth: false` 才是公开页，`requiresAdmin: true` 则是管理员页。守卫还会处理安装向导、支付/风控开关、简易运行模式、后端模式白名单和管理员合规确认。

导航完成后会在浏览器空闲时间预取可能的下一路由。如果部署更新导致旧 HTML 加载不存在的 chunk，路由错误处理会带 10 秒节流地刷新页面。

### 状态管理

Pinia 主要保存跨页面、跨组件或需要轮询的状态：

- `auth`：用户、访问/刷新令牌、待完成认证会话、运行模式和定时刷新。
- `app`：侧边栏、全局 loading 计数、Toast、公开设置和版本信息。
- `subscriptions`、`announcements`、`payment`：跨页数据、轮询和流程状态。
- `adminSettings`、`adminCompliance`：管理端配置和合规门禁。
- `onboarding`：新手引导回放状态。

普通页面数据多使用本地 `ref/reactive` 自行管理，或通过 `useTableLoader`、`useAutoRefresh` 等 composable 复用部分模式。项目没有独立的服务端状态库。

### API 与数据流

`src/api/client.ts` 是单例 Axios 客户端，域 API 文件只负责 URL、参数和返回类型。完整链路为：

```text
页面/store/composable
  -> 业务 API 函数
  -> Axios request interceptor
     -> Bearer Token + locale + timezone + UI 来源头
  -> Go API
  -> Axios response interceptor
     -> { code, message, data } 解包
     -> 401 刷新令牌与原请求重放
     -> 功能关闭/合规状态全局事件
     -> 结构化错误
```

认证同时具备主动刷新和 401 被动刷新。被动刷新失败时会比对刷新前后的 token 和用户快照，防止旧请求误清理另一标签页刚建立的新会话。

### UI 组织

项目没有采用 Element Plus、Ant Design Vue 等大型组件库，而是使用 Tailwind 、全局 `.btn/.card/.tabs` 等语义类、scoped CSS 和自研组件形成设计系统。`AppLayout` 负责侧边栏和顶栏，`AuthLayout` 负责认证页，`TablePageLayout` 规范操作区、筛选区、表格滚动和分页。

代码组织是混合形态：大部分代码按 `views/components/api/stores/utils/types` 技术层平铺；新的 `prompt-audit` 则把 API、types、view model、组件和测试放在同一 feature 中，模块内聚更好，适合作为后续新功能的参考模式。

## 构建与部署

- 开发：Vite 默认在 `3000` 端口运行，将 `/api`、`/v1`、`/setup` 代理到 Go 后端。
- 构建：`vue-tsc -b && vite build`，产物直接写入 `backend/internal/web/dist`。
- 分包：手动分出 Vue、UI/XLSX、Chart、I18n、Stripe 和其他 vendor；路由再自动分包。
- 生产：Go 在 `embed` build tag 下嵌入 `dist`，使用单进程同时提供 API 和 SPA。
- 缓存：静态资源由文件服务提供，`index.html` 与 SPA 路由单独处理并注入当前公开设置。

这种交付形态的优点是版本原子性强、部署简单、不需要单独配置 CORS 和前端服务；代价是前端发布与后端二进制发布绑定，不能独立滚动升级。

## 测试与质量基线

- Vitest 默认运行在 jsdom，测试超时 10 秒，并统一 mock storage、idle callback、media query 和 observer。
- 覆盖率使用 V8，statements、branches、functions、lines 全局阈值均是 80%。
- 约 779 个 `src` 文件中，测试相关文件约 249 个，覆盖 API、store、composable、路由守卫、视图和专用 feature。
- 生产 TypeScript 配置排除 `__tests__`、`.spec.ts` 和 `.test.ts`，因此常规 `typecheck` 不会对测试代码做完整静态类型检查。
- ESLint 启用 recommended 基线，但 `no-explicit-any`、`ban-ts-comment`、Vue 多词组件名等规则被关闭，未使用参数只作警告。

## 架构优势

1. 启动协议清晰。公开配置在开发与生产保持同构，并在挂载前完成品牌、语言和首航初始化。
2. 统一请求层较成熟。它不仅封装 URL，还统一了语言、时区、响应协议、刷新重放和并发会话保护。
3. 前后端交付边界简单。同源 API、Go embed 和 SPA fallback 减少了部署与运维变量。
4. 性能意识到位。路由懒加载、vendor 分包、locale 懒加载、路由空闲预取、长列表虚拟化和 chunk 失效恢复均已实现。
5. 测试面较宽。尤其认证刷新、路由门禁、支付和复杂管理功能有专门测试。

## 主要风险

| 优先级 | 风险 | 证据 | 影响 |
|---|---|---|---|
| P0 | 超大 SFC 和超大域文件 | `SettingsView.vue` 约 1.3 万行，多个页面/弹窗 5000 行以上，`types/index.ts` 约 2346 行 | 审查困难、回归面大、冲突率高，难以独立测试业务逻辑 |
| P1 | 路由与守卫集中过度 | `router/index.ts` 约 1011 行，同时定义全部路由和多种门禁策略 | 新功能容易引入顺序依赖、重定向循环和跨模式回归 |
| P1 | 服务端状态管理分散 | 缓存、轮询、取消、并发去重和错误状态由各 store/页面实现 | 重复实现与数据新旧不一致的概率随功能增加 |
| P1 | 全局副作存在隐式耦合 | Axios 拦截器会 dispatch `window` 事件和直接修改 `window.location` | 请求基础设施与 UI/路由相互感知，单测和复用成本上升 |
| P2 | 设计系统实现分散 | 778 行全局 CSS + Tailwind 配置 + scoped CSS + 自研组件 | 语义类、原子类与局部样式容易漂移，样式变更的影响面不易判断 |
| P2 | 持久化令牌的 XSS 暴露面 | access/refresh token 位于 `localStorage` | 任意脚本执行漏洞可读取会话；迁移 HttpOnly Cookie 则会引入 CSRF 等新约束 |
| P2 | 文档与实现偏离 | Router README 只列少量路由，Store README 只介绍两个 store | 新成员依赖过期文档会得到错误边界认知 |

## 演进方案

### 方案 A：只做规则治理

为新文件设定行数/复杂度阈值，补齐文档，但不处理存量超大文件。成本最低、见效最快，但只能防止问题加速，无法降低当前核心模块的变更风险。

### 方案 B：按业务变更渐进垂直切片（推荐）

保留 Vue/Pinia/Axios/Tailwind，参考 `features/prompt-audit` 的方式，当某个大页面下次发生实质业务变更时，再把对应子域的 types、API、view model、components 和 tests 一起迁入 `features/<domain>`。先拆 `Settings`、`Account Editor`、`Groups` 三个高变更区，每次只迁一个闭环子域。

同时：

1. 把路由表拆为 public、user、admin 三个 route manifest，守卫拆为认证、运行模式、feature flag、compliance 四个可单测策略函数。
2. 先在现有 composables 之上定义统一的 async resource 约定（loading/error/data/cancel/refresh），只有当跨页缓存与失效复杂度确实持续上升时，再评估 Vue Query。
3. 把 Axios 产生的功能事件转换为显式注入的 session/feature event adapter，让 HTTP 层不直接导航。
4. 将 `types/index.ts` 按 auth、billing、accounts、channels、settings 拆分，保留短期 barrel export 平滑迁移。
5. 为测试添加独立 `tsconfig.test.json` 或类型检查脚本，不让测试只依赖 Vitest 转译。

这条路径的代偿是短期内新旧结构会并存，但变更面可控，最适合当前已经有大量回归测试的生产项目。

### 方案 C：全面重构或更换栈

一次性拆分所有页面，或更换状态/UI 栈。理论上可快速得到形式统一的新架构，但会同时暴露认证、支付、功能开关和管理业务的大面积回归风险，成本与收益不匹配，不建议。

## 已确认事实

- 项目是前后端同仓，前端位于 `frontend/`，后端位于 `backend/`。
- 前端包含独立的 `package.json`、Vite、TypeScript、Tailwind 和 Vitest 配置。
- 源码已按 `api`、`views` 等目录分层，并有 API 单测、视图单测和集成测试。
- 核心栈为 Vue 3.4、TypeScript 5.6、Vite 5、Vue Router 4、Pinia 2、Vue I18n 9、Axios 1.18 和 Tailwind CSS 3.4。
- TypeScript 启用 `strict`、未使用变量/参数检查和 bundler 模块解析，别名 `@` 指向 `src`。
- Vite 开发服务将 `/api`、`/v1`、`/setup` 代理到 Go 后端，生产构建输出到 `backend/internal/web/dist`。
- 构建按 Vue 核心、UI/XLSX、图表、国际化、Stripe 和其他依赖手动分 chunk。
- Vitest 使用 jsdom 与 V8 覆盖率，全局阈值设为 80%；常规 TypeScript 构建主动排除测试文件。
- `main.ts` 的启动顺序是：主题/iOS 视口处理 -> 创建 Vue/Pinia -> 从 `window.__APP_CONFIG__` 恢复公开配置 -> 加载当前语言包 -> 安装 Router/I18n -> 等待首次导航 -> 挂载。
- `App.vue` 是跨页面编排层，除 `RouterView` 外还统一挂载导航进度、Toast、公告和管理员合规对话框，并管理订阅/公告的预加载与轮询。
- 路由表约 1011 行，页面组件全部动态导入；权限模型为公开、登录用户、管理员三层，叠加部署模式与功能开关校验。
- Pinia 店铺分为认证、全局应用、订阅、公告、支付、引导、管理员设置与合规状态；长期会话数据主要通过 `localStorage` 恢复。
- 国际化支持中英文，语言包按当前 locale 异步加载，并将选择持久化到 `localStorage`。
- Axios 单例默认超时 30 秒、携带 Cookie；请求拦截器注入 Bearer Token、`Accept-Language`、GET 时区以及管理端/用户端标记。
- 响应拦截器将 `{ code, message, data }` 解包为 `data`，并将 API/网络错误统一转为结构化拒绝。
- 认证采用访问令牌 + 刷新令牌：认证店铺按到期时间主动刷新，Axios 遇到 401 时被动刷新并重放原请求。
- 刷新失败前会比对当前 `refresh_token` 和用户快照，避免过期并发请求销毁已被其他标签页替换的会话。
- 路由守卫同时管理安装态、公开路由、RBAC、后端模式白名单、简易模式限制、支付/风控开关、管理员合规和 chunk 加载失败自恢复。
- Go 后端在 `embed` 构建标签下用 `//go:embed all:dist` 嵌入前端，静态资源由 `http.FileServer` 提供，未命中文件的 SPA 路径回退到 `index.html`。
- 后端的 HTML 缓存层会将公开设置注入 `index.html`，与 Vite 开发期 `inject-public-settings` 插件保持同一启动协议。
- `src` 约有 779 个文件，其中 `components` 311、`views` 175、`api` 79、`utils` 62、`i18n` 43、`composables` 34、`features` 28。
- 主体组织方式为按技术层分目录，`features/channel-monitor-v2` 和 `features/prompt-audit` 开始采用包含 API、类型、视图模型、组件和测试的垂直切片。
- 页面外壳通过 `AppLayout`、`AuthLayout` 和 `TablePageLayout` 复用；页面内部通过 common/业务组件与 composables 复用。
- 源码中约有 303 个 Vue 文件和 458 个 TypeScript 文件，测试相关文件约 249 个，测试密度较高。
- 规模风险明显：`SettingsView.vue` 约 12998 行，`CreateAccountModal.vue` 约 6867 行，`GroupsView.vue` 约 6796 行，`EditAccountModal.vue` 约 5319 行，`types/index.ts` 约 2346 行。
