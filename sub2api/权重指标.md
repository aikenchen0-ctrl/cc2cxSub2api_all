# Sub2API 权重指标与上游账号调度说明

> 本文根据当前代码实现整理。重点针对 OpenAI WebSocket/高级调度路径；不同平台、图片接口、旧版调度路径可能使用不同的筛选和排序细节。

## 1. 先理解两个“优先级”

系统里有两个容易混淆的概念：

| 名称 | 作用 | 数值方向 |
| --- | --- | --- |
| 账号 `priority` | 管理员给账号设置的基础优先级 | 数值越小越优先 |
| 调度 `score` | 根据当前候选账号的实时状态计算出的综合分 | 分数越大越优先 |

账号 `priority` 会参与综合评分，但不是综合分本身。综合分中的优先级因子还会根据“本次请求的候选池”做归一化，因此它是相对值。

例如当前候选账号的优先级是 `10、20、50`，系统会把它们映射为接近 `1、0.75、0` 的优先级因子。候选池改变后，同一个账号的因子也可能改变。

账号优先级可通过 Admin API 修改：

```http
PUT /api/v1/admin/accounts/{account_id}
x-api-key: <ADMIN_API_KEY>
Content-Type: application/json

{"priority": 10}
```

## 2. 账号指标返回结构

请求账号列表时，显式加入 `include_scheduler_score=1`：

```http
GET /api/v1/admin/accounts?platform=openai&include_scheduler_score=1
```

单个账号可能返回：

```json
{
  "id": 123,
  "priority": 10,
  "scheduler_score": {
    "base_score": 3.42,
    "sticky_score": 11.42,
    "sticky_score_infinity": false,
    "sticky_weighted_enabled": true
  },
  "scheduler_scores": [
    {
      "group_id": 5,
      "group_name": "默认组",
      "group_priority": 1,
      "base_score": 3.42,
      "sticky_score": 11.42,
      "sticky_score_infinity": false,
      "sticky_weighted_enabled": true
    }
  ]
}
```

字段说明：

- `priority`：账号自身的全局优先级原值。
- `scheduler_score`：未按具体分组区分时的基础/粘性评分。
- `scheduler_scores`：按账号所属分组分别计算的评分；同一账号在不同组的候选池可能不同，因此分数也可能不同。
- `group_priority`：账号在该分组关系中的优先级，和账号全局 `priority` 不是同一个字段。
- `base_score`：普通调度综合分。
- `sticky_score`：在基础分上加入粘性偏好的参考分。
- `sticky_score_infinity`：粘性加权未启用时为 `true`，前端显示为 `+∞`；此时旧逻辑仍可能对命中的粘性账号进行硬优先处理。
- `sticky_weighted_enabled`：是否启用高级调度的粘性加权。

评分列的显示格式是“分组名 / 基础分 / 粘性分”。系统只有在请求参数开启时才计算和返回评分；普通账号列表默认仍会返回顶层 `priority`。

## 3. 综合评分公式

高级调度计算的基础分可以概括为：

```text
base_score =
    priority_weight       * priority_factor
  + load_weight           * load_factor
  + queue_weight          * queue_factor
  + error_rate_weight     * error_factor
  + ttft_weight           * ttft_factor
  + reset_weight          * reset_factor
  + quota_headroom_weight * quota_headroom_factor
  + upstream_cost_weight  * upstream_cost_factor
```

每个因子通常都被归一化到 `0 ~ 1` 附近，再乘以管理员配置的权重。除非特别说明，因子越大表示越适合被调用。

### 3.1 `priority_factor`：账号基础优先级

- 来源是账号的 `priority`。
- 当前候选池中优先级数值最小的账号得到最高因子。
- 优先级数值最大的账号得到最低因子。
- 如果候选池中所有账号的优先级相同，则所有账号该因子相同。
- 这意味着 `priority` 不是绝对分数，而是当前候选账号之间的相对排序信号。

默认权重：`1.0`。

### 3.2 `load_factor`：当前并发负载

根据账号当前负载率计算：

```text
load_factor = 1 - clamp(load_rate / 100, 0, 1)
```

通俗地说：账号越空闲，分数越高；负载达到或超过 100% 时，该因子接近 0。

默认权重：`1.0`。

### 3.3 `queue_factor`：等待队列长度

根据候选池内的等待数计算：

```text
queue_factor = 1 - clamp(account_waiting / max_waiting_in_pool, 0, 1)
```

等待请求越少，分数越高。它主要用来避免请求继续集中到已经排队严重的账号。

默认权重：`0.7`。

### 3.4 `error_factor`：近期错误率

错误率会被限制在 `0 ~ 1`：

```text
error_factor = 1 - error_rate
```

错误越多，分数越低。刚启动、还没有错误率样本时，通常按中性/正常状态处理，而不是直接惩罚账号。

默认权重：`0.8`。

### 3.5 `ttft_factor`：首 Token 延迟

TTFT（Time To First Token）表示请求发出后收到第一个 Token 的耗时。

- 候选账号中 TTFT 越低，因子越高。
- 当没有足够的 TTFT 样本时，系统使用中性值 `0.5`。
- 该指标只反映已采集到的运行时数据，不是账号静态配置。

默认权重：`0.5`。

### 3.6 `reset_factor`：会话窗口重置时间

该因子用于“尽快使用即将重置的窗口”（use-it-or-lose-it）策略：

- 有活跃窗口且剩余时间越短，因子越高。
- 没有活跃窗口的账号通常为 `0`。
- 所有候选账号窗口剩余时间相同时，统一按高因子处理。
- 默认权重为 `0`，即默认关闭该因素对综合分的影响。

### 3.7 `quota_headroom_factor`：额度余量

该因子反映账号还剩多少可用额度/容量：

- 余量越大，因子越高。
- 只有将 `quota_headroom` 权重设为大于 `0` 时才参与评分。
- 默认权重为 `0`，不会自动因为额度余量改变排序。

### 3.8 `upstream_cost_factor`：上游成本/倍率

该因子用于在账号上游计费倍率不同的情况下进行成本感知调度：

- 只有请求路径启用上游成本信号，且权重大于 `0` 时才生效。
- 账号的上游倍率会被转换成候选池内的相对因素。
- 没有足够可比较样本时使用中性值，不强行改变排序。
- 这不是用户下游收费倍率；它关注的是调用不同上游账号的相对成本。

默认权重：`0`。

### 3.9 账号 `load_factor`：容量覆盖，不是评分因子

账号对象还有一个容易和评分中的 `load_factor` 混淆的字段：`load_factor`。

- 它表示该账号用于并发槽位和调度容量计算的有效容量。
- 设置后会覆盖账号默认的 `concurrency`；未设置时使用 `concurrency`。
- 它越大，账号能同时承载的请求槽位越多，因此可能更频繁地被调度。
- 它不会直接出现在 `base_score` 加权公式中；评分里的 `load_factor` 指的是“当前负载越低越高分”的实时比例。
- 设置为 `0` 或负数通常表示清除覆盖值，恢复使用 `concurrency`；正值上限为 `10000`。

因此，`load_factor` 适合表达“这个账号能吃多少并发”，而 `load` 权重表达“当前是否空闲”。两者解决的是不同问题。

## 4. 粘性调度

Sub2API 识别两类会话锚点：

- `previous_response_id`：OpenAI Responses 链路的前序响应。
- `session_hash`：客户端/会话维度的稳定哈希。

### 粘性加权开启时

粘性不再一定是“命中后绝对锁定”，而是成为额外加分：

```text
sticky_score = base_score
             + previous_response_weight   （命中 previous_response_id 时）
             + session_sticky_weight       （命中 session_hash 时）
```

默认权重：

```text
previous_response: 5.0
session_sticky:    3.0
```

因此，只要粘性账号没有严重错误、过载、配额或能力问题，通常会获得明显偏好；但更合适的账号仍可能胜出。

### 粘性加权关闭时

系统保留旧式硬粘性路径：如果会话锚点命中了可用账号，通常优先尝试该账号。若账号触发配额、错误、TTFT、能力或其他限制，则会逃逸并重新选择。

## 5. Sub2API 实际调度顺序

综合评分不是第一步。请求大致按以下顺序处理：

### 第一步：建立候选池

先排除不符合条件的账号，包括但不限于：

- 账号未启用调度（`schedulable=false`）。
- 账号状态不可用、临时不可调度或处于错误/限流状态。
- 平台、账号类型、请求模型不匹配。
- 不满足所需传输方式或接口能力。
- 不满足隐私、分组、紧凑上下文等请求要求。
- 被请求显式排除的账号。

评分和排序只在合格候选账号之间进行。

这里的“合格”还包括一些不会直接写进综合分、但会改变候选池的规则：

- 账号的 `concurrency`/`load_factor` 容量是否还有可用槽位。
- 请求实际下游倍率与账号 `rate_multiplier` 是否满足最低毛利约束；不合格账号不会进入候选池。
- 某些配置可以在高级调度之外启用“低倍率上游优先”；该模式下先偏向倍率较低的合格账号，再比较账号优先级和实时负载。高级实验调度开启后，此旧开关不生效。
- 订阅账号优先开关会把合格候选进一步分成订阅池和非订阅池，优先在订阅池中选择。

这说明“权重评分”只负责合格账号之间的偏好，不能绕过容量、倍率、权限、能力或健康状态限制。

### 第二步：处理会话和特殊策略

- 有效的硬粘性命中可能先尝试粘性账号。
- 开启“订阅账号优先”时，会优先考虑符合条件的订阅账号池。
- 额度、RPM、会话窗口等限制可能进一步缩小候选池。
- 粘性账号如果触发逃逸条件，会回到普通调度流程。

### 第三步：高级调度计算综合分

高级调度开启后，系统计算上述 `base_score`，必要时加入粘性加分，然后按分数从高到低形成候选顺序。

当前候选账号会共享同一套归一化范围。例如某账号负载从 20% 变成 40%，它自己的负载因子下降；如果其他账号的负载也同时变化，所有账号的相对排序都可能随之调整。

默认 `lb_top_k=7`：系统通常从评分靠前的 Top-K 账号中继续做负载均衡/随机化选择，而不是每次都机械地调用绝对第一名。这可以减少单账号热点，同时保留权重偏好。

### 第四步：最终选择与失败切换

- 在分数接近或排序条件相同的账号之间，系统可能按负载、最近使用时间或随机打散选择。
- 请求失败、上游限流、账号临时不可用时，会排除已失败账号并继续尝试其他候选账号。
- 代理熔断等部分保护逻辑支持在没有其他路径时进行降级重试，但健康代理仍会在第一轮优先。

## 6. 非高级调度路径

高级调度关闭时，并不是所有请求都使用综合加权分。旧式路径主要遵循：

```text
账号优先级（数值小优先）
  -> 负载率（低优先）
  -> 最近使用时间（更久未使用优先）
  -> 同条件账号随机打散
```

对于部分接口（例如图片能力），还可能先按能力进行筛选，再在可用账号中使用普通调度；如果没有满足高级能力的账号，系统可能按明确的能力降级规则回退到基础能力账号。

## 7. 默认权重与可调配置

当前代码默认权重为：

| 配置项 | 默认值 | 作用 |
| --- | ---: | --- |
| `priority` | `1.0` | 账号基础优先级 |
| `load` | `1.0` | 当前负载 |
| `queue` | `0.7` | 等待队列 |
| `error_rate` | `0.8` | 近期错误率 |
| `ttft` | `0.5` | 首 Token 延迟 |
| `reset` | `0.0` | 会话窗口重置时间 |
| `quota_headroom` | `0.0` | 额度余量 |
| `upstream_cost` | `0.0` | 上游成本/倍率 |
| `previous_response` | `5.0` | previous_response 粘性 |
| `session_sticky` | `3.0` | session_hash 粘性 |

可通过管理端的 OpenAI 高级调度设置覆盖这些权重。覆盖值必须是非负且有效数字；高级调度总开关关闭时，数据库中的覆盖值不会生效。

## 8. 如何根据目标调整

### 想固定优先调用某个上游账号

优先把该账号的 `priority` 设置得更小，例如主账号 `10`、备用账号 `50`。但要注意：负载、错误、限流、能力不匹配仍可能让主账号暂时退出候选池。

### 想让多个账号平均分担

把账号 `priority` 设置相同，再保留负载和队列权重。不要把所有账号优先级拉开过大，否则优先级因子会长期压过实时负载因素。

如果目标是提高某个账号的承载量，而不是让它“更优先”，应调整该账号的 `load_factor`/`concurrency`，不要单纯降低 `priority`。前者改变容量，后者改变候选偏好。

### 想优先低成本账号

启用上游成本信号并提高 `upstream_cost` 权重，同时确认账号的上游倍率数据有效。默认该权重为 `0`，因此系统默认不会因为倍率自动改变调用顺序。

### 想优先低延迟账号

提高 `ttft` 权重，并确保运行时间足够长、各账号都有 TTFT 样本。没有样本时该因子接近中性，刚加入的账号不会因为缺少历史数据被直接判定为慢。

### 想保持多轮会话连续性

开启粘性加权，合理设置 `previous_response` 和 `session_sticky` 权重，同时保留错误/延迟逃逸机制，避免会话长期绑定到已经不健康的账号。

## 9. 结论

Sub2API 的调度不是单一“权重越大越调用”的静态轮询，而是：

```text
先过滤不可用账号
  -> 处理能力、分组、配额和粘性约束
  -> 在当前候选池内归一化各项指标
  -> 按配置权重计算综合分
  -> Top-K 负载均衡/粘性选择
  -> 失败后切换到其他合格上游账号
```

管理员如果只想控制“主账号优先、备用账号兜底”，直接调整账号 `priority` 最简单；如果还要综合考虑负载、延迟、错误率、额度或上游成本，再调整高级调度权重。
