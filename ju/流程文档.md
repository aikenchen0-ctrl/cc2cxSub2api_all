# Ju 与 Sub2API 对接流程

> 强制约束：模型请求只能由当前 HttpOnly Session 映射出的用户身份发起。服务端必须发送应用凭据、`X-Sub2API-On-Behalf-Of` 和 `X-Sub2API-Satellite`；缺少 Session 不得回退到共享 Key 或 SuperKey。

本文记录本次 Ju 与 Sub2API 单点登录（SSO）对接、Docker 部署、问题修复和验收过程。文档中的密钥只使用环境变量名表示，不记录真实密钥。

## 一、目标

完成以下能力：

1. 用户登录 Sub2API 后，从「智能剧场」进入 Ju。
2. Ju 按 Sub2API 的用户身份建立自己的本地用户和会话。
3. 浏览器不接触 Sub2API 的 JWT、API Key、应用凭据或 SuperKey。
4. SSO 登录票据、交换记录和 SSO 会话有效期统一为三天。
5. 保留一次性消费、重放保护、跨站校验、用户隔离和全局撤销能力。
6. Ju 以独立 Compose 运行，只把 backend 接入 Sub2API 的 Docker 网络。

## 二、部署前检查

先确认 Docker Desktop 正常运行，并检查是否已经存在 Ju 和 Sub2API 容器：

```powershell
docker ps --format '{{.Names}} {{.Status}}'
docker network ls
```

需要重点确认：

- Ju backend、web 是否已经存在；
- Sub2API 实际使用的网络名称；
- Ju 是否使用旧镜像；
- Ju 数据库是否已经迁移到当前 schema 版本；
- Redis 是否使用持久化 volume。

本次部署使用的容器和网络包括：

```text
ju-backend-1
ju-web-1
ju-sso-redis-1
deploy_sub2api-network
```

## 三、SSO 配置

### 1. Ju 配置

在 `ju/.env` 中配置以下变量：

```dotenv
SUB2API_SSO_SECRET=<与 Sub2API 完全相同的随机密钥>
SUB2API_RELAY_BASE_URL=http://sub2api:8080/v1
SUB2API_APP_CREDENTIAL=<服务端卫星应用凭据>
CANVAS_ALLOWED_PRIVATE_UPSTREAM_HOSTS=sub2api
```

`SUB2API_SSO_SECRET` 两端必须一致，长度至少 32 字符。真实密钥不能写入文档、命令行参数或跳转 URL。

### 2. Sub2API 配置

在 Sub2API 部署环境中配置：

```dotenv
SUB2API_SSO_SECRET=<与 Ju 完全相同的随机密钥>
JU_SSO_CALLBACK_URL=http://localhost:3000/api/auth/sso/callback
```

生产环境应将回调地址改为 HTTPS，例如：

```dotenv
JU_SSO_CALLBACK_URL=https://ju.example.com/api/auth/sso/callback
```

回调路径必须精确为 `/api/auth/sso/callback`，不能附带查询参数或片段。

## 四、登录流程

### 1. 从 Sub2API 发起登录

用户已经登录 Sub2API 后点击「智能剧场」。Sub2API 后端：

1. 从当前认证上下文获取用户 ID。
2. 查询用户资料并确认账号处于启用状态。
3. 生成随机 `jti`。
4. 生成包含以下字段的 JSON：

   - `iss: sub2api`
   - `aud: ju`
   - `sub: Sub2API 用户 ID`
   - `email`、`username`、`displayName`、`avatarUrl`
   - `iat`、`exp`
   - `jti`
   - 安全的站内 `next` 路径

5. 使用 `SUB2API_SSO_SECRET` 计算 HMAC-SHA256：

   ```text
   base64url(JSON).base64url(HMAC-SHA256(encodedPayload, secret))
   ```

6. 返回 Ju 回调地址，并将票据放入 `ticket` 查询参数。

登录票据有效期为三天。

### 2. Ju 回调

浏览器访问：

```text
/api/auth/sso/callback?ticket=<一次性票据>
```

Ju 后端执行：

1. 校验票据签名、`iss`、`aud`、字段长度和时间范围。
2. 将 `jti` 的 SHA-256 摘要持久化，阻止票据重放。
3. 创建随机 handoff 令牌，并只在数据库保存令牌摘要和身份 JSON。
4. 创建三天有效的 `ju_sso_handoff` Cookie。
5. Cookie 属性为 `HttpOnly`、`SameSite=Strict`，生产 HTTPS 下使用 `Secure`。
6. 清理地址栏中的票据，重定向到 `/auth/sso`。

### 3. 浏览器交换本地会话

Ju 前端在 `/auth/sso` 页面发起同源请求：

```http
POST /api/auth/sso/exchange
X-Ju-SSO: 1
Origin: <Ju 当前源>
```

Ju 后端：

1. 校验 `Origin`、`Sec-Fetch-Site` 和 `X-Ju-SSO`。
2. 读取并立即清除 `ju_sso_handoff` Cookie。
3. 原子消费数据库中的 handoff 记录，重复消费直接拒绝。
4. 按 `sub2api + sub` 查找或创建 Ju 用户身份。
5. 创建 Ju 自己的 HttpOnly 会话 Cookie。
6. 返回安全的 `next` 路径，前端进入 `/projects`。

SSO 会话和普通 Ju 本地登录会话统一有效三天。

## 五、全局登出流程

Sub2API 全局撤销会话时：

1. Sub2API 生成 `aud=ju:logout` 的独立签名票据。
2. 通过服务端 POST 请求 Ju：

   ```text
   POST /api/auth/sso/logout
   Content-Type: application/json
   {"ticket":"<撤销票据>"}
   ```

3. Ju 校验撤销票据并记录用户的撤销时间。
4. Ju 删除该用户在撤销时间之前创建的 SSO 会话。
5. Sub2API 只有收到 Ju 的确认后，才报告全局登出成功。

撤销通知仍使用短时票据，与登录票据的三天有效期相互独立。

## 六、数据库和 Redis

Ju 当前 schema 版本为 11，SSO 相关表包括：

- `sso_tickets`：已消费登录票据摘要；
- `sso_handoffs`：待交换的 handoff 摘要和身份数据；
- `sso_revocations`：用户撤销时间；
- `auth_sessions.sso_subject` 和 `auth_sessions.sso_issued_at`：SSO 会话关联信息。

部署前检查和迁移：

```powershell
docker exec ju-backend-1 migrate-schema verify
```

需要执行迁移时：

```powershell
docker exec ju-backend-1 migrate-schema up
docker exec ju-backend-1 migrate-schema verify
```

SSO replay store 使用持久化 Redis：

```text
REDIS_URL=redis://sso-redis:6379/0
volume=ju_sso-redis-data
```

## 七、覆盖构建和部署

Ju 使用以下 Compose 文件：

```text
ju/docker-compose.local.yml
ju/docker-compose.sub2api.yml
```

启动前必须指定现有 Sub2API 网络：

```powershell
$env:SUB2API_DOCKER_NETWORK='deploy_sub2api-network'
```

重新构建 Ju 镜像：

```powershell
docker compose `
  -f docker-compose.local.yml `
  -f docker-compose.sub2api.yml `
  --env-file .env build backend web
```

覆盖运行中的 Ju 容器：

```powershell
docker compose `
  -f docker-compose.local.yml `
  -f docker-compose.sub2api.yml `
  --env-file .env up -d --force-recreate backend web
```

重建 web 的原因是 Nginx 可能缓存旧的 backend IP；重建后会重新解析 `backend`。

## 八、部署验收

检查容器：

```powershell
docker ps --format '{{.Names}} {{.Status}}'
```

检查 Ju 页面和健康接口：

```powershell
Invoke-WebRequest -UseBasicParsing http://localhost:3000/ -TimeoutSec 10
Invoke-WebRequest -UseBasicParsing http://localhost:3000/api/health/ready -TimeoutSec 10
```

检查 web 到 backend：

```powershell
docker exec ju-web-1 sh -lc 'getent hosts backend; wget -qO- http://backend:8080/api/health/ready'
```

检查 backend 的网络和 Redis：

```powershell
docker inspect ju-backend-1 --format '{{json .NetworkSettings.Networks}}'
docker inspect ju-backend-1 --format '{{range .Config.Env}}{{println .}}{{end}}' | Select-String '^REDIS_URL='
```

预期结果：

- Ju 页面返回 HTTP 200；
- `/api/health/ready` 返回 HTTP 200，并显示 schema ready；
- backend 同时存在 `ju_default` 和 `deploy_sub2api-network`；
- `getent hosts sub2api` 能解析到 Sub2API 容器；
- `REDIS_URL` 指向 `sso-redis`；
- `ju-backend-1`、`ju-web-1`、`ju-sso-redis-1` 均为 healthy。

## 九、常见问题

### “单点登录已失效，请返回 Sub2API 重新进入”

检查以下项目：

1. 是否访问了旧的、已经消费过的回调 URL；
2. Sub2API 和 Ju 的 `SUB2API_SSO_SECRET` 是否完全一致；
3. `JU_SSO_CALLBACK_URL` 是否指向当前 Ju 地址；
4. handoff Cookie 是否被浏览器拦截；
5. Ju backend 是否能够连接 `sso-redis`；
6. 两端系统时间是否相差过大；
7. 是否覆盖重建了 backend 和 web，而仍在使用旧镜像。

刷新或重复打开同一个 `ticket` 不会重新登录，因为票据设计为一次性。应返回 Sub2API，从「智能剧场」重新发起登录。

### 页面出现 502

先检查：

```powershell
docker exec ju-web-1 sh -lc 'getent hosts backend; wget -qO- http://backend:8080/api/health/ready'
docker logs --tail 100 ju-web-1
docker logs --tail 100 ju-backend-1
```

如果日志仍连接旧 backend IP，执行：

```powershell
$env:SUB2API_DOCKER_NETWORK='deploy_sub2api-network'
docker compose -f docker-compose.local.yml -f docker-compose.sub2api.yml --env-file .env up -d --force-recreate web
```

### Go 命令找不到

Windows Go 安装路径通常为：

```text
C:\Program Files\Go\bin
```

将该目录加入用户 PATH 后，重新打开终端并验证：

```powershell
go version
gofmt -h
```

## 十、开发验证

Ju 后端测试：

```powershell
go test ./internal/auth ./internal/handler ./internal/repository
```

如果测试使用 SQLite，需要启用 cgo，并确保系统存在 GCC；否则会出现：

```text
cgo: C compiler "gcc" not found
```

构建环境可直接使用 Docker，因为 Ju 的 backend Dockerfile 已包含 Linux 构建所需工具。不要因为宿主机测试环境缺少 GCC 就判断 Docker 部署失败。
