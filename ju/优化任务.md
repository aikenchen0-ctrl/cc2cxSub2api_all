# JU（Infinite Canvas）优化任务

> 项目：`ju/`（卫星应用，菜单“AI导演台/影策”）。基线：2026-11-14。
> 全局约束见根目录 `评估报告.md`、`优化任务-总调度.md`；本文件只负责 `ju/` 内落地。

## 1. 项目定位与边界

- 卫星应用，Go 后端 + Next.js 前端；从文字走到分镜、角色和影视镜头资产。
- SSO 使用 handoff + 3 天本地 Session；服务端代调主站模型。
- 本项目只改 `ju/`，不改主站协议、根 Compose 或其他卫星。

## 2. 结论与商用判定

MIT 许可证相对清晰，但历史记录中的迁移缺失、权限、SQLite `db busy` 和支付/插件风险尚未在当前版本复测。**当前不能宣称发布通过；须先复测并修复 P0/P1 问题。**

## 5. 缺陷清单与补强方案

### JU-01 迁移漏建 `sso_revocations`、`sso_tickets`、`sso_handoffs`（P0，需复测）

**现象与证据**
- 历史任务书称迁移漏建上述表，导致 SSO 消费/撤销异常。
- 当前仓库已有迁移与 SSO 代码，**必须先在当前版本执行迁移并检查表结构**，不能直接沿用旧结论。

**实施步骤**
1. 在临时 SQLite/PostgreSQL 数据库执行迁移，列出实际表与索引。
2. 与 SSO 代码使用的表名、唯一键、时间字段逐一对照。
3. 若缺失，补幂等迁移；若已存在，更新任务状态并补回归测试。
4. 迁移必须可在空库和已有库重复执行，不破坏旧数据。
5. 补票据消费并发、撤销、过期清理测试。

**验收**
```powershell
cd ju\backend
go test ./internal/database ./internal/auth ./internal/handler -run 'Migration|SSO|Ticket|Handoff|Revocation' -count=1
```
- 空库迁移后表/索引齐全；重复迁移不报错；SSO 消费唯一键有效。

### JU-02 权限 666 与插件 manifest 不一致（P1，需复测）

**实施步骤**
1. 复现实际文件权限，确认是否仍为 666；生产应为最小权限。
2. 校验插件 manifest 与运行时能力一致；未声明能力不得调用。
3. 上传/导入插件做路径穿越、符号链接、覆盖测试。
4. 补失败路径测试并记录修复前后证据。

**验收**
- 无全局可写敏感文件；非法 manifest/越权插件被拒绝。

### JU-03 SQLite `db busy`（P1，需复测）

**实施步骤**
1. 用并发请求复现 `database is locked`，记录连接数、事务长度和 WAL 设置。
2. 缩短写事务、设置 busy timeout、避免长事务持锁；必要时改用 PostgreSQL。
3. 补并发测试；不得用重试掩盖数据竞争。
4. 数据量增长前做容量评估。

**验收**
- 并发压测无不可恢复 `db busy`；事务冲突有明确错误与重试上限。

### JU-04 SSO 与计费（P0/P1）

**现象与证据**
- 有 `sso_tickets/sso_handoffs/sso_revocations` 设计与实现，但本轮未验证并发/重启。
- Compose 多数入口仍允许空应用凭据；依赖主站 S2A-01。
- 当前调用使用裸 `X-Sub2API-On-Behalf-Of`；主站 S2A-07 后改为短期用户断言。
- 同步/媒体 Provider 调用统一经 `applyProviderAuth`（`backend/internal/app/provider_http_client.go:149-168`）只设置鉴权与卫星身份头，不发送 `X-Client-Request-ID`；`postJSON`/`postForm`/`postStreamingBinary`（`:103-117/170-184/87-101`）及 `provider_text.go:910`、`provider_image.go:81-105/259/385`、`provider_video.go:85-111/234/319`、`provider_audio.go:61` 都复用该客户端。读超时、断连或人工重提时，主站无法把同一业务意图归并到同一结算键。

**实施步骤**
1. 校验 SSO `iss/aud/sub/iat/exp/jti`，TTL ≤ 2 分钟，`aud=ju` 精确匹配。
2. 验证票据消费数据库唯一键、handoff 60 秒、Session 3 天、注销撤销。
3. 补并发、重启、多副本、跨用户重放测试。
4. 服务端代调带 `ju` slug 和当前用户断言；缺凭据不得回退。
5. 验证文本/图片/视频计费与 usage 归属。
6. 主站 S2A-01/06/07 完成后改用专属凭据/派生密钥。
7. 所有主/备 Compose 的 `SUB2API_APP_CREDENTIAL`、`SUB2API_SSO_SECRET` 改为 `:?`；缺失即失败。
8. 计费只走主站 `ju` slug 配置或当前用户余额；不得发送或接受 `X-Sub2API-Payer`、`X-Sub2API-Commission-Rate`。
9. 分镜、角色、媒体任务与 usage 均记录当前用户和稳定任务 ID；重试、断线重连、重复提交只有在主站已接收并校验稳定 `X-Client-Request-ID`（或按同一业务键可查重）时才可断言只产生一次扣款，否则必须进入“结果不确定/需对账”。
10. 同步/媒体 Provider 提交在调用前持久化 `(user_id, task_id/业务键, operation, 请求摘要)` 意图，并把同一业务键作为 `X-Client-Request-ID` 发送；命中进行中意图返回真实状态或冲突，已完成返回原结果。响应丢失、超时、断连、5xx、524 先按该键查 `/v1/sub2api/usage`；只有主站 `request_admission=rejected_before_upstream`、`dispatch_state=not_started`（须由写出点事件证明，不得仅凭时间戳为空）、`funds_effect=none` 且 `quota_effect=none` 时，才可按同一键重发；`not_seen`/`accepted`/`unknown`/0 行均只能待对账。不得用本地随机订单号或每次新 `request_id` 冒充稳定键。
11. **提交入口必须先持久化幂等意图**：`CreateTask` 的任务 ID 由 `newID()` 随机生成（`app/task_creation.go:89`），`RequestID` 又来自服务端 `RequestID(c)`（`handler/request-context.go:23-35`、`handler/routes.go:61`），不能作为客户端重试键；计费订单幂等键是 `"task:"+task.ID+":"+newID()`（`app/finance.go:457/481/525`），每次重提都会生成不同订单。必须接收并持久化客户端幂等键（或按 `user_id + 请求体摘要` 派生），以 `(user_id, idempotency_key)` 唯一约束绑定任务与订单；同一键重提只返回既有任务，不得再次建单、再次预留或再次调用上游。

12. **显式系统渠道与 RunningHub 提交必须在网络 I/O 前落“提交意图”，且不得在结果不明时自动重发**：`resolveTaskModelSelection` 对带 `channelId` 的显式系统渠道返回 `routed=nil`（`app/task_creation.go:147-176`），任务因此没有 `LogicalModelID`，`beginTaskRouteAttempt` 直接返回（`app/model_router.go:962-964`），`markRouteAttemptDispatching` 的 `submission_unknown` 栅栏不生效；`runRunningHubWorkflow` 先 `POST /task/openapi/create`，只在拿到 `taskId` 后才调用 `recordWorkflowProviderRequest`（`app/workflow_provider.go:450-538`），未调用 `BeginTaskProviderSubmission`。因此“上游已受理但本地未写 `taskId`”或“提交后进程中断”会被下一次 worker 当成首次提交再次建单，重复消耗 RunningHub 积分；失败切换与人工重试也无法从持久状态判断原提交是否已发生。必须：系统渠道任务在调用上游前用任务行持久化 `submitting/unknown` 意图（无 `ProviderRequestID` 时不得重发）；RunningHub 提交前先条件写入该意图，拿到 `taskId` 后立即持久化任务与账单关联，写入失败也保留“结果不确定”，不得静默继续并允许重提；只有明确未受理（4xx 且响应可证明未创建）才可释放意图或切换备用路由；超时、断连、5xx、524、响应解析失败一律进入 `unknown/需对账`，由人工或对账确认后再选择重发。
13. **重试前必须先终止旧计费订单，不得在旧 `reserved/running` 仍冻结时新建预扣**：`CheckRetryEligibility`（`app/task_billing.go:78-93`）只拒绝 `uncertain`，`RetryTaskWithBilling`（`repository/finance.go:432-477`）在任务 CAS 成功后另建 `order` 并再次 `reserveBillingOrder`，旧订单从未关闭。因此失败/取消任务若留下 `reserved`（未进入 worker 或 `MarkBillingRunning` 前失败）或 `running`（worker 中途失联但终态未写），重试会同时占住两笔预授权：旧 `reserved_microcredits` 永久冻结，新订单再扣一次可用余额；若旧订单实际已向上游提交，还会形成两次 Provider 调用而本地只看到一条新订单。修复必须先按 `billing_order_id` 读取旧订单并分类：仅 `refunded`/已释放且可证明上游未受理的订单允许新建；`reserved` 必须与任务 CAS 在同一事务内关闭并释放预留（或复用同一订单变更意图，而不是新建）；`running` 只有在 `ProviderRequestID`/提交栅栏证明未发送，或已完成退款/对账时才可重试；`uncertain`、`running` 且无可靠未受理证据、旧订单与新订单金额/渠道不一致一律拒绝进入重试。新订单的创建与任务从 `failed/cancelled` 到 `queued` 的 CAS 必须在同一事务，且 `(user_id, idempotency_key)` 命中已有订单时不得再次预留。补测试：`reserved` 旧单重试后仅剩一笔占用；`running` 无 `ProviderRequestID` 拒绝；`refunded` 旧单可重试；并发两次重试只有一个事务成功且只扣一次。 若旧订单已被上游受理（存在 `ProviderRequestID` 或提交栅栏未证明未发送），释放本地预扣不能抹掉 Provider 侧费用；此时新任务只能在该旧订单结算/退款/人工对账完成后创建，或进入 `unknown/需对账`，不得以“旧预扣已释放”当作上游只调用一次的证明。
14. **预留、结算、退款必须使用同一金额字段，且不得从浮点/当前余额重建**：`reserveBillingOrder`（`repository/finance.go:496-537`）按 `AmountMicrocredits` 扣可用并记 `reserved`，token 结算（`:708-726`）按 `ReservedAmountMicrocredits` 释放，非 token 结算（`:768-774`）与 `RefundBillingOrder`（`:953-958`）却按 `AmountMicrocredits`。只有两者恰好相等时才不串账；一旦预授权金额与报价金额分离（token 估算、部分授权、人工调价），结算/退款会多退或少退并触发 `reserved credit balance is inconsistent`，把订单卡在未终态。必须固定 `reserved_amount_microcredits` 为唯一预占事实，结算释放、退款、恢复与账本流水均读同一字段；`amount_microcredits` 仅表示报价/授权上限，不得在释放时替换。补测试：`ReservedAmountMicrocredits != AmountMicrocredits` 的普通结算、退款、`RestoreRefundedBillingOrder` 各只释放/退回真实预占额；并发结算与退款只能一个成功，另一个返回明确冲突且余额不变。
15. **无计费订单的任务不得进入付费上游执行**：`CreateTask` 在 `taskBillingOrder` 返回 `nil` 时仍创建任务（`app/task_creation.go:102-126`），`taskBillingOrder` 对自定义渠道、缺少 `channelId`、或关闭 `FeatureCredits` 直接返回 `nil`（`app/finance.go:427-458`）；worker 只对非空 `BillingOrderID` 调 `MarkBillingRunning`（`app/task_worker.go:186`），随后照常执行上游，终态 `SettleBilling("")`/`RefundBilling("")` 又都直接返回 `nil`（`app/task_billing.go:46-65`）。这意味着“任务没有计费订单”与“免费任务”被混为一谈，任何绕过报价的请求都可免费调用 Provider。必须显式区分：`FeatureCredits` 关闭且产品明确免费时，任务行记录 `billing_mode=free`/`pricing_source=free` 并禁止收费口径；启用计费时，任务执行前必须有唯一 `BillingOrderID` 且金额已冻结，缺失即失败关闭、不得调用上游。自定义渠道若允许用户自带 Key，必须明确它不消耗站长额度；不得用“无订单”静默放行系统渠道、工作流或媒体 Provider。补测试：启用 credits + 自定义渠道/缺 `channelId` + 系统 Provider → 建单前 4xx 或进入免费模式并标注来源；worker 对 `billing_mode!=free` 且空 `BillingOrderID` 的任务必须失败且上游调用次数为 0。

16. **同步代理的幂等键为空时必须失败或派生稳定键，且命中既有订单要返回原订单而不是再次预留**：`proxySystemRequestPath` 把 `X-Idempotency-Key` 原样传给 `ReserveProxyBillingWithBody`（`handler/auth.go:1039`），后者在空键时执行 `idempotencyKey = newID()`（`app/finance.go:547-549`），于是每次重提都得到新的 `proxy:<uuid>` 并再次 `ReserveBillingOrder`；`billing_orders` 虽有 `(user_id, idempotency_key)` 唯一索引（`model/models_finance.go:37-38`），但空键随机化使唯一约束永远不命中。且 `reserveBillingOrder`（`repository/finance.go:496-536`）先改余额再 `Create(order)`，唯一键冲突时靠事务回滚，调用方拿到错误而非既有订单。必须：POST 计费请求缺少客户端幂等键时，要么在扣款前 4xx 拒绝，要么按 `(user_id, 规范化请求摘要)` 派生稳定键并持久化；插入冲突时在同一事务内回查 `(user_id, idempotency_key)`，返回原订单/真实状态或 409，不得再次预留、再次调用上游；`MarkBillingRunning` 也须按订单状态 CAS，已是 `running/settled/uncertain` 时不得重复推进。补测试：同键并发两次仅一笔 `reserved` 与一次上游调用；空键两次请求不得生成两笔订单；唯一键冲突后可返回首单且余额只扣一次。

**预扣与退款必须同锚、同 CAS（2026-11-15 只读核对）**：`RefundBillingOrder`（`repository/finance.go:941-992`）按 `order.AmountMicrocredits` 释放，而 `reserveBillingOrder`（`:496-536`）实际冻结与 `SettleBillingOrder`（`:687-805`）按 `ReservedAmountMicrocredits` 释放；当 token 预授权、部分授权或人工调价令两者不等时，`RefundBillingOrder` 会按错误金额恢复可用额度并写 `refunded_amount_microcredits=AmountMicrocredits`，账户与订单无法复算。退款与恢复必须统一以本次订单实际冻结的 `ReservedAmountMicrocredits` 为唯一锚点；历史行 `reserved_amount_microcredits<=0` 才可按 `AmountMicrocredits` 兼容，且须在同一迁移中回填/标待复核，不得运行时二选一。`RefundBillingOrder` 读取订单后直接改账户与订单，没有 `WHERE status IN ('reserved','running','uncertain')` 与版本/CAS；两次并发或“退款 + 结算”并发时，第二次可能再次加可用额度，或把已 `settled`/`refunded` 的资金事实覆盖。必须固定可退款前置状态集（至少 `reserved/running/uncertain`，排除 `settled/refunded`），以订单状态 CAS 且 `RowsAffected==1`，账户更新同时校验 `reserved_microcredits>=锚点金额`；0 行整笔回滚，已 `refunded` 只幂等返回首次退款结果并比对金额/键，不得再次加款。若订单已被 Provider 受理或存在 `ProviderRequestID`，退款仅释放本地预扣并转人工对账，不得把本地退款当主站未计费证据。补验收：`ReservedAmountMicrocredits != AmountMicrocredits` 时退款只释放锚点金额；`settled` 订单退款被拒绝且余额不变；并发两次退款仅一次资金变化；`refunded` 后重复调用 0 资金变化；`reserved_microcredits` 不足时不写 `refunded` 终态。

**跨账退款边界（根 7.3.1 第 23 条）**：`RefundBillingOrder`/`RestoreRefundedBillingOrder` 只变更 JU 本地 `credit_accounts`/`billing_orders`，不得当作主站 usage `reversed` 或据此要求主站冲正；主站 usage 冲正也不得自动恢复本地 microcredits。Provider 已返回 `ProviderRequestID`、已受理或已产生费用时，任务失败/取消只能进入 `unknown/需对账` 或人工复核，不得仅凭 `failed/cancelled` 自动退；只有提交前失败、Provider 返回“4xx 且响应可证明未创建”或等价未受理回执且本地预扣可证时才可自动退；仅本地 `failed/cancelled`、`null`/解析失败、5xx/超时、存在 `ProviderRequestID` 或提交栅栏未证明未发送均不得视为未受理。两侧分别记录本地订单/退款键与主站 `request_id/api_key_id`，独立 CAS；禁止用一个退款单同时改两侧。验收：本地 reserved 已转 settled、Provider 已受理、任务失败 → 两侧均不自动退并产生对账项；预扣前失败 → 余额/流水平衡；重复/并发退款至多一次；主站冲正成功而本地未退 → 本地不变并告警。
17. **按 S2A-08 实现受理与别名契约**：调用上游前先提交 `accepted`；本地拒绝先提交 `rejected_before_upstream` 与真实 `funds_effect/quota_effect`，只有双零且 `dispatch_state=not_started` 才可标记可重发；同一请求只建一条 admission（先以临时键建行，最终键只一次 CAS 写入 `final_request_id`；dispatch 前拒绝可保持空，不得伪造），临时键经 `request_admission_alias` 单跳、双向唯一并外键归属该 admission；改绑、二次归属或引用未升级最终键均冲突。usage/反查必须返回完整 `admission_source/funds_effect/quota_effect/dispatch_state/state_version/query_request_id/final_request_id`，`query_request_id` 逐字等于查询键；别名缺失不得返回 `settled`。最终键升级、别名与权威 usage 同事务或同事务 outbox，任一步失败不得确认成功或换键重发；临时键查询别名缺失不得 `settled`，最终键查询唯一 usage 存在须 `settled`。

- **纯文本 token 缺失不得按次**：本项目若为主站 `custom` 模式配置了 `millionTokens` 规则，纯文本调用必须取得可信 token 合计后按 `token` 计价；上游未返回 usage、解析失败或仅有图片 token 时，不得静默落到 `request` 或模型价，必须失败关闭/进入待对账；同目标同时有 `token` 与 `request` 规则时固定优先 `token`。上游明确返回 0 token 可按 `millionTokens` 得到 0 金额，但 `billing_mode` 仍须为 `token`，并与“用量未知”分开断言。 **当前实现未满足该零用量分支**：`quoteSatelliteBilling` 仍以 token 合计 `>0` 才尝试 `millionTokens`，0 用量会落到 `request`/模型价；修复前该用例只能标为失败/待实现，不得按现网行为验收通过。
- **只读余额/状态查询不进入计费账本**：本项目存在经 `/api/sub2api/balance` 转发到主站 `GET /v1/sub2api/balance` 的展示/预检调用；该接口只能读取余额，不得生成 usage、占用计费键、扣余额/配额或作为“请求已成功结算”的证据。验收须断言余额查询前后 `usage_logs`/`billing_attempts` 行数、余额、Key/账号/平台额度均不变，且查询失败不得触发重试计费或改变本次模型请求的账本分支。若某次余额查询同时携带了模型结算键，仍只能按只读处理，不得复用该键产生 usage。
- 同一 Key、同一 `request_id` 的**已成功结算**请求重放：`/v1/sub2api/usage` 只返回首次权威记录（first-write-wins），不追加第二行；失败尝试走独立 `billing_attempts`（含 `attempt_no/failure_stage/error_code/actual_cost/charged_cost/total_cost/用量/video_duration_seconds/duration_source`），不占结算键，成功重试后才形成唯一权威行；同一账本下余额、Key 配额、订阅用量与 usage 行均只变化一次。去重键是 `(request_id, api_key_id)`；同一用户换 Key 使用同一 request_id 会生成第二条记录，不得写成全局“一个 request_id 只一条”。重放命中时不得用本次模型、token、金额、`billing_mode`、订阅或付款人覆盖首次 usage；付款人或费率与首次不一致时，必须返回明确冲突或既有结果并写审计，不得静默换人扣款。
- **媒体请求缺数量不得按次/按 token 成功**：本项目若存在生图或图片编辑路径，主站 `quoteSatelliteBilling` 只在 `ImageCount>0` 时尝试 `image` 规则；请求已明确为生图但张数为 0 时会落到 `token`/`request`。验收必须覆盖 `ImageCount=0` 的明确生图请求，断言失败关闭/待对账而不是按次成功；视频同理覆盖 `VideoCount=0`、`VideoDurationSeconds>0`。若本项目确无该媒体路径，须在卡内显式写“无此路径”并给出路由/调用证据，不得默认跳过。
- 若主站对该 slug 启用 `custom/request/points` 规则：本卫星实际使用的目标/单位必须在规则中命中；未命中时请求必须失败关闭并返回可定位错误，不得静默按模型价扣费。`points` 模式只允许整数点数，金额按 `点数 × 0.01` 换算；`request` 单位得到 `billing_mode=per_request` 且 `actual_cost = 点数 × 0.01`，`image`/`videoSecond` 分别按图片数/秒数乘点数，`millionTokens` 必须被配置校验拒绝（`satellite_billing.go:114-122/356-359`）。不得把 `per_request` 一律当作固定 1 次请求而不乘 0.01，也不得把 `points` 的 `request` 规则误判为 `custom` 的 token 兜底。
- 本项目若存在异步上游任务/轮询/回调（视频、导出、批处理、WebSocket 结果等），必须用服务端可复用的稳定业务键派生 `request_id`：优先取上游任务 ID，或调用方在提交时已验明的业务幂等键；创建、多次轮询、完成回调只能产生一个结算键。服务端随机生成的本地 `jobId`/`taskId` 若每次重提都会变化，不得当作结算键；若仅在创建后才取得上游任务 ID，必须先持久化创建意图，不能等拿到 ID 再补键。**主站已按 S2A-02 接收并校验 `X-Client-Request-ID` 后**，才可断言最终恰有一条权威 usage / 只扣一次；未落地前必须标记“结果不确定/需对账”，不得每次轮询新生成 `request_id` 或据本地键默认成功。补“同一任务轮询 N 次 + 回调 1 次”只产生一条权威 usage、`/v1/sub2api/usage` 只一条的端到端测试；若本项目无此类路径，须在验收中显式写“无异步上游任务”并给出路由/调用证据。
- 本项目确有异步/媒体任务与本地信用账本：`internal/model/models_task.go:8-46` 持久化 `RequestID/BillingOrderID/ProviderRequestID/PollStage`，`internal/model/models_finance.go:57-72` 持久化退款与结算状态，`internal/repository/finance.go:405-416,687,836,941` 以订单行做预留、结算、恢复与退款。本卡验收必须进一步证明：创建任务并预留成功后重启服务，worker 能从任务行恢复轮询；同一 `BillingOrderID` 的轮询、重试、`RestoreRefundedBillingOrder` 与 `RefundBillingOrder` 均按持久状态 CAS，成功/退款/恢复各只改变一次余额与 `allocated`；进程在“上游已创建、订单未绑定”或“已结算、终态未写”之间中断时，必须能靠 `ProviderRequestID`/任务行对账，不能重新创建上游任务或二次扣费。
- **显式系统渠道/RunningHub 提交崩溃窗口**：覆盖三种场景并断言上游 create 只发生 1 次：①提交前进程退出，重启后任务保持 `submitting/unknown` 且不自动重发；②上游已返回 `taskId`、本地写任务/账单前退出，重启后能按持久 `taskId` 继续轮询或进入人工对账，不得再次 `create`；③提交超时/524/连接重置且无法证明未受理，任务进入 `unknown/需对账`，不得切换备用路由或自动重试。另须验证系统渠道任务与逻辑模型任务走同一提交栅栏：有 `channelId`、无 `LogicalModelID` 的任务也必须在首次上游调用前产生可审计的提交意图，而不是依赖 `RouteAttempt` 为空跳过保护。
- 退款后人工恢复不是安全的资金路径：`RestoreRefundedBillingOrder`（`repository/finance.go:836-931`）先直接 `available_microcredits - actual`（`:870-876`），没有 `available_microcredits >= actual` 条件，也不返回 `ErrInsufficientCredits`；余额不足时会被扣成负数，随后仍把订单写成 `settled` 并记消费流水。须改为条件扣款（不足则拒绝且订单保持 `refunded`/待复核）或等值预占，并覆盖余额 0、差 1 microcredit、并发两次恢复三个边界。
- **重试状态机验收**：对 `failed`/`cancelled` 任务分别构造旧订单为 `reserved`、`running`（有/无 `ProviderRequestID`）、`uncertain`、`refunded`、`settled`：`reserved` 重试必须在同一事务内释放旧占用并只产生一笔新占用；`running` 无 `ProviderRequestID` 必须拒绝；`running` 有 ID 但未完成对账不得新建第二笔；`uncertain`/`settled` 一律拒绝并要求人工处理；`refunded` 才可按新报价重试；若旧订单已被上游受理（存在 `ProviderRequestID` 或提交栅栏未证明未发送），释放本地预扣不能抹掉 Provider 费用，新任务只能在旧订单结算/退款/人工对账完成后创建，或进入 `unknown/需对账`。并发两个重试请求只能一个成功，失败方不得留下孤立订单或扣款流水。断言 `credit_accounts.reserved_microcredits` 在重试前后差值等于最终唯一订单的 `reserved_amount_microcredits`，旧订单不得永久占住。

- **金额字段一致性验收**：构造 `ReservedAmountMicrocredits != AmountMicrocredits` 的订单（token 预授权、部分授权、人工调价），分别执行普通结算、`RefundBillingOrder`、`RestoreRefundedBillingOrder`；断言释放/退回/补扣均以 `reserved_amount_microcredits` 为锚，`credit_ledger_entries` 的 `reserved_delta_microcredits` 合计与账户变更相等，且不出现负 `reserved_microcredits` 或“余额一致但订单未终态”。

- **无订单任务验收**：启用 `FeatureCredits` 时，对自定义渠道、缺 `channelId`、工作流/RunningHub 与普通系统渠道各提交一次任务：若产品不允许免费，必须在建任务前 4xx；若允许用户自带 Key，必须持久化 `billing_mode=free`/`pricing_source` 且仅在该明确模式下跳过订单。worker 对 `billing_mode!=free` 且 `BillingOrderID` 为空的任务必须失败，断言上游 Provider 调用次数为 0，不得先调用后靠空订单跳过结算。

## 6. 全链路验收

- 从主站菜单进入，SSO/handoff 成功、Session 3 天、注销可撤销。
- 主站 usage/反查必须返回 `request_admission` 六态（`not_seen`/`accepted`/`rejected_before_upstream`/`settled`/`conflict`/`unknown`）及真实最终键、`admission_source/funds_effect/quota_effect/dispatch_state/state_version/query_request_id/final_request_id`；0 行、`not_seen`、`accepted`、`conflict`、`unknown` 均不得触发自动重发、免费释放或重复扣款，只有 `rejected_before_upstream` 且 `dispatch_state=not_started`（须由写出点事件证明，不能靠时间戳为空、4xx 状态码或本地异常推断）才可重试。自动重发/免费处理还必须 `funds_effect=none`（余额、欠款、订阅用量无资金变化）且 `quota_effect=none`（Key/限流、账号、平台、订阅额度均未写）；本站钱包释放只按本地预留与主站资金效果判断；`quota_effect` 既不是释放前提，也不是拒释前提，不得因主站额度变化改扣本站钱包。`accepted`/`unknown` 表示可能已调上游，必须待对账；已读到唯一成功 usage 必须为 `settled`，不得因冲突态降级为未结算。同一请求只能有一条 admission（先以临时键建行，最终键只一次 CAS 写入 `final_request_id`），临时键与最终键必须经 `request_admission_alias(alias_request_id, api_key_id, admission_id, final_request_id)` 单跳反查同一受理事实，alias 行以外键绑定该 admission，禁止引用尚未升级最终键的行；同一临时键改绑、同一最终键归属第二条 admission、别名引用未升级最终键的 admission、别名缺失或 CAS 失败时不得确认。调用上游前必须先提交 `accepted`（临时键仅作 `admission_key`，最终键未定时不得写可解析别名），提交失败不得调用上游；本地拒绝先提交零效果受理，提交失败只能返回 `unknown`/不可重试；最终键、别名与权威 usage 同事务或同事务 outbox，任一步失败不得确认成功，不得自动换键重发。
- **受理与别名验收必须可执行**：同一临时键并发绑定两个最终键时恰一条成功、另一条 `conflict`；同一请求由临时键建 admission 后改用最终键查询，不得产生第二条 admission，最终键只能一次 CAS 写入；同一最终键被两个临时键/两条 admission 指向时恰一条成功；临时键别名缺失而最终 usage 已存在时，查询必须返回 `unknown`/待对账，不得返回 `settled`；直接查询最终键且唯一 usage 存在时必须返回 `settled`（`admission_source=usage`），不得因别名未写降级；所有查询（含 `usage_count=0`）必须回传完整 `admission_source/funds_effect/quota_effect/dispatch_state/state_version/query_request_id/final_request_id`，且 `query_request_id` 逐字等于查询键；临时键与最终键反查必须命中同一 `state_version`。注入受理写入失败时上游调用计数必须为 0；注入别名或 usage 写入失败时不得返回成功或自动换键重发。
- 分镜、角色、媒体任务归属当前用户；跨用户 403/404。
- 迁移可在空库/已有库重复执行；SQLite 并发无不可恢复锁。
