# 16 参考实现状态与边界

本文把设计文档与当前 `agentapi/backend`、`agentapi/frontend` 的实际能力对齐，避免把规划中的主站控制面误认为已经完成。

## 1. 已实现链路

| 链路 | 当前实现 | 入口 |
| --- | --- | --- |
| 品牌 | Agent 名称、站点名、Logo 公开配置与管理员在线修改 | `GET /api/v1/settings/public`、`/api/v1/agent/admin/branding` |

| 部署 worker | 独立受控 worker：provisioning-only 凭据、管理 API 列表 + ID-only SSE 提示/周期 GET、90 秒 claim lease（20 秒续租）、租约保护的进度/激活、失租取消任务、Compose/Nginx、DNS/TLS/healthz/readyz 和失败恢复 | `backend/cmd/agentapi-provision-worker`；需运维主机单独构建/配置 |
| 托管实例状态门控 | 使用主站返回的 `agt_<uuid>` ID；逐站 runtime GET 初始/周期刷新，Sub2API 数据库通知 SSE 仅触发权威重读；非 active、状态未知或过期拒绝业务请求，探针保留 | `AGENT_PROVISIONING_CONTROL_*`、`GET /api/v1/agent-runtime/agent/stream`、`/healthz`、`/readyz` |
| 开站部署包 | 幂等锁、slug/domain 唯一占用、生成包与同级受保护 runtime Secret 目录分离、Compose/Nginx/非秘密环境配置生成、逐站凭据哈希输出 | `go run ./cmd/agentapi-provision --agent-id <main-agent-id>` |

前端生产源码已完成独立裁剪，只保留 AgentAPI 页面、路由、会话和接口适配层；默认 Vitest 配置扫描所有保留测试，不再携带 Sub2API 管理后台、支付 SDK、旧 OAuth 或 localStorage JWT 实现。

开站失败重试会保留有效的 `current_step` 检查点，管理员重试后 worker 从失败步骤继续；旧记录若只保存 `current_step=failed`，则兼容地从 `queued` 重启。该逻辑已有自动化测试覆盖；生产 edge 上真实失败与恢复演练仍未验收。

`agt_*` 是托管 Agent 的保留 ID 前缀；对该类实例显式设置 `AGENT_PROVISIONING_CONTROL_ENABLED=false` 会使配置加载失败，避免通过环境变量绕过主站暂停/撤销状态。非托管本地 ID 仍可在开发环境关闭该门控。

托管 `agt_*` 实例必须配置合法 DNS `AGENT_DOMAIN`，否则拒绝启动，保证 Host 隔离不会因空配置退化为允许任意主机。Origin 和 Host 判断不信任客户端 `X-Forwarded-Host` 或标准 `Forwarded` 头；反向代理必须保留公开 Host。

AgentAPI 的卫星 slug 和 SSO audience 固定为 Sub2API 注册表中的 `agentapi`；运行配置若覆写为未注册值会拒绝启动，避免模型头或 SSO 校验漂移到其他卫星身份。

## 2. 当前未实现或仅有契约

- 自动部署 worker 代码已实现，含跨进程租约和失租取消，但并未自动随 Sub2API/AgentAPI 生产服务启动；需在专用 edge 运维节点构建、注入共享的 provisioning-only 凭据及 AgentAPI 运行实例的外部 Secret 文件、Docker/Nginx 权限与预期 DNS edge IP。worker 凭据仅限开站列表/SSE/GET/claim/lease/progress/activate，不是逐 Agent 凭据；租约保护主站控制面，但不能为 Docker/Nginx 副作用提供 fencing。生产节点安装、实际 DNS/TLS/Compose 和真实端到端开站仍未验收；
- 多 Agent 共享集群的 Host → Agent 路由；当前镜像按一个 `AGENT_ID` 运行；
- provider-neutral 充值订单、HMAC webhook、支付事件幂等记录和等待 Owner 额度的本地分配已经实现；但真实支付供应商 SDK、渠道专属签名/支付页、退款、拒付和主站自动入账仍未实现；
- 逐站 runtime control/model 凭据、管理 API scope、主站 model credential 公开目录 allowlist 和数据库通知 SSE 已实现；共享 provisioning worker 凭据仍是单独的开站专用 allowlist credential。生产 edge 的 Secret 文件注入/轮换、worker Docker/Nginx 权限隔离、DNS/TLS/Compose 真实验收仍未完成；
- 视频和显式异步图片任务已支持归属隔离、受控轮询与原 settlement 结算；后台分别按 `AGENT_VIDEO_TASK_RECONCILE_AGE`、`AGENT_IMAGE_TASK_RECONCILE_AGE` 探测长期无人轮询任务。失败任务只有在权威 usage API 确认没有记录时才释放冻结，查到实际费用时按实结算，usage 查询失败/不可用或费用超过预留时保留 pending；同步图片仍按缓冲接口处理。未列入 AgentAPI 白名单的其他异步媒体端点不会透传；
- 自动证书申请、自定义域名 DNS 验证和平台级 Nginx 编排；
- 公共卫星 `/v1` 头部含义维持原契约；AgentAPI 专用的 runtime control/model scope 扩展位于 Sub2API 管理 API，不更改普通卫星的 SSO、公共凭据或请求头语义。

### 2.3 结算数据来源约束

模型请求的实际费用必须优先来自逐站 runtime API `GET /api/v1/agent-runtime/usage?request_id=...` 返回的同一 `request_id` usage 记录。Sub2API 在服务端再次限制为当前 Agent Owner。`actual_cost` 字段存在时按其结算（包括明确的 `0`）；仅旧版 DTO 缺少该字段时才回退 `total_cost`，字段存在但无效则保持 pending。SQLite 会保存白名单用量快照：请求/上游模型、路由、服务层级、reasoning effort、Token/cache/image 数量、费用分项（USD 纳美元整数）、耗时/TTFT、计费类型及来源标记；当前来源标记为 `sub2api_owner_runtime_usage`，旧快照中的 `sub2api_admin_usage` 仍可读取，管理 DTO 中的 IP、账号和用户对象不会传给分站用户。即时结算与后台对账共用此快照，Usage 页把主站事实与仅供旧版兼容的 Owner 余额差回退明确区分。找不到记录、主站接口超时或返回其他错误时，AgentAPI 保持 `settlement_pending`，不得用代理 Owner 余额前后差推断当前请求费用，因为同一 Owner 余额可能同时被主站其他入口、其他代理或人工操作使用。

仅为兼容不提供逐站 Runtime usage API 的旧主站版本，才可通过 `AGENT_MAIN_USAGE_API=false` 显式启用旧余额差路径；生产部署应保持默认 `true`，并把主站 usage API 作为上线前置条件。

### 2.1 账务桥接的实现边界

当前参考实现已经有本地代理钱包和用户子余额。AgentAPI `/v1` 使用当前 Session 用户作为 `X-Sub2API-On-Behalf-Of` 身份；Sub2API 验证该用户是当前 Agent 的 active 映射成员，再以 Agent Owner SuperKey 做真实扣费。因此不能把本地子余额预授权和 Owner 主站扣费同时当成两笔独立的最终账务。

当前已冻结并按方案 A 实现：`agent_owner_main_user_id` 是主站唯一计费身份，代理用户余额只用于本地预授权和归属；主站余额差额/usage 是结算依据。主站不能确认 usage 时记录保持 `pending`，由管理员对账接口处理，不自动退款。

### 2.2 充值桥接边界

`recharge_orders` 和 `payment_events` 已提供最小可运行的订单/回调状态机：合法支付事件先进入 `paid_pending_allocation`，只有同步到足够的 Owner 主站余额后才会原子地增加用户子余额。webhook 不会直接增加主站余额，不接受浏览器提交的代理或用户归属，也不会生成佣金。支付关闭、签名错误、金额/币种不匹配和重复事件均不会改变钱包。

这仍不等于主站已经提供原子“用户间额度转移”；如果未来产品要求主站原生按代理用户统计扣费，必须切换到方案 B 并先改造主站控制面，不能在 AgentAPI 内伪造转账。

## 3. 上线前强制条件

1. 主站提供或确认受控的用户创建、模型代调和额度结算契约；
2. `AGENT_RUNTIME_CONTROL_CREDENTIAL`、逐站 `SUB2API_APP_CREDENTIAL`（model credential）、satellite app credential 与 `SESSION_SECRET` 通过 Secret Manager/Docker Secret 注入；AgentAPI 业务运行时不使用 `SUB2API_ADMIN_KEY`；
3. AgentAPI 数据库位于持久卷，完成备份恢复和余额对账演练；
4. 仅配置一个内部 Agent 通过全部自动化测试后，再开放外部“一键开站”；
5. 明确支付主体、退款责任、代理预充值和用户子余额之间的合同与合规边界；
6. 完成主站 usage 查询权限、`settlement_pending` 对账演练和人工异常处理；
7. 若接入主站菜单，严格使用公共 HMAC SSO、3 天 Session 和公共模型目录，不另造主站 SSO 协议。

## 4. 版本策略

当前实现按 `agentapi` 初始版本管理。涉及主站头部、余额语义、Key 格式、Session TTL 或公开模型目录的变化，必须同步更新：

- `05-主站接口契约.md`；
- `06-认证与安全.md`；
- `07-预充值与账务.md`；
- `08-用户注册与模型请求.md`；
- `12-测试验收清单.md`；
- 本文和 Docker 示例配置。
