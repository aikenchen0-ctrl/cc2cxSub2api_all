# AgentAPI AI 开发规范与目标架构

更新日期：2026-09-30。

> 本文是 AgentAPI 的最高优先级产品与技术规范。修改 `agentapi/` 前，AI 和开发者必须完整阅读本文、`../docs/卫星应用接入公共层.md` 和 `../docs/卫星公开模型.md`。历史记录与本文冲突时以本文为准，不得从旧代码或旧文档恢复已经否定的产品方向。

## 1. AI 执行规则

你是维护 AgentAPI 的工程 AI。你必须使用明确、可验证、带边界的语言：

- **已实现**：代码或配置已经存在，不代表已经部署或验收。
- **已验证**：必须说明验证命令、范围和结果。
- **已部署**：必须说明环境、版本、数据迁移和健康状态。
- **已验收**：必须满足本文验收矩阵；单元测试、构建或健康检查不能替代验收。
- **计划中**：尚未完成，不得写成当前能力。
- **历史记录**：仅供追溯，不得作为新实现依据。

AI 每次处理 AgentAPI 任务必须：

1. 先区分目标架构、当前实现、迁移任务和历史记录；
2. 先检查工作树，保留用户已有改动；
3. 先确认租户、主站事实和密钥边界，再改页面或接口；
4. 实现后执行与风险相称的后端、前端、隔离和部署验证；
5. 汇报时分开说明完成项、验证项、未完成项和风险项。

AI 禁止：

- 发明新的 SSO、SuperKey、API Key 或菜单跳转协议；
- 信任浏览器提交的 `agent_id`、站长 ID 或主站用户 ID；
- 为每个代理站复制容器、数据库、端口或代码；
- 把主站管理员后台复制成代理站后台；
- 用本地余额、余额差值或估算费用冒充主站事实；
- 用隐藏菜单代替权限删除，或保留可直接调用的越权接口；
- 因历史文档出现过某功能就恢复已删除模块；
- 缺少证据时宣称“全部完成”“生产可用”或“已上线”。

## 2. 产品定义

AgentAPI 是 Sub2API 用户开通和经营代理站的**共享多租户站点**。

所有代理站共用一套 AgentAPI 前端、后端、部署和基础设施。Sub2API 用户点击“一键开分站”后成为一个代理站租户的站长；不同站长的数据通过可信 `agent_id`（等价于 `tenant_id`）严格隔离，而不是为每位站长部署独立 AgentAPI 实例。

## 3. 不可改变的架构事实

### 3.1 共享运行时

目标形态：

```text
一套 AgentAPI 服务
  ├─ 一套前端和后端
  ├─ 一套共享数据库或数据库集群
  └─ 多个逻辑租户（agent_id）
       ├─ 站长 A 的品牌、成员归属、用户自有 Key 和记录
       ├─ 站长 B 的品牌、成员归属、用户自有 Key 和记录
       └─ 站长 C 的品牌、成员归属、用户自有 Key 和记录
```

禁止把目标设计成“每站一个容器 + 一个 SQLite + 一个端口”。自定义域名和品牌只是租户配置，不代表独立运行时。扩容可以增加相同的无状态副本，但每个副本服务全部租户。

### 3.2 主站与代理站职责

Sub2API 权威负责：

- 主站身份、账户、余额、充值、订单和订阅；
- 模型目录、上游账号、调度、分组和计费；
- 真实用量和请求费用；
- 卫星 SSO、应用凭据和代用户调用协议；
- “一键开分站”的租户开通事实。

AgentAPI 负责：

- 消费主站确认的租户、站长和成员归属，并据此建立本站会话；
- 当前租户的品牌、公告、公开法律协议和必要展示策略；
- 服务端只接受仓库定义的卫星公开模型目录；租户不能另建模型权限策略，浏览器不提供模型目录或模型工作台；
- `sk-*` 的签发、哈希保存、撤销和归属校验；
- 当前登录用户自己的 Key、请求跟踪和主站用量只读副本；
- 当前租户核心订单、套餐、返利和基础设置。

AgentAPI 不得成为第二套 Sub2API。

### 3.3 永久排除的模块

AgentAPI 不提供以下模块，无论是写入、只读镜像、隐藏路由还是主站接口代理均不允许：

- 分组管理；
- 账号管理；
- 代理管理；
- 兑换码管理；
- 插件管理；
- 安全审计，包括风险控制和提示词审计；
- 上游核验。
- 模型广场和模型工作台；
- 模型权限/模型策略管理；
- 批量图片；
- 代理站开通管理（主站“一键开分站”流程本身不在此列）；
- 运营监控；
- 优惠码管理；
- 订阅管理；
- 渠道管理和模型定价页面；
- 代理站计费页面；
- 内容页面管理与自定义页面；
- 备份管理。

站长不得发行、枚举或管理兑换码或优惠码。本站普通操作记录不能包装成主站安全审计。AgentAPI 不提供租户内容页或法律协议 API；需要展示正式协议时只能链接主站统一发布的页面，不得借此恢复通用内容页面管理。

截至 2026-09-30，上述边界已落实为前后端永久排除：禁用模块没有菜单、页面、浏览器客户端方法或可用专属服务端 Handler；对应旧管理路径统一返回 `404`。站长也不能按 `main_user_id` 代其他用户创建、查看或撤销 Agent Key。内部成员映射、必要运行日志、模型网关和主站只读调用是核心服务的数据结构，不构成被删除的管理产品模块。

## 4. “一键开分站”流程

“一键开分站”是幂等租户开通，不是部署新容器：

```text
已登录 Sub2API 用户点击“一键开分站”
  → 主站按 owner_main_user_id 查找租户
  → 不存在则原子创建租户和站长成员关系
  → 已存在则返回原租户
  → 通过既有卫星 SSO 启动接口进入共享 AgentAPI
  → AgentAPI 校验一次性票据并建立 3 天 HttpOnly Session
  → Session 保存可信 agent_id + main_user_id + role
  → 站长进入自己租户的管理界面
```

必须满足：

- 同一主站用户重复或并发点击不会创建多个租户；
- 失败可重试，不产生半租户、孤儿站长或重复归属；
- 站长身份来自主站认证和服务端租户关系；
- 复用 `GET /api/v1/auth/integrations/:slug/start`；
- ticket 只用于建立 Session，浏览器不持有主站密钥或 JWT；
- AgentAPI 不信任任意 `?agent_id=` 参数。

如果公共层暂时无法安全表达租户入口，必须先统一公共层协议；不得在 AgentAPI 私自发明不可信方案。

## 5. TenantContext 规范

每个受保护请求必须先得到唯一、可信的上下文：

```text
TenantContext
  agent_id
  main_user_id
  role: owner | member
  tenant_status
  user_status
  source: session | agent_api_key
```

允许来源：

1. 浏览器：已签名、HttpOnly、Secure 的 AgentAPI Session；
2. 外部 API：由本站 `sk-*` 哈希反查 `agent_id + main_user_id`；
3. SSO 回调：由已验证 ticket 和服务端租户关系建立 Session；
4. 自定义域名：Host 只用于查找候选租户，仍要结合服务端配置与认证校验。

禁止来源：

- query、JSON、表单或任意请求头直接提交的 `agent_id`；
- localStorage 中的租户编号；
- 只凭 Logo、域名文本或页面路由推断身份；
- 缺少身份时回退到默认租户、环境变量租户或站长；
- 使用主站管理员身份自动获得任意代理站站长权限。

无法确定唯一租户时必须拒绝请求。

## 6. 数据隔离规范

所有租户表必须显式包含 `agent_id`；用户级数据还必须包含 `main_user_id` 或本地不可变用户标识。站长关系必须存在数据库成员关系中，不能长期由进程级环境变量决定。

AI 修改数据层时必须检查：

- SELECT、UPDATE、DELETE、JOIN 是否包含 `agent_id`；
- INSERT 的 `agent_id` 是否来自 TenantContext；
- 唯一键、缓存 Key、任务 Key、幂等 Key、对象路径是否包含租户命名空间；
- 导出、备份、恢复、统计和后台重试是否仍按租户限定；
- 404/403 是否避免泄露其他租户对象存在性。

创建租户、绑定站长、签发 Key、记录请求和同步用量必须幂等。单租户后台任务失败不能阻塞或污染其他租户。

## 7. 认证与密钥规范

- AgentAPI Session：固定 3 天，HttpOnly，生产环境 Secure；
- SSO ticket：短时一次性票据，不等于 Session；
- `SUB2API_APP_CREDENTIAL`：只在 AgentAPI 服务端调用 `/v1`；
- `X-Sub2API-On-Behalf-Of`：必须是当前成员的主站用户 ID，不能用站长 ID代付；
- `X-Sub2API-Satellite`：使用注册 slug `agentapi`；
- `SUB2API_ADMIN_API_KEY`：仅可信部署环境可持有，不用于模型调用；长期应替换为主站最小权限注册能力；
- 本站 `sk-*`：完整值只显示一次，数据库只保存哈希，不转发主站；`sk-super-*` 必须拒绝；
- SuperKey：不得进入浏览器、URL、日志、AgentAPI 数据库或普通 Authorization。

凭据缺失或身份无效时必须失败，不得回退到共享 Key、默认用户或站长钱包。

## 8. 模型调用与计费

```text
用户或 API 客户端
  → AgentAPI 解析 TenantContext
  → 校验租户、用户和固定卫星公开模型目录
  → 服务端携带公共层三个身份头调用 Sub2API
  → Sub2API 选择上游、执行、计费并保存真实用量
  → AgentAPI 按请求 ID保存租户范围内的只读副本
```

只能使用 `../docs/卫星公开模型.md` 中的公开模型名；站长不能创建、扩展或收窄租户级 allowlist，也不存在模型策略写入口。

AgentAPI 不维护可消费子余额，不由站长代付，不用余额差值或估算价格冒充实际费用。主站明细未同步时显示“待确认/不可用”，不能显示为零。本地同步失败不能导致成功的主站请求再次执行或重复扣费。

## 9. 站长权限

站长只能管理当前 `agent_id` 的品牌、基础系统设置、公告、支付统计、订单处理和必要的用量同步。成员归属与用户状态只作为服务端访问门禁存在，不提供账号管理界面；Agent Key 仅由其所属用户自行管理；主站套餐只供当前用户按主站事实购买，站长没有套餐覆盖、隐藏、排序或编辑能力；模型目录固定来自公共契约。

站长不能获得 Sub2API 管理员权限，不能查看其他租户，不能管理主站全局资源，不能读取主站密钥或渠道凭据，不能修改主站真实余额、计费和用量，也不能通过前端参数切换租户。

## 10. 共享部署目标

生产环境只部署一套 AgentAPI 服务，可水平扩容多个相同副本：

- 所有副本读取同一权威租户数据库；
- 不再用进程级 `AGENT_ID`、`AGENT_DOMAIN`、`AGENT_OWNER_MAIN_USER_ID` 绑定唯一站点；
- 自定义域名通过映射表解析租户；
- 默认共享域名通过可信 Session 或服务端入口状态解析租户；
- Session、缓存、队列和限流支持多副本；
- SQLite 只用于单机开发或迁移验证，生产共享多副本使用支持并发、备份和迁移的数据库；
- provision worker 不再为租户生成 Compose、端口、数据库或 Secret。

健康检查只证明进程存活，不能替代 SSO、租户隔离、模型和真实计费验收。

## 11. 当前实现差距

截至 2026-09-30，共享多租户核心已经完成第一批可验证改造：

- `agent_config` 已从 `id=1` 单例表迁移为以 `agent_id` 为主键的多租户表，旧库可原位升级；
- Session 持久化可信 `agent_id + main_user_id + role`；共享生产不接受缺失 `agent_id` 的旧 Session，只有运维显式设置 `AGENT_ID` 的单租户迁移模式才能把旧 Session 绑定到该兼容租户；
- 本站 `sk-*` 可由服务端哈希反查所属租户，模型转发、用量和结算使用凭证解析出的 TenantContext；
- 公开品牌、公开模型、SSO 回调和密码登录可通过数据库中的规范化 Host 映射选择租户；
- 域名大小写不敏感唯一，浏览器提交的 `agent_id` 查询参数和 `X-Agent-ID` 不参与租户选择；
- 已有双租户同库、Key 隔离、Session 隔离、Host 隔离和旧库迁移测试；
- 主站已新增共享租户/成员表和按 owner 幂等的 `EnsureSharedTenant`，AgentAPI 的 SSO start 会先取得逻辑租户；
- 既有 SSO 票据已扩展签名的 `agent_id + role + agent_name`，AgentAPI 严格校验后创建缺失逻辑租户并建立 3 天会话；
- 既有租户 owner 在 AgentAPI 数据层不可变，后续票据或进程重启不能重新绑定站长；
- 后台结算、充值订单、图片和视频任务巡检已显式枚举 active 租户；
- 余额敏感的模型结算、充值同步、异步任务结算和后台核验已统一使用数据库持久化的按主站用户租约；租约支持续期、过期接管和 owner token 校验释放，两个独立 Store 实例的回归已证明不会同时进入同一用户的临界区；
- 本地已部署一套共享 Sub2API + AgentAPI，`246/247` 已登记，旧 provisioning 表已删除；
- 本地真实 SSO 已验证同一用户重复开站幂等，两个站长获得不同 `agent_id` 且共享容器数不变；
- 两个租户的个人 Key 创建、列表、跨用户拒绝和 `/v1/usage` 鉴权已验证隔离；共享 Host 会忽略旧单租户遗留域名认领，非共享自定义域名仍保留冲突拒绝；
- `246/247` 已在临时 PostgreSQL 16 完成历史数据收敛、旧表/函数删除及事务失败回滚测试。

共享多租户运行时仍**部分完成**，不能宣称生产改造已经完成。当前剩余事实包括：

- AgentAPI 内部的逐站 provision 命令、worker、runtime-control 路径和凭据已删除；共享生产默认不设置 `AGENT_ID`，启动不会创建固定租户，只有运维显式配置时才启用旧单租户迁移兼容；
- 主站逐站 provisioning/runtime 管理路由、Handler、worker 凭据、专用运行时模型凭据分支和管理前端已删除；
- Compose 仍使用单 SQLite 数据卷，尚未迁移到共享生产数据库和多副本 Session/队列；结算与充值的互斥已不再依赖进程内 mutex，但这只消除了一个并发风险，不能据此把当前 Compose 当作完整多副本拓扑；
- 主站新增前向迁移会先把历史 owner 收敛为共享租户，再删除旧 provisioning/runtime 表；本地部署和临时 PostgreSQL 回归均已通过，但尚未在正式生产库执行灰度核数、备份和回滚演练；
- 正式 AgentAPI 镜像、源码和启动配置，以及主站当前路由和依赖注入，均不再包含逐站 provision/runtime-control 实现；
- 本地主站 SSO、共享部署和双租户隔离已完成；尚未完成正式域名浏览器验收、真实付费模型计费核对、多副本、灰度迁移、灾备和生产隔离验收。

AI 必须同时陈述“已实现的可信链路”和“仅在显式 `AGENT_ID` 下启用的单租户迁移兼容”，不得把兼容模式描述为共享生产的默认架构，也不得把局部完成写成全部完成。

迁移完成前：

- 当前 Compose 只作为单副本 SQLite 的开发/迁移验证环境；
- 不再扩展逐站容器方案；
- 不新增依赖固定 `cfg.AgentID` 的功能；
- 新接口优先设计为显式 TenantContext；
- 文档必须区分当前实现和目标架构。

## 12. 迁移路线

### 阶段 0：冻结错误方向

- 以本文统一文档；
- 停止新增逐站部署能力；
- 历史文档标记为历史证据；
- 为已删除模块建立路由与符号回归测试。

### 阶段 1：请求级 TenantContext

- **已完成**：Session 和 Agent Key 返回可信租户与用户；
- **已完成**：模型转发、公开品牌、公开模型、SSO 回调和密码登录接入 TenantContext/Host 解析；
- **已完成**：拒绝 query/header 覆盖租户，并拒绝跨租户 Session 与 Host 混用；
- **大部分完成**：核心 Handler、支付回调、模型/用量/结算路径使用 TenantContext 或显式 `agent_id`；
- **已完成（核心巡检）**：结算、充值订单、图片和视频后台巡检显式枚举 active 租户；
- **已完成（代码）**：AgentAPI 与主站内的旧 provisioning/runtime-control 依赖已删除；共享生产启动不依赖 `cfg.AgentID`，显式 `AGENT_ID` 仅用于旧单租户迁移。

### 阶段 2：共享持久化

- **部分完成**：站长关系可由 `agent_config.billing_main_user_id` 解析为 Session owner 角色；
- **部分完成**：站点配置、用户、Key、Session、账务和任务表具备租户字段，域名建立唯一索引；新库不再初始化内容页、套餐策略、模型策略、分组策略、备份管理、提示词审计和风险控制专属表，旧库启动迁移会删除这些退役表；
- **已验证（关键业务标识）**：视频任务、图片任务和结算允许不同租户复用相同 `task_id` / `request_id`，读取和更新仍严格限定在各自 `agent_id`；
- **已验证（余额敏感互斥）**：模型结算、充值同步、图片/视频轮询和后台核验按主站用户使用可续期数据库租约；独立 Store 实例覆盖竞争、续期、过期接管和旧 owner 释放，不再依赖单进程 mutex；
- **部分完成**：旧单例 `agent_config` 提供自动迁移与测试；
- **已完成（核心结构与路径审计）**：所有现行租户业务表均由自动化结构门禁检查非空 `agent_id`，关键查询索引以 `agent_id` 起始；Key、Session、账务、订单、支付事件、公告、图片/视频任务及幂等键已有跨租户回归。公告已读关系额外由数据库插入/更新触发器校验父公告属于同一租户，升级启动会拒绝既有跨租户或孤立关系，不能静默带病运行；
- **待完成**：迁移到共享生产数据库并实现回滚、校验、全局备份和单租户导出恢复。

### 阶段 3：一键开站改造

## 13. AI 修改检查清单

每次修改必须回答：

- 功能属于代理站还是主站全局管理？
- 是否触碰七类永久排除模块？
- `agent_id` 是否来自可信 TenantContext？
- Session、API Key、后台任务和 SSO 是否使用同一租户语义？
- 所有读写、JOIN、缓存、任务和幂等键是否带租户边界？
- 余额、计费、用量和模型事实是否仍由 Sub2API 权威提供？
- 浏览器是否完全接触不到主站密钥、JWT 和 SuperKey？
- 是否新增隔离测试并说明验证范围？
- 是否区分已实现、已验证、已部署和已验收？
- 是否同步更新相关文档？

## 14. 最终验收矩阵

1. 两个主站用户分别一键开站，容器数不变，得到不同 `agent_id`；
2. 同一用户重复开站只返回原租户；
3. 两个站长同时登录共享 AgentAPI，只能看到自己的数据；
4. 篡改 query/body/header/cookie 不能切换租户；
5. A 站 Session、Key、对象 ID、请求 ID和幂等键不能影响 B 站；
6. 普通用户不能进入站长接口，主站管理员不会自动成为站长；
7. 本文列出的全部永久排除模块没有菜单、路由、前端 API、后端管理 API或备份入口；新库不初始化已删除模块的专属表；
8. Session 为 3 天，ticket 一次性且短时有效；
9. 浏览器、日志、数据库和错误响应不含敏感主站凭据；
10. 文本、流式、图片、视频和异步请求均按真实用户只计费一次；
11. 主站用量未同步时显示未知或待确认；
12. 共享域名、自定义域名、缓存和 CDN 不串品牌或 Session；
13. 多副本、后台任务、限流、备份恢复和租户停用保持隔离；
14. 真实主站联调、浏览器验收、部署和回滚演练均有记录。
