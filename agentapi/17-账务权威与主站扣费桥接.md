# 17 账务权威与主站扣费桥接

## 1. 为什么必须单独定义桥接

AgentAPI 有代理钱包和用户子余额，Sub2API 主站也有真实用户余额与用量账本。两套账本如果都被当成“最终余额”，就会产生三类不可接受的问题：

1. 用户在 AgentAPI 扣了一次，主站 `/v1` 又按同一请求扣一次；
2. AgentAPI 已经放行请求，但主站余额不足或未产生主站用量；
3. 主站管理员调账、用户直连主站或重试请求后，两边余额无法对账。

因此，任何生产实现必须先回答两个问题：

- 一次模型调用到底由哪个主站身份承担最终扣费；
- AgentAPI 的本地余额是权威账本、预授权镜像，还是仅用于展示。

在这两个问题拍板前，不能把当前参考实现当作生产计费实现。

## 2. 三个身份必须分开

| 身份 | 含义 | 是否承担主站模型扣费 |
| --- | --- | ---: |
| `agent_id` | 代理站/域名的稳定编号 | 否 |
| `proxy_user_id` | AgentAPI 本地映射记录 | 否 |
| `main_user_id` | Sub2API 中的真实用户 | 取决于桥接方案 |
| `agent_owner_main_user_id` | 代理管理员在主站的真实账户 | 方案 A 推荐承担 |

浏览器和客户端只能表达“我是当前 AgentAPI 用户”，不能提交任意 `main_user_id` 或 `agent_owner_main_user_id`。这些值必须由服务端通过当前 Agent、Session 和映射得到。

## 3. 桥接方案对比

### 3.1 方案 A：代理管理员主站账户承担模型扣费（推荐的最小改动方案）

方案 A 下，模型请求使用当前 Session 映射出的主站用户作为卫星请求身份；Sub2API 校验该用户是当前 Agent 的 active 映射成员后，再由逐站 `agt_model_` 凭据解析 Agent Owner 的 SuperKey 承担主站扣费：

```http
Authorization: Bearer <SUB2API_APP_CREDENTIAL>
X-Sub2API-On-Behalf-Of: <current_session_main_user_id>
X-Sub2API-Satellite: agentapi
```

请求头继续遵循公共卫星协议，不能冒充 Owner 或由浏览器覆盖；AgentAPI 专用 model credential 在主站做 Agent/Owner/Session 用户映射校验并将计费 Key 固定为 Owner。主站只对 `agent_owner_main_user_id` 做一次真实扣费；AgentAPI 根据当前代理用户的本地子余额决定是否放行，并在本地记录该用户的用量归属。

请求链路：

```text
代理用户登录 AgentAPI
  → AgentAPI 解析 agent_id + proxy_user_id + main_user_id
  → 本地子余额预授权
  → 查询代理管理员主站余额作为预检
  → 以当前 main_user_id 发送 X-Sub2API-On-Behalf-Of
  → Sub2API 验证该用户 active 且映射到此 Agent
  → Sub2API 以 agent_owner_main_user_id 的 SuperKey 计费
  → 主站完成唯一一次真实扣费和用量记录
  → AgentAPI 按主站 usage/余额差额结算本地预授权
  → 保存 proxy_user_id/main_user_id 到本地用量归属
```

这满足“代理用户使用时等量扣除分站管理员主站额度”，且不需要把管理员 Key 发给代理。代价是：

- 主站原生用量默认按代理管理员汇总，不会天然按代理用户拆分；
- AgentAPI 的用户维度用量是本地归属展示，主站用量仍以代理管理员为主；
- 代理管理员主站余额充值后，需要由同步任务或受控接口刷新 AgentAPI 可分配额度；
- 如果允许代理用户直接访问主站，必须禁止其绕过 AgentAPI 使用自己的主站余额。

方案 A 只有在主站接受“一个代理对应一个主站计费账户”时才成立。主站管理员账户必须拥有代理所需的模型分组权限，但管理员 Key 本身仍不能作为模型凭据。

### 3.2 方案 B：将主站额度原子转移到每个代理用户

代理预充值进入 `agent_owner_main_user_id` 后，分配用户额度时由主站控制面在一个数据库事务中完成：

```text
代理管理员主站余额 - amount
代理用户主站余额   + amount
写入转账流水、agent_id、幂等键
```

模型请求继续使用当前代理用户的 `main_user_id`，因此主站可以原生按用户统计用量。该方案的前提是主站新增“代理额度转账”受控接口或在主站内部实现原子事务。不能用两个普通管理员余额接口拼接成伪事务；如果第二步失败，会出现资金凭空减少或增加。

方案 B 的优点是主站用户余额和用量语义最直观；缺点是需要修改主站账务、增加转账权限、处理并发锁、退款、撤站和跨代理归属，实施量明显大于方案 A。

### 3.3 方案 C：只扣 AgentAPI 本地余额

AgentAPI 只在本地扣用户子余额，再以一个拥有无限或不计费额度的主站凭据调用模型。

该方案不接受：它会绕过主站真实计费和用量账本，无法保证成本回收，也不符合“主站负责最终计费”的边界。除非主站明确提供按请求签名的后付费结算接口，否则不得上线。

## 4. 推荐决策

在“最小修改主站、无佣金、代理预充值、代理管理员承担用户消费”这组条件下，推荐先采用 **方案 A**：

1. `agent_owner_main_user_id` 是唯一主站计费身份；
2. AgentAPI 用户的 `main_user_id` 只负责真实登录身份和本地归属；
3. AgentAPI 本地钱包是预授权/额度分配账本，不再独立创造主站可消费额度；
4. 主站 `/v1` 返回的成功请求只允许形成一次真实扣费；
5. 主站余额差额或主站返回的 `usage_id` 是实际结算依据；
6. 如果主站不能按代理管理员身份承担模型调用，必须切换到方案 B，不能悄悄降级为方案 C。

这项决策必须在实现前写入版本记录。未拍板时，代码只能验证认证、映射、接口转发和本地账务外壳，不能宣称计费闭环已完成。

## 5. 方案 A 的余额不变量

推荐把 AgentAPI 的本地余额解释为“可分配/已分配的主站额度镜像”，而不是另一套钱：

```text
agent_wallet.available
  + agent_wallet.allocated
  + agent_wallet.frozen
≤ 代理管理员主站可用余额（同步快照）
```

其中：

- `available`：尚未分配给任何代理用户的额度；
- `allocated`：已分配给代理用户、尚未消费的额度；
- `frozen`：正在进行中的请求预授权；
- 主站余额：唯一允许主站模型网关实际扣减的余额。

如果主站余额下降而本地没有对应 `usage_id`，进入 `settlement_pending`，禁止继续放大额度，等待对账；不能直接把差额当作佣金或静默冲平。

## 6. 方案 A 的一次请求状态机

```text
authorized
  → local_reserved
  → upstream_started
  → upstream_succeeded
  → main_settlement_confirmed
  → local_captured

local_reserved/upstream_started
  → upstream_failed → local_released

upstream_succeeded
  → main_settlement_unknown → settlement_pending
```

强制规则：

1. 本地预授权成功后才允许访问主站；
2. 主站请求必须使用固定的 `agent_owner_main_user_id`，客户端不能覆盖；
3. 主站错误或明确未产生用量时释放本地预授权；
4. 主站成功但用量查询超时不能立即全额退款，先进入待对账状态；
5. 同一 `request_id`、`usage_id` 和本地流水只能结算一次；
6. 重试必须复用原请求的幂等键，不能重新扣一笔预授权。

## 7. 充值、分配和消费的闭环

### 7.1 代理管理员充值

```text
代理管理员在主站完成充值
  → 主站余额增加并产生主站流水
  → AgentAPI 服务端同步余额快照
  → 增加 agent_wallet.available（仅增加可核对镜像）
  → 写入 agent_credit_sync 流水
```

同步接口必须带 `agent_id`、主站用户 ID、快照时间和幂等键。同步失败不能凭前端“支付成功”增加本地余额。

### 7.2 分配给代理用户

```text
校验 agent_wallet.available >= amount
  → available 减少
  → user_wallet.available 增加
  → 写入 agent_allocate/user_allocate 两条关联流水
```

方案 A 中这一步不改变主站余额，只改变本地可消费额度的归属；主站余额在模型实际调用时由主站网关扣减。

### 7.3 用户消费

```text
user_wallet.available 预授权
  → 主站以代理管理员身份真实扣费
  → 根据 usage/余额差额确定 actual_amount
  → user_wallet 按 actual_amount 扣减
  → agent_wallet.allocated 同步减少
  → 未使用部分写 release 流水
```

### 7.4 退款和冲正

主站已产生扣费时，退款必须先在主站完成并取得可验证的主站退款结果，再写本地 `refund/reversal` 流水。不能只在 AgentAPI 本地补回余额而让主站账务保持扣费状态。

## 8. 与当前实现的关系

当前 `agentapi/backend` 已按方案 A 落地以下关键约束：

- `/v1` 的 `X-Sub2API-On-Behalf-Of` 是当前 Session 的 `main_user_id`，不能由客户端覆盖；Sub2API 必须确认该用户是此 Agent 的 active 映射成员，再使用 Agent Owner SuperKey 计费；
- 本地用户余额预授权与 `settlements.pending` 在同一个 SQLite 事务中创建；
- 相同 `request_id` 的重试在访问主站前被拦截，不会重复转发或重复扣款；
- 主站明确拒绝时释放本地预授权；主站成功但余额/usage 不可立即确认时保持 pending；
- 管理员可通过 `/api/v1/agent/admin/settlements/reconcile` 以原始 `request_id` 查询逐站 `GET /api/v1/agent-runtime/usage`，并幂等完成确认和未使用额度退回；
- `AGENT_INITIAL_BALANCE` 和本地充值接口在 `owner_upstream` 模式下禁用。

这里的 `actual_cents` 在主站 usage 可见时取 `actual_cost`，否则回退 `total_cost`；如果两者都不可见，不能猜测、不能退款。方案 A 仍然要求主站管理员确认 usage 查询权限和账务语义后才可生产上线。

## 9. 必须新增的验收项

- [x] 主站计费身份不能由浏览器或客户端覆盖；
- [x] 一次成功模型请求在主站和 AgentAPI 各只有一条可关联结算记录；
- [x] 主站余额扣减与 AgentAPI 本地流水可以按 `request_id/usage_id` 对账；
- [x] 主站成功但结算查询超时时进入 `settlement_pending`，不会静默退款；
- [x] 代理管理员余额不足时，任何代理用户都不能继续调用；
- [x] 本地分配额度不会凭空增加主站余额；
- [ ] 主站发生真实扣费后的退款先验证主站退款结果，再产生本地反向流水；（首版不开放自动退款）
- [x] 主站用户直连入口不能通过 AgentAPI 绕过本地额度策略；
- [x] 方案 A 的主站用量按代理管理员汇总、代理用户用量按 AgentAPI 归属展示，产品文案明确二者差异；
- [ ] 若产品要求主站按代理用户统计，必须改用方案 B 并验收原子转账。
