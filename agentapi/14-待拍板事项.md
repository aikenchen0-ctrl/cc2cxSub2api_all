# 14 待拍板事项

## 1. 已经确定

- [x] AgentAPI 是独立代理应用，不复制 Sub2API；
- [x] 用户注册后真实记录进入主站数据库；
- [x] AgentAPI 保存 `main_user_id` 映射；
- [x] 采用代理预充值额度 A 方案；
- [x] 不采用佣金策略；
- [x] 主站统一执行模型和实际扣费；
- [x] 管理员 Key 不进入浏览器；
- [x] 第一版一个用户只属于一个代理；
- [x] 代理额度和用户子余额必须有账务流水；
- [x] 不允许通过复制数据库或直接写主站数据库实现同步。
- [x] 主站扣费身份与 AgentAPI 本地余额的桥接方案：采用方案 A（`agent_owner_main_user_id` 唯一承担主站模型扣费，详见 17）；

## 2. 仍需产品/运营确认

账务身份已经按方案 A 冻结；以下是支付、部署和运营层面的选择，不改变主站唯一扣费身份。

### 2.1 用户支付是否自动转为主站额度

**推荐：首版不自动转。**

代理先向主站预存额度，用户支付给代理后，代理在可用额度范围内给用户分配子余额。这样主站不会因为一个伪造或未确认的外部支付回调就产生可消费额度。

如果业务要求用户付款后自动增加主站代理额度，需要另外定义：

- 支付主体是否就是主站；
- 代理支付账户是否由主站托管；
- 自动结算比例和时机；
- 退款和拒付如何影响主站额度；
- 主站是否愿意承担代理垫资风险。

### 2.2 代理用户的支付余额和主站额度是否一一等价

**推荐：用户子余额是代理主站额度的分配结果，不是独立凭空产生的余额。**

如果允许代理先给用户授信，必须记录授信额度、到期时间和风险上限，不能直接绕过 `agent_wallet`。

### 2.3 部署方式

**推荐：同一个镜像、每个代理独立实例。**

后续代理数量很大时，再改为共享集群和 Host 映射。两种方式使用同一套 AgentAPI 业务协议。

### 2.4 用户是否允许访问主站

**推荐：首版只允许从代理站访问。**

如果未来允许主站直连，需要为用户凭证绑定 `agent_id`，并让主站继续执行代理额度检查。

### 2.5 价格规则

**推荐：先使用主站统一价格，不允许代理修改实际模型价格。**

代理可以配置页面展示和充值面额，但不能因为前端修改价格字段而改变主站实际扣费规则。

### 2.6 支付渠道

首版只接入一个支持服务端签名回调、退款和交易查询的支付渠道。多渠道接入放到第一版稳定后。

### 2.7 主站扣费身份

**推荐：方案 A——代理管理员主站账户承担模型扣费。**

方案 A 只需要 AgentAPI 做本地用户额度预授权，并使用 `agent_owner_main_user_id` 调用主站 `/v1`；主站用户维度的用量在 AgentAPI 本地归属展示。若必须让主站原生按每个代理用户统计和扣费，则改选方案 B，并先实现主站原子额度转移接口。具体状态机、余额不变量和阻断条件见 [17-账务权威与主站扣费桥接](17-账务权威与主站扣费桥接.md)。
