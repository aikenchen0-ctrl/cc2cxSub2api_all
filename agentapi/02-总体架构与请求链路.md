# 02 总体架构与请求链路

## 1. 逻辑架构

```text
                         ┌──────────────────────────┐
用户浏览器 ───────────────▶│ AgentAPI 前端/代理后端    │
  agent01.example.com     │ - HttpOnly Session      │
                          │ - 用户/代理权限          │
                          │ - 支付入口               │
                          └─────────────┬────────────┘
                                        │ HTTPS API
                                        ▼
                          ┌──────────────────────────┐
                          │ Sub2API 主站              │
                          │ - 真实用户与身份          │
                          │ - 代理账户和额度          │
                          │ - 模型网关                │
                          │ - 用量与账务              │
                          └─────────────┬────────────┘
                                        │
                                        ▼
                               主站上游账号/模型
```

## 2. 组件职责

### AgentAPI Web/API

- 共享集群方案可根据请求 Host 解析 `agent_id`；当前 Docker 参考实现是一实例一 Agent，直接使用 `AGENT_ID`，不在进程内做多租户路由；
- 从 HttpOnly Session 解析 `proxy_user_id`；
- 通过映射找到 `main_user_id`；
- 调用主站控制接口和模型接口；
- 不向浏览器下发管理员 Key、SuperKey 或主站用户 API Key。

### AgentAPI 数据库

- 保存代理站、域名、用户映射、支付配置引用、操作审计和本地缓存；
- 不直接保存主站密码、SuperKey 和未加密的支付密钥；
- 不作为模型消费余额的最终来源。

### 主站 Agent 控制面

- 创建/暂停代理账户；
- 为代理分配预存额度；
- 创建主站用户并标记 `agent_id`；
- 查询用户余额和用量；
- 处理账务流水；
- 校验 AgentAPI 的服务身份。

### 主站模型网关

- 使用主站现有模型路由和上游账号；
- 根据已经拍板的账务桥接方案进行唯一扣费；方案 A 使用 `agent_owner_main_user_id`，方案 B 使用当前代理用户的 `main_user_id`；
- 记录 `agent_id` 作为来源归属；
- 仅接受公共层规定的服务请求头。

账务身份不能由浏览器传入。方案 A 的代理用户 `main_user_id` 只做登录身份和 AgentAPI 本地归属，主站模型请求必须使用代理管理员 `agent_owner_main_user_id`；方案 B 才能直接使用代理用户主站余额。两种方案的详细差异见 [17-账务权威与主站扣费桥接](17-账务权威与主站扣费桥接.md)。

## 3. 域名到代理的解析

每个请求进入 AgentAPI 后，先执行：

```text
规范化 Host
  → 查询 domain_bindings
  → 校验 agent.status == active
  → 将 agent_id 写入请求上下文
  → 后续所有用户、订单和请求操作强制使用该 agent_id
```

域名不能由请求体中的 `agent_id` 覆盖。客户端传入的 `agent_id` 只能用于一致性校验，不能作为权限来源。

## 4. 开站链路

```text
主站用户点击一键开站
  → 控制面创建 pending Agent
  → 分配 slug/domain
  → 创建主站代理账户和钱包
  → 生成代理服务凭据
  → 写入 AgentAPI 配置/创建实例
  → DNS/TLS/Nginx 或 Ingress 就绪
  → 健康检查
  → Agent 进入 active
```

域名分配可以使用平台通配符 DNS 和通配符证书。未知域名必须由 AgentAPI 或入口层拒绝。

## 5. 用户注册链路

```text
浏览器 → AgentAPI /register
  → 校验当前域名对应 agent_id
  → 校验注册信息和风控
  → 主站创建 main_user_id
  → 主站绑定 source_agent_id
  → AgentAPI 保存 agent_id + main_user_id 映射
  → 创建 AgentAPI 本地 Session
```

主站创建接口必须支持幂等键。若 AgentAPI 保存映射失败，可凭同一幂等键重新获取原来的 `main_user_id`，不能重复创建用户。

## 6. 模型请求链路

```text
浏览器携带 AgentAPI HttpOnly Session
  → AgentAPI 解析 agent_id / proxy_user_id / main_user_id
  → AgentAPI 检查用户状态
  → AgentAPI 预授权本地用户子余额
  → AgentAPI 服务端以已拍板的主站计费身份调用主站 /v1
  → 主站校验服务凭据、计费身份和 agent 归属
  → 主站执行模型请求
  → 主站结算用量并记录唯一流水
  → AgentAPI 按 usage/余额差额结算本地预授权
  → AgentAPI 返回脱敏结果
```

按照仓库公共层，模型请求服务端必须携带：

```http
Authorization: Bearer <SUB2API_APP_CREDENTIAL>
X-Sub2API-On-Behalf-Of: <已拍板的主站计费身份>
X-Sub2API-Satellite: agentapi
```

方案 A 中“已拍板的主站计费身份”是 `agent_owner_main_user_id`；方案 B 中才是当前代理用户的 `main_user_id`。不能一边按代理管理员余额收费，一边把当前用户 ID 当作主站扣费身份而不做额度转移。

如果 AgentAPI 最终注册为卫星项目，`agentapi` 的 slug、audience、菜单和回调必须遵循现有 `apps.go`、公共 HMAC SSO 和 3 天 Session 约定，不另写一套协议。

## 7. 充值链路

```text
用户在 AgentAPI 创建充值订单
  → AgentAPI 记录 agent_id + main_user_id
  → 用户完成支付
  → 支付渠道回调 AgentAPI
  → AgentAPI 验证签名、金额、订单状态
  → 代理管理员主站预充值或受控额度同步已确认
  → 更新本地可分配额度和代理用户子余额
  → 模型消费时由主站计费身份完成唯一扣费
```

第一版建议严格区分“代理向主站预存额度”和“用户向代理付款”。外部支付回调不能直接凭一条 HTTP 请求把主站额度改成已支付；是否自动结算到主站额度见 [14-待拍板事项](14-待拍板事项.md)。

## 8. 失败边界

| 失败位置 | AgentAPI 行为 | 主站行为 |
| --- | --- | --- |
| 域名未绑定 | 404/421 | 不接收业务请求 |
| Agent 暂停 | 403/423 | 拒绝消费和新注册 |
| Session 无效 | 401 | 不尝试默认用户 |
| 主站不可用 | 503 + request_id | 不生成本地成功记录 |
| 余额不足 | 402/403 | 不调用上游模型 |
| 上游失败 | 返回可重试错误 | 释放/冲正冻结额度 |
