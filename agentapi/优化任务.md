# AgentAPI 代理站优化任务

> 项目：`agentapi/`（代理站，独立计数，不是第 12 个卫星）。
> 当前证据基线与全局约束见根目录 `评估报告.md`、`优化任务-总调度.md`。基线：2026-11-14。
> 本项目涉及主站管理员 Key、租户资金和付款结算，优先级高于普通卫星功能优化。

## 1. 项目定位与边界

- 共享多租户代理站：所有站长共用一套代码/容器，按 `agent_id` 与服务端 Session 隔离；不按租户新建容器、数据库或端口。
- 用户浏览器经 SSO 进入；服务端代理主站 `/v1`，并可执行站长付款、订单、退款、对账。
- 与 11 个卫星的本质区别：AgentAPI 拥有**服务端付款/抽成能力**；该能力不得下放给普通卫星。
- 本项目只改 `agentapi/`；根 Compose、根 SSO 协议、主站计费规则由协调 Agent 处理。

## 2. 结论与商用判定

**当前不适合开放注册、支付或对外商用。**

直接阻断项：

- 源码中存在主站管理员 Key，且缺配置时回退该 Key；测试还要求 fail-open。
- 根 Compose 未显式注入 `SUB2API_APP_CREDENTIAL`，干净部署可能缺网关凭据。
- 租户、付款、退款、对账需在“用户绑定断言 + 服务端计费唯一口径”落地后重新验收。
- 仓库未发现 LICENSE，商用授权待法务确认。

## 5. 缺陷清单与补强方案

### AGA-01 删除硬编码管理员 Key（P0）

**现象与证据**
- `backend/admin_key_config.go:7` 含明文主站管理员 Key，前缀为 `admin-4eb1...`（报告中不复制完整值）。
- `backend/admin_credential.go` 在缺失/占位符时返回内置 Key。
- `backend/admin_credential_test.go` 明确断言“缺失部署 Key 必须使用内置 Key”。

**影响**
- 任何拿到源码/Git 历史的人都可能获得主站管理员能力。
- 部署漏配时静默使用固定凭据，暴露面扩大且难以审计。
- 一旦该 Key 仍有效，属于最高级别凭据泄露。

**实施步骤**
1. **先由有权限的运维/用户轮换或吊销该 Key**；不要在轮换前改代码并继续使用旧值。
2. 删除 `admin_key_config.go` 中的明文常量和 `admin_credential.go` 的回退分支。
3. 缺失、空白、占位符、不可读 `_FILE` 一律返回空；注册/管理员功能 fail closed。
4. 删除“回退正确”的测试，改为断言未配置时明确失败。
5. 用 `git log -S` 定位历史泄露；清理历史需单独授权，不得擅自 force push。
6. CI 增加 secret 扫描；启动日志只说明“未配置”，不打印值。

**验收**
```powershell
cd agentapi\backend
go test ./... -run 'TestMainAdminCredential|TestRegistration|TestStation|TestTenant' -count=1
rg -n "admin-4eb1|builtinMainAdminAPIKey" .
```
- 第二条命令无结果。
- 未配置 Key 时注册/管理接口返回明确错误，不使用任何内置凭据。
- 本地钱包负债恒等式：任意成功结算与 `SyncOwnerBalance` 后，`SUM(agent_user_wallets.balance_cents) == agent_wallets.allocated_cents`；直扣路径必须同时释放 `allocated_cents` 并留下可复算流水。
- 新 Key 只在 Secret/环境变量中存在；源码、镜像、构建产物均无泄露值。

### AGA-05 租户、付款与结算必须由服务端确定（P0）

**现象与风险**
- AgentAPI 是唯一应具备付款/抽成能力的项目；当前主站对普通卫星也开放付款头，导致边界混淆。
- `main.go:3003-3025` 在本站钱包模式下把 `Payer` 设为站长、`commission` 设为 0；`main_client.go:977-991` 仅在 `Payer != 当前用户` 时发送付款头。
- 若浏览器可传 `agent_id`、付款主体或费率，可能跨租户扣款或伪造抽成。
- 主站已有按 slug 计费配置，代理站不应另建一套客户端费率口径；`ModelRateMultiplier` 是本站对用户加价，不是主站 commission。
- 当前费率在请求开始时读取配置；若重试/补单时重读，金额可能漂移。
- 主站现有订阅检测依赖 `apiKey.Group` 与中间件加载订阅；AgentAPI 走卫星 SuperKey 时该条件不成立，Google/Gemini 入口甚至不解析 `X-Sub2API-Group-ID`。若不先修主站，本站钱包代付可能在用户已有订阅时仍然生效，且本地钱包与主站订阅额度会同时消耗。
- **主站当前仍是组判定，不能按“已支持订阅口径”对接**：`sub2api/backend/internal/service/gateway_usage_billing.go:841` 仍是 `subscription != nil && apiKey.Group != nil && apiKey.Group.IsSubscriptionType()`；`openai_gateway_usage.go:346` 同类判定；未绑组 SuperKey 即使存在唯一有效订阅也不会被识别。主站当前只定义 `ListActiveUserSubscriptions`（`subscription_service.go:793-801`），未定义 `ErrMultipleActiveSubscriptions`，`billingErrorDetails`（`gateway_handler.go:2434-2478`）也未映射 `MULTIPLE_ACTIVE_SUBSCRIPTIONS`。因此任意多订阅场景当前只会落 403 `billing_error`，AgentAPI 必须按“主站未实现专用码”做兼容：不按错误文案猜测、不重试余额、不扣本地钱包；等主站落地专用码后再断言精确错误码。
- 本地钱包扣款主体是 `ProxyMainUserID`，主站代付主体是站长 `Payer`；两者是两本账，必须用同一 `request_id` 关联，不能把本地余额差额当主站退款。
- 主站预检余额按 User，不是 Payer：`billing_cache_service.go:735-777` 在非订阅模式调用 `checkBalanceEligibility(ctx, user.ID)`，`879-897` 只查 `user.ID`。AgentAPI 本站钱包模式下 `Payer` 是站长、`User` 是终端用户，会出现“用户余额为 0 但站长大站有余额却被拒”或“用户有余额但站长不足，预检通过后后扣透支站长”。
- 主站付款头解析不是显式 fail closed：`satellitePayerFromRequest` 的调用方在 `!ok` 时只 `return`（依赖 `AbortWithError` 的副作用）；只带 `X-Sub2API-Commission-Rate` 不进入解析；`NaN` 可通过 `rate < 0 || rate >= 1` 检查并进入 `BillingCommissionRate`。AgentAPI 不得依赖这些隐式行为，必须按 S2A-02 的最终口径对接。

**实施步骤**
1. `agent_id`、租户归属、站长身份只能从 SSO 票据/服务端 Session 解析，禁止信任浏览器参数；`agent_id` 不能出现在可写请求体、查询串或客户端 Header 中。
2. 保留 `agentapi/收费模块.md` 的两种模式，不得合并成含糊的“代付”：
   - 默认 `user_upstream`：不加价，由用户映射的主站用户扣费；本模式不发送 Payer/Commission。
   - 开启本站支付：订单先充本站钱包；模型请求由服务端持久化策略确定 Payer（站长），并按本站 `ModelRateMultiplier` 对用户本站钱包计费。仅当主站快照为余额模式时，站长主站余额按上游实际费用扣、差额留在本站；若用户解析出唯一有效订阅，按 `SUBSCRIPTION_ACTIVE` 在扣款前拒绝，不扣本站钱包也不扣站长余额。
3. 付款主体与费率只由服务端持久化配置确定；普通卫星、浏览器和请求头都不得携带可影响账务的 `Payer`、`Commission-Rate` 或费率。付款主体与费率在请求开始时固化快照；同一 `request_id` 的重放不得切换 Payer，也不得重读最新配置生成不同 `PayerCost`。
4. 每个结算在请求开始时写费率/模式快照；重试、补单、退款只读快照，不重读最新配置。切换模式不得追溯已发起请求。主站对付款费率不得静默钳制：`buildUsageBillingCommand` 当前把 `rate > 0.95` 改成 0.95（`gateway_usage_billing.go:318-328`），若本站允许 `0.99` 等费率，主站必须显式支持或明确拒绝；不得出现“本站按 0.99 记账、主站 Payer 按 0.95 少扣”。
5. 区分三种资金动作，不能用“退款”统称：
   - 订单退款：支付渠道退回，冲减本站钱包入账；
   - 预留释放：`FinalizeSettlement` 按实际用量退回未使用预留，只改 `reserved - charged`；
   - 本地扣款冲正：`Credit` 只对 AgentAPI 本站 `agent_user_wallets` 新增反向 `refund` 流水，不改历史 ledger；它不冲正主站 usage，也不得作为主站冲正键。主站 usage 冲正另属独立账本域 `main_usage_reversal:<request_id>:<api_key_id>`（当前未实现，见根 7.3.1 第 23 条）。
   三者均带 `agent_id/user_id/settlement_id/order_id/idempotency_key`；同一订单/usage 重复或乱序回调只产生一次资金变动。
6. 与主站 S2A-02/S2A-09 对齐：卫星价或 AgentAPI 收费只能有一个客户扣费权威；余额模式且 0 条订阅时 `Payer != User` 只扣 Payer，不得再扣用户主站余额；必须按主站 S2A-02/S2A-09 冻结的“用户全部有效订阅”判定：0 条走余额；1 条时若本请求需要本站钱包代付，必须在扣款前返回 `SUBSCRIPTION_ACTIVE`（HTTP 403）并终止：不扣本地钱包、不扣订阅、不扣站长余额、不写成功 usage；不得把订阅优先当作已收费，也不得在本地另扣一次；2 条及以上由主站请求前拒绝，AgentAPI 不得吞错。不得按请求头 `X-Sub2API-Group-ID`、实际调度账号组或订阅 ID 排序任选一条。预检必须检查 Payer 余额，并明确 User 余额是否仍为附加门槛；不得预检 User、后扣 Payer。
   - 账本分支只能由主站响应中的显式事实决定：不得因 `subscription` 为空、`is_subscription_bill` 缺失或 usage 返回 `total_cost=0` 就自行改判余额或重试成余额请求。主站返回多订阅拒绝（`ErrMultipleActiveSubscriptions` / `MULTIPLE_ACTIVE_SUBSCRIPTIONS`，HTTP 403）时必须原样透传并终止本次代付，不扣本站钱包、不释放为成功、不换 Key 重试；当前 `billingErrorDetails`（`gateway_handler.go:2434-2478`）未显式映射时会落 403 `billing_error`，AgentAPI 不得按错误文案猜测分支。
7. 对账可按租户、用户、时间窗口、`request_id/order_id/settlement_id` 复算；差异只告警，不用二次扣款“抹平”。
   - 订阅判定必须在请求开始时冻结：AgentAPI 本站钱包代付若需判断主站订阅，预检与结算必须复用同一“用户全部有效订阅”快照，不得各自重查；预检后新增/失效订阅不得改变本次代付拒绝或扣款分支。
8. 补跨租户、越权付款、重复结算、部分退款、乱序回调、模式切换、费率快照、普通卫星伪造付款头测试；另补预检主体用例（余额模式、0 条订阅）：User 余额 0 + Payer 有余额不得被拒，User 有余额 + Payer 不足必须在请求前拒绝；唯一订阅 + 非本人 Payer 必须在扣款前 403 `SUBSCRIPTION_ACTIVE`，不得进入上述余额预检。
9. **按 S2A-08 实现受理与别名契约**：调用上游前先提交 `accepted`；本地拒绝先提交 `rejected_before_upstream` 与真实 `funds_effect/quota_effect`，只有双零且 `dispatch_state=not_started` 才可标记可重发；同一请求只建一条 admission（先以临时键建行，最终键只一次 CAS 写入 `final_request_id`；dispatch 前拒绝可保持空，不得伪造），临时键经 `request_admission_alias` 单跳、双向唯一并外键归属该 admission；改绑、二次归属或引用未升级最终键均冲突。usage/反查必须返回完整 `admission_source/funds_effect/quota_effect/dispatch_state/state_version/query_request_id/final_request_id`，`query_request_id` 逐字等于查询键；别名缺失不得返回 `settled`。最终键升级、别名与权威 usage 同事务或同事务 outbox，任一步失败不得确认成功或换键重发；临时键查询别名缺失不得 `settled`，最终键查询唯一 usage 存在须 `settled`。

**验收**
- 浏览器篡改 `agent_id` 不能访问其他租户。
- 普通用户不能为其他站长付款；非 AgentAPI 卫星不能携带付款头。
- 重复结算不重复扣款；对账差异可定位。预留释放不得伪装成订单退款，用量冲正不得改写历史流水。
- `user_upstream` 下不产生主站 Payer 头；本站钱包模式下仅当主站快照为 `ledger_mode=balance` 且 0 条订阅时，扣站长主站余额一次、用户本站钱包按快照倍率扣一次；若解析出唯一有效订阅，必须 403 `SUBSCRIPTION_ACTIVE` 且两侧均不扣。充值入账与模型 usage 是两条独立账本，不能互相抵消。
- 主站卫星报价命中但模型/渠道成本缺失时不得把 `total_cost=0` 当正常成本：若 usage 返回 `total_cost=0` 且本次确实调用了模型，本站必须显式告警或标记未归类，不能据此计算上游差额、站长成本或对账结果。
- 修改 `ModelRateMultiplier` 后，已发起/待补单请求仍按旧快照结算。同一 `request_id` 首次成功后重放必须遵循 first-write-wins：复用首次权威 usage，不得把付款人从 A 改成 B，也不得让 B 再产生本地 `reserve/consume` 或主站扣款；若主站返回既有结果，必须能看出本次重放未改变资金。
- **Payer 有值但佣金为 0/缺失必须显式决定**：当前本站 `withRelayPayer` 仅在 `0 < rate < 1` 时写佣金（`relay_group.go:46-59`），`main_client.go:986-990` 只在 `rate > 0` 时发 `X-Sub2API-Commission-Rate`；主站 `satellitePayerFromRequest` 缺省 `rate=0`（`super_key_satellite.go:151-159`），结果就是“只设 Payer、不设佣金”，Payer 按全额扣款。必须由服务端持久化策略明确该语义：当前主站按 `PayerCost=ActualCost*(1-rate)` 计算，故 0 表示平台不抽成、Payer 承担全额 `ActualCost`，绝不是 `PayerCost=0`。若要求显式头，Payer 存在且费率缺失/非法时必须 4xx；若允许省略，必须写死“省略=0=全额承担”并可审计。不得把佣金 0 记成本地或主站零扣款，也不得因费率缺失静默改口径。补测试：Payer 存在且费率为 0、缺失、`NaN`、`Inf`、`>=1` 时，本站与主站一致：0/缺失按策略承担全额或 4xx，非法值 4xx，且 `charged_cost=actual_cost`。
- **代付金额必须与 usage 快照同精度**：`PayerCost=ActualCost×(1-rate)` 必须在主站仓储扣款、usage `charged_cost` 与平台配额累计前统一量化为 8 位 half-away-from-zero；当前 `quantizeMonetaryFields` 未覆盖 `PayerCost`（`sub2api/backend/internal/service/usage_billing.go:85-91`），第 9 位 half 边界（`0.000078125×(1-rate)`）修复前必须标未通过。AgentAPI 对账只能比较同一量化值，不得在本地按分四舍五入后判等。
- 费率边界：主站接受的 commission rate 必须是有明确上界的服务端值。若本站配置 `0.9501`/`0.99`/`0.999`，断言主站要么按该值计算 `PayerCost`，要么在扣款前明确 4xx 拒绝；不得接受后静默按 0.95 少扣。
- 普通卫星携带 `X-Sub2API-Payer` 或 `X-Sub2API-Commission-Rate` 被主站 403；只带 `Commission-Rate`、不带 Payer 同样 403，不得静默忽略。
- **亚分成本不得被截断为 0，也不能用分粒度做跨服务对账**：`nanosToCents` 当前四舍五入到分（`main_client.go:894-898`），`4_999_999` 纳秒即 0.004999 美元会返回 0；`stationChargeCents` 再对 `actualCents<=0` 返回 0（`store.go:2907-2916`）。因此一笔真实成本小于半分、倍率最高 1000 的请求仍可能完全不扣款。必须二选一：保留纳秒/微美元精度直到乘倍率后再向上取整，或对 `0<actual<1` 分显式按 1 分起扣并记录原值；不得把亚分成本当免费。主站权威金额与本地分账之间的对账必须使用主站 `*_usd_nanos`/定点字符串，不得先经 `nanosToCents`；只有本地钱包落账才换算为分，且换算规则须写入 settlement 快照。当前 `stationChargeCents`（`store.go:2907-2916`）是“倍率量化 6 位后对分金额向上取整”：`scaled=round(rate×1e6)`、`charged=ceil(actualCents×scaled/1e6)`；文档与验收必须按此实现判定，若改为其他规则须版本化快照并补测试，不得只改文字。补测试：`actual=0.000078125/0.001/0.004999/0.005/0.009999` 美元 × 倍率 1/2/1000，断言不出现“真实成本 > 0 但 `charged_cents=0`”，并断言主站 nanos 原值未被截断。
- **本地钱包下限与最大请求成本必须前置**：当前本站钱包预检只要求 `localCents > 0`（`main.go:3010-3018`），而 `PrepareDirectSettlement` 以 `MaxRequestCostCents` 作为预留（`store.go:2618-2642`）；结算时 `debitUserUsageTx` 又把负余额截断为 0（`store.go:2937-2940`）。结果是用户只剩 1 分也能发起、并被允许透支到 0，超出部分不再收费。必须二选一：预检要求 `localCents >= 预计用户扣费`（或至少 `>= MaxRequestCostCents` 的可配置上限），或把结算改为欠款/冻结状态并显式阻断后续请求（欠款必须写入与站点退款“未消费额度/欠款”同一套负债账本，不得另建第二种欠款口径）；不得用“扣到 0”当结清。补测试：钱包 1 分 + 请求预计 100 分 → 请求前 402；并发两请求不得各自通过同一份余额；结算超过余额时不得静默写成功全额。
- **本站钱包与主站订阅必须互斥，不能只靠 Payer 头假设**：AgentAPI 在本站钱包模式只发 `X-Sub2API-Payer`（`main_client.go:977-990`），不发 `X-Sub2API-Group-ID`；主站则以 Key 自身 `group_id` 决定 `IsSubscriptionBill`（`sub2api/backend/internal/service/gateway_usage_billing.go:841`、`repository/api_key_repo.go:890-933`），订阅分支优先于 Payer 余额（`:313-329`）。若终端用户主站 Super Key 恰好绑定订阅组，模型请求会同时消耗主站订阅额度、并被本站钱包再次扣费；若 Key 无组但用户有订阅，当前主站又会落余额扣 Payer。AgentAPI 不能假设“发 Payer 就代表余额唯一账本”。固定策略：主站在预检快照中返回显式 `ledger_mode/charge_subject`；AgentAPI 仅在 `ledger_mode=balance` 且 `charge_subject=Payer` 时扣本地钱包并转发 Payer。若解析出唯一有效订阅，主站必须对“订阅事实 + 非本人 Payer”返回 403 `SUBSCRIPTION_ACTIVE`，AgentAPI 原样透传并终止，不扣本地、不扣订阅、不扣 Payer、不写成功 usage。不得先扣本地再按主站结果改判，也不得把订阅优先静默当作已收费。验收：用户有 1 条订阅时发送站点钱包请求，主站 403 且本地/订阅/usage 均无资金效果；无订阅时只扣 Payer 与本地各一次；订阅到期后重试按余额分支只扣一次。
- **站点支付开关、`payment_config.enabled` 与租户 `BillingMode` 必须只由一个权威派生**：`stationBillingPolicy`（`station_billing.go:1717-1726`）只看 `station_payment_settings.enabled`，一旦启用就 `BillLocalWallet=true`，模型请求据此外扣本地钱包并向主站声明 Payer（`main.go:3003-3020`）；`tenantBillingMode` 读 `agent.BillingMode`（`main.go:2419-2425`），用于充值、支付回调与余额展示；公开 `payment_enabled` 又单独读 `payment_config.enabled && BillingMode != user_upstream`（`main.go:1616-1617`）。三条写入路径并非同一事务：`SaveStationPaymentSettings` 会同步 `station_payment_settings` 与 `agent_config.billing_mode`（`station_billing.go:160-226`，已有原子测试），但旧 `paymentAdminConfig` 先 `UpdatePaymentConfig` 再 `SetBillingMode`（`main.go:2548-2560`），第二步失败会留下“支付开、模式仍旧”的持久分叉；`payment_config.enabled` 与 `station_payment_settings.enabled` 也可各自独立变化。后果不是“模型免费”：`owner_upstream` 且站点支付关闭时 `stationBillingPolicy` 返回 `BillLocalWallet=false`，请求仍由主站按终端用户余额/订阅扣款，只是本地不预检、不扣本地钱包、不代付，用户可继续花自己的主站余额并把客户价格与站长额度口径分离。必须让三者同源：由同一份服务端计费快照派生 `BillLocalWallet`、`BillingMode`、充值/Webhook/余额展示与公开 `payment_enabled`；跨表写入必须单事务或可补偿，读取冲突时 fail closed。补测试：四种组合（站点支付开/关 × 模式两种）加旧支付配置写入失败注入，断言只有一套账本，且不存在“支付开但模式未同步”的持久状态。
- 本站钱包模式下预检余额必须按 Payer：User 余额 0 + Payer 有余额不得因 User 余额被拒；User 有余额 + Payer 不足必须在请求前拒绝，不能等后扣透支。预检与后扣必须同一主体、同一金额口径。
- **本站钱包模式下预检、主站扣款、本地钱包扣款、缓存与低额通知必须共用同一资金主体**：主站当前 `CheckBillingEligibility` 在非订阅模式只查 `user.ID`（`sub2api/backend/internal/service/billing_cache_service.go:735-777/879-897`），DB 却按 `PayerUserID/PayerCost` 扣款（`usage_billing_repo.go:181-190`），缓存与通知又按 `User/ActualCost`（`gateway_usage_billing.go:453/459-484`）；legacy `postUsageBilling` 完全不读 Payer（`:135-159`）。AgentAPI 本站钱包模式下 `Payer=站长`、`User=终端用户`，会在预检、主站扣款、Redis 余额视图、低额通知之间产生四种口径。必须要求主站在请求开始时冻结唯一的 `BillingSubject{UserID, PayerUserID, ChargeAmount, LedgerMode}`，AgentAPI 也以同一快照核对响应；预检只检查最终可扣主体，Payer 不足必须请求前拒绝，不得“预检 User、后扣 Payer”。AgentAPI 本地钱包扣款仍是独立账本，不得因主站按 Payer 扣款就再扣用户主站余额；本地扣款金额用本站快照倍率计算，主站扣款金额用 Payer 快照，两者必须能在同一 `request_id` 下逐项对账。补测试：User 余额 0 + Payer 充足 → 主站只扣 Payer 且本地只扣一次；User 充足 + Payer 不足 → 请求前拒绝、本地不扣、不写成功 usage；主站强制 legacy 路径时不得改扣 User。
- **异常金额与缺失钱包不得被当作免费**：`FinalizeSettlement` 把负 `actualCents` 截断为 0（`store.go:2800-2802`），`debitUserUsageTx` 在本地钱包行不存在时直接 `return nil`（`store.go:2930-2933`），`stationChargeCents` 对 `actualCents<=0` 返回 0（`:2907-2916`）。因此“上游返回负成本”“用户钱包行被删/未建”“charged>0 但无任何 `user_consume` 流水”都可能被写成 `confirmed` 成功。必须 fail closed：负/非有限成本、应扣金额大于 0 但钱包行缺失、确认成功却查不到对应扣款流水，一律进入 `pending` 人工复核或显式错误，不得确认；补测试覆盖负 `actual_cost`、缺钱包行、扣款流水缺失与重复 finalize。
- **收费上限必须作用于客户扣费金额，而非上游 actual**：`main.go:3197`/`:3523` 只比较 `usage.ActualCents > MaxRequestCostCents`；随后 `store.go:2817` 的 `stationChargeCents` 还要乘 `ModelRateMultiplier`，配置允许到 1000（`station_billing.go:744-747`）。上游 actual 100 分、倍率 1000 的请求能通过上限校验，最终 `charged_cents=100000`；`debitUserUsageTx` 把余额截断为 0（`store.go:2937-2940`），超出部分静默消失。`PrepareDirectSettlement`（`store.go:2618-2654`）在本站钱包模式下只写 settlement 行，不预扣本地钱包，`reserved_cents` 只是快照；`FinalizeSettlement` 的超额检查（`store.go:2841-2843`）又只在 `hasLocalReservation` 为真时生效，本站钱包直扣路径永远不触发。必须统一到客户扣费口径：上限校验用 `charged = stationChargeCents(actual, rate)`，预估预扣至少 `ceil(MaxRequestCostCents * rate)`（或按模型/请求类型报价），余额不足请求前 402；结算 `charged > 可扣额度` 必须进入人工复核或欠款冻结，不得截断。补测试：倍率 1000、上游 actual 1/50/100 分、本站钱包 1/100/100000 分，断言不出现“charged 超额度却 confirmed”。
- **直扣路径的异步确认不得绕过收费上限**：`MaxRequestCostCents` 当前只在同步非流式 `main.go:3197`、流式 `:3523` 与后台对账 `:3639` 检查，且后两处都带 `HasLocalReservation` 条件；图片轮询 `:3328`、视频轮询 `:3385`、过期图片 `:455`、过期视频 `:392` 也只检查 `settlement.HasLocalReservation && actual > settlement.ReservedCents`。`PrepareDirectSettlement` 不产生 `reserve:` 流水（`store.go:2618-2654`），所以本站钱包直扣的异步任务 `HasLocalReservation=false`，这些入口会直接把任意大的 `usage.ActualCents` 写成 `confirmed`，再在 `debitUserUsageTx` 中把余额截断为 0。必须把上限校验抽成与同步路径同一函数，按“是否本站钱包计费”决定是否生效，不再以 `HasLocalReservation` 代替账本判断；在确认 `confirmed` 前统一比较 `stationChargeCents(actual, snapshotRate) > 可扣额度` 或 `> MaxRequestCostCents`，超限写 `pending` 并告警。补测试：直扣 settle 的图片/视频任务 + `actual=上限+1` → 轮询/过期/对账均不确认、不扣款；同步直扣与异步直扣在相同 actual 下结果一致。
- **主站 usage 键含未发送的 `client:` 前缀，AgentAPI 用裸键必然查不到**：主站 `resolveUsageBillingRequestID`（`sub2api/backend/internal/service/gateway_usage_billing.go:206-226`）优先使用 `ctxkey.ClientRequestID` 并写成 `client:<id>`；`ClientRequestID` 中间件在请求未带 `X-Client-Request-ID` 时生成随机 UUID（`middleware/client_request_id.go:19-45`）。AgentAPI 的 `OpenModelResponse` 只发 `X-Request-ID`（`agentapi/backend/main_client.go:992-994`），从不发 `X-Client-Request-ID`，所以主站 usage 的 `request_id` 几乎总是 `client:<uuid>`，而 AgentAPI 之后用 `chargeID` 精确查询（`main.go:3625`、`:3271`）永远命中不了。必须让两端共享同一稳定键：非强制键路径可由 AgentAPI 发 `X-Client-Request-ID: <chargeID>`（同步、流式；图片/视频仅当主站最终键确为 `client:<id>` 时成立），并且主站 `ClientRequestID` 中间件必须新增“读取该请求头”的逻辑——当前它只读 context 值，缺省直接生成 UUID，从不解析请求头（`middleware/client_request_id.go:19-45`），因此只改 AgentAPI 发送端无效。接收时只能对已验明 `agentapi` 应用凭据 + slug 的卫星请求启用，并做长度/字符校验；普通客户端或普通卫星不得通过该头控制计费去重键，避免重放键碰撞。若产品不接受该头，则主站必须提供按 `X-Request-ID`/上游任务 ID 反查的接口。禁止靠 `local:`/`client:` 前缀猜测。补端到端测试：AgentAPI 同步请求与非强制键异步任务能按发送的键查到 usage；视频等强制键任务必须按主站最终键（如 `grok-video:<task>`）回写后才能命中，仅发送客户端键不得视为已对账。故意漏发稳定键时必须失败告警，而不是静默永久 pending。**主站门禁未落地前，AgentAPI 只能把本地结算保持 `pending` 并进入对账，不得宣称“同一任务只扣一次”或据本地 `chargeID` 确认已结算。**

- **请求身份必须来自短期用户绑定断言，不能来自裸 `On-Behalf-Of`（S2A-07 迁移口径）**：过渡期当前仍用 `X-Sub2API-On-Behalf-Of` 表示请求用户（`main.go:3004-3008/3127/3316/3373/3467/3590-3629`），但它只是迁移期兼容头，不得作为生产身份依据或租户隔离已完成证据。S2A-07 落地后，请求身份必须由卫星服务端签发的短期、可验证、可撤销、不可重放的用户断言解析；裸 `On-Behalf-Of` 必须仅在显式调试开关下保留且默认关闭。无论哪一阶段，`ProxyMainUserID`（usage/余额查询与请求主体）必须与 Payer（扣款主体）严格分离：usage 按请求用户查询，Payer 只用于金额与扣款；若断言与 Payer 都缺失、冲突或无法验证，必须 fail closed。补测试：裸头被禁用时请求 4xx；只改 `On-Behalf-Of` 不能切换租户或读取他人 usage；断言过期/重放/错误 aud 被拒；Payer≠User 时 usage 归属仍为请求用户。

- **终态 settlement 不得被重放覆盖首次 usage 快照**：`FinalizeSettlement` 对已终态记录执行“同状态 + 同 usageID + 同金额”重放时，仍调用 `updateSettlementUsageSnapshot` 覆盖 `main_usage_snapshot`（`store.go:2813-2830/2951-2960`；同片段还把负 `actualCents` 截断为 0（`:2798-2801`），不得作为“合法零成本”依据）；任何调用方只要重复传入同一 usageID、但快照被重建或字段漂移，就会把首次权威快照改成后到版本，破坏 first-write-wins 与“只按首次金额/主体复算”。必须二选一并固定：已终态且已有非空 `main_usage_snapshot` 时只做校验、不写回，快照任一字段不一致即冲突/待人工复核；或给快照写入增加 `main_usage_snapshot IS NULL` 条件并保留原值。验收：先以完整快照确认，再用同 usageID、同金额但 `api_key_id`/`payer/charged_cost` 不同的快照重放 → 不覆盖、状态与快照保持首次值并报冲突；快照为空的历史终态行补写一次成功后，后续重放不再改变。
- 本站钱包 + 主站目标用户存在有效订阅：必须按主站 S2A-02/S2A-09 冻结的“用户全部有效订阅”口径确认：0 条走余额，1 条时命中订阅；2 条及以上请求前拒绝。1 条命中时主站必须在扣款前拒绝代付，AgentAPI 不得把该错误吞成成功，也不得继续扣本地钱包。不得假设“实际调度组”一定存在或等于请求头 `X-Sub2API-Group-ID`，也不得把多订阅错误当普通余额不足处理。主站若返回 `IsSubscriptionBill=true` 但订阅为空/归属不符，本站必须按业务错误处理，不得把它当余额请求重试。
- 账本分支透传：主站返回 `MULTIPLE_ACTIVE_SUBSCRIPTIONS`（或未映射时的 403 `billing_error`）时，本站必须保留原错误、不扣本地钱包、不写结算成功、不自动换 Key 或降级余额重试；主站返回 `IsSubscriptionBill=true` 但订阅为空/归属不符时同样按业务错误终止。必须补“主站 403 多订阅 → 本地 0 扣款 0 结算”测试。
- **非流式与流式结算都不得用余额差额冒充权威用量**：两条路径在取不到主站 usage 时，都会以 `before-after` 余额差写入 `user_balance_delta_fallback` 并 `confirmed`（非流式 `main.go:3211-3251`、流式 `:3531-3556`）。该差额可能受其他并发消费、充值、站长余额变动影响，不能作为用户扣费依据；收费文档也明确“未确认用量保持待确认，不用余额差额估算”。必须删除该 fallback 或改为仅写 `pending` 且进入对账，不得确认扣本地钱包。补测试：主站 usage 暂不可见 + 余额发生变化 → 本地不扣费、状态仍 pending；usage 恢复后只按权威金额结算一次；`AGENT_MAIN_USAGE_API=false`、旧主站 `/v1/sub2api/usage` 返回 404、或 usage 行缺少主站 `api_key_id` 快照时，同步、流式、图片/视频轮询、过期任务与 `reconcileTenantSettlements` 均不得进入 `user_balance_delta_fallback`，只能保持 `pending` 并标注 `legacy_usage_unavailable`（或无该能力时请求前拒绝本站钱包收费），不得出现同步确认、异步挂起的双语义。 `mainUsageForRequest` 在旧主站不提供 usage 接口时返回 `available=false`，当前非流式/流式会走余额差 fallback，而视频/图片失败任务与 `reconcileTenantSettlements` 则保持 `pending`；同一 `available=false` 不得出现“同步确认、异步挂起”两套语义。要么旧主站也统一挂起并标注 `legacy_usage_unavailable`，要么明确禁用本站钱包收费并要求升级主站，不得用差额兜底。
- **上游非 2xx 不得直接释放预留，`released`/`reversed` 也必须有权威 usage 或明确未扣证明**：当前同步非流式与流式在 `status < 200 || status >= 300` 时，只对 429/5xx 保持 `pending`，其余 4xx 直接 `FinalizeSettlement(..., "released", 0, ...)`（`main.go:3138-3152`、`:3477-3497`）；但主站鉴权通过后的 4xx 仍可能已记录失败尝试、已扣订阅/配额，或流式响应已开始后断开，不能仅凭 HTTP 状态断言“未扣款”。同时 `FinalizeSettlement` 对 `released`/`reversed` 与 `confirmed` 走同一退款路径，只按 `record.ReservedCents - chargedCents` 退本地预留（`store.go:2866-2874`），不校验 usageID、主站 usage 或主站扣款结果；`released` 传入 `actualCents=0` 会把全部预留退回，`reversed` 若误传正实际额则会少退/多退。必须把“上游非 2xx”统一视为“结果不确定”：先按同一 `request_id + 主站 api_key_id` 查询权威 usage；只有同时满足“主站未产生任何扣款效果”与“本地预留未对应任何已发生用量”时才可 `released`：可用证据为 `request_admission=rejected_before_upstream` 且 `dispatch_state=not_started`（须由写出点事件证明，不得仅凭时间戳为空；明确在调用上游前拒绝），或成功 usage 行明确为零客户扣款：`billing_subject=free` 且 `ActualCost=0` 且 `TotalCost=0`；`request_admission=not_seen/accepted/unknown` 或 usage 0 行均不等同“未受理”，必须保持 `pending`；`billing_subject=subscription` 且 `charged_cost=0` 只能证明主站未扣客户资金，不能单独证明本站未扣本地钱包，必须同时有非空 `subscription_id`、明确 `subscription_cost`（零成本为 `0`）、无余额实扣证据（usage 行 `billing_subject=subscription` 且 `charged_cost=0`，并确认主站资金流水无该 `request_id + api_key_id` 的余额扣减；不得单凭 `charged_cost=0` 反推），并证明本次未产生本地 settlement 或本地快照倍率扣费为 0；缺任一主体/金额事实时保持 `pending`/人工复核；五类额度可能已按 `ActualCost` 记账，不构成“客户被扣资金”，不得因额度变化误释放或误挂起；若只是订阅命中且主站 `charged_cost=0`，不得把已用请求当成“未发生”，也不得在本站自动另扣一次；必须按快照策略处理：策略为拒绝站点钱包代付时本不应进入结算，已发生则转人工复核；策略为允许本地计费且本地确有 settlement 时，按 `stationChargeCents(actual_cents, 快照倍率)` 与该 settlement 对账，只有证明本地未扣才可释放。其余情况保持 `pending`/待对账。`released` 只允许“确认未扣费”的终态并退还全部预留；主站 `request_admission=rejected_before_upstream` 必须先同时返回 `funds_effect=none`，否则不得释放；`quota_effect=changed/unknown` 不阻断本站释放，但不得因主站额度变化改扣本站钱包；释放不等于可免费重跑，若随后自动重发或免费处理，仍须 `quota_effect=none` 或完成额度冲正，`reversed` 只允许“已确认扣费后用反向流水冲正”，必须携带原 usage 与金额，禁止把 `released` 与 `reversed` 混用；两者都必须写唯一流水、重复调用不改变余额。补测试：主站返回 400/401/403/404/409/422 且 usage 不可见 → 不释放、不扣本地钱包、保持 pending；usage 明确 `free` 且 `ActualCost=0` 且本地无 settlement → 只释放一次；订阅 `charged_cost=0` 但本地已结算 → 不得 released，须对账/人工复核；订阅 `charged_cost=0` 且本地无 settlement → 可释放但需记录两条事实；usage 有正扣费 → 不得 released；流式已开始后中断 → 不释放；`released` 重放/`reversed` 重放/两者交叉均不二次退款。
- **本站钱包模式的 `chargeID` 必须由服务端身份派生，客户端键不得跨用户共享结算身份**：当前 `chargeID := requestIDFrom(r, nil)`（`main.go:2997`）优先采用客户端 `Idempotency-Key`，仅在 `billingMode == "user_upstream"` 时才把它与 `agentID/proxyUserID` 做哈希（`:3021-3029`）；本站钱包模式下客户端可直接决定全局 `(agent_id, request_id)` 主键。结果是：同一租户内 A 用户猜/复用 B 已用键时，`PrepareDirectSettlement` 命中既有行并走 `writeSettlementReplay`（`:3102-3113`、`:3320-3330` 附近），B 的键被占用、A 的请求被拒绝；若键碰撞跨租户则由 `agent_id` 隔离，但同租户仍无归属校验。必须把 `chargeID` 固定为 `hash(agent_id, proxy_main_user_id, agent_api_key_id, client_key)`（或等价的不可逆命名空间键），在本站钱包与 `user_upstream` 两种模式统一派生；`Prepare*` 幂等命中还必须校验 `proxy_main_user_id/agent_api_key_id` 与当前请求一致，不一致返回冲突，不得仅凭 `request_id` 重放。客户端键只允许作为同一用户同一 Key 的重试标识，长度/字符集校验后使用；不得直接作为 `settlements.request_id`、usage 查询键或跨用户去重键。派生后的 `chargeID` 必须同时用于本地 settlement `request_id`、转发主站的 `X-Client-Request-ID` 与后续 usage 查询；不得本地用哈希键、主站仍发原始客户端键，否则同步/异步都无法按同一键查回。视频等强制键仍按主站最终键回写，派生只作用于非强制键范围。补测试：A/B 同租户使用同一 `Idempotency-Key` → 生成不同 `chargeID`、各自只扣一次；A 用 B 的键不得命中 B 的 settlement；同用户同 Key 重试 → 命中同一 settlement 且只转发一次；同用户换 Key 同键 → 冲突。
- AgentAPI 的本地钱包扣款与主站 `Payer` 扣款必须共用同一 `request_id`，可在两侧用同一 usage 复算；本地 `reserve/consume/refund` 与主站 usage 只能各记一次。
- **对账必须覆盖资金主体与额度主体，而不是只比余额**：主站当前余额按 `(PayerUserID, PayerCost)` 扣，但 Key 配额、限流、账号配额与平台配额仍按请求用户/`ActualCost` 计（`gateway_usage_billing.go:120-130`、`:186-188`/`:331-339`/`:405-407`，`usage_billing_repo.go:181-218`）。AgentAPI 本站钱包 + Payer≠User 时，本地以站点倍率扣终端用户，主站以 Payer 扣上游成本，若对账只校验余额差额会漏掉“终端用户 Key 配额被扣而 Payer 额度未计”或“Payer 平台配额按终端用户累计”。主站必须按 S2A-09 返回账本分支/订阅快照，并按 S2A-08 返回 typed 金额与额度字段：`api_key_id`（主站 `usage_logs.api_key_id`，非本站 `agent_api_key_id`）、`account_id`、`subscription_id`、`billing_subject`、`payer_user_id`、`charged_cost`、`api_key_quota_cost`、`api_key_rate_limit_cost`、`account_quota_cost`、`platform_quota_subject_user_id`、`platform_quota_platform`、`platform_quota_cost`、`subscription_cost`，以及对应 `*_usd_nanos`/定点十进制。AgentAPI 对账逐项比对，任一缺失或口径不一致即保持 `pending`/报错，不得只比 `actual_cost` 或本地余额差。Key 额度按 `ActualCost`，不得按 `PayerCost`；账号配额仅对 `APIKey`/`Bedrock` 类型账号按 `TotalCost * AccountRateMultiplier`，其他类型 `account_quota_cost=0` 且不写账号配额；平台仅在余额模式按资金主体与 `charged_cost`。补测试：本站钱包 + Payer≠User 的同步与异步任务，主站 usage 与本地 settlement 能逐项复算五类金额；失败尝试查询补 0 行/多行/重复 `attempt_no` 三种断言（均不得确认或产生本地扣款）；Key 配额、平台配额任一不一致时不得确认；佣金 0 表示 Payer 承担全额（`charged_cost=actual_cost`），不是零扣款；订阅行才是“成功但未扣客户资金”的合法零扣款（`billing_subject=subscription`、`charged_cost=0`）；`billing_subject=free` 仅表示 `ActualCost=0` 且 `TotalCost=0` 的正常成功行，五类额度均为 0；若客户报价为 0 但上游 `TotalCost>0`，必须按余额/订阅免费策略核对，`APIKey`/`Bedrock` 账号配额仍按 `TotalCost * AccountRateMultiplier` 独立复算，不得写成 free；完全不计费的旁路不得伪装成 usage 行。若未来显式开放 100% 抽成，`billing_subject=balance` 且 `charged_cost=0` 也必须与历史 `NULL` 分开判定，并断言主站未按 `PayerCost > 0` 回退成对 Payer 扣 `ActualCost`；`usage_billing_repo.go:183-189` 的该回退缺陷必须以仓储测试锁定。
  - **金额精度必须是 nanos/定点，不是分**：主站 `UsageBillingMonetaryScale=8`（`sub2api/backend/internal/service/usage_billing.go:63-77`），`billing_usage_entries.delta_usd` 仍是 `DECIMAL(20,10)`（`migrations/027_usage_billing_consistency.sql:38-57`），而 AgentAPI `nanosToCents` 四舍五入到分（`main_client.go:894-898`）、`stationChargeCents` 对 `actualCents<=0` 返回 0（`store.go:2907-2916`）。对账时不得先把主站金额降到分；必须优先使用主站返回的 `actual_cost_usd_nanos/charged_cost_usd_nanos/...` 或定点字符串，比较前统一同一刻度。只有写入本地 `*_cents` 账本、`stationChargeCents` 计算本站用户扣款、`reserved_cents/charged_cents` 落库时才允许换算为分；当前规则固定为“倍率量化 6 位后对分金额向上取整”（`scaled=round(rate×1e6)`、`charged=ceil(actualCents×scaled/1e6)`，见 `store.go:2907-2916`），并须把原 nanos、量化倍率、取整方式与结果作为版本化快照保存（当前 `settlements` 仅有 `station_rate_multiplier`，`store.go:546-566` 未保存原 nanos 与规则，属待实现项，不得据此宣称已可复算）；主站金额与本地分账的差额必须显式可解释，不得把 `0.004999` 与 0 当成相等。
  - **亚分与 100% 抽成用例**：`actual=0.000078125`、`0.004999`、`0.005`、`0.009999`，倍率 1/2/1000；断言主站 nanos 原值不被截断，`charged_cost != actual_cost` 时逐项对账，订阅 `billing_subject=subscription`、`charged_cost=0` 时，只有 `subscription_id` 非空且 `subscription_cost=ActualCost`（`ActualCost=0` 时为 `0`）才可确认，缺主体/金额保持 pending；`free` 仅 `ActualCost=0` 且 `TotalCost=0`，五类额度均为 0；客户报价 0 但上游 `TotalCost>0` 必须按余额/订阅免费策略核对，不得当成 `free`；完全不计费的旁路没有 usage，不得按零扣款确认，未来 100% 抽成 `billing_subject=balance` 且 `charged_cost=0` 不得误判为未结算或免费。`stationChargeCents` 也不得把正成本算成 0 后成功确认；若采用 1 分起扣，必须记录原 nanos 与取整规则。
- **主站 usage 若不含 typed 快照，AgentAPI 不得确认结算**：当前 `usage_logs` 无 `payer_user_id/charged_cost` 列，`/v1/sub2api/usage` 只返回请求用户视角的 `actual_cost` 与浮点字段（`sub2api/backend/internal/handler/gateway_satellite_balance.go:65-120`），因此本站钱包 + Payer≠User 时无法从主站权威行复算“谁被扣了多少”。S2A-08 已要求新增迁移字段并在 usage 返回；AgentAPI 对账必须把 `payer_user_id`、`charged_cost`、`billing_subject`、五类额度主体/金额与对应 `*_usd_nanos`/定点十进制作为必需字段：任一字段缺失、`null`（历史/未快照）或与本地 `settlement` 的付款主体/金额不一致时，状态必须保持 `pending` 或显式失败，不得按 `actual_cost`、余额差或本地快照“补猜”后确认。不得用 `quota_subject_user_id` 这类泛化字段代替 Key/账号/平台主体判断。 同一判定还必须校验主站 `api_key_id` 与 settlement 的主站 Key 快照：usage 行未返回主站 `api_key_id`、快照为 `NULL`、或行内 Key 与首次命中不一致时，不得确认；不得改用本地 `agent_api_key_id` 或首行。
  - **usage 查询结果不得替代资金扣款证据**：主站 usage 命中且快照一致只证明“计费已完成、金额与主体可复算”，不能证明 Payer 余额实际减少、Payer 从未被重复扣、或平台配额已持久累计；本地 `confirmed` 仍须由资金流水与本地钱包/额度快照共同支撑。若 Payer 扣款分支被 `BalanceCost=0` 跳过、缓存/通知与 DB 主体不一致、或平台配额只写 Redis，则即使 usage 行存在也必须保持 `pending`/人工复核，不得据 usage 反推“已扣款”。验收：分别伪造“usage 一致但 Payer 余额未变”“usage 一致但 charged_cost 与平台配额不符”“usage 一致但只有缓存流水”，三条均不得 `confirmed`。
  - `charged_cost=0` 只在订阅（含零成本订阅）、`free`（仅 `ActualCost=0` 且 `TotalCost=0`）、客户报价 0 但上游 `TotalCost>0` 的余额/订阅免费策略行（保留账号配额），或未来显式开放的 100% 抽成余额行上合法；必须与 `charged_cost IS NULL`（历史/未快照）区分。不得把合法 0 判为“未结算”，也不得把 `NULL` 判为“已结算”，更不得把佣金 0 的余额行当成零扣款。
  - 同步、流式、异步任务与后台 `reconcileTenantSettlements` 必须共用同一判定函数；只有主站行包含完整 typed 快照且与本地 `request_id`、**主站 `api_key_id` 快照**、`payer/amount` 全部对齐时才允许 `confirmed`；不得用本地 `agent_api_key_id` 代替主站 Key。补测试：旧主站无快照字段 → 保持 pending；历史行 `null` → pending/人工队列；订阅行 `billing_subject=subscription` + `charged_cost=0` 时，只有 `subscription_id` 非空且 `subscription_cost` 有明确值（零成本为 `0`）才可确认、本地流水为 0，缺任一字段保持 pending；`billing_subject=free` 仅 `ActualCost=0` 且 `TotalCost=0` 可确认且五类额度为 0，不得替代缺失的订阅主体；佣金 0 的代付行 `charged_cost=actual_cost` → 不得当零扣款；快照金额或 payer 不符 → 不确认、不二次扣本地钱包；`actual=0.004999` 等亚分值与主站 nanos 不等时不得因四舍五入到分而误判相等。
- **Google/Gemini 入口不得静默绕过本站钱包代付**：`api_key_auth_google.go` 在卫星认证后只解析 `X-Sub2API-Group-ID` 与 SuperKey 组，完全没有读取 `X-Sub2API-Payer` / `X-Sub2API-Commission-Rate`（`api_key_auth_google.go:63-161`，对比主入口 `api_key_auth.go:209-218`）。本站钱包模式下 AgentAPI 会发送 Payer，但走 Gemini 入口时主站按 `apiKey.User` 全额扣终端用户，同时 AgentAPI 又扣用户本地钱包，形成双重扣款；若用户主站余额不足还会在代付场景下误拒。该入口必须消费同一服务端付款快照：0 条订阅时按 Payer 扣一次；唯一订阅 + 非本人 Payer 在扣款前 403 `SUBSCRIPTION_ACTIVE`；多条按 `MULTIPLE_ACTIVE_SUBSCRIPTIONS` 拒绝。不得静默忽略付款头后按 User 全额扣费，也不得保留“扣 Payer 或拒绝”二选一。补测试：AgentAPI 本站钱包 + Payer≠User 的 Gemini 请求分三组：0 条订阅时主站只扣 Payer 一次且本地只扣一次；唯一订阅时 403 `SUBSCRIPTION_ACTIVE`，主站、本地与订阅额度均不变化且不写成功 usage；2 条及以上按 `MULTIPLE_ACTIVE_SUBSCRIPTIONS` 拒绝。
- **同一笔站点支付只能产生一份可用余额，回调与人工分配必须走同一账本**：`creditStationUserRecharge` 先 `CreditUserRecharge` 记本地钱包与 `user_recharge`（`store.go:1543-1575`），成功后 `AdminAddUserBalance(ctx, order.MainUserID, ...)` 又给同一终端用户加主站余额（`main.go:2194-2203`、`main_admin_users.go:90-113`）。这不是“先扣站长再记本地”，而是同一笔钱同时变成可用本地钱包和可用主站余额，形成双份购买力；若第二步失败，本地已 `allocated` 且可消费，重试又因 `payment_events` 已存在、订单状态已是 `allocated` 而不再补主站加款（`main.go:2174-2191`、`store.go:1967-1980/1569-1573`），形成永久无锚增发。人工分配路径却走 `syncAndAllocateRechargeOrderForTenant → AllocateRechargeOrder`，只记本地钱包并扣减 `agent_wallets`（`main.go:3773-3795`、`store.go:2043-2109`），与回调路径的资金效果不同；同一订单经不同入口会产生不同余额。`AdminAddUserBalance` 也未发送 `Idempotency-Key`（`main_admin_users.go:98-106`），主站 `UpdateBalance` 的幂等仅在带键时生效（`sub2api/backend/internal/handler/admin/user_handler.go:403-416`、`service/idempotency.go:217-229`），超时重试可重复加主站余额。必须二选一并写死：若站点钱包是唯一可用余额，回调不得再给终端用户加主站余额；若主站余额是唯一账本，则不得先记本地钱包。无论选哪种，回调与人工分配必须共享同一幂等键、同一账本转换和同一失败补偿；主站加款必须携带由订单号派生的 `Idempotency-Key`。补测试：主站加款成功但响应丢失后重试、第二步失败后重试、同一订单分别走回调和人工分配，断言最终只有一份可用余额且两侧流水可一一对应。
- **站点网关充值/退款必须有上游资金锚定，不得只扩本地钱包**：`settleStationOrder`（`station_payment_reconcile.go:57-69`）支付完成后只调用 `CreditUserRecharge` 增加本地用户钱包，不调整 `agent_wallets.available_cents/allocated_cents`；`station_payment_refund.go:48-87` 的退款只预留/扣减本地用户钱包，也不调整站长可用/已分配额度。这样本地充值可无限扩表，而模型请求仍按站长主站余额扣上游成本，形成“本地可售额度 > 上游可覆盖资金”；`main.go:2071` 的下单提示“只在验证回调与 owner-balance 同步后分配”也与该路径不符。必须明确并强制资金锚定：站点订单入账时，本地可售额度只能来自已被主站余额同步确认的 `agent_wallets` 可用额度（或显式记录现金账户 → 上游资金池的转换流水）；退款必须同时冲减锚定额度并保留可复算流水。验收断言对任意 `agent_id`：`Σ本地用户钱包可用余额 ≤ agent_wallets.available_cents + agent_wallets.allocated_cents`，且 `agent_wallets.allocated_cents + 本地待消费余额` 不超过经 `SyncOwnerBalance` 确认的上游可覆盖额度；退款后不得只冲本地钱包而保留上游资金；超额时必须拒绝入账/退款，不得仅告警。 现有退款实现进一步确认：`beginStationRefund` 先对 `agent_user_wallets` 扣减并写 `payment_refund`（`station_payment_refund.go:34-83`），`finishStationRefund` 在渠道失败时只把本地钱包加回并写 `payment_refund_reversal`（`:90-126`）；两处都不触碰 `agent_wallets.available_cents/allocated_cents`。必须同时规定：成功退款与失败退回对上游锚定额度只能各产生一次变化方向——退款成功冲减一次，渠道拒绝则恢复本地钱包且不冲减上游；不得因“先预留本地、后退回”而重复调整上游。补测试：已完成订单退款 → 本地钱包与锚定额度同向减少各一次；渠道 `REFUND_FAILED` → 本地钱包恢复、上游额度不变；重复回调/重复退款查询不产生第二次变化。
   - **退款金额的“已入账”证据必须精确绑定订单与账本**：`beginStationRefund`（`station_payment_refund.go:48-55`）用 `int64(math.Round(order.Amount*100))` 从浮点金额重建应退分额，且只按 `agent_id + main_user_id + kind=user_recharge + request_id="recharge:"+out_trade_no` 汇总 `wallet_ledger`；没有比较该流水的 `order_id` 是否等于当前订单，也没有确认该 `request_id` 唯一属于同一订单。若金额为 `0.29` 这类无法精确表示的浮点值，`Round(24.999999...)` 与账本分额可能差 1；若同订单号/同键流水被其它入口写入，汇总仍可能“恰好相等”而通过。必须：退款金额一律从订单持久的最小货币单位/定点字段读取，或用 10 进制字符串一次性解析，不得经 `float64*100` 再 `Round`；金额字段必须带 `currency` 与 ISO `minor_unit_digits`，JPY/KRW 为 0 位、KWD 等为 3 位，禁止把所有币种都当两位；`wallet_ledger` 增加/校验 `order_id`（或与订单同事务的唯一退款事实），退款前断言“该订单恰好一条 `user_recharge`、金额等于订单入账额、`main_user_id` 与订单一致”；`SUM` 命中不同 `order_id`、多行或金额不等时 fail closed，不得退款。验收：`0.29/0.57/1.01` 等浮点边界全额/部分退款与账本分额逐分相等；伪造同 `request_id` 的另一订单流水不得被当前订单认领；多行充值流水不得 `SUM` 后通过；重复退款仍不二次扣款。
- **套餐购买必须持久化不可变快照，并在下单时完成币种一致性校验**：`station_payment_plans` 只有当前价/币种/有效期（`store.go:763-779`），订单只保存 `plan_id`（`:793`）；用户下单后管理员改价/改币种/改有效期，支付成功仍按订单金额入账，但权益发放与实际购买内容无法复算。下单时必须在同一事务把 `plan_id/plan_version/name/price_cents/currency/validity_days/validity_unit/features_hash` 写入订单快照，支付与退款只读快照；`plan.Currency` 与所选渠道币种不一致时下单前 4xx，不得用 `stationGatewayAmount` 仅对 `subscription+CNY` 乘汇率后按渠道币种重算套餐价（`station_payment_routing.go:18-25`），也不得把套餐价当普通余额金额。验收：下单后改套餐价/币种/有效期再支付，订单金额、权益与退款仍按快照；异币种套餐 4xx 且不建单；重复回调不改变快照。
- **套餐权益必须落到主站订阅账本，不得在 AgentAPI 另建余额或第二套订阅**：AgentAPI 的 `station_payment_plans` 只有价格/币种/有效期，没有权益主键；主站已有 `SubscriptionService.AssignOrExtendSubscription`、管理员 `POST /api/v1/admin/subscriptions/assign` 与 `/revoke`（`sub2api/backend/internal/service/subscription_service.go:193-221/411-445`、`handler/admin/subscription_handler.go:136-160/270-283`），且主站支付履约已用“订单备注锚点 + `SUBSCRIPTION_ASSIGNED` 审计 + 事务内幂等”实现同一订单只发一次（`service/payment_fulfillment.go:584-655`）。站点套餐必须二选一并写死：①套餐直接映射主站订阅 `GroupID`，支付成功后由 AgentAPI 以 `order.ID` 派生的稳定幂等键调用主站管理员分配接口（或主站新增受信服务端履约接口），主站按 `order.ID` 写分配审计并自行校验分组为订阅类型；②产品明确不做套餐，下线 `order_type=subscription` 入口并拒绝新单。无论哪种，`subscription` 支付成功不得调用 `CreditUserRecharge` / `AdminAddUserBalance`，不得只在 AgentAPI 本地创建“订阅记录”供计费读取而主站不知情；退款只撤销该订单对应的订阅权益（按订单审计可定位、只撤一次），不得退成现金余额。验收：`subscription` 支付成功后 `agent_user_wallets.balance_cents` 不变、主站订阅对该用户恰好一条且 `GroupID/ExpiresAt` 与订单快照一致；重复回调/响应丢失重试不延长两次；主站分配成功但本地状态未提交时可恢复且不重复延长；退款后订阅失效或按产品策略保留但不得产生现金；若套餐无对应主站订阅组则下单前 4xx，不得建单。
- **AgentAPI 预检必须取得主站账本分支，不能只看本地钱包与主站余额**：本站钱包入口只检查 `UserWalletCents(...) > 0`（`main.go:3010-3018`），主站预检 `CheckBillingEligibility` 又按传入 `group+subscription` 判断，非订阅只查 `user.ID` 余额（`billing_cache_service.go:735-777/878-897`）；AgentAPI 既没有向主站请求“本次预计走订阅还是余额”，也没有在 usage 快照中要求返回该分支（`main_client.go:84-128/510-528`）。结果是本地预检通过后，主站仍可能按订阅额度或按另一主体余额扣费，预检与扣费不同源。必须二选一：主站提供只读、带请求身份的计费预检接口，返回显式的 `ledger_mode/billing_subject/subscription_id/subscription_cost/group_id/charge_subject/estimated_amount` 并持久化到本次请求快照，AgentAPI 只按该快照决定是否扣本地钱包；当 `ledger_mode=subscription` 时必须 `subscription_id` 非空、`subscription_cost` 字段存在（预检阶段可为“待定/预计值”，最终成功 usage 必须为确定数值，零成本为 `0`）且 `billing_subject=subscription`，缺任一字段或与 `charge_subject` 冲突时 4xx/503 并保持 pending，不得按余额或 `free` 放行；**不得把预检的预计 `subscription_cost` 当最终扣减额**，最终金额只能由 usage 权威行给出；`estimated_amount` 只表示预检预计值/收费上限，非空时必须与 `estimated_currency/estimate_version` 成对，不得用于扣本地钱包、释放预留或写入最终 usage，缺失时只能表示“未估算”，不能反推免费；`ledger_mode=balance` 时必须 0 条订阅且订阅主体为空/`0`；或在本站钱包入口显式要求主站返回“余额模式 + 付款主体一致”才放行，无法取得时 4xx/503，不得先扣本地再按主站结果改判。预检、代付、usage 查询必须复用同一请求快照，预检后不得重查订阅或组改判。验收：唯一订阅用户必须 403 `SUBSCRIPTION_ACTIVE` 且 0 资金变化；无组 SuperKey 与 Key 组/订阅组不一致不得改变结论；多订阅按 `MULTIPLE_ACTIVE_SUBSCRIPTIONS`（未映射时 403）拒绝；0 条订阅时只扣 Payer 与本地各一次；主站余额不足但本地充足时请求前拒绝，无法确认分支时 0 资金变化。
- **站点钱包没有币种维度，非 CNY 渠道充值必须拒绝或显式换算**：`agent_user_wallets` 只有 `balance_cents`（`agentapi/backend/store.go:495-503`），`wallet_ledger.amount_cents` 也无币种；但站点支付允许 Stripe/Airwallex 使用实例配置币种（`station_billing.go:1302-1306`），订单按渠道币种写入 `amount/pay_amount/currency`（`:1399-1421`），入账时 `settleStationOrder` 直接 `int64(math.Round(completed.Amount*100))` 加到同一个 `balance_cents`（`station_payment_reconcile.go:65-66`）。因此一笔 `USD 10.00` 或 `JPY 1000` 的支付会按数字直接变成 1000 分人民币购买力，既没有汇率也没有币种快照；前端充值页也按所选渠道币种直接允许输入，后端不做套餐/钱包币种一致性校验（`station_billing.go:1368-1400`）。必须二选一并写死：站点钱包统一为单一记账币种（默认 CNY）时，只允许该币种的渠道/套餐，发现 `order.Currency` 与钱包币种不一致必须下单前 4xx；或引入显式换算（服务端汇率快照、`amount_cents` 原币最小单位、`credited_cents` 记账币种、换算版本）并在同一订单上持久化，模型扣费与退款都按该快照复算。不得把渠道原币数字直接写入 `balance_cents`，也不得用当前汇率重算历史订单。验收：USD/JPY 订单在未配置换算时被拒绝且不建单；配置换算后 `credited_cents` 与订单快照一致、退款按同一快照反算；重复回调与汇率变更不改写已入账金额。
- **站点订单必须有 `EXPIRED` 终态与按渠道取消能力分支的过期扫描，不得让过期单永久停在 `PENDING`**：`CountPendingStationOrders` 与每日/实例限额只把“`status='PENDING' AND expires_at>now`”计入占用（`station_billing.go:566-578`、`station_payment_routing.go:42-52`），但代码中没有任何定时任务把过期订单写成 `EXPIRED`；`UpdateStationOrderStatus` 的调用点只有管理员取消、用户取消和下单失败（`station_billing.go:581-597/1108-1113/1191-1197/1433-1437`）。因此订单超时后 UI/列表仍显示 `PENDING`，用户以为还能支付，支付渠道侧也从未调用 `CancelPayment`（仓库无 `CancelableProvider` 使用点）。更危险的是站点回调与 `reconcileStationOrder` 都不拒绝过期订单：只要渠道确实扣款，系统会把一个“界面已超时、额度已释放”的订单补成 `COMPLETED` 并入账，和用户刚下的一笔新单叠加，产生超出预期的余额/套餐。必须新增站点订单过期扫描（按租约、批量、幂等），在过期时先按渠道能力分支处理：支持 `CancelableProvider` 的 Stripe/Airwallex/支付宝/微信先 `CancelPayment` 并记录结果，EasyPay 等无取消能力的渠道只能记录“不可取消、禁止自动收款”并转人工；所有渠道都要以 CAS 写 `EXPIRED`，取消失败不得阻止本地终态；回调/对账遇到已 `EXPIRED` 的订单只能进入人工复核（或按明确规则原路退款），不得静默补成 `COMPLETED`。`expires_at` 必须由服务端持久值判定，不得依赖前端倒计时。验收：过期后列表/限额/回调/对账/PENDING 扫描口径一致；渠道取消失败可重试且有审计；过期后被渠道扣款不会产生第二份可用余额。
- **渠道退款“不确定”必须有后台查询闭环，不能依赖管理员重复点击**：`refundStationOrder` 在首次请求后把未返回明确成功/失败的渠道结果写成 `REFUND_PENDING`（`station_payment_refund.go:90-98/197-203`），此后只有再次调用退款接口才会走 `RefundQueryProvider.QueryRefund`（`:191-193`）；后台 `reconcilePendingInBackground`（`main.go:325-348`）只扫 settlement、充值订单、视频/图片任务和 `PENDING` 站点订单，没有退款扫描。更关键的是只有 Stripe、Airwallex、微信实现了 `QueryRefund`（`payment/provider/stripe.go:254`、`airwallex.go:303`、`wxpay.go:478`），EasyPay 与支付宝官方没有查询实现，而对非 `QueryRefundProvider` 的订单当前直接返回 202 并保持 `REFUND_PENDING`（`station_payment_refund.go:191-195`），只能人工核对。必须二选一并写死：为所有退款渠道实现可验证的退款查询（或渠道回调）并接入后台持久扫描（按退款单租约、退避、次数上限、人工复核）；或在无法查询的渠道上禁止自动退款/明确提示“需人工确认”，不得把 202 当作成功。`RefundResponse` 目前只有 `RefundID/Status`（`payment/types.go:197-201`），没有金额、币种、订单号，无法证明渠道实际退了多少；必须扩展或以订单+退款单+渠道回执三方核对金额/币种/订单号后才能写 `REFUNDED`。验收：渠道超时/无响应/返回 pending、重启、重复点击、渠道拒绝、部分退款各注入一次，断言不会永久停留、不会二次扣款/回补、金额与订单一致才终态。
- **退款必须按持久退款单支持部分退款，并同步冲减上游锚定额度**：当前 `refundStationOrder` 只接受 `REFUNDING`/`REFUND_PENDING` 或首次全额退款，金额固定为 `fmt.Sprintf("%.2f", order.PayAmount)`（`station_payment_refund.go:187-192`），`beginStationRefund` 用 `credit = order.Amount*100` 一次性扣光用户钱包（`:48-83`），`finishStationRefund` 只把 `station_payment_refunds.state` 与订单状态改掉（`:90-132`），从不调整 `agent_wallets.available_cents/allocated_cents`。因此：① 不支持部分退款，累计退款无法表达；② 即使全额退款成功，站长可售额度与本地钱包负债也不会同步下降，生成“用户已退款但上游额度仍可用”的虚增购买力；③ `REFUND_FAILED` 回补只按 `credit_cents` 原额加回，若未来做部分退款会多补。必须新增持久退款单（`refund_id`、`refund_id_source`、`requested_cents`、`deducted_cents`、`provider_refund_id`、累计已退、`currency`、`minor_unit_digits`、状态），按退款单而不是订单状态幂等；每次退款（全额/部分）都在同一事务内扣减本地用户钱包并冲减对应锚定额度，累计不得超过实付；`REFUND_FAILED` 只回补该次未成功的预留，且回补本身也按退款单幂等。**入账与退款额度必须同源可复算**：当前 `settleStationOrder` 只 `CreditUserRecharge(completed.Amount)`（`station_payment_reconcile.go:65-66`），`agent_wallets.allocated_cents` 完全不变，因此不能只凭“本地钱包增加了本金”就断言站长已被锁定额度；若退款要冲减 `agent_wallets`，必须先补“付费订单 → 站长额度占用/释放”的持久流水（至少 `order_no/currency/principal_minor/topup_minor/offset_available/offset_allocated`），并在入账、退款、失败回补、对账四处共用同一订单快照。不得从余额差额或 `PayAmount-Amount` 临时推算额度冲减；入账没有对应占用记录时，退款只能退用户钱包并进入人工复核，不得擅改站长可用额度。验收：连续两次部分退款累计正确、余额与 `allocated_cents` 同向下降、渠道失败只回补一次、重复回调不二次变化、退款后再次分配/退款被拒；`REFUNDING`/`REFUND_PENDING` 期间并发消费必须被冻结或拒绝，退款成功后不得再消费已退额度。锚点方向必须固定为：入账时真实 `agent_wallets.available_cents` 减少、`allocated_cents` 增加，订单锚点写 `offset_allocated = principal_minor`、`offset_available = 0`；退款成功时先按订单锚点校验累计退款上限，再真实 `available_cents` 增加本次本金、`allocated_cents` 减少本次本金，并同步 `offset_available += 本次本金`、`offset_allocated -= 本次本金`；模型消费必须按订单分配顺序（FIFO，`order_no/allocated_at`）在同一事务减少 `offset_allocated` 并写消费流水；已消费部分只减少 `offset_allocated`，不得增加 `offset_available`。每次退款本金 `R` 必须满足 `R <= offset_allocated`（退款前的未消费占用），超出即拒绝或转人工，不得按当前钱包余额反推可退额。任一时刻 `offset_available`、`offset_allocated`、`consumed_minor` 均非负，且三者之和等于 `principal_minor`；`offset_allocated = topup_minor - consumed_minor`；任一 CAS 命中 0 行或越界均整笔回滚。**退款未终态期间必须冻结对应额度**：退款单进入 `REFUNDING`/`REFUND_PENDING` 后，消费分配只能使用未被该退款单预留的 `offset_allocated`；实现可以锁定同一订单锚点行、排除存在未终态退款单的订单，或写入等额冻结占用，但不得让已扣用户钱包的退款额度再次被模型消费；`REFUND_PENDING` 只表示等待渠道或人工确认，不代表额度可恢复。
- **渠道退款请求号必须由本地持久退款单派生，不能由时钟或“订单+金额”临时拼出**：退款单当前只有一条 `station_payment_refunds` 记录并按订单主键（`store.go:807-812`），`refundStationOrder` 在 `REFUNDING` 超过 5 分钟或进程重启后会对同一订单再次调用适配器（`station_payment_refund.go:140-192`），因此渠道请求号是资金安全的最后一道幂等线，但各适配器并不稳定：支付宝 `OutRequestNo` 使用 `time.Now().UnixNano()`（`payment/provider/alipay.go:341-346`），Stripe 用 `re-<order>-<minor>`（`payment/provider/stripe.go:228-236`），微信 `wxpayRefundID` 只拼订单与金额（`payment/provider/wxpay.go:461-467/511-521`），Airwallex 只含意图与金额（`payment/provider/airwallex.go:276-281`）。当前崩溃恢复路径会转入 `QueryRefund` 而非盲目重发（`station_payment_refund.go:191-193`），所以不能据此断言现网已重复退款；但一旦把“重试/人工恢复”接上 `Refund`、或对同一订单做两笔同额部分退款，渠道无法区分“同一意图重试”与“第二笔合法退款”，本地也没有任何持久字段可证明渠道侧只退了一次。必须由持久退款单生成稳定且全局唯一的 `provider_refund_request_id`（含 `refund_intent_id`、订单号、第几次退款、金额、币种），首次调用前写入，所有重试、查询、回调和人工复核复用同一值；渠道返回的退款号、金额、币种与本地退款单不一致时不得写 `REFUNDED`。验收：同一退款在渠道超时、5 分钟内/后重试、进程重启后只产生一个渠道退款；两笔同额部分退款得到两个不同渠道退款号且本地累计正确；Alipay/Stripe/微信/Airwallex 各覆盖重复点击与查询恢复。
- **退款重试只能恢复同一退款意图，不能按当前钱包重建金额**：`beginStationRefund`（`station_payment_refund.go:34-83`）当前预留/扣减本地用户钱包并写 `payment_refund`，`finishStationRefund`（`:90-126`）在渠道失败时只回补本地钱包；若进程在扣款后、渠道调用前中断，或 `REFUND_FAILED` 后再发起一次退款，必须按持久退款单（`refund_id/order_no/deducted_cents/rollback_status`）恢复，不得重新读取当时的用户余额并再次扣款。退款成功将本地与上游锚定额度各减一次；渠道失败只回滚本地；重复回调/查询只返回既有终态。验收：扣款后注入中断与渠道失败，重试及回调均不得第二次扣款/回补，审计可按退款单复算。
- **站点支付订单必须只有一张状态机，回调与人工分配不得各自定义资金效果**：当前回调入口在 `paid_pending_allocation` 时调用 `creditStationUserRecharge`，先记本地 `user_recharge` 再尝试主站加款（`main.go:2174-2203`），并把订单直接写成 `allocated`（`store.go:1569-1573`）；人工分配则走 `syncAndAllocateRechargeOrderForTenant → AllocateRechargeOrder`，先同步站长余额，再在同一事务里扣 `agent_wallets.available_cents`、增 `allocated_cents`、加用户本地钱包并写 `user_allocate/agent_allocate`（`main.go:3773-3795`、`store.go:2043-2109`）。同一订单从两个入口进入会出现“本地钱包已加但 `agent_wallets` 未扣/未加”或“主站加款失败但本地已可消费”的不同终态。必须收敛为唯一状态机并写进实现与测试：`created/pending → paid_pending_allocation → allocated`，以及 `allocated → refunding → refunded`（部分退款用累计退款额表示，不新增可绕过幂等的状态）；`failed/expired/closed` 只允许从 `pending` 进入且不得产生任何入账。每个状态下只允许下列资金动作：`paid_pending_allocation` 允许记录已验签事件与待分配金额，但不得增加任何可用余额；`allocated` 必须恰好由一次原子操作同时完成上游锚定额度扣减、本地用户钱包增加与订单状态更新；`refunding` 只允许预留退款额度、不得再次增加可用余额；`refunded` 必须同时冲减本地用户钱包和锚定额度，且累计退款不得超过实付。任何一步失败必须回滚整笔，或留下可重放的明确中间态（不得出现“本地已加、上游未扣”的 `allocated`）。回调与人工分配必须调用同一内部函数，使用由 `order_no` 派生的同一幂等键；`payment_events` 去重不能替代账本幂等。`AdminAddUserBalance`（`main_admin_users.go:90-113`）当前既不带 `Idempotency-Key` 也传 `float64` 金额，必须改为定点金额并由订单号派生稳定键，否则主站加款成功但响应丢失时无法证明只加一次。补测试：同一订单分别先走回调或先走人工分配，最终两边金额/状态/流水完全一致；在本地加款与上游扣减之间注入失败，重试后恰好一份可用余额；部分退款两次、重复回调、退款后再次分配均被拒绝且状态不变。
- **站点订单完成与钱包入账必须在同一事务，或留下可被后台重放的显式中间态**：`settleStationOrder`（`station_payment_reconcile.go:60-70`）先调 `CompleteStationOrder`（`station_billing.go:599-622`）把订单写成 `COMPLETED`，再在另一个事务里 `CreditUserRecharge`；入账失败时订单已是终态。渠道回调重试仍会再次调用 `CreditUserRecharge`（`:61-66` 未按 `created` 短路），故“有回调重试”可补账；但回调丢失后 `reconcilePendingStationOrders` 只扫 `status='PENDING'`（`store.go:3331-3336`），`COMPLETED` 未入账订单不会再被扫描，只能人工修账。必须二选一：把订单状态与钱包入账合并为一个事务；或新增 `PAID_PENDING_CREDIT`/`CREDIT_FAILED` 等显式中间态，`CreditUserRecharge` 成功后才写 `COMPLETED`，并让后台按该中间态持续重试（带租约、退避与人工复核上限）。`COMPLETED` 只能在账本幂等键 `recharge:<out_trade_no>` 已存在且金额/主体/订单号一致时出现；判定时不得只用订单状态。补测试：在 `CompleteStationOrder` 之后、`CreditUserRecharge` 之前注入失败与进程中断，断言订单不会显示为已入账、后台能重放且只入账一次；`CreditUserRecharge` 已写入账本但结算/订单状态因后续步骤失败而未提交时，重试必须按 `recharge:<out_trade_no>` 命中既有流水并补齐状态，不得二次加钱。
- **套餐订单必须发放订阅权益，且下单必须锁定套餐快照，不得只存 `plan_id` 后按金额充值余额**：`stationCheckoutInfo` 对外列出 `plans`（`station_billing.go:1204-1216`），前端充值页允许 `order_type=subscription` 并提交 `plan_id`（`AgentRechargeView.vue:230-231`），下单时后端只把 `plan.Price` 写进订单金额、`planID` 写进订单（`station_billing.go:1368-1375/1418-1422`），`station_payment_orders` 没有套餐名称/价格/币种/有效期快照（`store.go:781-804`）；管理员随后改价、下架或改币种，历史 `PENDING`/`COMPLETED` 订单无法证明购买时权益，渠道币种与 `plan.Currency` 不一致也未拒绝或换算（`:1399-1401`）；但支付成功后 `settleStationOrder`（`station_payment_reconcile.go:60-70`）与 `creditStationUserRecharge`（`main.go:2194-2203`）对 `order_type` 完全不分支，一律按订单金额调用 `CreditUserRecharge` 和 `AdminAddUserBalance`。代码中没有订阅权益表、没有按 `plan_id/validity_days` 发放的调用，也没有消费侧读取订阅的路径；结果是用户购买“订阅套餐”后得到等额钱包余额，套餐本身从未生效，且退款按同一余额回冲，权益与资金口径完全错位。必须二选一并写死：实现套餐权益账本（订单支付成功 → 同一事务/可重放中间态写入订阅记录、有效期与额度，并与模型计费读取口径一致；退款只能撤销未使用/按规则计算的权益，不得再把套餐金额当充值退款）；或在套餐未实现前从充值页与下单接口移除 `subscription`，只允许 `balance`，对历史套餐订单手工核对并禁止再创建。无论哪种，资金入账都必须先按 `order_type` 分支，`subscription` 不得进入 `CreditUserRecharge`/`AdminAddUserBalance`；`COMPLETED` 只能表示该类型订单的权益已落库。验收：购买套餐后余额不变、订阅记录与有效期正确、模型请求按套餐额度结算；重复回调/退款/部分退款不增加现金余额；`order_type` 非法或套餐下架返回 4xx 且不建单。
  - 当前套餐还缺币种一致性校验：下单直接 `amount = plan.Price`（`station_billing.go:1368-1375`），而支付网关金额按所选渠道 `limit.Currency` 换算（`:1390-1401`）；`plan.Currency` 与渠道币种不同时未拒绝、未换算、也未写入订单快照，套餐价会被当成渠道币种金额。实现权益账本时必须同时锁定 `plan.Currency/id/version/price` 快照，币种不一致直接拒绝下单，历史订单不得按当前套餐价重算。
- **站点回调与后台分配必须互斥同一 owner 资金事务**：`creditStationUserRecharge`（`main.go:2194-2203`）直接写本地钱包后调用主站加款，全程未获取 `settlement:user:<owner>` 租约；人工/后台分配 `syncAndAllocateRechargeOrderForTenant`（`:3773-3795`）与模型结算 `acquireUserOperationLease`（`:3757-3766/3804-3810`）却持有该租约。结果是“回调入账线程”和“后台同步/分配线程”可以同时读写同一 `agent_wallets`/`agent_user_wallets` 版本：后台先读 version，回调先提交，后台 CAS 命中 0 行后（若未检查 `RowsAffected`）继续写流水；即使检查了，也会把用户可观察的充值失败放大为 5xx/重试。站点入账必须与同一 owner 的所有余额变更共用同一把持久租约（或统一改成数据库行锁/CAS 重试），并在租约内完成“本地钱包 + 主站加款 + 订单状态”的全部步骤；回调不得绕过。验收：并发执行回调入账与后台分配/模型结算，断言只串行推进版本，回调不会被无谓打断，且不存在同一订单两份余额。
- **`paid_pending_allocation` 必须有独立的后台恢复扫描，且与回调共用同一原子入账**：站点钱包模式的回调在 `RecordPaymentEvent` 后调用 `creditStationUserRecharge`（`main.go:2174-2203`），该函数同时写本地 `user_recharge` 与主站加款，失败只返回 202，订单仍是 `paid_pending_allocation`；后台 `reconcilePaidRechargeOrdersForTenant`（`main.go:476-498`）虽然会扫 `PaidPendingRechargeOrders`，但它要求 `BillingMode=owner_upstream`、支付开关开启、站长 ID 与 `AppCredential` 均存在（`:478`），且只走 `syncAndAllocateRechargeOrderForTenant → AllocateRechargeOrder`（`:3773-3795`），与回调的 `CreditUserRecharge + AdminAddUserBalance` 是两套资金效果。任一前置条件不满足（如用户上游模式、支付配置关闭、主站凭据临时缺失）时，`paid_pending_allocation` 永久停留，既无告警也无人工入口；而 `PENDING` 的站点订单只按 7 天窗口扫描（`station_payment_reconcile.go:146-157`、`store.go:3331-3336`）。必须把“已验签付款、尚未入账”的订单做成独立、持续、可观测的恢复队列：不依赖当前计费模式与支付开关、不设 7 天截止、按租约串行处理、失败记录原因与重试次数并暴露给站长，超过上限进入人工复核但不得丢弃；恢复动作必须与首次回调完全同一函数、同一 `order_no` 幂等键，禁止两套入账。补测试：在 `paid_pending_allocation` 注入主站超时、主站 5xx、进程重启、关闭支付开关、切换 `BillingMode`，断言后台仍能收敛到唯一一份余额或明确待复核，不会永久静默。
- **版本/状态条件更新必须检查受影响行数，0 行不得继续写流水**：`agent_wallets`/`agent_user_wallets` 的多处资金写入都使用 `WHERE ... AND version=?` 但丢弃 `Exec` 返回结果，例如 `DebitUserUsage`（`store.go:1534`）、`CreditUserRecharge`（`:1566`）、`AllocateRechargeOrder`（`:2085/:2088`）、`SyncOwnerBalance`（`:2499`）、`PrepareSettlement`（`:2587/:2590`）、`SettleSettlementWithUsage`（`:2892/:2895`）、`debitUserUsageTx`（`:2941`）、`Allocate/Consume/Credit/CreditAgent`（`:3123/:3130/:3178/:3181/:3227/:3230/:3267`）。当前单进程只有一条 SQLite 连接（`:264`），且部署为 `restart: unless-stopped` 单容器（`docker-compose.yml:2-5`），所以正常路径不会并发写同一 version；但一旦多副本、外部维护进程或未来换库，CAS 命中 0 行仍会继续 `INSERT wallet_ledger`，把旧余额写成 `balance_after_cents`，形成“流水成功、余额未变”。必须统一封装资金与状态更新：`RowsAffected()!=1` 即视为 `version_conflict`/`not_found` 并中止整个事务，不写流水、不推进订单/结算状态；禁止忽略 `RowsAffected` 或把 0 行当成功。`SettleSettlementWithUsage` 的终态推进（`store.go:2854`，`WHERE ... AND status='pending'`）也必须以该 CAS 为门，0 行时整笔回滚，不得继续扣款/退款。补测试：注入过期 version、并发双写、钱包行被删除三种情况，断言事务回滚且余额/流水/状态均不变；多副本部署前必须把 SQLite 换成支持跨进程写锁的数据库，或明确禁止共享数据库的多副本。
- **站点下单必须持久化请求意图，并对“渠道已建单、URL 未落库”可恢复**：`handleAgentPayment` 只接收 `AgentPaymentOrderRequest`（`payment_checkout.go:68-77/253-267`），没有任何 `Idempotency-Key`/请求键；`createStationCheckoutOrder` 每次用 8 字节随机数生成新的 `out_trade_no`（`station_billing.go:1414-1417`），先 `CreateStationOrder` 落 `PENDING`（`:1428-1432`），再请求渠道（`:1433-1438`），最后才单独 `UPDATE ... pay_url=?, qr_code=?`（`:1439-1443`）。因此浏览器双击/超时重提/网络重试都会生成多个独立可支付订单；渠道建单成功后若本地 URL/QR 更新失败或进程中断，响应返回 5xx 但渠道侧已有可支付单，用户既看不到链接又可能通过渠道回调补成 `COMPLETED`，而本地 `PENDING` 扫描对这笔“已建单未回填”只能凭 `out_trade_no` 查询，无法区分“渠道未建单”和“已建单但 URL 丢失”。必须由服务端持久化下单意图：客户端提供稳定 `Idempotency-Key`（缺失即 4xx，或由服务端身份+订单类型+金额+套餐精确派生），以 `UNIQUE(agent_id, main_user_id, request_id)` 绑定订单与渠道号，命中时返回同一订单及其当前支付结果；渠道建单结果（`provider_trade_no/intent_id/pay_url/qr_code/result_type`）必须在本地订单状态机中持久化，不能只回给浏览器；渠道建单已成功而本地持久化失败时，必须能凭原 `out_trade_no` 查询渠道并恢复 URL 或取消该单，不得让重试再建第二单。`subscription` 的 `plan_id`、币种、价格快照也必须进入该请求键比较，不能只比金额。验收：双击/并发两次/响应丢失后重提只产生一个渠道订单与一个可支付入口；渠道成功后注入本地 UPDATE 失败和进程重启，断言能恢复或取消该单且不会出现第二张可支付单；不同金额/套餐复用同一请求键返回 409，不新建订单。
- **站点支付对账必须使用渠道可查询的支付意图号，不得把本地 `out_trade_no` 当 Stripe/Airwallex 的交易号**：`reconcileStationOrder` 统一以 `impl.QueryOrder(ctx, order.OutTradeNo)` 查询（`station_payment_reconcile.go:119-135`），但 Stripe `QueryOrder` 把入参当 PaymentIntent ID 调 `V1PaymentIntents.Retrieve`（`payment/provider/stripe.go:144-169`），Airwallex 同样要求 payment intent ID（`payment/provider/airwallex.go:200-219`）；而这两家的建单结果 `TradeNo/IntentID` 只放进响应（`stripe.go:137-141`、`airwallex.go:190-197`），站点订单只保存了 `provider_trade_no` 且要等 `COMPLETED` 才写入（`station_billing.go:599-622`），渠道建单成功后并不落库。结果：这两类订单在 `PENDING` 时后台查询必然失败或查不到，只能等回调；回调丢失即永久 `PENDING`，与“有后台对账”的承诺不符。必须在渠道建单成功后立即持久化 `provider_trade_no/intent_id`（与 `pay_url/qr_code` 同一状态写入），对账按渠道明确的查询键分支（Stripe/Airwallex 用 intent ID，Alipay/Wxpay/EasyPay 用商户订单号），并把查询键/渠道交易号写入审计；渠道查询返回的订单归属、金额、币种与本地订单不一致时必须 fail closed，不得据此入账。验收：Stripe/Airwallex 在无回调场景下 30 秒内可由后台查询补成一次入账；删除 intent 快照后不得误用 `out_trade_no` 查询并静默失败；伪造另一 intent 的已支付回执不得结算本订单。
- **支付回调的事件标识必须被签名覆盖，且事件去重不能只看 `event_id`**：`verifyPaymentSignature`（`main.go:2395-2408`）只对请求体做 HMAC，`X-Agent-Payment-Event-ID` 与 `X-Agent-Payment-Timestamp` 未进入签名；`handlePaymentWebhook` 又在验签前读取事件 ID（`:2109-2127`），`payment_events` 唯一键仅为 `(agent_id, provider, event_id)`（`store.go:595-608`）。这意味着同一已签名请求体只要改写事件 ID，就能写入新的 `payment_events` 行；当前因订单在首次处理后已是 `allocated`，`RecordPaymentEvent` 会在状态检查处拒绝（`store.go:1991-1992`），所以尚不能直接重复加款，但去重、审计与“同一事件只处理一次”的承诺不成立，也给未来状态机扩展留下重复入账入口。必须把 `event_id`、时间戳、订单号、金额、币种、`provider_trade_no` 纳入签名域（或采用渠道原生签名规范并记录验证版本），并在验签通过后再使用这些字段；同时增加订单级/交易号级唯一约束或状态守卫，确保同一 `order_no` 或同一渠道交易号至多产生一次入账。补测试：保持请求体与签名不变、仅替换事件 ID → 必须 401 或 409 且不新增事件/不改变订单；相同事件 ID 不同请求体 → 冲突；已 `allocated` 订单收到新事件 ID 的 `paid` → 不进入 `creditStationUserRecharge`。
- **本地钱包历史扣款接口不得把透支截断为 0 后继续成功**：`DebitUserUsage`（`agentapi/backend/store.go:1507-1540`）在 `balance - cents < 0` 时直接把 `next` 设为 0，并按“成功扣款”写 `user_consume` 流水；调用方若据此放行模型请求，就会出现“余额 1 分、消费 100 分、余额归零”的超额消费，且流水金额与实际可用资金不一致。该接口当前虽未找到调用点，但只要保留就不得作为可用的余额守卫。必须二选一并固定测试：余额不足返回 `errInsufficientBalance` 且不写流水/不改变余额；或同一事务内只扣可用余额并显式记录部分扣款/欠款状态，由调用方拒绝继续上游请求。验收须覆盖余额为 0、1 分、差 1 分三种边界，断言不存在“请求成功但钱包余额被截断为 0”的路径。
- **结算时本地钱包行缺失不得静默成功**：`FinalizeSettlement` 在本站钱包直扣路径（`BillLocalWallet && !hasLocalReservation`，`store.go:2860-2864`）调用 `debitUserUsageTx`，而后者在 `agent_user_wallets` 无对应行时直接 `return nil`（`:2930-2933`）。结果是订单/结算被写成 `confirmed`、上游成本已发生，但本地没有任何扣款流水与余额变化；若并发创建/迁移账号导致钱包行短暂缺失，也会被当作已结算。必须 fail closed：钱包行不存在时不得确认，需在同一事务内创建余额为 0 的行并按“可用余额不足”处理，或把结算置 `pending`/`awaiting_manual_review` 并告警，禁止写 `confirmed`；只有在显式免费/不扣本地策略下才可跳过。补测试：本站钱包 `chargedCents>0` 且钱包行缺失、删除钱包行后重放、并发首次建行，断言不出现“confirmed 但无 user_consume”；恢复钱包行后按同一 `request_id` 只扣一次。

### AGA-03 支付、退款、对账（P1）

**实施步骤**
1. 覆盖订单创建、支付回调验签、幂等、到账、退款、部分退款、余额更新、对账补偿。
2. 验证金额精度、重复回调、乱序回调、并发回调、取消订单和部分退款；退款累计不得超过原订单。渠道退款请求金额必须从持久化的币种与最小单位整数（或十进制字符串）生成，禁止固定 `fmt.Sprintf("%.2f", order.PayAmount)`；订单须有 `currency` 与 ISO `minor_unit_digits`，复用 `payment/currency.go` 的换算规则。渠道退 `PayAmount`、本地钱包退 `Amount` 时，差额承担方必须持久化并可复算；仅退本金则两者同用本金。**金额恒等式必须写死**：`fee_minor = pay_amount_minor - amount_minor`，且 `fee_minor >= 0`；**扣费侧必须与钱包币种同精度**：`stationChargeCents` 当前只接受 `actualCents` 与倍率、固定按“分”向上取整（`store.go:2907-2916`），而 `agent_user_wallets.balance_cents` 没有币种列（`store.go:495-503`）。若钱包允许非 CNY，必须把钱包币种与 `minor_unit_digits` 一并持久化，扣费先用主站 8 位金额乘倍率，再按该币种最小单位量化；JPY/KRW 不得按两位小数扣，KWD 等不得截成两位。若产品选择钱包只记 CNY，则非 CNY 订单必须在下单前拒绝或完成显式换汇快照，不能在扣费时把外币数字当分。任何方案都必须让“订单本金 → 入账 → 模型扣费 → 退款”四步使用同一币种与最小单位；默认策略（手续费不退）下，全额退款的本金为 `amount_minor`、渠道请求也为 `amount_minor`，`fee_minor` 留作已收手续费并从退款回执对账中单列；部分退款的“已退本金/已退手续费”只累计本金口径，`Σ已退本金 ≤ amount_minor`。若未来允许退手续费，必须新增显式策略字段并在退款单中分别累计 `refunded_principal_minor/refunded_fee_minor`，两者各自有上限；不得用 `PayAmount` 作为钱包扣减额，也不得让一次退款同时按两个金额口径各自累计。
3. 确保付款主体只由服务端确定，不能由普通卫星请求头伪造。
4. 对账结果保留可审计快照；异常差异告警，不静默吞掉。订单入账与模型 usage 是两条独立账本，不能用余额差额抵消。
5. 区分订单退款、预留释放、用量冲正；三者分别有唯一 `idempotency_key`，重复执行返回既有结果。退款终态写入必须以当前状态 CAS：`finishStationRefund` 读取 `state` 后不得无条件更新，钱包回补、退款单与订单状态的任一更新命中 0 行都必须整笔回滚；已 `REFUNDED` 的请求仍须载入并比对首次回执。
- **退款失败后重新发起只能恢复同一退款意图，不得重建扣款**：`beginStationRefund`（`station_payment_refund.go:34-88`）当前按订单金额重新计算并一次性扣用户钱包，任何状态重置或管理员再次点击都会进入新的扣款路径；即使后续补了 `REFUND_FAILED` 回补，也必须把“回补完成”与“允许重新扣款”分开。持久退款单必须记录 `refund_intent_id/order_no/currency/minor_unit_digits/principal_minor/refunded_principal_minor/deducted_minor/rollback_state/provider_refund_request_id/state`；订单额度锚点还必须记录 `topup_minor/offset_available/offset_allocated/consumed_minor`，其中 `offset_available` 为累计已退本金、`offset_allocated` 为剩余未消费占用、`consumed_minor` 为已消费本金；任一时刻 `principal_minor = offset_available + offset_allocated + consumed_minor`，`topup_minor` 为未退款占用且仅因退款减少，`offset_allocated = topup_minor - consumed_minor`；退款失败回补只恢复本次退款已扣的钱包余额，不恢复额度占用、不修改订单锚点、`topup_minor` 或累计退款；`REFUND_FAILED` 后重试只允许：①复用原 `refund_intent_id` 与同一 `provider_refund_request_id` 查询/重发渠道；②若原扣款未回补，先按原行 CAS 完成回补，再以同一意图的新渠道尝试继续，不得再扣用户钱包；③若已回补且渠道请求号不可复用，必须显式作废该意图并由人工创建新退款单，新单仍须满足 `R <= offset_allocated` 且累计本金不超过 `principal_minor`。禁止按当前余额、当前订单金额或“再次点击”生成第二个扣款意图。验收：扣款后注入渠道失败/进程中断/`REFUND_FAILED` 重试/查询成功四种路径，用户钱包累计扣减不超过该订单本金一次，回补最多一次；重复点击只返回既有退款单状态或 409，不得产生第二笔扣款。
- **`released` 必须无条件全额释放，不得按 `actual_cents` 再扣一次**：`FinalizeSettlement`（`store.go:2793-2901`）对 `confirmed/released/reversed` 统一先计算 `chargedCents = stationChargeCents(actualCents, rate)`，随后仅把差额 `reserved - charged` 退回用户并归还 `allocated`。调用方（`main.go:3147`、`:3492`）虽然传 `actual=0`，但接口本身没有强制；任何误传非零金额、历史记录修复、人工重放或未来新增调用都会把“明确失败应全额退款”变成按失败金额扣费。必须按状态固定语义：`released` 的 `charged_cents` 强制为 0 且不写 `user_consume`，只全额退回 reservation；`reversed` 只能冲正既有已确认扣款，不得再次扣款；只有 `confirmed` 才允许 `charged>0`。并且 `released` 不得因 `BillLocalWallet` 分支进入 `debitUserUsageTx`。补测试：预留 150、`released(actual=100)` → 用户余额加回 150、`allocated` 减 150、`charged=0`、无 `user_consume`；`reversed` 只回补此前 confirmed 的净额；重复 `released` 余额不变。
- **直扣余额不足时不得静默截断为 0，也不得在本站钱包引入隐式信用**：`debitUserUsageTx`（`store.go:2918-2948`）在 `next < 0` 时用 `next = 0` 覆盖，仍把 settlement 标为 `confirmed` 并写 `user_consume`，等于平台替用户承担差额且不留应收。必须在同一事务内以条件更新校验余额足够（`balance_cents >= charged`），不足则整笔回滚并进入显式 `awaiting_manual_review`/失败状态，记录 `shortfall_minor`。本站钱包一律采用严格拒绝：不得把 `shortfall_minor` 落成可消费的负余额或本地信用额度；主站账本若启用显式信用，也只属于主站对 Payer 的应收，不能自动抵扣、冲销或抵充本站应付，更不得据主站欠款放宽本站预检，不得把 `confirmed` 与 `charged > 实际扣款` 并存。主站欠款冻结必须按主站用户身份生效，覆盖卫星代付/Payer 请求：本站钱包预检在扣款前读取主站冻结事实，命中即 402/403，不扣本地、不扣 Payer、不写成功 usage；不得通过切换 `user_upstream`/本站钱包或改用 Payer 绕过冻结。判定顺序固定为“主站冻结/黑名单 → 用户全部有效订阅 0/1/多条 → 余额/Payer 预检 → 扣款”，冻结命中时不得进入订阅分支或返回 `SUBSCRIPTION_ACTIVE` 代替冻结错误；唯一订阅请求也必须先被冻结拦截，不能因订阅与 Payer 互斥而漏掉欠款用户。补测试：余额 50、`charged=120` → 不写 `user_consume`、余额不变、settlement 非 `confirmed`、`shortfall=70`；并发两次确认只有一笔成功；重试人工处理只产生一次扣款。
- **直扣后的 `reversed` 必须走独立冲正，不得落进“无本地预留可退”的空返回**：直扣路径 `PrepareDirectSettlement`（`store.go:2618-2653`）只记 settlement，`hasLocalReservation=false`；`FinalizeSettlement` 在 `refund := reserved - charged` 前没有按状态分流，`:2867-2870` 对无本地预留直接 `return tx.Commit()`。因此对已 `confirmed` 的直扣请求调用 `reversed` 时，即使 `actualCents` 更低或为 0，也不会把差额退回用户钱包，也不会写反向流水，形成“冲正显示成功但钱未退”。必须规定：`reversed` 只允许引用已确认的直扣/预留结算，按原 `user_consume`/`consume` 事实生成唯一反向 `refund` 或 `user_refund` 行，金额 = 原扣款额 - 已冲正额，且不超过原扣款；不得重新读取当前余额或当前报价。若没有可引用的扣款流水，必须返回冲突而不是空提交。补测试：直扣 confirmed(120) 后 reversed(50) 用户余额 +50 且流水唯一、第二次 reversed(50) 返回冲突；直扣未确认时 reversed 拒绝；预留路径的 reversed 只释放差额且不退两次。
- **本地钱包退款不得冒充主站 usage 冲正，任务失败也不得自动退已发生费用**：`FinalizeSettlement` 的 `settlement_reversal:<request_id>` 只冲正 AgentAPI 本站 wallet 已确认扣款，不得在 `user_upstream` 模式或主站已扣费时据此要求主站冲正；本地钱包退款成功也不得当成主站 `usage` 未扣费证据，反之主站 usage 冲正不得自动给本站钱包加款。两侧必须分别记录 `local_charge_id`、`main_request_id`、`main_api_key_id` 与各自唯一退款/冲正键并独立 CAS。异步图片/视频任务失败时，只有 Provider 返回显式“4xx 且可证明未创建/未受理”回执或本地扣款前失败才可自动退；仅本地 `failed`、`null`/解析失败、5xx/超时、已取得 Provider task ID 均不得视为未受理；已拿到 Provider task ID、已发生上游费用、轮询超时/5xx/解析失败只能进入 `unknown/需对账` 或人工复核，不得因任务状态是 `failed` 就退款。验收：本地已确认 120、主站已计费、任务最终失败 → 两侧均不自动退并产生对账项；本地扣款前失败 → 余额与流水不变；并发/重复本地退款至多一次；主站冲正成功而本地未退 → 本地不改余额并告警。
- **终态迁移、CAS 与冲正键必须显式，不能靠“调用方传 0”保证资金安全**：`FinalizeSettlement` 当前对任何非 `pending` 记录只比较本次参数，状态不同即返回冲突（`store.go:2818-2828`），所以 `confirmed→reversed` 实际上不可能成功；而参数完全相同又允许重放进入 `updateSettlementUsageSnapshot`（`:2819-2825`），在终态覆盖 usage 快照。状态更新（`:2854`）也没有读取/校验 `RowsAffected`。冻结后的目标状态机为：`pending→confirmed|released`、`confirmed→confirmed(部分冲正)|reversed(全额冲正)`；`released`、`reversed` 为终态，禁止 `confirmed→released`、`released→reversed`、`released→confirmed`。`released` 必须固定 `actual_cents=0`、`charged_cents=0`、全额释放，忽略调用方非零 actual；`confirmed` 是唯一可产生扣费的状态；冲正必须保存原 `charged_cents`、累计 `reversed_cents`，令 `net_charged_cents = charged_cents - reversed_cents`，累计不得超过原扣款；部分冲正保持 `confirmed` 并可见，只有净额归零才进入 `reversed`，否则会与“已确认不可再更新”矛盾。所有 settlement 状态写入必须 `UPDATE ... WHERE status=<expected>` 并检查 `RowsAffected()==1`；并发/过期状态导致 0 行时整笔回滚并返回冲突。释放预留使用 `settlement_release:<request_id>`，冲正使用 `settlement_reversal:<request_id>`（若允许分批则加 `<sequence>`），不得共用 `refund:<request_id>`，也不得与订单退款 `payment-refund:<out_trade_no>` 混用。终态重放必须返回首次结果并逐项比对 `charged_cents/reversed_cents/usage_id/actual_cents`；不得在终态更新 `main_usage_snapshot`、`model`、金额或 usage ID。`usage_id` 只允许从创建占位升级为一次权威值；已绑定权威 usage 后再传入不同 usage 必须冲突。`debitUserUsageTx`（`:2918-2948`）在钱包行不存在时 `sql.ErrNoRows` 直接返回 nil，必须改为失败并整笔回滚，不得把“无钱包”标成已确认。补测试：预留 150 → released(actual=100) 只加回 150、`charged=0`、无 `user_consume`；confirmed(120) → reversed(50) 余额 +50 且 `reversed_cents=50`、状态仍 confirmed；再 reversed(70) 进入 reversed；第三次冲正冲突；confirmed(120) → released 冲突；终态重放改快照/改 usage/改金额均冲突；并发释放与冲正只成功一个；钱包缺失的 confirmed 不写成功。

**测试清单**
- 预留释放：`PrepareSettlement` 预留 150、实际 100，`FinalizeSettlement` 后用户余额只加回 50、`allocated` 只减 50；账本出现 `refund:<request_id>`，不是 `payment-refund:<out_trade_no>` 订单退款流水。
- 预留释放重放：同一 `request_id/usage_id/金额/状态` 再次 finalize 返回成功且余额不变；改金额或改 usage 返回状态冲突。
- 用量冲正：`Credit` 生成新的反向 `refund` 流水；历史 `consume` 行的金额、时间、余额快照不变。
- 冲正幂等：相同 `requestID` + 相同金额重放只写一次；相同 `requestID` + 不同金额返回幂等冲突。
- 订单退款：部分退款累计不超过原订单；重复退款只入账一次；退款只写 `payment_refund` / `payment_refund_reversal`，不写 `refund:<request_id>`，也不直接改模型 usage。

- **本地用户钱包负债必须与 `agent_wallets.allocated_cents` 相等，直扣必须显式释放负债**：现有 `store_test.go:623-629` 已断言 `SUM(agent_user_wallets.balance_cents) == agent_wallets.allocated_cents`，但 `PrepareDirectSettlement`（`store.go:2618-2654`）只记录 settlement，不占用也不释放 `allocated_cents`；`FinalizeSettlement` 在 `BillLocalWallet=true` 且无本地预留时走 `debitUserUsageTx` 只减用户钱包（`store.go:2860-2865`、`:2918-2948`），既不减 `allocated_cents`，也不写反向 `agent_allocate` 流水，导致“用户钱包合计 < allocated”的永久漂移，后续 `SyncOwnerBalance`（`:2489-2492`）又按 `allocated_cents` 重复扣减站长可用额度。必须二选一并写死：直接扣款时在同一事务内同时 `agent_user_wallets.balance_cents -= charged` 与 `agent_wallets.allocated_cents -= charged`，并写可复算的 `agent_consume`/`agent_allocate` 反向流水；或废止“站点钱包直扣”的独立路径，统一走 `PrepareSettlement` 的真实预占。不得让用户钱包与 `allocated_cents` 在成功结算后失去等式。补测试：分配 1000 分、直扣 120 分后断言用户钱包 880、`allocated_cents=880`、`SUM(user_wallet)=880`；重复 finalize 不二次释放；`SyncOwnerBalance` 前后 `available_cents` 不得因已结算请求而被额外扣减。
- **pending 的占用语义必须显式，`reserved_cents` 不得默认视为“已从上游扣走”**：`SyncOwnerBalance`（`store.go:2485-2492`）当前用 `available = main_balance - allocated - Σ(pending.reserved_cents)` 做重算；本地 `PrepareSettlement` 已同时扣用户钱包与 `allocated_cents`，因此再扣 pending 会把同一笔预留从两个口径各压一次。注意这不是“每次同步累减”：重复同步在 pending 集合不变时结果相同，真正的缺陷是本地已占的 pending 仍被重复计入、直扣 pending 未显式区分，以及陈旧 pending 长期压制额度。必须给 settlement 增加显式资金状态（至少 `no_local_reservation` / `local_reserved` / `upstream_reserved` / `settled`），重算只能使用真实上游预占：`available = main_balance - allocated - Σ(upstream_reserved)`；本地 `reserve:` 已占用户钱包与 `allocated_cents` 的不得再计入，直扣 pending 在确认前只是上限快照。确认、失败释放、过期释放必须在同一事务内把对应占用清零；陈旧 pending 必须有超时/复核/释放状态，不能无限压制额度。补测试：分配 1000、本地预占 300 后 `allocated=700`、用户钱包 700，因本地预占已计一次，`SyncOwnerBalance(main_balance=1000)` 求得的 `available` 不得再减 300；直扣 pending 且真实上游预占为 0 时同样不得减；若采用上游预占方案，则必须另建真实占用并断言只计一次。
- **超额或长期 pending 必须有唯一后续状态，不能靠“继续 pending”无限放行**：图片/视频轮询（`main.go:392`/`:455`）、后台任务对账（`:3639`）和租户 settlement 对账（`:3639-3647`）在 `actual > reserved` 时只把状态写回 `pending + manual review required`，既不升级真实预占、不冻结同一租户/用户的新请求，也不阻止下一次自动确认；若 `reserved_cents` 只是上限快照，直扣路径甚至不会进入该分支，而是把任意大 `actual` 直接 `confirmed` 后由 `debitUserUsageTx` 把余额截断为 0（`store.go:2937-2940`）。必须引入显式 `awaiting_manual_review`（或等价终态前状态），并规定：进入该状态后同一 settlement 不得再被自动 `confirmed`；同一租户/用户是否继续放行必须由策略显式决定，默认应冻结该用户本站钱包新请求或降级为上游直扣；补记差额定金（`actual - reserved`）与负责人，人工确认或冲正只能按唯一幂等键执行一次；超过时限（如 24h）必须告警而非静默维持 pending。补测试：直扣图片/视频 `actual=MaxRequestCostCents+1` 时轮询、过期任务、后台对账均进入待复核且余额不变；复核确认后只扣一次；重复对账/重复确认不产生第二次扣款。

只能用于幂等定位，不得用于证明“渠道已退款”。**币种来源也必须可区分**：Stripe/Airwallex/Wxpay 能从渠道对象或固定币种得到币种并标 `currency_source=provider`；支付宝/EasyPay 当前没有独立退款币种字段（`payment/provider/alipay.go`、`easypay.go` 全文件无 currency），只能由非空订单币种绑定并标 `currency_source=order`。允许 `currency_source=order` 作为终态比对值，但必须持久化来源且 `currency` 非空；它只能证明“与本地订单一致”，不能冒充渠道回执。渠道回执有币种时必须以 `currency_source=provider` 为准，二者不一致即 409/人工复核；首次终态以 `order` 绑定的，后续同值 `provider` 只补审计，不改写终态金额，值不同即冲突。补测试：终态后重复成功回执、成功后再失败回执、不同 `refund_id` 的同额回执、成功但缺渠道 `refund_id`、回执缺金额、回执只有本地派生退款号、支付宝/EasyPay 订单币种为空且渠道无币种、支付宝/EasyPay 订单币种非空绑定成功、渠道币种与订单币种不一致、首次 `currency_source=order` 后同值/异值 `provider` 回执。
- 退款失败重试同一意图：扣款成功后注入渠道失败/进程中断/`REFUND_FAILED` 重试/查询成功，断言用户钱包累计扣减只一次、回补最多一次；重复点击返回既有退款单或 409，不得按当前余额重建第二个扣款意图。
- 站点订单过期：超过 `expires_at` 后必须进入 `EXPIRED`；Stripe/Airwallex/支付宝/微信先 `CancelPayment`，EasyPay 无取消能力时记录不可取消并转人工，不得阻断本地终态；渠道取消结果必须与 `EXPIRED` 分字段持久化（成功/不可取消/失败可重试），取消失败不得把订单留在 `PENDING` 或回滚本地过期；列表、待支付上限、每日/实例限额、回调、对账使用同一服务端时间判定；过期后收到成功支付不得静默入账，只能人工复核或原路退款；渠道取消失败可重试且有审计。
- **过期状态必须拆成“本地关闭”与“渠道是否仍可付款”两个事实**：`ExpireRechargeOrders`（`store.go:1937-1941`）只把本地 `pending` 改成 `expired`，不发渠道取消；站点订单目前更是没有过期扫描（`station_payment_orders` 无 `EXPIRED` 写入）。当前支付回调在订单已 `expired` 时，`RecordPaymentEvent`（`store.go:1991-2016`）直接返回 `errRechargeStateConflict`/`errRechargeExpired`，HTTP 层统一回 409（`main.go:2160-2170`）；若渠道实际已扣款（尤其 EasyPay 等无取消能力或过期未及时取消），用户资金已出但本地无 `paid_pending` 记录，只能靠渠道后台人工发现，属资金丢单。必须持久化 `expired_at/expire_reason`、`provider_cancel_status`（`not_requested/requested/succeeded/unsupported/failed`）、`provider_cancel_error` 与 `late_payment_status`（`none/observed/pending_review/refunded`）等独立字段，不得用一个 `status` 同时表达“本地已关闭”和“渠道不会再扣款”。收到签名有效、金额/币种/`provider_trade_no` 均匹配的真实 `paid` 回调时，即使本地已过期，也必须原子写入“迟到支付事实”并进入人工待入账或原路退款，不得仅返回通用 409 让渠道重试或丢弃证据；同一 `order_no`/渠道交易号只能有一条迟到支付记录。补测试：本地过期后渠道仍成功扣款、渠道取消成功但回调迟到、EasyPay 不可取消、过期扫描与回调并发；断言四类结果可区分，不静默生成第二份余额，也不把真实到账误判为普通状态冲突。

## 6. 全链路验收

- 从主站菜单进入 AgentAPI，SSO 成功、Session 3 天、注销可撤销。
- 主站 usage/反查必须返回 `request_admission` 六态（`not_seen`/`accepted`/`rejected_before_upstream`/`settled`/`conflict`/`unknown`）及真实最终键、`admission_source/funds_effect/quota_effect/dispatch_state/state_version/query_request_id/final_request_id`；0 行、`not_seen`、`accepted`、`conflict`、`unknown` 均不得触发自动重发、免费释放或重复扣款，只有 `rejected_before_upstream` 且 `dispatch_state=not_started`（须由写出点事件证明，不能靠时间戳为空、4xx 状态码或本地异常推断）才可重试。自动重发/免费处理还必须 `funds_effect=none`（余额、欠款、订阅用量无资金变化）且 `quota_effect=none`（Key/限流、账号、平台、订阅额度均未写）；本站钱包释放只按本地预留与主站资金效果判断；`quota_effect` 既不是释放前提，也不是拒释前提，不得因主站额度变化改扣本站钱包。`accepted`/`unknown` 表示可能已调上游，必须待对账；已读到唯一成功 usage 必须为 `settled`，不得因冲突态降级为未结算。同一请求只能有一条 admission（先以临时键建行，最终键只一次 CAS 写入 `final_request_id`），临时键与最终键必须经 `request_admission_alias(alias_request_id, api_key_id, admission_id, final_request_id)` 单跳反查同一受理事实，alias 行以外键绑定该 admission，禁止引用尚未升级最终键的行；同一临时键改绑、同一最终键归属第二条 admission、别名引用未升级最终键的 admission、别名缺失或 CAS 失败时不得确认。调用上游前必须先提交 `accepted`（临时键仅作 `admission_key`，最终键未定时不得写可解析别名），提交失败不得调用上游；本地拒绝先提交零效果受理，提交失败只能返回 `unknown`/不可重试；最终键、别名与权威 usage 同事务或同事务 outbox，任一步失败不得确认成功，不得自动换键重发。
- **受理与别名验收必须可执行**：同一临时键并发绑定两个最终键时恰一条成功、另一条 `conflict`；同一请求由临时键建 admission 后改用最终键查询，不得产生第二条 admission，最终键只能一次 CAS 写入；同一最终键被两个临时键/两条 admission 指向时恰一条成功；临时键别名缺失而最终 usage 已存在时，查询必须返回 `unknown`/待对账，不得返回 `settled`；直接查询最终键且唯一 usage 存在时必须返回 `settled`（`admission_source=usage`），不得因别名未写降级；所有查询（含 `usage_count=0`）必须回传完整 `admission_source/funds_effect/quota_effect/dispatch_state/state_version/query_request_id/final_request_id`，且 `query_request_id` 逐字等于查询键；临时键与最终键反查必须命中同一 `state_version`。注入受理写入失败时上游调用计数必须为 0；注入别名或 usage 写入失败时不得返回成功或自动换键重发。
