# 07 预充值与账务

## 1. A 方案定义

A 方案是“代理预充值额度模式”：

```text
代理先向主站预存额度
        ↓
主站记录 agent_wallet
        ↓
代理将额度分配给代理用户
        ↓
用户调用模型
        ↓
从用户子余额和代理可用额度中扣减
```

本方案不设置佣金和分成。用户消费金额就是本次从代理额度中消耗的金额，主站仍可记录成本，但不生成佣金流水。

本版本已经冻结方案 A：主站由 `agent_owner_main_user_id` 唯一承担模型扣费，代理用户 `main_user_id` 只用于登录和本地归属。AgentAPI 本地钱包是预授权镜像，不是第二个主站账本。

## 2. 两层额度

### 2.1 代理主站额度

代理先向主站支付并获得（方案 A 为代理管理员主站账户的可用余额镜像）：

```text
agent_wallet.available
```

它是主站允许该代理继续使用模型服务的总额度；主站才是最终扣费方，AgentAPI 不得凭空创造主站额度。

### 2.2 代理用户子余额

代理将可用额度分配给某个用户：

```text
agent_user_wallet.available
```

它是用户在代理站可以消费的余额。

约束：

```text
所有用户子余额之和 ≤ 代理主站可用额度
```

如果系统使用“按用户流水汇总代理余额”的实现，则不能再有第二个可独立修改的总余额字段；总额必须从同一账本汇总得到。

## 3. 用户充值与代理预存的关系

必须区分两种资金事件：

### 代理向主站预充值

这是主站认可的服务额度增加事件，成功支付并确认后增加 `agent_wallet`。

### 代理用户向代理充值

这是代理与用户之间的收款事件。它可以形成用户子余额，但不能绕过主站支付确认直接增加主站额度。

第一版建议：

1. 代理先有足够的主站预存额度；
2. 用户充值订单验证成功后，代理可以把可用额度分配给该用户；
3. 用户子余额分配不得超过代理可用额度；
4. 用户支付给代理的外部资金和主站预存资金在账务上分别记录；
5. 如未来需要“用户支付自动转为主站额度”，另行实现经过验证的自动结算流程。

这样不会把外部支付回调错误地当作主站已经收到的预存款。

## 4. 充值入账

充值成功时，使用一个账务事务完成：

```text
校验订单状态和支付事件
  → 写入充值流水
  → 增加代理账户或用户子账户
  → 更新订单为 paid
  → 写入审计事件
```

如果任一步失败，不能只更新订单或只更新余额。支付事件可以重试，但同一个订单和支付事件只能入账一次。

## 5. 消费扣款算法

### 5.1 同步文本请求

```text
1. 根据 Session/服务头确定 agent_id、proxy_user_id 和 main_user_id
2. 校验 Agent、用户和钱包状态
3. 预估最大扣款金额
4. 在 AgentAPI 一个事务中写入 pending settlement 并扣减用户子余额/代理 allocated
5. 校验余额足够，写入 consume 流水
6. 固定以 `agent_owner_main_user_id` 调用上游模型
7. 等主站 usage/余额差额可验证后确认 settlement
8. 释放未使用冻结金额
9. 写入 usage_id、request_id 和结果
```

主站成功但 usage/余额差额暂时无法确认时，不能直接执行全额 release；必须进入 `settlement_pending`，由后台对账后再决定 capture 或 reversal。

### 5.2 流式请求

- 请求开始前冻结最大可能金额；
- 流结束后按照实际用量结算；
- 客户端断开时由服务端完成释放或按已计量用量结算；
- 超时任务必须有后台补偿，不允许永久占用冻结余额。

### 5.3 图片、视频和异步任务

- 创建任务时冻结预算；
- 任务完成回调或轮询结果后结算；
- 失败、取消和过期任务释放冻结；
- 每个异步任务有独立幂等 `request_id`；
- 重试只能引用原任务或产生新的明确任务，不能重复扣同一任务。

## 6. 余额不足策略

以下任意条件不满足，都不得调用上游：

```text
Agent.status == active
用户.status == active
agent_wallet.available >= 预计金额
agent_user_wallet.available >= 预计金额
```

此外，主站计费身份的余额也必须通过服务端预检。客户端不能提交主站计费用户 ID。

返回统一的 `AGENT_INSUFFICIENT_BALANCE`，并记录 request_id。余额不足不应被重试机制当作网络错误无限重试。

## 7. 退款和冲正

历史消费流水不可修改。退款必须新增反向流水：

```text
原 consume 流水
        ↓
refund/reversal 流水
        ↓
恢复用户子余额和代理可用额度
```

退款必须关联原始 `usage_id` 或 `request_id`，并设置唯一冲正标识。

## 8. 无佣金规则

- 不计算 `commission_amount`；
- 不生成佣金待结算状态；
- 不提供佣金提现；
- 不因代理用户消费自动增加代理余额；
- 代理的服务额度来源只有预充值、人工调整或批准的信用额度；
- 主站成本只用于内部分析和价格策略，不进入代理分成流程。

## 9. 对账

至少每日执行：

```text
代理钱包期初余额
+ 充值/调整
- reserve/consume
+ release/refund
= 代理钱包期末余额
```

同时核对：

- 用户子余额汇总是否不超过代理额度；
- 充值订单与支付渠道状态是否一致；
- 主站 usage 记录与 AgentAPI 展示缓存是否一致；
- 是否存在无 Agent 归属的请求；
- 是否存在重复 request_id 或重复订单入账。
