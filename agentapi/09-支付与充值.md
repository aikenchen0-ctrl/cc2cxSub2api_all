# 09 支付与充值

## 1. 支付角色

AgentAPI 的支付功能是代理的收款入口，不等于主站账务已经入账。必须把以下三件事分开：

```text
支付渠道确认收到钱
代理用户获得可消费子余额
代理主站预存额度增加
```

第一版采用严格预充值模式：代理先向主站预存额度；用户支付给代理后，由代理在已经同步确认的可用额度范围内给用户分配子余额。用户支付回调不能绕过主站充值确认直接增加主站代理额度，也不能把本地收款记录冒充主站余额。主站扣费身份与本地子余额的关系见 [17-账务权威与主站扣费桥接](17-账务权威与主站扣费桥接.md)。

## 2. AgentAPI 支付配置

每个 Agent 可以配置一组支付方式：

| 配置 | 说明 |
| --- | --- |
| `provider` | 支付渠道类型 |
| `merchant_id` | 商户号或收款主体 |
| `secret_ref` | 加密密钥引用，不保存明文 |
| `notify_url` | 服务端回调地址 |
| `return_url` | 用户支付完成后的展示地址 |
| `currency` | 支持币种 |
| `enabled` | 是否启用 |
| `min_amount`/`max_amount` | 金额限制 |

支付配置必须与 `agent_id` 绑定，不能出现“一个代理的页面调用另一个代理的商户配置”。

## 3. 用户充值流程

```text
1. 用户登录 AgentAPI
2. 根据 Session 得到 agent_id/main_user_id
3. 创建 RechargeOrder
4. 返回支付渠道的待支付参数
5. 用户完成支付
6. 支付渠道回调 AgentAPI
7. AgentAPI 验签和校验订单
8. AgentAPI 幂等记录代理侧收款；只有平台/主站作为收款主体并完成主站确认时，才进入主站入账流程
9. 在代理主站额度镜像足够时，把可用额度分配给用户子账户
10. 用户查询到新的可用余额
```

订单创建时金额、代理、用户和支付方式全部由服务端确定，不能信任前端提交的 `agent_id` 或任意用户 ID。

## 4. 代理预充值流程

```text
1. 代理在主站或平台后台创建预充值订单
2. 代理完成支付
3. 主站验证支付回调
4. 主站增加 agent_wallet.available
5. 记录 agent_recharge 流水
6. 允许 AgentAPI 分配用户子余额
```

代理主站预存额度不足时，即使代理外部支付账户已经收到用户付款，也不能让主站模型请求无限继续。可以选择等待代理补充主站额度，或者由平台批准信用额度。

## 5. 订单状态机

```text
created → pending → paid → allocated
             │        │
             ├──────▶ failed
             └──────▶ closed

paid/allocated → refunded
```

规则：

- `paid` 只能由验证过的支付事件产生；
- `allocated` 表示已经分配到用户子余额；
- 重复回调只能返回原处理结果；
- `closed` 不得再次支付入账；
- `refunded` 必须产生反向余额流水；
- 订单金额不能被回调参数覆盖。

## 6. 回调校验

回调处理顺序：

```text
校验来源/签名
  → 查询本地订单
  → 校验商户号、币种、金额、订单状态
  → 校验 provider_trade_no 是否重复
  → 写入支付事件幂等记录
  → 若收款主体是主站，调用主站入账接口并等待确认；否则只记录代理侧收款
  → 标记订单为已验证/待分配，而不是直接增加主站额度
```

主站入账失败时，订单不能伪装成成功。应保留 `paid_pending_posting` 或等价状态，由后台重试和对账任务处理；代理侧收款订单也必须等待可用主站额度后才能分配子余额。

## 7. 退款、拒付和过期

- 用户退款：生成退款订单和反向钱包流水；
- 渠道拒付：冻结相关用户和代理额度，进入人工审核；
- 订单过期：关闭订单，不产生余额；
- 代理撤站：停止新充值，保留已支付订单的处理和退款能力；
- 充值回调晚到：依据订单最终状态幂等处理，不重复入账。

## 8. 对账

每日比较：

```text
支付渠道成功订单
↔ AgentAPI RechargeOrder
↔ 主站充值流水
↔ 用户子余额变化
```

差异必须能够按照 `order_no`、`provider_trade_no`、`agent_id` 和 `main_user_id` 定位。对账任务只生成补偿任务，不直接静默修改余额。

## 9. 无佣金约束

支付模块不生成佣金或分成字段。代理收到用户的资金是代理与用户之间的收款关系；主站只认可已经预存或批准的主站服务额度。

## 10. 当前实现：provider-neutral 充值桥接

当前 `agentapi/backend` 已实现一个默认关闭的、与具体支付供应商无关的订单桥接。它不是支付 SDK，也不会把支付回调当成主站充值接口。

配置：

```env
AGENT_PAYMENT_ENABLED=false
AGENT_PAYMENT_PROVIDER=manual
AGENT_PAYMENT_CURRENCY=CNY
AGENT_PAYMENT_WEBHOOK_SECRET=
AGENT_PAYMENT_MIN_AMOUNT=1.00
AGENT_PAYMENT_MAX_AMOUNT=10000.00
AGENT_PAYMENT_ORDER_TTL=30m
AGENT_PAYMENT_CHECKOUT_URL_TEMPLATE=
```

接口：

```text
POST /api/v1/agent/recharge/orders       # Agent Session，创建自己的订单
GET  /api/v1/agent/recharge/orders       # Agent Session，只能查看自己的订单
GET  /api/v1/agent/admin/recharge/orders # Agent 管理员 Session，查看本实例订单
POST /api/v1/agent/admin/recharge/allocate # 管理员重试已支付订单的本地分配
POST /api/v1/payments/webhook             # 支付供应商，HMAC 签名，不使用 Cookie
```

创建订单时，服务端从 Session 得到 `main_user_id`，从环境配置得到 `agent_id/provider/currency`，只接受金额和幂等键。订单状态落在 `recharge_orders`，支付事件落在 `payment_events`；同一事件 ID 与不同内容复用会返回冲突。

回调签名约定为：

```text
X-Agent-Payment-Event-ID: evt_xxx
X-Agent-Payment-Signature: sha256=<HMAC-SHA256(secret, raw_body)> 的十六进制值
X-Agent-Payment-Timestamp: <可选 Unix 时间戳，允许前后 10 分钟>
```

回调 JSON 至少包含：

```json
{
  "order_no": "ord_xxx",
  "status": "paid",
  "amount_cents": 10000,
  "currency": "CNY",
  "provider_trade_no": "trade_xxx"
}
```

`paid` 事件只会把订单置为 `paid_pending_allocation`，随后尝试读取主站 Owner 的真实余额并调用本地原子分配。主站不可用、Owner 额度不足或同步结果不足时，订单保持 `paid_pending_allocation`，回调返回可重试的 `202`；系统不会通过 webhook 直接增加主站余额，也不会凭空调用本地 `CreditAgent`。管理员可在主站补足额度后调用 `admin/recharge/allocate` 重试。

后台 reconciler 也会按 `AGENT_SETTLEMENT_RECONCILE_INTERVAL` 和批量上限扫描 `paid_pending_allocation`，在主站恢复或 Owner 补足额度后自动重试分配；它与模型 settlement 使用同一 Owner 锁，避免同步余额与模型扣费并发竞争。

当前明确未实现：真实支付供应商 SDK、支付页面签名参数、退款/拒付自动处理、支付渠道对账和主站自动入账。接入真实渠道前必须把渠道签名、收款主体、退款责任和主站充值流水补充到本契约，并增加端到端验收。

实现状态名称与上方概念状态的对应关系为：`pending`（待支付）、`paid_pending_allocation`（已验证支付但等待主站额度）、`allocated`（已分配）、`failed`、`closed`、`expired`。当前版本不实现 `refunded` 状态；退款必须先完成渠道合同、主站冲正接口和反向流水设计。
