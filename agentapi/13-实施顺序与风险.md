# 13 实施顺序与风险

## 1. 实施阶段



### P0：方案确认

- 确认 A 方案、无佣金、代理预充值和用户子余额；
- 在 [17-账务权威与主站扣费桥接](17-账务权威与主站扣费桥接.md) 中拍板主站唯一扣费身份（推荐方案 A）；
- 确认用户是否允许直连主站；
- 确认支付渠道和部署方式；
- 评审本文档并冻结接口契约。



### P1：主站控制面

- 建立 Agent、代理账户、用户归属和状态模型；
- 建立受控代理接口；
- 增加幂等、审计和 scope；
- 不把通用管理员接口暴露给 AgentAPI。



### P2：AgentAPI 基础服务

- 创建独立服务和数据库；
- 实现域名解析、Agent 配置和 Session；
- 实现用户映射和健康检查；
- 实现服务凭据加载与轮换。



### P3：一键开站

- 实现 Agent 状态机；
- 接入域名/TLS/部署编排；
- 实现开站幂等、重试和失败恢复；
- 先完成测试环境平台子域名。



### P4：用户和模型链路

- 实现主站用户创建；
- 实现用户注册、登录和映射；
- 按公共层发送三个服务头；
- 按方案 A/B 固定主站计费身份，禁止客户端覆盖；
- 接入公开模型名；
- 完成用量归属。



### P5：账务和额度

- 实现代理预充值账户；
- 实现用户子余额和流水；
- 覆盖同步、流式、图片、视频和异步请求；
- 实现冻结、结算、释放、退款和对账。
- 主站成功但结算未知时进入 `settlement_pending`，不能静默释放；



### P6：支付

- 接入一个支付渠道；
- 实现订单状态、验签、幂等和对账；
- 首先上线代理预充值，再决定是否支持用户自动结算。



### P7：试点和上线

- 先创建一个内部代理；
- 使用测试支付和小额额度；
- 验证两个代理之间隔离；
- 通过全部验收清单后再开放更多代理。



## 2. 主要风险

| 风险                   | 缓解措施                                     |
| ---------------------- | -------------------------------------------- |
| 全局管理员 Key 泄露    | 服务端密钥、白名单、独立服务凭据、轮换       |
| 代理与用户余额重复记账 | 明确方案 A/B 的唯一主站扣费身份、幂等流水、每日对账 |
| 主站用户可绕过代理     | agent 归属、Key 绑定、禁止直连或统一网关校验 |
| 多请求并发超扣         | 事务锁、冻结/结算、原子扣减                  |
| 支付回调伪造           | 验签、金额校验、事件幂等和人工对账           |
| 开站半成功             | 状态机、Saga 补偿、可重试步骤                |
| AgentAPI 版本漂移      | 版本化契约、兼容窗口、集成测试               |
| 代理服务被入侵         | 每 Agent 凭据隔离、scope、限速和吊销         |



## 3. 第一版不做

- 自定义域名自动证书全流程；
- 多代理共享一个主站用户；
- 用户直接拿主站 API Key；
- 佣金/分成/差价；
- 代理自定义任意计费价格；
- 多种支付渠道同时接入；
- 复杂订阅、套餐、赠送余额；
- 无审计的人工余额修改。



## 4. 上线门槛

以下条件全部满足后才允许生产开站：

1. 管理员 Key 不进入浏览器和镜像；
2. 开站、注册、充值和请求都有幂等键；
3. 两个代理之间的数据和额度隔离通过测试；
4. 余额不足和并发扣款测试通过；
5. 支付重复回调和退款测试通过；
6. 主站故障恢复和对账流程可执行；
7. 代理凭据可以独立吊销；
8. 账务负责人确认预充值和退款规则；
9. 本地预授权与主站 `usage_id`/余额差额可以完整对账，`settlement_pending` 补偿演练通过。
