# 05 主站接口契约

本文定义 AgentAPI 与 Sub2API 主站之间的接口边界。托管 AgentAPI 使用逐站 runtime control/model 凭据，以及 Sub2API 公开认证和模型 API；业务进程不使用全局管理员 Key 读取用户、余额、usage 或状态，也不直连主站数据库。主站开站控制面只接受主站管理员或具有明确路由 allowlist 的 provisioning worker 凭据，不把通用 `/admin/*` 暴露给浏览器。

当前参考实现已提供的服务端调用包括：主站注册/登录/2FA/刷新/当前用户/登出、当前用户 Profile/密码自助接口、逐站 Owner/usage/runtime 状态管理 API、带用户身份证明的 Agent 映射、模型 `/v1` 转发，以及开站记录的管理员控制 API。用户 Profile/密码只用对应 Session 的主站 JWT 调用 `/api/v1/user/*`，不使用管理员 Key；开站 API 只写入主站控制面状态，不执行部署。DNS/TLS/Compose/Nginx/健康检查的真实环境验收、多实例运维和支付渠道仍未完成。

## 1. 总体原则

1. AgentAPI 不直连主站数据库；
2. 主站接口必须进行 agent 范围校验；
3. 所有创建、充值、消费和状态变更都支持幂等；
4. 查询接口默认只返回当前 Agent 的数据；
5. 不提供“任意 main_user_id + 任意管理动作”的通用代理；
6. AgentAPI 不使用全局管理员 Key；逐站 control/model 凭据只在服务端使用，并且不进入浏览器；
7. 接口版本化，响应中返回 `request_id` 和业务状态。

### 1.1 逐站 Agent Runtime API

托管 AgentAPI 的运行时管理请求必须带 `X-AgentAPI-Runtime-Control: <agt_ctl_...>`。该控制凭据仅能读取当前 Agent/Owner/usage、绑定用户、更新已绑定用户状态并订阅当前 Agent 的状态提示；Sub2API 根据凭据哈希解析 `agent_id` 和 Owner，不能由请求体覆盖。

```http
GET   /api/v1/agent-runtime/agent
GET   /api/v1/agent-runtime/agent/stream
GET   /api/v1/agent-runtime/owner
GET   /api/v1/agent-runtime/usage?request_id=<request_id>
POST  /api/v1/agent-runtime/users/{user_id}/map
PATCH /api/v1/agent-runtime/users/{user_id}/status
X-AgentAPI-Runtime-Control: <agt_ctl_...>
```

绑定用户还必须提供与路径 `user_id` 相同的当前用户身份：普通登录/注册代理流程使用 Sub2API 签发的 `Authorization: Bearer <user JWT>`；菜单 SSO 流程复用原有短时 `agentapi` HMAC ticket，通过服务端请求头 `X-AgentAPI-SSO-Ticket` 传递。Sub2API 校验签名、audience、时效与 subject；这不会改变浏览器 SSO URL、ticket 格式或 Session 协议。缺少/不匹配证明、Inactive 主站用户或跨 Agent 重复绑定均拒绝，runtime control 凭据本身不能把任意 ID 加入映射。

`PATCH .../status` 只允许 `active`/`disabled`，且目标必须已经绑定到凭据对应的 Agent；Owner 不能被该接口停用。`GET .../agent/stream` 是 PostgreSQL 提交后 `LISTEN/NOTIFY` 的 ID-only 提示流，只发本 Agent ID、初始 `resync` 和心跳。AgentAPI 收到提示后必须重新 `GET /agent` 读取权威状态，断流时继续周期 GET；事件不携带可直接执行的状态。

## 2. 代理控制面接口

### 2.1 创建代理

```http
POST /api/v1/agent-provisioning/agents
Idempotency-Key: <key>
```

主要输入：`requested_slug`、`display_name`、`owner_main_user_id`、`plan_id`、品牌配置。

`Idempotency-Key` 必填（8–200 字符），按主站管理员身份隔离保存哈希；相同键与相同规范化请求重放会返回同一 Agent，不同请求复用则 `409 AGENT_DUPLICATE_REQUEST`。Owner 必须是主站中启用且未删除的管理员用户。第一版只接受 `domain_mode=platform_subdomain`，slug 会生成 `<slug>.cc2.cx`，并拒绝保留名/重复 slug；`plan_id` 目前只做格式校验，不验证或创建套餐。品牌 Logo 只接受 HTTPS URL。

首次请求创建 `pending` / `queued` 记录并立即返回 `202`，不是开站成功：

```json
{
  "agent_id": "agt_<uuid>",
  "status": "pending",
  "domain": "agent01.cc2.cx",
  "request_id": "<主站请求 ID>",
  "status_url": "/api/v1/agent-provisioning/agents/agt_<uuid>"
}
```

### 2.2 查询开站状态

```http
GET /api/v1/agent-provisioning/agents/{agent_id}
```

主站管理员可查询，受限 worker 凭据只允许读取记录和 pending/provisioning 列表、认领与续租任务，以及上报进度和激活。响应包含当前步骤、最近错误、`can_retry`、域名状态和公开品牌/Owner/套餐标识，不含任何部署密钥。当前首次状态为 `pending`、`current_step=queued`、`domain_status=pending`。AgentAPI 仓库已提供独立 worker 源码，但它必须部署在有 Docker/Nginx 运维权限的受控节点；主站服务不会替运维平台启动 worker。

管理列表使用 `GET /api/v1/agent-provisioning/agents?page=1&page_size=20&status=pending&q=agent`，支持状态与 slug/domain/display name/Owner ID 关键词筛选，`page_size` 最大为 100。变更订阅使用 `GET /api/v1/agent-provisioning/agents/stream`；数据库提交后 SSE 的 `agent` 事件只携带 `{"agent_id":"agt_..."}`，并发送初始 `resync` 和心跳。worker 及托管 AgentAPI 实例只把事件当作唤醒提示，必须 GET 自己的权威记录后才能更新状态。

### 2.2.1 认领与续租

```http
POST /api/v1/agent-provisioning/agents/{agent_id}/claim
X-AgentAPI-Provisioning-Credential: <worker-credential>
```

只有专用 provisioning worker 凭据可以认领 `pending/provisioning` 记录。认领在主站事务中原子完成；另一 worker 持有未过期租约时返回冲突，已不可认领的状态不会被接管。成功响应包含 Agent、一次性 `lease_token` 和 `lease_expires_at`；响应必须带 `Cache-Control: no-store`、`Pragma: no-cache`。主站只存 SHA-256 token hash，不存原文。

```http
POST /api/v1/agent-provisioning/agents/{agent_id}/lease
X-AgentAPI-Provisioning-Credential: <worker-credential>
X-AgentAPI-Provisioning-Lease: <lease-token>
```

默认租期为 90 秒，worker 每 20 秒续租；有效进度更新也会刷新租期。租约缺失、过期或 token 不匹配时续租、worker 进度更新和 worker 激活均被拒绝。worker 失租后取消部署 context。租约约束主站控制面并发，但并不能为 Docker/Nginx 副作用提供 fencing，因此主机端部署动作仍需具备幂等性。

### 2.2.2 部署 worker 进度

```http
PATCH /api/v1/agent-provisioning/agents/{agent_id}/progress
Idempotency-Key: worker-step-<unique-key>
X-AgentAPI-Provisioning-Credential: <worker-credential>
X-AgentAPI-Provisioning-Lease: <lease-token>
Content-Type: application/json
```

```json
{"step":"bundle_generated"}
```

只接受主站管理员或专用 provisioning worker 凭据；worker 必须另带当前有效租约头，主站管理员人工操作可不带。步骤必须按 `validating → bundle_generated → deploying → domain_check → tls_check → readiness_check` 顺序推进；`pending` 或 `failed` 只能从 `validating` 重新开始。每个步骤使用不同幂等键。失败使用受限代码，例如 `{"step":"failed","failure_code":"readiness_failed","retryable":true}`。服务端不接受任意 `error` 文本，而是生成固定、无凭据的错误说明。跳步、Agent 已激活/暂停/撤销、失租、幂等键冲突均拒绝。进度、Agent 状态、租约续期及事件在一个事务内提交，变更也会触发 SSE；worker 或 Agent 实例仍应 GET 主站记录确认当前权威状态。

### 2.2.3 重试可恢复失败

```http
POST /api/v1/agent-provisioning/agents/{agent_id}/retry
Idempotency-Key: retry-<unique-key>
```

仅主站管理员可调用；worker 凭据不包含 retry 权限。仅当状态为 `failed` 且 `can_retry=true` 时有效。它以一笔事务清除旧错误、重置步骤/域名状态为 `pending/queued/pending` 并记录事件；worker 随后必须 GET 记录并从 `validating` 重新上报。不可重试失败、暂停或撤销记录不能调用此操作。部署包生成器按主站 request ID 保持幂等，因此重试不会更换 Agent ID 或随机 Session Secret。

### 2.3 激活就绪实例

```http
POST /api/v1/agent-provisioning/agents/{agent_id}/activate
Idempotency-Key: activation-01
Content-Type: application/json
```

```json
{"confirm_agent_id":"agt_<uuid>","readiness_confirmed":true}
```

此操作允许主站管理员或 provisioning worker 凭据调用，并要求路径 ID 与确认值一致。worker 必须同时携带当前有效的 `X-AgentAPI-Provisioning-Lease`；成功激活会释放该 Agent 的租约。它将 `pending/provisioning/failed` 转为 `active`、`current_step=ready`、`domain_status=ready`；管理 UI 要求操作者确认已从目标域名验证 `/readyz`。API 自身不会访问分站执行探活，也不代表 DNS/TLS、Owner、Secret 或容器由主站自动配置。外部 worker 完成真实检查后可以调用同一幂等接口。

### 2.4 暂停/恢复/撤销

```http
POST /api/v1/agent-provisioning/agents/{agent_id}/suspend
POST /api/v1/agent-provisioning/agents/{agent_id}/resume
POST /api/v1/agent-provisioning/agents/{agent_id}/revoke
```

三种变更仅主站管理员可调用，worker 凭据明确拒绝 suspend/resume/revoke；均要求 `Idempotency-Key`，作用域为操作者；状态不允许的操作返回 `409 AGENT_STATE_CONFLICT`。撤销是不可逆状态，JSON 请求体必须包含 `{"confirm_agent_id":"<同一路径 agent_id>"}`。对配置了同一 `agt_<uuid>` 且启用主站状态控制的运行实例，AgentAPI 会在 `active` 以外拒绝业务流量；SSE 断线由定期 GET 兜底，权威状态过期或不可读时 fail closed。`/healthz`、`/readyz` 不受业务门控影响。此机制控制已有实例请求，不会自动部署实例、执行 DNS/TLS 或推进开站状态。

### 2.5 权限和审计边界

- 路由为 `/api/v1/agent-provisioning/*`，使用主站管理员鉴权、管理面限流、合规门控和审计；普通用户及 AgentAPI Session/客户端 Key 均不可调用。
- 当前权限仍是主站全局管理员级别，没有按 Agent 切分的 manager/scope 凭据；不能把此 API 暴露给代理商浏览器。
- 创建、幂等键占位、Agent 记录和创建事件在同一 PostgreSQL 事务中提交；状态变更使用行锁，状态事件与变更原子提交。主站通用审计日志记录操作者、动作、请求 ID 和结果。
- 创建开站记录的接口不创建主站代理余额、不签发或返回服务凭据、不调用部署 CLI，也不将 `pending` 自动改为 `active`。后续受限 worker 接口只登记 worker 在目标主机生成的逐站 control/model 凭据哈希，不接收明文，也不代替部署或 readiness 检查。

部署 worker 使用独立的 `X-AgentAPI-Provisioning-Credential`，Sub2API 通过 `AGENT_PROVISIONING_WORKER_CREDENTIAL` 或只读 Secret 文件 `AGENT_PROVISIONING_WORKER_CREDENTIAL_FILE` 验证。该共享凭据仅能读取 `pending/provisioning` 列表、监听 provisioning SSE、GET 单个 Agent、POST claim/lease、PATCH 进度和 POST 显式激活；它不能创建、暂停、恢复、撤销、重试开站记录，也不能访问其他 Admin API。租约 token 通过独立 `X-AgentAPI-Provisioning-Lease` 头传递，不替代 worker credential；claim 响应禁止缓存。审计认证身份标记为 `agent_provisioning_worker`。它是全局 provisioning-only 凭据，不是逐 Agent 凭据；AgentAPI 每个运行实例仍有独立的管理员/模型服务凭据待收敛问题。

**当前 worker allowlist 补充**：上述共享凭据还可在有效租约下调用 `POST /api/v1/agent-provisioning/agents/{agent_id}/runtime-credentials`，仅登记当前 Agent 的 `control_token_hash` 与 `model_token_hash`。部署包 CLI 在 worker 主机生成明文凭据并写入逐站 Secret 文件；Sub2API 不接收明文、只保存哈希。worker 凭据仍是跨 Agent 共享的开站身份，而已登记的 runtime control/model 凭据是逐 Agent 的业务运行时身份。生产 Secret 注入和 edge 安装验收仍未完成。

## 3. 用户控制面接口

### 3.1 创建主站用户

```http
POST /api/v1/agent-control/agents/{agent_id}/users
Idempotency-Key: <registration-request-id>
```

请求示例：

```json
{
  "email": "user@example.com",
  "display_name": "User",
  "registration_source": "agentapi"
}
```

响应示例：

```json
{
  "main_user_id": "u_10001",
  "agent_id": "agt_01H...",
  "status": "active",
  "session_bootstrap": "<仅在采用既有登录/SSO流程时返回的短期结果>"
}
```

密码和登录凭据必须按照主站现有认证机制处理，不能在响应中返回主站 SuperKey。

### 3.2 修改代理用户

```http
PATCH /api/v1/agent-control/agents/{agent_id}/users/{main_user_id}
```

可修改范围由 `plan_id` 和代理权限决定，例如启停、分组、限额和展示资料。不能修改全局设置、其他 Agent 用户或主站管理员。

### 3.3 查询余额和用量

```http
GET /api/v1/agent-control/agents/{agent_id}/users/{main_user_id}/balance
GET /api/v1/agent-control/agents/{agent_id}/users/{main_user_id}/usage
```

接口必须验证：

```text
main_user_id 属于 agent_id
agent.status == active 或允许只读查询
调用凭据具有对应 scope
```

当前 AgentAPI 的映射用户启停通过本地 Owner Session 保护，并在映射范围校验后调用 Sub2API `PATCH /api/v1/agent-runtime/users/{id}/status`，请求只包含 `status`。AgentAPI 不直连主站数据库；Sub2API 再次校验逐站 control credential 与用户映射。禁用先关闭本地访问门控，启用须等主站返回目标状态后才打开本地门控；状态更新失败时本地访问保持 fail-closed。该操作改变的是 Sub2API 用户的全局状态。

## 4. 额度和账务接口

### 4.1 代理预充值

```http
POST /api/v1/agent-control/agents/{agent_id}/wallet/recharge-orders
Idempotency-Key: <order-create-key>
```

该接口创建代理向主站预存额度的订单。支付确认后由主站账务服务入账。

### 4.2 充值确认

```http
POST /api/v1/agent-control/recharge-orders/{order_no}/confirm
Idempotency-Key: <provider-event-id>
```

不接受客户端直接传入“已支付”作为唯一依据。必须完成支付签名、金额、商户号和订单状态验证。

### 4.3 分配用户额度

```http
POST /api/v1/agent-control/agents/{agent_id}/users/{main_user_id}/wallet/allocate
```

请求示例：

```json
{
  "amount": "100.00",
  "reason": "user_recharge",
  "source_order_no": "R202609210001"
}
```

分配必须满足代理可用额度足够，并在同一个账务事务中写入代理账户和用户子账户流水。

## 5. 模型代理接口

模型请求继续使用主站公共 `/v1` 协议，不把管理员接口当作模型代理接口：

```http
POST {LINK}/v1/chat/completions
Authorization: Bearer <SUB2API_APP_CREDENTIAL>
X-Sub2API-On-Behalf-Of: <CURRENT_SESSION_MAIN_USER_ID>
X-Sub2API-Satellite: agentapi
```

方案 A 下该头使用当前 Session 的 `main_user_id`；Sub2API 校验 active Agent 用户映射后，以逐站 model credential 绑定的 `agent_owner_main_user_id` SuperKey 承担扣费。浏览器不能传入或覆盖此头；身份验证和最终扣费身份分离的关系见 [17-账务权威与主站扣费桥接](17-账务权威与主站扣费桥接.md)。

图片和视频使用仓库公开模型文档中的接口和模型名。浏览器不得直接发送这三个服务头；它们只由 AgentAPI 服务端生成。

## 6. 运行时凭据与最小权限

- 托管 AgentAPI 使用逐站 `agt_ctl_` control 凭据和 `agt_model_` model 凭据；明文只在 AgentAPI 服务端外部 Secret 文件中，Sub2API 仅存哈希并记录凭据用途，可逐 Agent 撤销；
- control 凭据由 Sub2API 的 `/api/v1/agent-runtime/*` 路由 allowlist 限制，只能读取对应 Agent/Owner/usage、绑定经身份验证的用户、更新当前 Agent 已绑定用户状态、同步该 Agent 的公开模型 allowlist 和订阅该 Agent 的状态事件；
- `PUT /api/v1/agent-runtime/model-policy` 只更新 control credential 所属 Agent 的模型范围；Sub2API 验证名称属于公开目录，将配置持久化到该 Agent 的 model credential，并在 `/v1` 网关入口强制校验请求体模型、阻止缺失模型绕过显式策略，同时限制 `/v1/models` 发现结果。NULL 范围代表公开目录默认范围，显式空数组代表禁止全部模型；
- 用户余额、模型调用和额度读取使用 Sub2API `/v1` 接口及服务端 `SUB2API_APP_CREDENTIAL`、`X-Sub2API-On-Behalf-Of`、`X-Sub2API-Satellite` 请求头；不回退到全局管理员 Key；
- 部署 worker 另用共享、provisioning-only 凭据，访问独立开站 API allowlist。该凭据不能用于 Agent 业务运行时，也不具备主站管理员接口权限；
- 控制状态 SSE 使用数据库提交后通知，事件只作重读提示；AgentAPI 保留周期 GET 兜底，并在权威状态不可读或过期时 fail closed。

本地模型策略用于 AgentAPI UI、预授权前校验和主站策略同步；托管 Agent 的 Sub2API model credential 另有服务端强制 scope，二者都必须生效。生产 edge Secret 注入/轮换、worker 运维权限和真实 DNS/TLS/部署验收仍是独立上线工作。

## 7. 统一错误格式

```json
{
  "error": {
    "code": "AGENT_USER_NOT_FOUND",
    "message": "user is not mapped to this agent",
    "request_id": "req_01H...",
    "retryable": false
  }
}
```

建议错误码：

| 错误码 | 含义 |
| --- | --- |
| `AGENT_NOT_FOUND` | Agent 不存在 |
| `AGENT_SUSPENDED` | Agent 已暂停 |
| `AGENT_DOMAIN_NOT_READY` | 域名未就绪 |
| `AGENT_USER_NOT_FOUND` | 用户不属于当前 Agent |
| `AGENT_CREDENTIAL_REVOKED` | 服务凭据已撤销 |
| `AGENT_INSUFFICIENT_BALANCE` | 代理或用户额度不足 |
| `AGENT_DUPLICATE_REQUEST` | 幂等键已经处理 |
| `PAYMENT_NOT_VERIFIED` | 支付尚未验证 |
| `BILLING_CONFLICT` | 账务并发冲突 |
| `UPSTREAM_UNAVAILABLE` | 主站或上游不可用 |
