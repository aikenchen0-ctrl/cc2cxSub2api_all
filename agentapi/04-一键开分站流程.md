# 04 一键开分站流程

## 1. 目标

用户点击“一键开分站”后，系统自动完成代理账户、域名、代理服务配置和主站额度账户的编排。开站接口是一个长流程，必须支持幂等、重试、状态查询和失败恢复。

## 2. 开站前置条件

- 操作者已经登录主站；
- 操作者拥有开站权限；
- 代理方案、默认模型、限额和支付能力已配置；
- 请求域名或 slug 符合格式和保留字规则；
- 目标域名没有被其他 Agent 使用；
- 主站控制面可用；
- 如果采用独立实例部署，镜像和运行环境已准备好。

## 3. 推荐接口

```http
POST /api/v1/agent-provisioning/agents
Idempotency-Key: <一次性开站幂等键>
Authorization: <主站当前管理员会话或受控服务凭据>
Content-Type: application/json
```

请求示例：

```json
{
  "requested_slug": "agent01",
  "display_name": "Agent 01",
  "owner_main_user_id": "u_10001",
  "plan_id": "standard",
  "brand": {
    "name": "Agent 01",
    "logo_url": null
  },
  "domain_mode": "platform_subdomain"
}
```

首次响应建议立即返回任务记录，而不是长时间阻塞 HTTP：

```json
{
  "agent_id": "agt_01H...",
  "status": "provisioning",
  "domain": "agent01.cc2.cx",
  "request_id": "req_01H...",
  "status_url": "/api/v1/agent-provisioning/agents/agt_01H..."
}
```

## 4. 编排步骤

### Step 1：校验和锁定幂等键

1. 校验当前操作者、方案和开站数量限制；
2. 规范化 slug 和域名；
3. 检查 `Idempotency-Key` 是否已经成功或正在处理；
4. 对 `requested_slug` 和 `hostname` 加唯一锁；
5. 创建 Agent 记录，状态为 `pending`。

### Step 2：分配代理身份

生成稳定的 `agent_id`，并保存：

```text
agent_id
code/slug
domain
owner_main_user_id
plan_id
status = provisioning
```

`agent_id` 不因重试变化。域名和代理编号一旦进入 `active`，不能静默改名。

### Step 3：创建主站代理账户

在主站控制面创建：

- 代理预存账户；
- 可用模型/分组范围；
- 默认限额和请求策略；
- `source_agent_id` 归属标记；
- 代理服务凭据或密钥引用。

这一步不向代理管理员返回全局管理员 Key。

### Step 4：配置域名和 TLS

平台子域名优先使用通配符 DNS/TLS。流程只需确认域名可解析、入口可以识别 Host、证书覆盖该域名。

自定义域名需要额外完成：

1. DNS 所有权验证；
2. 域名指向检查；
3. ACME/证书签发；
4. Host allowlist 更新。

### Step 5：写入 AgentAPI 配置

配置至少包括：

```text
AGENT_ID
AGENT_DOMAIN
MAIN_API_URL
MAIN_AGENT_ACCOUNT_ID
SERVICE_CREDENTIAL_REF
PLAN_ID
BRAND_CONFIG
```

独立实例模式下，配置写入部署平台并启动实例；共享实例模式下，写入 AgentAPI 控制面并刷新配置缓存。

### Step 6：健康检查

依次检查：

- DNS/入口 Host；
- TLS；
- AgentAPI `/healthz`；
- AgentAPI 能否使用服务凭据访问主站健康接口；
- 主站能否识别 `agent_id`；
- 测试用户流程不会触发真实扣费。

健康检查失败时，Agent 保持 `provisioning` 或转为 `failed`，不能提前显示为可用。

### Step 7：激活

所有步骤成功后：

```text
agents.status = active
domain_bindings.status = active
service_credential.status = active
```

向操作者返回域名、状态、管理员入口和下一步说明。永远不返回管理员 Key 明文。

## 5. 状态机

```text
pending
  ↓
provisioning ──失败──▶ failed
  ↓                         │
 active ◀────重试───────────┘
  ↓
 suspended ───────────────▶ active
  ↓
 revoked（终态）
```

状态规则：

- `pending`：记录已创建，尚未开始外部操作；
- `provisioning`：正在执行编排；
- `active`：可以注册、充值和消费；
- `suspended`：保留数据，但拒绝新业务；
- `failed`：可重试，不能重复产生资源；
- `revoked`：凭据和域名均不可恢复使用。

## 6. 补偿和回滚

| 已完成步骤 | 后续失败 | 补偿动作 |
| --- | --- | --- |
| 创建 Agent | 创建主站账户失败 | Agent 标记 `failed`，保留失败原因 |
| 创建主站账户 | 域名配置失败 | 暂停账户，不删除已产生的用户/账务对象 |
| 创建凭据 | 实例启动失败 | 撤销凭据，允许重新生成 |
| 用户映射已写入 | 主站用户创建重复 | 使用幂等键查询原用户，不再新建 |
| 支付配置已写入 | 代理激活失败 | 支付入口关闭，未支付订单自动关闭 |

原则：账务和用户数据不做盲目物理删除，优先使用状态关闭和补偿流水。

## 7. 重试规则

- 网络超时：使用相同 `request_id` 和幂等键重试；
- 业务拒绝：不自动重试，记录可读原因；
- 已经成功但响应丢失：查询状态，不重复创建；
- 服务凭据过期：先轮换凭据，再重试受影响步骤；
- 连续失败达到阈值：转 `failed`，要求人工处理。

## 8. 当前可执行的部署基元

`backend/cmd/agentapi-provision` 已实现平台子域名模式的部署包生成，供主站控制面或受控运维任务调用。它负责：

- 校验并规范化 slug、域名、Owner、主站 URL 和镜像引用；
- 以全局锁串行更新本地 provisioning 状态；
- 对相同 `Idempotency-Key + 请求参数` 返回原结果，不重新生成 Session Secret；
- 拒绝幂等键复用、slug 冲突和域名冲突；
- 生成每站独立的 Compose、持久卷、Nginx Host 配置和 Session Secret；
- 只引用管理员 Key、应用凭据和 SSO Secret 的外部文件路径，生成结果不包含这些秘密。

生成状态为 `generated`，不等于 `active`。平台控制面仍必须完成通配符 DNS/TLS 前置检查、创建外部 Docker 网络、提供三个服务端秘密文件、启动 Compose、安装 Nginx 配置并通过 `/readyz` 后，才可以把主站开站任务标记为 `active`。
