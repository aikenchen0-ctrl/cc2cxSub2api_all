# 04 一键开分站流程

## 1. 目标

用户点击“一键开分站”后，系统自动完成代理账户、域名、代理服务配置和主站额度账户的编排。开站接口是一个长流程，必须支持幂等、重试、状态查询和失败恢复。

## 2. 开站前置条件

- 操作者已经登录主站；
- 操作者拥有开站权限；
- 代理方案、默认模型、限额和支付能力已配置；
- 请求域名或 slug 符合格式和保留字规则；
- 目标域名没有被其他 Agent 使用；
- 主站控制面可用；
- 如果采用独立实例部署，镜像和运行环境已准备好。

## 3. 推荐接口

```http
POST /api/v1/agent-provisioning/agents
Idempotency-Key: <一次性开站幂等键>
Authorization: <主站当前管理员会话或受控服务凭据>
Content-Type: application/json
```

请求示例：

```json
{
  "requested_slug": "agent01",
  "display_name": "Agent 01",
  "owner_main_user_id": "u_10001",
  "plan_id": "standard",
  "brand": {
    "name": "Agent 01",
    "logo_url": null
  },
  "domain_mode": "platform_subdomain"
}
```

首次响应建议立即返回任务记录，而不是长时间阻塞 HTTP：

```json
{
  "agent_id": "agt_01H...",
  "status": "provisioning",
  "domain": "agent01.cc2.cx",
  "request_id": "req_01H...",
  "status_url": "/api/v1/agent-provisioning/agents/agt_01H..."
}
```

## 4. 编排步骤

### Step 1：校验和锁定幂等键

1. 校验当前操作者、方案和开站数量限制；
2. 规范化 slug 和域名；
3. 检查 `Idempotency-Key` 是否已经成功或正在处理；
4. 对 `requested_slug` 和 `hostname` 加唯一锁；
5. 创建 Agent 记录，状态为 `pending`。

### Step 2：分配代理身份

生成稳定的 `agent_id`，并保存：

```text
agent_id
code/slug
domain
owner_main_user_id
plan_id
status = provisioning
```

`agent_id` 不因重试变化。域名和代理编号一旦进入 `active`，不能静默改名。

### Step 3：创建主站代理账户

在主站控制面创建：

- 代理预存账户；
- 可用模型/分组范围；
- 默认限额和请求策略；
- `source_agent_id` 归属标记；
- 代理服务凭据或密钥引用。

这一步不向代理管理员返回全局管理员 Key。

### Step 4：配置域名和 TLS

平台子域名优先使用通配符 DNS/TLS。流程只需确认域名可解析、入口可以识别 Host、证书覆盖该域名。

自定义域名需要额外完成：

1. DNS 所有权验证；
2. 域名指向检查；
3. ACME/证书签发；
4. Host allowlist 更新。

### Step 5：写入 AgentAPI 配置

配置至少包括：

```text
AGENT_ID
AGENT_DOMAIN
MAIN_API_URL
MAIN_AGENT_ACCOUNT_ID
SERVICE_CREDENTIAL_REF
PLAN_ID
BRAND_CONFIG
```

独立实例模式下，配置写入部署平台并启动实例；共享实例模式下，写入 AgentAPI 控制面并刷新配置缓存。

### Step 6：健康检查

依次检查：

- DNS/入口 Host；
- TLS；
- AgentAPI `/healthz`；
- AgentAPI 能否使用服务凭据访问主站健康接口；
- 主站能否识别 `agent_id`；
- 测试用户流程不会触发真实扣费。

健康检查失败时，Agent 保持 `provisioning` 或转为 `failed`，不能提前显示为可用。

### Step 7：激活

所有步骤成功后：

```text
agents.status = active
domain_bindings.status = active
service_credential.status = active
```

向操作者返回域名、状态、管理员入口和下一步说明。永远不返回管理员 Key 明文。

## 5. 状态机

```text
pending
  ↓
provisioning ──失败──▶ failed
  ↓                         │
 active ◀────重试───────────┘
  ↓
 suspended ───────────────▶ active
  ↓
 revoked（终态）
```

状态规则：

- `pending`：记录已创建，尚未开始外部操作；
- `provisioning`：正在执行编排；
- `active`：可以注册、充值和消费；
- `suspended`：保留数据，但拒绝新业务；
- `failed`：可重试，不能重复产生资源；
- `revoked`：凭据和域名均不可恢复使用。

## 6. 补偿和回滚

| 已完成步骤 | 后续失败 | 补偿动作 |
| --- | --- | --- |
| 创建 Agent | 创建主站账户失败 | Agent 标记 `failed`，保留失败原因 |
| 创建主站账户 | 域名配置失败 | 暂停账户，不删除已产生的用户/账务对象 |
| 创建凭据 | 实例启动失败 | 撤销凭据，允许重新生成 |
| 用户映射已写入 | 主站用户创建重复 | 使用幂等键查询原用户，不再新建 |
| 支付配置已写入 | 代理激活失败 | 支付入口关闭，未支付订单自动关闭 |

原则：账务和用户数据不做盲目物理删除，优先使用状态关闭和补偿流水。

## 7. 重试规则

- 网络超时：使用相同 `request_id` 和幂等键重试；
- 业务拒绝：不自动重试，记录可读原因；
- 已经成功但响应丢失：查询状态，不重复创建；
- 服务凭据过期：先轮换凭据，再重试受影响步骤；
- 连续失败达到阈值：转 `failed`，要求人工处理。

## 8. 当前可执行的部署基元

`backend/cmd/agentapi-provision` 已实现平台子域名模式的部署包生成，供主站控制面或受控运维任务调用。它负责：

- 校验并规范化 slug、域名、Owner、主站 URL 和镜像引用；
- 以全局锁串行更新本地 provisioning 状态；
- 对相同 `Idempotency-Key + 请求参数` 返回原结果，不重新生成 Session Secret；
- 拒绝幂等键复用、slug 冲突和域名冲突；
- 生成每站独立的 Compose、持久卷和 Nginx Host 配置；随机 Session Secret 与逐站 runtime control/model 凭据写入同级受保护的 `runtime-secrets/<slug>/` 目录，生成包不包含明文秘密，Compose 只引用这些 Secret 文件的绝对路径；
- 只引用逐站 runtime control/model 凭据和 SSO Secret 的外部文件路径，生成结果不包含这些秘密。

Sub2API 主站现有 `POST /api/v1/agent-provisioning/agents` 管理接口可幂等创建一条开站控制记录，并提供状态查询、暂停、恢复、可重试失败重置和撤销接口。主站 API 本身不在 Sub2API 进程里直接运行 Docker 或 Nginx 操作；worker 在 claim 租约后由部署包 CLI 生成逐站 runtime control/model 凭据，在启动实例前通过 `POST /api/v1/agent-provisioning/agents/{agent_id}/runtime-credentials` 登记两个凭据的 SHA-256 哈希。主站不接收明文凭据；该登记只接受当前 Agent 的哈希和有效 worker 租约，并支持部署重试幂等。

Agent Owner 配置模型 allowlist 后，AgentAPI 通过逐站 control API `PUT /api/v1/agent-runtime/model-policy` 将同一公开模型集合写入 Sub2API；主站将它绑定到该 Agent 的 model credential，并在 `/v1` 入口执行服务端校验。初始未配置的范围为公开卫星目录，显式空数组禁止全部模型。

主站另提供管理员鉴权的 `PATCH /api/v1/agent-provisioning/agents/{agent_id}/progress`，供受控部署 worker 以幂等、按序方式报告 `validating → bundle_generated → deploying → domain_check → tls_check → readiness_check` 阶段。失败只提交受限 `failure_code`，由主站映射安全的固定错误文案，不接收可能带密钥的任意日志。每次进度更新与事件在同一事务提交，并通过数据库通知触发 SSE；SSE 消费者仍需 GET 权威记录。

多 worker 并发由主站租约控制：worker GET 权威记录后调用 `POST /api/v1/agent-provisioning/agents/{agent_id}/claim` 原子认领 `pending/provisioning` 任务。主站只持久化随机租约 token 的 SHA-256 哈希；原始 token 只在 claim 响应中返回一次，响应带 `Cache-Control: no-store` 和 `Pragma: no-cache`。租约默认 90 秒，worker 每 20 秒用 `POST .../{agent_id}/lease` 续租；worker 的进度和激活请求必须带 `X-AgentAPI-Provisioning-Lease`，成功进度更新也会延长租约。无有效租约、租约过期或另一 worker 已持有租约时，主站拒绝对应操作；失租后 worker 取消部署 context，不再推进主站状态。该租约用于控制面所有权，但并不能为 Docker/Nginx 副作用提供 fencing；真实主机副作用仍要求部署操作幂等。

AgentAPI 新增 `cmd/agentapi-provision-worker` 受控主机 worker 程序：启动后先用 Sub2API 管理 API 分页扫描 pending/provisioning 记录，之后通过受限鉴权 SSE 获取变更提示并定期轮询兜底；SSE 只携带 Agent ID，每个任务在执行前 GET 权威记录。它调用幂等部署 CLI 生成包，检查/创建专用 Docker edge network，启动独立 Compose 实例，安装并校验 Nginx 配置（失败回滚），确认公开 DNS 全部解析至配置的 edge IP allowlist，固定 edge IP 验证 TLS/healthz，最后轮询 `/readyz`。全部通过后由 worker 使用现有幂等 activation API 确认 readiness 并激活。进程重启会按最新主站记录恢复；网络/DNS/TLS/ready 失败用安全错误码写回。失败记录不会被 worker 自动重试；仅 `can_retry=true` 时由管理员在主站 UI 显式触发 retry，主站将其重置为 pending 后 worker 再从头处理。

worker 是独立受控部署程序，不在 Sub2API 进程/容器内运行。它必须部署到能访问目标 Docker daemon 与 Nginx 配置目录的专用 edge 运维节点，并通过管理 API 访问 Sub2API。worker 自身以 `X-AgentAPI-Provisioning-Credential` 发送 `AGENT_PROVISIONING_WORKER_CREDENTIAL_FILE` 中至少 32 字节的凭据；Sub2API 只允许该凭据读取 `pending/provisioning` 列表、监听 SSE、GET Agent、POST claim/lease、PATCH progress 和 POST activate。claim 返回的一次性租约 token 不可写入日志或工单；凭据在当前主站范围内共享，不是逐 Agent runtime 凭据。部署时还需配置逐站 `AGENT_RUNTIME_CONTROL_CREDENTIAL_FILE`、`SUB2API_APP_CREDENTIAL_FILE`（model credential）、`SUB2API_SSO_SECRET_FILE`、`AGENTAPI_NGINX_CONFIG_DIR`、`AGENTAPI_NGINX_CONTAINER` 和 `AGENTAPI_EDGE_IPS`。AgentAPI 运行实例不使用 `SUB2API_ADMIN_KEY_FILE`；用户、Owner、usage 与托管状态通过 Sub2API 公开认证 API、逐站 runtime API 和逐站模型 credential 完成。所有服务秘密只以绝对文件路径挂载，不复制进包或 Compose 环境值。Sub2API 服务端需配置同一 `AGENT_PROVISIONING_WORKER_CREDENTIAL`，或将 `AGENT_PROVISIONING_WORKER_CREDENTIAL_FILE` 指向只读挂载文件。若未设置 `MAIN_API_URL`，worker 可回退读 `LINK`；本地省略协议的 `localhost:18080` 会规范为 HTTP，远端控制面必须显式使用 HTTPS。独立 worker 的环境模板位于 `backend/cmd/agentapi-provision-worker/.env.example`。使用同一源码版本构建：

当前版本的 worker allowlist 还包括在有效租约下调用 `POST /api/v1/agent-provisioning/agents/{agent_id}/runtime-credentials`，登记 CLI 在 worker 主机上生成的当前 Agent `control_token_hash` 和 `model_token_hash`。主站只保存两个哈希、不接收明文；worker provisioning 凭据仍是共享的控制面身份，和逐站 runtime credential 不是同一凭据。

```bash

```

worker 要持有对 Docker/Nginx 的部署权限，并持有共享的 provisioning-only 主站凭据；这是有基础设施写权限的高风险运维组件，必须限制节点登录、文件权限、网络出口并轮换凭据。该凭据缩小了 Sub2API API 面，但不限制 worker 节点上的 Docker/Nginx 权限；仍没有逐 Agent scope worker 凭据。不可把 worker 暴露为 HTTP 服务或由浏览器调用。

部署包生成状态 `generated` 不等于主站任务 `active`。只有 worker 实际通过 DNS、TLS、`/healthz` 和 `/readyz` 检查并成功调用显式 activation API 后才会 active；若没有运行/配置 worker，仍须外部运维完成同一部署流程并经主站管理员确认 readiness。

托管实例的 `AGENT_ID` 必须直接使用主站创建记录返回的 `agt_<uuid>`，CLI 通过必填 `--agent-id` 写入该值。此类实例默认启用主站期望状态控制：服务端使用逐站 runtime control 凭据通过 `GET /api/v1/agent-runtime/agent` 读取状态，并监听 `GET /api/v1/agent-runtime/agent/stream` 数据库通知 SSE；SSE 只触发重新读取权威记录，周期 GET 作为断流兜底。主站状态不是 `active`、权威状态超过陈旧窗口或查询不可用时，AgentAPI 拒绝业务流量；`/healthz` 和 `/readyz` 仍可用于部署探测。部署 operator 通过管理员鉴权的 `POST /api/v1/agent-provisioning/agents/{agent_id}/activate` 并显式确认 readiness 后，才可把 pending 记录切为 active；当前接口不会自行执行 readiness 检查。这个请求门控让 suspend/resume/revoke 对已启动的托管实例生效，但不会替代外部部署 worker，也不会自动部署或配置 DNS/TLS。
