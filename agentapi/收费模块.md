# 代理站收费模块

日期：2026-10-04。

本文按当前代码记录。站长收费配置、渠道、套餐和订单都存在本站数据库，并且每条记录都带 `agent_id`。

## 谁收费

用户在代理站付款，钱进入该站站长自己配置的支付渠道。支付确认后，额度记入该用户在本站的钱包。之后这个用户调用模型时，主站从站长账户扣实际费用，不从该用户的主站余额再扣一笔。

站长没有开通收费时，充值页不能创建订单。
收款总开关切换后会立即保存；如果服务商和支付方式已配置但总开关仍关闭，设置页会提供“立即开启收款”，充值页会明确提示站长尚未开启在线收款，而不是笼统显示没有可用支付方式。

## 站长配置

站长入口是系统设置里的「支付设置」，地址 `/admin/settings?tab=payment`。界面沿用 Sub2API 支付设置：支付开关、限额、手续费、汇率、取消频率、支付宝选项、帮助图文，以及可拖拽的服务商实例。接口在 `/api/v1/agent/admin/billing`，只接受当前租户的站长 Session。

收费设置包括：开关、最低和最高金额、每日限额、订单超时、待支付上限、手续费率、模型计费倍率、订阅美元兑人民币、渠道分配、商品名、开放的支付方式、支付宝显示开关、说明文字和说明图片。

支付渠道支持 `easypay`、`alipay`、`wxpay`、`stripe`、`airwallex`。每个渠道保存名称、启用状态、支付模式、排序、支持的支付方式、限额 JSON、退款开关和渠道密钥。密钥加密后只存在服务端，列表接口不返回密钥明文。

套餐保存名称、价格、原价、币种、有效期、特性和是否在售。订单保存金额、支付方式、渠道、状态和所属用户。取消和退款只作用于本站订单。当前管理员/用户取消只把本地订单从 `PENDING` 改成 `CANCELLED`，没有调用渠道 `CancelPayment`；`UpdateStationOrderStatus` 与 `cancelStationUserOrder` 都不重建渠道实例，因此渠道侧可能仍可付款。上线前必须补“先取消渠道、再 CAS 本地状态”，并按渠道能力记录成功/不可取消/失败可重试；取消不得只改本地状态。
套餐目前只有本站价格与展示字段，没有订阅权益主键：`order_type=subscription` 支付成功后仍按普通充值进入本站钱包与主站余额，既没有写入主站 `user_subscriptions`，也没有本地权益表或按权益结算的模型路径（`agentapi/backend/station_billing.go:1368-1375`、`station_payment_reconcile.go:60-70`、`main.go:2194-2203`）。在补齐“套餐映射主站订阅组 + 订单幂等履约 + 退款只撤权益”之前，不得把套餐当作已生效订阅对外展示；`subscription` 入口应下线或 4xx 且不建单，不得按普通充值履约。套餐订单不得创建现金充值锚点，退款只撤销或缩短权益，权益已部分消费时只能作废剩余额度或转人工，不得按 `amount_minor`/`offset_allocated` 折算现金。套餐若最终映射到主站订阅，还必须服从主站 `S2A-09` 的订阅事实与 Payer 互斥：本站钱包代付遇到用户唯一有效订阅时 403 `SUBSCRIPTION_ACTIVE`，不得把主站订阅额度当作本站套餐已交付。

另一个站长读取渠道、套餐或订单时，看不到本站记录。

### 数据隔离与下单规则

- 租户和用户由本站 Session 决定，忽略请求体/查询参数中的 `agent_id`、用户或付款人选择；跨租户渠道 ID 返回 404。匿名和普通成员不能修改管理配置。
- 支付配置、加密商户凭据、订单、实例限额、取消次数和钱包记录均按 `agent_id` 隔离。回调路径由服务端生成 `/api/v1/agent/billing/webhook/{agent_id}/{provider}`，复制另一站的配置也不会保留其租户路径。
- 每用户每日额度按「本站 + 当前用户」统计，跨支付方式合并；实例每日额度按「本站 + 实例 + 支付方式」统计，Stripe 共用实例额度。到期未付款订单不占额度。当前日界线按服务端 UTC 零点计算。
- 下单和支付配置变更使用本站独立的数据库租约，串行执行限额检查和订单预留。先记录订单，再请求服务商，避免快速回调找不到订单；创建失败保留失败订单且不回传 SDK 内部错误或密钥。
- 全局充值金额限制应用于输入充值金额；实例限额应用于含手续费的应付金额。手续费按币种最小单位向上取整（如 JPY/KRW 为整数）。订阅汇率仅在所选服务商币种为 CNY 时应用。
- 多实例同一方式允许轮询或最小交易额选择。同一方式币种冲突时采用首个排序实例的币种，不在支付过程中静默切换币种。Stripe 收银台使用本次选中实例的公开密钥。
- 存在有效待支付或处理中订单时，禁止删除渠道、替换商户凭据或移除订单需要的支付方式；名称、排序和停用新单等安全操作仍可执行。
- 回调校验签名、商户身份（SDK 提供时）、本站订单、渠道实例、金额和币种。跨站通知不入账，重复通知幂等；Stripe/Airwallex 签名头兼容 HTTP 大小写规范。
- 浏览器不共享可变回调路径。切换站点/用户或退出会话时清理旧付款恢复信息；SVG 上传预览经过净化。

自动化验证覆盖两个站长和普通成员的访问边界、配置局部更新、密钥保留/加密、未完成订单保护、并发待支付上限、每用户限额、汇率/币种手续费、五类表单、自定义方式、早到/重复/跨站回调及带签名的 Stripe/Airwallex 通知。外部服务商实际支付和退款仍需各站长使用自己的测试商户联调；本次不产生真实交易。

## 用户付款

充值页读取 `GET /api/v1/agent/payment/checkout-info`。返回的支付方式和套餐来自当前站点，不读取主站收银台。

创建订单走 `POST /api/v1/agent/payment/orders`。浏览器不能指定用户或站点。EasyPay 会按该站保存的 `pid`、`pkey` 和 `apiBase` 生成支付地址。回调地址是 `/api/v1/agent/billing/webhook/{agent_id}/easypay`，签名用该站自己的密钥校验。验签通过后，只给这笔订单所属用户增加本站钱包额度，重复通知不会再次入账。

余额充值按“本金” 1:1 入账，不存在充值到账倍率。例如充值 100 元、渠道手续费 2%，用户实付 102 元，站内余额增加 100 元。金额恒等式为 `pay_amount_minor = amount_minor + fee_minor`，这里 `amount_minor` 是入账本金、`fee_minor` 是渠道手续费；手续费不得计入用户余额，也不参与模型计费倍率。站长利润统一通过模型计费倍率或分组计费倍率获得；历史配置中残留的充值倍率字段不再读取、保存或参与下单，即使旧数据库值为 1.25 也按 1 倍处理。

支付宝、微信、Stripe、Airwallex 和易支付都使用该站自己保存的密钥发起支付和校验回调。回调地址带当前 `agent_id`，验签失败不会入账。

### 主站计费键对齐（2026-11-15 只读核对）

主站 `middleware/client_request_id.go:26-40` 只从请求上下文读取 `ctxkey.ClientRequestID`，从未读取 `X-Client-Request-ID` 请求头；调用链上也没有把该头写入上下文的入口。因此“卫星发送稳定 `X-Client-Request-ID`，主站按该键去重/回查”目前只是目标，不是现有能力。AgentAPI 自身 `main_client.go:992-994` 也只发送 `X-Request-ID`，与主站和卫星约定不一致。

在 S2A-02 落地前，AgentAPI 不得因本地 `chargeID/request_id` 稳定就宣称主站只扣一次，也不得据本地 settlement 唯一键推断主站 usage 唯一。落地时必须同时满足：主站中间件从请求头读取 `X-Client-Request-ID`、校验长度/字符集、校验应用凭据与 slug 匹配后才写入上下文，非法值 4xx 拒绝而非静默换成随机 UUID；AgentAPI 转发模型请求时必须发送与本地 `chargeID` 相同的 `X-Client-Request-ID`，不得另发只供日志关联的 `X-Request-ID` 来代替计费键。两端验收：同一 `chargeID` 重放只形成一条主站权威 usage；`X-Request-ID` 与 `X-Client-Request-ID` 不一致时不得命中去重；普通客户端伪造该头被 4xx；无该头的主站请求仍生成随机值，但只能在响应中标为非计费关联，不能用于卫星去重。

**受理状态必须与 usage 同键返回**：主站 usage/反查接口必须返回持久 `request_admission`，至少 `not_seen`（本端未记录该键）、`accepted`（已受理、可能尚无 usage）、`rejected_before_upstream`（调用上游前明确拒绝）、`settled`（唯一权威 usage）、`conflict`（多行/指纹或付款主体冲突）、`unknown`（状态不可读或未持久化）。只有 `rejected_before_upstream` 且 `dispatch_state=not_started`（须由主站写出点事件证明，不得仅凭时间戳为空）才可作为 AgentAPI 自动重发或免费处理的证据；自动重发/免费处理还必须 ## 模型扣费

本站收费开通后，模型请求仍带当前用户的 `X-Sub2API-On-Behalf-Of`，另外带站长的 `X-Sub2API-Payer`。主站只从站长余额扣实际费用。用户本站钱包不大于 0 时，请求直接拒绝。 注意：主站当前仍先按 Key 组判定订阅，若终端用户存在有效订阅，可能先消耗订阅额度而不扣站长余额；这与本站已经扣费的用户钱包不一致，属于待修缺陷，不能据此宣称“只扣站长余额”已成立。

用户实际扣费按“主站实际费用 × 模型计费倍率”计算；主站权威金额先以 `*_usd_nanos`/定点十进制读取，只有写入本站 `*_cents` 账本或生成支付金额时才换算为分。当前实现固定为：先把倍率量化到 6 位（`round(rate×1,000,000)`），再计算 `ceil(actual_cents × scaled / 1,000,000)`，即先把金额换算为分后乘倍率并向上取整；不得先按分四舍五入再乘倍率。结算必须保存原 nanos/定点金额、原始倍率、量化后的倍率、取整方式与最终 `charged_cents`，且同一 settlement 重放只能按首次快照复算，不能读取最新设置或改用另一种取整方式。当前 `settlements` 只有 `station_rate_multiplier`（`store.go:546-566`），未保存原 nanos 或取整方式，属于待实现项：修复前只能按现有字段复算并明确标记“快照不完整”，不得宣称已满足上述可复算要求。若后续改为其他规则，必须作为显式版本化策略写入快照并补迁移/回归测试，不能在未记录规则时静默改变金额。站长仍按主站实际费用结算，差额留在本站。主站代付金额必须与 `PayerCost`、usage `charged_cost` 及平台配额使用同一 8 位 half-away-from-zero 量化值；第 9 位 half 边界不得只在本地分账或对账侧舍入。倍率最低 0.01、最高 1000，默认 1。每个结算在请求开始时快照当时的倍率，之后修改设置不会追溯已发起或待补单的请求。

充值订单的请求幂等键还必须由服务端持久化为唯一值：空键不得静默生成随机键后新建订单，表上应有 `UNIQUE(agent_id, request_id)`，命中重复键要比较用户/金额/币种/渠道。站点订单金额必须以最小货币单位整数持久化（当前 `station_payment_orders.amount/pay_amount/fee_rate` 为 `REAL`，`store.go:781-804`），入账、退款与对账都不得用 `float64*100` 再 `Round`。站点订单的“完成”与“钱包到账”还必须是同一原子结果或显式可重放中间态：当前 `settleStationOrder` 先把订单写成 `COMPLETED`，再另开事务 `CreditUserRecharge`；入账失败时订单已是终态，后续回调因 `COMPLETED` 不再补账，后台只扫 `PENDING`/`paid_pending_allocation`，会永久出现“显示已支付、钱包未加”。必须把“渠道已支付”和“本地入账完成”分成可持久恢复的两态（例如 `PAID`→`RECHARGING`→`COMPLETED`），或提供独立恢复扫描：凡 `COMPLETED` 但 `user_recharge:<order_no>` 账本不存在者，必须按原订单金额与幂等键补入账，不得按当前余额或最新配置重算。`paid_pending_allocation` 也不能只靠一次回调推进，必须有不依赖计费模式、支付开关与 7 天窗口的持久恢复队列，并与首次入账共用同一函数和 `order_no` 幂等键。所有资金表 CAS 更新命中 0 行时必须整笔回滚，不得继续写流水。验收：在 `CompleteStationOrder` 成功后注入 `CreditUserRecharge` 失败并重启进程，断言后台扫描能以同一 `order_no` 唯一补账一次；重复回调不产生第二笔 `user_recharge`；恢复扫描不得处理 `order_type=subscription` 的权益订单。
渠道退款结果不确定时当前只写 `REFUND_PENDING`：后台没有退款扫描，EasyPay/支付宝也没有退款查询实现，只能由管理员再次点击；因此这类订单不能向用户承诺“自动退款完成”，必须在界面标为待人工确认。上线前必须区分可查询与不可查询渠道：支持 `RefundQueryProvider` 的渠道由后台按持久退款单轮询，只有回执金额、币种/最小单位、订单号与退款号逐项一致才可推进终态；不支持查询的渠道不得伪装成自动完成，必须持久保留 `REFUND_PENDING` 与人工待办并按 SLA 告警。后台扫描不得依赖管理员点击或进程内状态，重启后仍按 `refund_intent_id/trade_no` 继续；同一退款单并发查询与终态更新必须 CAS 至多一次，`REFUND_PENDING` 期间继续冻结对应额度，不得因超时自动回补钱包。验收：可查询渠道在提交成功后重启，后台能收敛到唯一终态；不可查询渠道保持待人工且不会重复退款；查询回执不确定/冲突保持原状并告警。
站点订单超时目前没有自动终态：超过 `expires_at` 后只是不再计入待支付/额度，界面仍显示 `PENDING`，也不会调用渠道取消；若用户此后仍完成支付，系统会按正常成功回调入账。上线前必须补过期扫描：Stripe/Airwallex/支付宝/微信先调用 `CancelPayment` 并记录审计，EasyPay 等无取消能力的渠道记录“不可取消”并转人工，但不得因此阻断本地 `EXPIRED` CAS；过期后到账只能人工复核或原路退款，不得静默生成第二份余额。
过期还必须拆成两个可核对事实：本地订单已关闭（`expired_at/expire_reason`）与渠道是否仍可能扣款（`provider_cancel_status=succeeded/unsupported/failed`）不能共用 `status`。当前 `ExpireRechargeOrders`（`store.go:1937-1941`）只更新本地行，回调随后在 `RecordPaymentEvent`（`store.go:1991-2016`）被状态守卫拒绝；若渠道已真实扣款，用户资金会处于“渠道已付、本地无待入账记录”的丢单状态。必须在验签、金额、币种、渠道交易号全部匹配时原子记录 `late_payment_status` 并转人工待入账或原路退款，不得用普通 409 让渠道重试；同一 `order_no` 与渠道交易号只允许一条迟到支付事实，且不得自动产生第二份余额。
站点退款终态还必须拒绝冲突回执：`finishStationRefund` 当前在 `REFUNDED`/`REFUND_FAILED` 后直接返回，不比对本次的有效退款金额、`provider` 来源退款号、订单号与有效币种值；必须逐项一致才幂等返回，冲突返回 409/人工复核，不得静默丢弃。币种无渠道值时可按非空订单币种绑定并标 `currency_source=order`，但来源降级或值不同仍是冲突。比对前必须先补齐回执结构：当前 `payment.RefundResponse` 只有 `RefundID/Status`，必须扩展或经 `QueryRefund` 取得 `refund_id/refund_id_source/amount/currency/currency_source/order_no/status`（`amount` 为渠道确认的有效退款额，`currency_source=provider|order`，`refund_id_source=provider|request|derived`），并把首次回执完整持久化；有效金额、`provider` 来源退款号与订单号只能作渠道证据，本地订单值只能作期望值；币种优先取渠道回执并标 `currency_source=provider`，渠道无币种概念时可按非空订单币种绑定并标 `currency_source=order`。退款号还须区分来源：支付宝未拿到渠道号时会回退为 `订单号-refund`，EasyPay 直接用订单号/交易号，这些本地派生值只能做幂等定位，不能证明渠道已退款；只有 `provider` 来源的退款号可参与终态证明。币种同样要区分来源：Stripe/Airwallex/Wxpay 可取渠道币种；支付宝/EasyPay 无独立退款币种字段，只能标记 `currency_source=order` 并使用非空订单币种，不能冒充渠道回执；渠道币种与订单币种不一致即 409/人工复核。渠道返回成功但有效金额缺失、无 `provider` 来源退款号、订单号缺失，或有效金额/退款号/订单号/有效币种与首次回执不一致时，不得写 `REFUNDED`；订单币种为空且渠道无币种同样不得终态。渠道回执币种与订单币种不一致时以 `provider` 为准并 409/人工复核，不得静默改用订单币种重试；首次终态以 `currency_source=order` 绑定的，后续同值 `provider` 只补审计，值不同即冲突。站点退款目前只支持全额：`refundStationOrder` 固定按订单实付金额调用渠道退款，`beginStationRefund` 一次性扣光用户钱包，`finishStationRefund` 不回补也不调整站长锚定额度。`REFUND_FAILED` 后重新发起必须复用原 `refund_intent_id` 与已持久扣款额，只能查询/重发同一渠道退款请求；不得按当前钱包余额或当前订单金额重新扣一次，也不得把“已回补成功”当作可再次扣款的依据。注意入账侧也没有订单级额度锚点：`settleStationOrder` 只把 `completed.Amount` 加到用户钱包（`station_payment_reconcile.go:65-66`），`agent_wallets.allocated_cents` 不变。因此在补“订单 → 站长额度占用”的持久流水（含 `order_no/currency/minor_unit_digits/principal_minor/topup_minor/offset_available/offset_allocated`，其中 `offset_available` 为累计已退本金、`offset_allocated` 为剩余未消费占用、`consumed_minor` 为已消费本金，`principal_minor = offset_available + offset_allocated + consumed_minor`，`topup_minor` 仅因退款减少）之前，退款不得凭本地余额差额去改站长额度；没有该锚点、锚点重复或金额不符时必须 fail closed，只能退用户钱包并转人工复核，不得改站长额度。锚点方向固定为：入账时真实 `agent_wallets.available_cents` 减少、`allocated_cents` 增加，订单锚点写 `offset_allocated = principal_minor`、`offset_available = 0`；退款成功时真实 `available_cents` 增加本次本金、`allocated_cents` 减少本次本金，并同步 `offset_available += 本次本金`、`offset_allocated -= 本次本金`；模型消费按订单分配顺序（FIFO）在同一事务减少 `offset_allocated` 并写消费流水；已消费部分只减少 `offset_allocated`，不增加 `offset_available`；每次退款本金必须 `<= offset_allocated`，超出即拒绝或转人工，不得按当前钱包余额反推可退额；`REFUND_FAILED` 只回补本次钱包预留，不修改订单锚点、`topup_minor` 或累计退款。`offset_available`、`offset_allocated`、`consumed_minor` 均非负且合计等于 `principal_minor`，且 `offset_allocated = topup_minor - consumed_minor`；任何一侧 CAS 命中 0 行都整笔回滚。因此部分退款、累计退款与“退款后额度同步下降”都尚未实现；在补持久退款单之前，只能在界面提供全额退款，且退款成功后必须人工核对 `agent_wallets.available_cents/allocated_cents`，不得把“已退款”当作上游额度已释放。
站点退款还有一条独立精度门禁：应退金额必须直接取订单持久的最小货币单位/定点金额，或按十进制字符串解析，不得用 `float64*100` 再 `Round` 重建；订单必须带 `currency` 与 ISO `minor_unit_digits`，JPY/KRW 为零小数、KWD 等为三位，禁止把所有币种都当两位。渠道退款请求当前固定 `fmt.Sprintf("%.2f", order.PayAmount)`（`station_payment_refund.go:188`），对不同小数位币种会请求错误金额；必须按 `payment/currency.go:24-49/92-117` 的同一换算规则从持久金额生成十进制字符串。渠道退款用 `PayAmount`、本地钱包只回退 `Amount` 时，必须显式定义手续费差额承担方并写入退款单与对账，不能默认渠道多退、钱包少退仍算一致；若仅退本金，则渠道请求也必须改用本金。默认安全口径为“手续费不退、用户只收回实充本金”：渠道请求也按 `Amount` 发起，`PayAmount-Amount` 仅作为已收手续费留存并进审计；若产品决定退手续费，必须新增显式策略与渠道能力校验，不能仅因渠道按实付退款就自动按实付回补本地钱包。金额恒等式固定为 `fee_minor = pay_amount_minor - amount_minor` 且不得为负；默认策略下，渠道请求额、钱包扣减额与累计已退本金必须同值，手续费不得混入本金累计；开启退手续费时，退款单分别记录 `refunded_principal_minor/refunded_fee_minor` 并各自设上限。模型扣费也必须与钱包币种同精度：`stationChargeCents` 固定按“分”取整（`store.go:2907-2916`），而钱包表没有币种列（`store.go:495-503`）；若支持非 CNY 钱包，必须持久化币种与 `minor_unit_digits`，先按主站 8 位金额乘倍率，再按该币种最小单位量化；若钱包只记 CNY，则非 CNY 订单必须在下单前拒绝或完成显式换汇快照。订单本金、入账、扣费、退款不得各自假定两位小数。退款回执的 `amount` 只能是十进制字符串或最小单位整数 + `minor_unit_digits`，不得接收浮点，`minor_unit_digits` 必须与 `currency` 的 ISO 位数一致。退款终态更新还必须带当前状态 CAS：`finishStationRefund` 在读完 `state` 后无条件更新，并发成功/失败回执可能重复回补钱包；资金、退款单与订单状态任一命中 0 行即整笔回滚，已 `REFUNDED` 的请求仍须比对首次回执。退款前必须校验 `wallet_ledger` 中恰有一条属于本订单的 `user_recharge`，其 `order_id`、主体与金额都与该订单一致，多行或不一致一律 fail closed，不得用 `SUM` 碰巧相等通过。

流式请求、图片/视频异步任务和待结算补单共用同一条最终结算路径，只有拿到主站权威用量后才扣本站余额；未确认用量保持待确认，不用余额差额估算。用量页同时展示主站实际费用、本站倍率和用户扣费，并标明 `payer_user_id`、`charged_cost`、`billing_subject` 与五类额度主体（Key 配额/限流、账号配额、平台配额、订阅）；站长可在待结算面板区分上游成本与用户扣费。对账比较主站 `*_usd_nanos`/定点值与本地 settlement 快照，不得把分粒度金额当作主站权威值。 **失败与释放同一门禁**：上游非 2xx、断流、受理后失败都不得仅凭状态码释放本地预留；只有同时满足“主站未产生任何扣款效果”与“本站预留未对应已发生用量”时才可 `released` 并退还全部预留；证据可以是主站 `request_admission=rejected_before_upstream`、`dispatch_state=not_started`（须由写出点事件证明，不得仅凭时间戳为空）且 `funds_effect=none`（明确在调用上游前拒绝且无余额/欠款/订阅用量变化；`quota_effect` 不阻断本站释放；该受理写入必须已成功，写入失败只能 `unknown` 且不得释放），或成功 usage 明确为零客户扣款（`billing_subject=free` 且 `ActualCost=0` 且 `TotalCost=0`；`billing_subject=subscription` 且 `charged_cost=0` 只能证明主站未扣客户资金，不能单独证明本站未扣本地钱包；只有该行同时带非空 `subscription_id`、明确 `subscription_cost`（零成本为 `0`）且无余额实扣证据（须确认主站资金流水无该 `request_id + api_key_id` 的余额扣减，不得单凭 `charged_cost=0` 反推）时，才可作为订阅零扣款事实，仍须同时证明本次未产生本地 settlement 或本地快照倍率扣费为 0 才可 `released`；缺主体、缺金额或证据冲突时保持待确认/人工复核）；五类额度是否变化不是释放前提。订阅命中时的本地扣费必须按快照中的唯一策略处理：若策略为拒绝站点钱包代付，则必须在请求前返回 `SUBSCRIPTION_ACTIVE`，不进入本站结算；若主站已受理并返回订阅 usage，则不得把主站 `charged_cost=0` 当作本站用户免费，也不得在本站另扣一次，必须按该结算快照进入人工复核/对账。`reversed` 只用于已确认扣费后的反向流水，必须携带原 usage 与冲正金额，不得与 `released` 混用；当前实现没有生产调用点，且 `FinalizeSettlement` 对 `released`/`reversed` 复用“退还预留未用部分”的路径，接入前必须拆分，不能把用量冲正写成预留释放。 **状态与直扣金额固定语义**：`FinalizeSettlement` 当前对 `confirmed/released/reversed` 统一按 `stationChargeCents(actualCents, rate)` 计算，再按 `reserved - charged` 退差额；调用方传 `actual=0` 不能代替接口约束，任何误传或历史修复都会让“明确失败”按失败金额扣费。必须写死：`released` 的 `charged_cents` 恒为 0、只退全部预留且不得进入 `debitUserUsageTx`；`reversed` 只按既有 confirmed 扣款做等额冲正，不得二次扣费；仅 `confirmed` 允许 `charged>0`。直扣不得把余额不足截断为 0：`debitUserUsageTx` 在 `next<0` 时置 0 仍写 `user_consume` 并标 `confirmed`，必须改为余额条件更新，不足则整笔回滚、记录 `shortfall_minor` 并进入待复核。验收：预留 150 后 `released(actual=100)` 只退 150 且无 `user_consume`；余额 50 直扣 120 不得成功；并发确认只扣一次。 直扣还有一个独立的冲正缺口：`PrepareDirectSettlement` 只记 settlement 且 `hasLocalReservation=false`，`FinalizeSettlement` 在 `refund := reserved - charged` 前未按状态分流，`!hasLocalReservation` 分支直接 `return tx.Commit()`；因此对已 confirmed 的直扣请求执行 `reversed` 时不会上调用户余额、不会写反向流水，形成“冲正成功但未退款”。必须按原 `user_consume` 事实生成唯一反向 `user_refund`（金额不超过原扣款），没有可引用扣款流水时返回冲突；重复冲正只允许一次。**状态迁移必须与资金键一一对应**：`pending→confirmed|released`、`confirmed→confirmed(部分冲正)|reversed(全额冲正)`，`released`/`reversed` 为终态；`released` 固定 `actual_cents=0`、`charged_cents=0` 并全额释放，`confirmed` 才可扣费。本站钱包余额不足一律整笔回滚并进入待复核，不得截断为 0、不得写本地欠款或负余额；主站账本若启用显式信用只约束主站 Payer 应收，不能自动抵扣本站用户钱包额度。冲正保留原 `charged_cents` 并累计 `reversed_cents`，`net_charged_cents=charged_cents-reversed_cents`，累计不得超过原扣款；部分冲正仍为 `confirmed` 且可见，净额归零才进入 `reversed`，禁止 `confirmed→released` 或 `released→reversed`。释放使用 `settlement_release:<request_id>`，冲正使用 `settlement_reversal:<request_id>`，不得与订单退款共用 `refund:<request_id>`。所有状态写入必须带当前状态 CAS 并校验 `RowsAffected==1`，0 行整笔回滚；终态重放只返回首次结果并比对金额/`usage_id`/`reversed_cents`，不得更新 usage 快照或换绑另一条 usage。`debitUserUsageTx` 在钱包行缺失时不得当成功，必须整笔回滚。本地钱包退款与主站 usage 冲正是两套独立账本：本地退款只能撤销本站已确认扣款，不得要求主站冲正；主站冲正不得自动给本站加款；Provider 已受理或已发生费用时任务失败只能进入人工对账，不得仅凭 `failed` 自动退款。 **本地 `Credit` 也必须绑定原扣款而不是只凭退款键幂等**：`Store.Credit` 目前只按 `(agent_id, kind=refund, request_id)` 查已有行并比对 `main_user_id/amount`（`store.go:3203-3213`），随后直接加用户余额与 `agent_wallets.allocated_cents`，没有校验该键对应的 `user_consume` 是否存在、是否属于同一用户、累计退款是否超过原扣款；因此只要换一个退款键就能对同一消费重复加款，或对从未发生的消费凭空加款。`Credit` 必须要求持久 `original_consume_ledger_id`（或等价的扣款流水主键）与 `original_request_id`，在同一事务验证：原扣款为本站已确认 `consume`、用户/币种一致、本次金额 `<= 原扣款 - 已累计退款`，并写唯一 `refund_key`；同一 `refund_key` 重放只返回首次结果，超出累计上限或无可引用扣款返回冲突/人工复核。`settlement_reversal:<request_id>` 必须映射到该 `original_consume_ledger_id`，不得把订单退款 `refund:<request_id>`、预留释放或其他任务失败退款混用。验收：伪造从未消费的 `refund_key` → 余额与 `allocated_cents` 均不变；同一消费两次不同 `refund_key` 累计超过原扣款 → 第二次拒绝；同一 `refund_key` 重放 → 只加一次且返回首次结果；原扣款属于 A、退款主体 B → 冲突且零资金变化。 验收：confirmed(120)→reversed(50) 余额 +50 且状态可见；再 reversed(70) 进入终态；第三次冲突；released(actual=100) 仍只退全额预留；并发释放/冲正确认只成功一个。
