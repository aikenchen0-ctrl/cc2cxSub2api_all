# 招标监控（Yibiao）优化任务

> 项目：`yibiao/`（卫星应用，菜单“AI找标投标”）。基线：2026-11-14。
> 全局约束见根目录 `评估报告.md`、`优化任务-总调度.md`；本文件只负责 `yibiao/` 内落地。

## 1. 项目定位与边界

- 卫星应用，招投标信息监控、筛选、AI 分析与通知；Python 后端 + 前端。
- SSO 建立 3 天 HttpOnly Session；服务端代调主站模型。
- 涉及目标站点抓取和邮件/短信/Webhook 通知，合规风险需单独门禁。
- 本项目只改 `yibiao/`，不改主站协议、根 Compose 或其他卫星。

## 2. 结论与商用判定

**当前不适合公开发布或商用。** 自动化测试接近 0、调度/通知幂等未建立，且仓库无 LICENSE、抓取/通知合规未确认。MIT 或其他授权不能默认推定。

- 没有可重复的单元/集成测试基线。

**实施步骤**

**验收**

- 测试可重复通过；外部请求默认 mock；失败有独立证据。

### YIB-02 调度器与任务幂等（P1）

**现象与证据**
- 监控是否运行只存在进程内 `AppState.is_running`（`server/app.py:83`），调度器对象也在内存（`:85`）；`persist_active_state()` 只保存到 `user_states` 字典，不写跨进程持久状态。
- `lifespan` 启动时只 `load_config()` 并记日志，不读取上次运行状态、不重建 scheduler、不重入队未完成任务（`:582-595`）。
- `/api/start` 设置 `is_running=True` 后只用 FastAPI `BackgroundTasks` 启动一次 `run_monitor_task`（`:780-796`）；`/api/run-once` 同样只 `background_tasks.add_task(...)`（`:829-858`）。进程退出时正在执行的本轮任务直接终止，重启后既不会标记失败，也不会续跑或补偿。
- 单轮内用 `current_task_running`/`manual_run_pending` 防并发，但这两个标记也只在内存；多实例或重启窗口无法提供互斥。
- 通知执行者不唯一且去重只落在发送后的布尔位：`MonitorCore.run_once` 在 `_send_notifications` 内发送并标记成功项（`src/monitor_core.py:395-398/457-533`），`_run_monitor_task` 随后又按 `new_count > 0` 调 `send_notifications`（`server/app.py:432-437`）。后者读取 `get_unnotified()` 并再次发送（`:483-524/563-573`），但成功后完全没有 `mark_notified`；同一批已成功发送的数据仍保持 `notified=0`（`src/database/storage.py:160-167`），后续每轮都会再次取出。邮件/微信每次只取前 10 条（`server/app.py:524/570`），超过 10 条时既无稳定游标也无逐条结果，容易“前 10 条重复、其余永久未通知”。

**影响**
- 用户看到“监控已启动”，重启后实际停止，但界面与配置没有明确转成“已停止/需人工恢复”，形成静默漏监控。
- 抓取已完成、通知未发送时，重启丢失 `new_count` 与未通知集合的处理上下文，可能出现漏通知。
- 多副本同时启动时各自持有 `is_running`，可能重复抓取/通知；当前没有持久租约。
- 通知幂等不能只依赖 `bids.notified` 一个全局布尔：它不区分渠道、联系人、轮次和失败原因，无法表达“邮件成功、微信失败”“用户 A 已发、用户 B 未发”或“发送成功但标记前崩溃”。

**实施步骤**
1. 把“监控是否启用、下一次计划时间、当前轮次 ID、执行者租约”写入持久状态（可复用每用户数据库），启动时按持久状态决定恢复或显式标记“上次异常中止”。
2. 用持久任务行替代或包裹 `BackgroundTasks`：创建轮次时先落 `scheduled/running/…` 行，执行体按 `round_id` 幂等；启动或定时扫描未完成行并续跑，超过重试上限进入明确失败态。
3. 单轮抓取与通知分别记录完成游标。通知只保留一个执行者：`MonitorCore` 与 API 层不得各发一次；`MonitorCore`/outbox 由本卡负责，`server/app.py` 的重复发送路径由 YIB-04 按本卡接口删除或改为只读查询。通知按“轮次 + 条目 + 渠道 + 接收人”落持久 outbox/去重行，状态含 `pending/sending/sent/failed`、尝试次数、下次重试时间和最后错误；发送成功后仅在 `sending → sent` 的条件更新成功时推进游标，失败按上限重试，超过上限进入可审计死信。不得再用“先发后标记 `bids.notified=1`”作为唯一幂等保证。
4. 多实例用数据库租约/条件更新选主；未持有租约的实例只能读状态，不得启动抓取。
5. 验证 APScheduler 的单实例/多实例行为，补并发、时钟、时区和长任务测试；同一招标信息只通知一次，跨用户监控项严格隔离。
6. AI/上游调用若带重试，必须携带可跨重试复用的稳定业务请求键，并由主站接收、校验后写入计费去重键；当前 `src/ai_guard.py:149-160/203-212` 最多重试 3 次，`server/auth_sso.py:231-242` 只发 `Authorization`、`X-Sub2API-On-Behalf-Of`、`X-Sub2API-Satellite`，主站中间件也不解析 `X-Client-Request-ID`（`sub2api/backend/internal/server/middleware/client_request_id.go:19-45`）。在协议落地前不得声称“超时重试只扣一次”。
   自动重试只允许“连接未建立/明确未提交”两类：DNS、TCP connect、TLS 握手在发送请求前失败可重试；`requests.exceptions.ReadTimeout`、连接重置、SSE 中断、HTTP 5xx/524 均必须先进入 `unknown/需对账`，按同一键查 `/v1/sub2api/usage`；只有主站 `request_admission=rejected_before_upstream`、`dispatch_state=not_started`（须由写出点事件证明，不得仅凭时间戳为空）、`funds_effect=none` 且 `quota_effect=none` 时才可重发；`not_seen`/`accepted`/`unknown`/0 行均只能保持待对账。不得把“请求已发出后读超时”当成未计费；当前 `ai_guard.py` 的 `Timeout` 分支不区分这两类，必须拆分。
7. **按 S2A-08 实现受理与别名契约**：调用上游前先提交 `accepted`；本地拒绝先提交 `rejected_before_upstream` 与真实 `funds_effect/quota_effect`，只有双零且 `dispatch_state=not_started` 才可标记可重发；同一请求只建一条 admission（先以临时键建行，最终键只一次 CAS 写入 `final_request_id`；dispatch 前拒绝可保持空，不得伪造），临时键经 `request_admission_alias` 单跳、双向唯一并外键归属该 admission；改绑、二次归属或引用未升级最终键均冲突。usage/反查必须返回完整 `admission_source/funds_effect/quota_effect/dispatch_state/state_version/query_request_id/final_request_id`，`query_request_id` 逐字等于查询键；别名缺失不得返回 `settled`。最终键升级、别名与权威 usage 同事务或同事务 outbox，任一步失败不得确认成功或换键重发；临时键查询别名缺失不得 `settled`，最终键查询唯一 usage 存在须 `settled`。

**验收**
- 启动监控后立即重启，断言状态不是静默“运行中但无执行者”：要么按持久状态恢复调度，要么明确转为 `interrupted` 并给出可恢复入口。
- 在一轮抓取中途杀进程，重启后未完成轮次能续跑或进入显式失败；同一 `round_id` 不产生重复抓取记录。
- 两个实例同时启动同一用户监控，仅一个取得租约；另一个返回“已由其他实例运行”或不执行。
- 同一轮、同一联系人、同一渠道至多发送一次：覆盖“`MonitorCore` 已发 + API 层再发”的现状回归，断言 mail/wechat 各只收到一次；通知成功但进程在 `sending → sent` 条件更新前退出，重启后重试不得重复发送；发送失败按上限重试并进入死信，不得无限重取同一批。

### YIB-03 爬虫与通知可靠性（P1）

**现象与证据**
- 通知确实会消耗站长自有现金：`src/notifier/sms.py:21-139` 的 `AliyunSMS.send` 直接向 `dysmsapi.aliyuncs.com` 发 `SendSms`，每次重试都重新生成 `SignatureNonce`（`:113`），请求/响应与 Provider 的 `BizId`/`RequestId` 没有落库，调用方只拿 `bool`；`server/app.py:532-546`、`src/monitor_core.py:493-507` 都用该 `bool` 直接判定 sent/failed。
- `src/notifier/voice.py:73-138` 的语音调用默认 5 次重试（含 DNS 预解析与 30 秒请求超时），每次重试都生成新的 `SignatureNonce` 与 `Timestamp`（`:96-98`）；超时/连接中断后上游可能已经发起呼叫，当前无法凭本地记录证明“未提交”，却在 `server/app.py:548-560`、`src/monitor_core.py:520-529` 直接记为失败或成功，没有 `CallId`/`RequestId` 持久事实源。
- `src/notifier/sms.py:142-181` 的腾讯云分支目前只写日志并返回 `True`，没有真实发送证明；不得把该 `True` 当作已送达或已计费。`server/app.py:1056-1102` 的 `/api/test/sms`、`/api/test/voice` 是登录用户可直接触发的真实付费入口，当前没有幂等键、频率上限或调用前意图。
- 这些 Provider 调用不经过主站 `/v1/sub2api/usage`，不能靠主站 usage 缺失证明未发送、未计费；邮件 SMTP 与 PushPlus/Webhook 也需按“外部副作用”登记，但本卡重点验收现金短信/语音。

**实施步骤**
1. 爬虫遵守目标站点条款和 robots；设置超时、重试、限速、熔断。
2. 处理页面结构变化、编码、验证码和登录失效；失败可观测。
3. 通知（邮件/短信/Webhook）有重试、去重、抑制和失败告警。
4. 通知发送必须走单一 outbox/cursor：邮件、微信等每次只处理有明确上限的批次，但批次之间以持久游标推进；成功按渠道/接收人条件标记，失败不阻塞后续条目，且不得因“只取前 10 条”让剩余条目永久滞留。
5. 不绕过访问控制或验证码；不抓取未授权个人数据。
6. 通知内容含退订/停止方式；记录同意来源。
7. 短信/语音在调用 Provider 前先写 `sending` 意图（`round_id + bid 集合摘要 + channel + 接收人 + provider + 模板/参数摘要`），使用 `(owner, idempotency_key)` 或等价唯一约束；调用成功后立即保存 Provider `BizId`/`CallId`/`RequestId`、Provider 返回码与计费时间，失败只更新同一行的尝试次数与最后错误。超时/断连但无法证明未提交时进入 `unknown/需对账`，不得自动重发，也不得直接判 `sent`。 **同一发送意图的重试不得换键或换幂等语义**：`SignatureNonce`/`Timestamp` 只是请求签名参数，不是业务幂等键；当前 `voice.py:77-133` 把 30 秒读超时、连接重置与 DNS 失败一并重试，每次还重新生成 nonce，可能在上游已受理后重复呼叫并重复计费；`sms.py:113-139` 对未知结果直接返回 `False`，调用方若按失败重发同样可能双发。每次 Provider 调用必须绑定持久 `send_intent_id`，重试只能复用该意图并比较 Provider 的 `BizId/CallId/RequestId` 或明确“不支持查询”；Provider 未提供幂等键时，超时/5xx/非 JSON 一律不得自动重发，只能待人工/账单对账。验收：模拟“Provider 已受理但响应超时”，自动重试次数必须为 0、同意图只有一行、费用只能归因一次；DNS/TCP 在请求发出前失败可安全重试且不产生 Provider 费用证据；切换模板/接收人/渠道必须生成新意图，不得复用旧键。
8. `/api/test/sms`、`/api/test/voice` 与人工“立即发送”必须使用独立测试额度/频率限制和显式确认；同一幂等键重复提交只返回首次 Provider 结果或真实状态，不得静默再发。腾讯云分支在接入官方 SDK 和真实响应前必须显式返回“未实现/不可发送”，不得返回 `True`。

**验收**
- 站点超时/改版时任务失败可定位；通知发送成功不重复，失败按上限重试；同一批超过 10 条时剩余条目可通过游标继续处理，不会因批次上限永久漏发。
- 退订后不再发送；无“无限速/绕过验证码”能力。
- 同一轮、同一接收人、同一模板重复提交短信/语音：Provider 创建/计费调用为 1 次，本地 intent 只有一行；响应丢失后重提能按已保存 `BizId`/`CallId`/`RequestId` 查回真实状态，或明确进入待对账。
- 模拟短信/语音读超时或连接中断：不得自动重发，不得把本次标成 `sent` 或普通 `failed`；必须保留 `unknown`、尝试次数与可对账字段，并由人工/Provider 账单核对。
- 两个实例同时处理同一 outbox 行：只有一个实例进入 `sending` 并调用 Provider；另一个只能读状态或返回冲突。重启后 `sending` 超过租约必须转为待对账，不得因为布尔 `notified=0` 再次发送。
- `/api/test/sms`、`/api/test/voice` 在重复请求、超频和 Provider 未知状态下的行为可验收；腾讯云未实现时不得出现 `success=true`。验收不得以“日志出现成功”或 Provider 调用返回 HTTP 200 代替真实 `BizId`/`CallId`。

### YIB-04 用户隔离与 SSO（P0/P1）

**现象与证据**
- `server/auth_sso.py` 有 `consumed_tickets` 表，较其他卫星完整；仍需并发/重启验收。
- 当前调用使用裸 `X-Sub2API-On-Behalf-Of`；主站 S2A-07 后改为短期用户断言。

**实施步骤**
1. 校验 SSO `iss/aud/sub/iat/exp/jti`，TTL ≤ 2 分钟，`aud=yibiao` 精确匹配。
2. 验证票据消费唯一键、并发、重启、多副本不可重放。
3. 验证 3 天 Session、生产 Cookie `Secure + HttpOnly`、注销可撤销。
4. 服务端代调带 `yibiao` slug 和当前用户断言；缺凭据不得回退。
5. 每个用户的监控项、通知配置、抓取结果和 AI 分析严格隔离；跨用户 403/404。
6. 管理员能力单独授权；主站 S2A-01/06/07 完成后改用专属凭据。
7. 计费只走主站 `yibiao` slug 配置或当前用户余额；不得发送或接受 `X-Sub2API-Payer`、`X-Sub2API-Commission-Rate`。
8. 定时任务和通知使用稳定业务键；同一招标条目/同一任务在本地 outbox 层只执行一次，重跑只补未完成部分。涉及主站计费时，只有在主站已接收并校验稳定键且能查到权威 usage 后才可断言不重复扣款；否则必须待对账，不得用本地任务 ID 代替主站结算键。
9. AI 分析与抓取任务的重试键必须由主站参与去重：`X-Client-Request-ID` 只有在主站按已验明应用凭据 + `yibiao` slug 接收并校验后才可作为计费键；普通客户端或调用方不得自行指定。协议未落地前，连接失败重试与“服务端已处理但客户端超时”重试必须区分，后者不得被自动重试。

**验收**
- 补跨用户读取、修改、删除测试；浏览器无 SuperKey/应用凭据。

及 `*_usd_nanos`/定点十进制：余额模式自付时 `payer_user_id=user_id` 且 `charged_cost=actual_cost`；订阅模式必须返回 `billing_subject=subscription`、`charged_cost=0`，且 `subscription_cost` 等于本次 `actual_cost`（零成本订阅即 `0`）；`free` 承担全额成本（`charged_cost=actual_cost`），不得误写成 0。余额模式下解析出平台后 `user_platform_quotas` 必须按同一资金主体与 `charged_cost` 累计。不得用泛化 `quota_subject_user_id` 或 JSON 浮点代替；金额验收比较 nanos/定点，不得先把主站 8 位金额四舍五入到分。  另须断言零扣款来源：`billing_subject=subscription` 且 `charged_cost=0` 只表示订阅账本，不得当作余额零扣款；`free` 仅 `ActualCost=0` 且 `TotalCost=0`，五类额度均为 0；其余成功行一律不得以 `charged_cost=0` 作为免扣款理由。另须覆盖失败尝试：后扣失败后，`usage_logs` 不得出现该 usage，不得双轨。
- **usage 命中不是结算证据**：查询必须按 `request_id + 主站 api_key_id`（或主站等价精确过滤）判定；0 行只表示主站暂时不可见/未写入，多行或主站 `api_key_id` 缺失 `NULL` 一律视为不可唯一确认。以上任一情况都不得把任务标为已结算、不得扣本地钱包/额度、不得重试生成新键、不得改用余额差或本地报价补猜，只能保持 `pending`/待对账；只有唯一权威行且 `request_id`、主站 `api_key_id`、付款主体与金额逐项一致时才允许确认。
- **订阅行主体必须完整且不得回退余额**：命中行 `billing_subject=subscription` 时，`subscription_id` 必须非空，`subscription_cost` 必须存在且等于该行 `actual_cost`（零成本订阅写 `0`，不得为 `NULL`），`charged_cost=0`；`balance_cost` 必须为 0 且不得同时出现余额实扣或非本人 Payer 实扣。缺主体、缺金额或与余额证据冲突时，只能 `pending`/人工复核，不得按 `charged_cost=0` 确认“未扣款”。`billing_subject=free` 仅限 `actual_cost=0` 且 `total_cost=0`，不得替代缺失的订阅主体。
- **纯文本 token 缺失不得按次**：主站 `custom` 模式若对本项目配置了 `millionTokens` 规则，纯文本调用必须取得可信 token 合计后按 `token` 计价；上游未返回 usage、解析失败或仅图片 token 时，不得静默落 `request` 或模型价，必须失败关闭/待对账；同目标同时有 `token` 与 `request` 时固定优先 `token`。上游明确返回 0 token 可按 `millionTokens` 得 0 金额，但 `billing_mode` 仍为 `token`，须与“用量未知”分开断言。 **当前实现未满足该零用量分支**：`quoteSatelliteBilling` 仍以 token 合计 `>0` 才尝试 `millionTokens`，0 用量会落到 `request`/模型价；修复前该用例只能标为失败/待实现，不得按现网行为验收通过。
- **配额主体必须与资金主体一致**：本项目不发送 Payer/抽成头，普通请求 `Payer == User`，但验收仍须能证明余额、Key 配额、Key 限流、账号配额与平台配额由同一计费快照复算：Key 配额/限流记在发起请求的 APIKey、金额为 `ActualCost`；账号配额仅对 `APIKey`/`Bedrock` 类型账号按实际 `account_id` 与 `TotalCost * AccountRateMultiplier` 累计（`usage_billing_repo.go:212`），其他账号类型 `account_quota_cost=0` 且不写账号配额；平台配额仅在余额模式按资金主体 `(PayerUserID 或 UserID, 请求平台)` 与 `charged_cost` 累计，订阅模式不写 `user_platform_quotas`。若主站将来对本项目启用代付，须按 S2A-09 冻结的账本事实与 Payer 互斥切换为 Payer 资金主体，并按 S2A-08 落 usage 金额与配额字段；Key 配额主键不变，不得出现“余额按 Payer、额度按 User”的分叉。**实现状态**：`UsageBillingCommand` 尚无平台配额字段，service 层仍按 `p.User.ID + cost.ActualCost` 另写；本条平台配额口径修复前验收必须标记未通过，不得把 Redis/DB 另写当作已满足。**PayerCost 同精度**：代付金额 `PayerCost=ActualCost×(1-rate)` 必须在任何仓储扣款、usage `charged_cost` 与平台配额累计之前按 8 位 half-away-from-zero 量化，三者使用同一量化值；当前 `quantizeMonetaryFields` 未覆盖 `PayerCost`（`usage_billing.go:85-91`），第 9 位为 5 的边界（如 `0.000078125×(1-rate)`）修复前必须标失败，不得只在仓储或 usage 单侧补舍入。
- `/v1/sub2api/usage` 当前实现缺口是不返回 `api_key_id` 或 `group_id`，同用户多把 Key 用同一 `request_id` 只能靠行 `id` 区分；这不是接口契约，S2A-08 落地后必须返回 `api_key_id` 并支持按 Key 过滤。在该字段落地前，响应中缺少 `api_key_id` 不得被解释为“当前用户只有一把 Key”或“可以按行 `id` 猜结算”；验收须显式标记为未满足并按 `pending`/人工复核处理。查询固定 `PageSize=20`，同用户大量 Key 可能截断，验收须给出上限/分页语义。
- 本项目仅文本/结构化输入，不要求视频回退；但仍须断言：若上游或代理误传 `VideoCount > 0`，主站不得静默落到 `token`/`request` 规则，必须按 S2A-08 fail closed。
- **只读余额/状态查询不进入计费账本**：本项目存在经 `/api/sub2api/balance` 转发到主站 `GET /v1/sub2api/balance` 的展示/预检调用；该接口只能读取余额，不得生成 usage、占用计费键、扣余额/配额或作为“请求已成功结算”的证据。验收须断言余额查询前后 `usage_logs`/`billing_attempts` 行数、余额、Key/账号/平台额度均不变，且查询失败不得触发重试计费或改变本次模型请求的账本分支。若某次余额查询同时携带了模型结算键，仍只能按只读处理，不得复用该键产生 usage。
- 同一 Key、同一 `request_id` 的**已成功结算**请求重放：`/v1/sub2api/usage` 只返回首次权威记录（first-write-wins），不追加第二行；失败尝试走独立失败审计、不占结算键，成功重试后才形成唯一权威行；同一账本下余额、Key 配额、订阅用量与 usage 行均只变化一次。去重键是 `(request_id, api_key_id)`；同一用户换 Key 使用同一 request_id 会生成第二条记录，不得写成全局“一个 request_id 只一条”。重放命中时不得用本次模型、token、金额、`billing_mode`、订阅或付款人覆盖首次 usage；付款人或费率与首次不一致时，必须返回明确冲突或既有结果并写审计，不得静默换人扣款。
- **媒体请求缺数量不得按次/按 token 成功**：本项目若存在生图或图片编辑路径，主站 `quoteSatelliteBilling` 只在 `ImageCount>0` 时尝试 `image` 规则；请求已明确为生图但张数为 0 时会落到 `token`/`request`。验收必须覆盖 `ImageCount=0` 的明确生图请求，断言失败关闭/待对账而不是按次成功；视频同理覆盖 `VideoCount=0`、`VideoDurationSeconds>0`。若本项目确无该媒体路径，须在卡内显式写“无此路径”并给出路由/调用证据，不得默认跳过。
- 若主站对该 slug 启用 `custom/request/points` 规则：本卫星实际使用的目标/单位必须在规则中命中；未命中时请求必须失败关闭并返回可定位错误，不得静默按模型价扣费。`points` 模式只允许整数点数，金额按 `点数 × 0.01` 换算；`request` 单位得到 `billing_mode=per_request` 且 `actual_cost = 点数 × 0.01`，`image`/`videoSecond` 分别按图片数/秒数乘点数，`millionTokens` 必须被配置校验拒绝（`satellite_billing.go:114-122/356-359`）。不得把 `per_request` 一律当作固定 1 次请求而不乘 0.01，也不得把 `points` 的 `request` 规则误判为 `custom` 的 token 兜底。
- 本项目当前没有视频/导出/批处理的异步上游任务；AI 分析是同步 `requests.post` 最多 3 次重试，监控轮次与通知是本地调度，不产生上游 task id。验收必须显式写“无异步上游任务”并引用 `src/ai_guard.py:145-212`、`src/monitor_core.py:395-398`。若将来引入轮询/回调，必须用服务端可复用的稳定业务键（优先上游任务 ID，或提交时已验明的业务幂等键）派生 `request_id`；服务端随机本地任务 ID 不作为结算键，若上游 ID 只能在创建后取得，则先持久化创建意图。只有主站已按 S2A-02 校验该键后，才可断言最终恰有一条权威 usage；否则标记待对账。

## 6. 全链路验收

- 从主站菜单进入，SSO 成功、Session 3 天、注销可撤销。
- 主站 usage/反查必须返回 `request_admission` 六态（`not_seen`/`accepted`/`rejected_before_upstream`/`settled`/`conflict`/`unknown`）及真实最终键、`admission_source/funds_effect/quota_effect/dispatch_state/state_version/query_request_id/final_request_id`；0 行、`not_seen`、`accepted`、`conflict`、`unknown` 均不得触发自动重发、免费释放或重复扣款，只有 `rejected_before_upstream` 且 `dispatch_state=not_started`（须由写出点事件证明，不能靠时间戳为空、4xx 状态码或本地异常推断）才可重试。自动重发/免费处理还必须 `funds_effect=none`（余额、欠款、订阅用量无资金变化）且 `quota_effect=none`（Key/限流、账号、平台、订阅额度均未写）；本站钱包释放只按本地预留与主站资金效果判断；`quota_effect` 既不是释放前提，也不是拒释前提，不得因主站额度变化改扣本站钱包。`accepted`/`unknown` 表示可能已调上游，必须待对账；已读到唯一成功 usage 必须为 `settled`，不得因冲突态降级为未结算。同一请求只能有一条 admission（先以临时键建行，最终键只一次 CAS 写入 `final_request_id`），临时键与最终键必须经 `request_admission_alias(alias_request_id, api_key_id, admission_id, final_request_id)` 单跳反查同一受理事实，alias 行以外键绑定该 admission，禁止引用尚未升级最终键的行；同一临时键改绑、同一最终键归属第二条 admission、别名引用未升级最终键的 admission、别名缺失或 CAS 失败时不得确认。调用上游前必须先提交 `accepted`（临时键仅作 `admission_key`，最终键未定时不得写可解析别名），提交失败不得调用上游；本地拒绝先提交零效果受理，提交失败只能返回 `unknown`/不可重试；最终键、别名与权威 usage 同事务或同事务 outbox，任一步失败不得确认成功，不得自动换键重发。
- **受理与别名验收必须可执行**：同一临时键并发绑定两个最终键时恰一条成功、另一条 `conflict`；同一请求由临时键建 admission 后改用最终键查询，不得产生第二条 admission，最终键只能一次 CAS 写入；同一最终键被两个临时键/两条 admission 指向时恰一条成功；临时键别名缺失而最终 usage 已存在时，查询必须返回 `unknown`/待对账，不得返回 `settled`；直接查询最终键且唯一 usage 存在时必须返回 `settled`（`admission_source=usage`），不得因别名未写降级；所有查询（含 `usage_count=0`）必须回传完整 `admission_source/funds_effect/quota_effect/dispatch_state/state_version/query_request_id/final_request_id`，且 `query_request_id` 逐字等于查询键；临时键与最终键反查必须命中同一 `state_version`。注入受理写入失败时上游调用计数必须为 0；注入别名或 usage 写入失败时不得返回成功或自动换键重发。
