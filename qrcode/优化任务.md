# QRCode 优化任务

> 项目：`qrcode/`（卫星应用，菜单“艺术二维码”）。基线：2026-11-14。
> **冻结保护：当前只允许只读盘点和任务书更新；任何代码、依赖、配置或艺术二维码链路修改，必须由用户明确解除冻结并指定文件。**
> 全局约束见根目录 `评估报告.md`、`优化任务-总调度.md`。

## 1. 项目定位与边界

- 卫星应用，可用二维码生成、艺术化、微信相关能力。
- SSO 建立 3 天 HttpOnly Session；服务端代调主站模型或第三方艺术二维码服务。
- 本项目只改 `qrcode/`；冻结期内不改任何业务文件。

## 2. 结论与商用判定

**当前不适合公开商用，且项目处于冻结状态。**
除共享信任边界外，本项目还有明确的 P0 安全问题：明文第三方 Key、固定临时隧道回调、浏览器持久化微信 `access_token`、进程内票据消费。**在用户解冻并授权前，只能记录，不得修复。**

## 5. 缺陷清单与补强方案

### QR-01 只读安全盘点（可立即做）

**实施步骤**
1. 只读核对 Key、回调、localStorage、SSO 消费和依赖来源，登记证据但不修改。
2. 确认明文 Key 是否仍有效；若有效，建议用户先轮换，再谈代码整改。
3. 确认生产回调是否依赖临时隧道；记录真实域名和部署方式。
4. 输出“解冻后待改文件清单”，交由用户逐项授权。

**验收**
- 盘点记录包含路径、风险、建议；没有修改任何业务文件。
- 不在报告/任务书中复制完整密钥或 token。

### QR-02 第三方 Key 与固定回调（P0，需解除冻结）

**现象与证据**
- `src/config.js:41` 明文第三方艺术二维码 Key。
- `src/config.js:47` 固定 `trycloudflare.com` 回调。
- **艺术二维码是站长自有额度的付费调用**：`POST /api/stylize-qr` 在 `stylize` 注入时调用 `stylizeQrImage`（`src/qr-app.js:531/848-862/868-889`），后者先 `POST /artQr.generateEndpoint`（`src/art-qr.js:48-93`），只以响应中的 `data.img_uuid` 作为后续 `detail` 轮询键（`:95-129`），再下载结果（`:131-150`）；`img_uuid`、提交意图和用户归属都不落库，`stylize` 返回的任务对象只在本次响应中出现。
- **提交重试会在无法证明未受理时再次创建付费任务**：`submitArtQrTask` 对非 JSON 且文本含 `timeout/timed out` 的响应做最多 `submitMaxAttempts=3` 次同请求体重试（`src/config.js:44`、`src/art-qr.js:60-93`），每次都没有幂等键或业务请求 ID；第一次可能已在第三方建单并产生额度，第二次会再建一个。`pollMaxAttempts=60`、间隔 3 秒（`src/config.js:45-46`）超时后只抛错，没有进入“待对账”或保留 `img_uuid` 的入口。
- **浏览器刷新/用户重提没有服务端去重**：入口只按 Session 校验用户（`src/qr-app.js:844-847`），未读取客户端幂等键，也没有 `(owner_user_id, idempotency_key)` 唯一行；同一二维码图片重复点击会再次提交第三方并消耗站长额度。

**实施步骤（解冻后）**
1. 轮换/吊销已泄露 Key；新值只来自服务端 Secret。
2. 回调地址改为显式环境变量，生产禁止临时隧道；缺失即失败。
3. 增加 Secret 扫描与构建产物检查。
4. 不把新 Key 写入前端、日志、示例或 Git。
5. **艺术二维码提交必须先持久化幂等意图**：在调用第三方 `generate` 前，以 `(owner_user_id, idempotency_key)`（或按 `owner + 规范化请求摘要` 派生）写入 `creating` 意图与唯一约束；同一键重提/重试命中既有行时返回该任务真实状态/结果或明确冲突，不得再次提交 `generate`。
6. **Provider 任务 ID 立即落库**：拿到 `img_uuid` 后立即写入任务行（含 `owner_user_id`、请求摘要、状态、`next_poll_at`），再开始 `detail` 轮询；轮询重启后从持久行恢复，不得重新提交。
7. **只对可证明未受理的失败自动重试**：4xx 且响应明确未创建可释放意图；超时、连接重置、非 JSON、5xx、524 一律标记 `unknown/需对账`，保留请求摘要与已取得的 `img_uuid`，由人工/对账确认后再决定是否新建；不得以固定重试次数替代幂等证明。

**验收**
- 源码与构建产物无该 Key 前缀；生产回调为稳定受控域名。
- 缺回调配置时启动失败，不静默使用旧隧道。
- **同一艺术二维码请求只建一个第三方任务**：同一 `(owner_user_id, idempotency_key)` 并发/重提/响应丢失后重试，断言 Provider `generate` 调用为 1 次、本地任务行 1 条、`img_uuid` 1 个；命中既有键时返回真实 `queued/running/succeeded/failed` 或有产物的结果，不得固定回 `queued` 或再次消耗额度。
- **提交崩溃窗口**：覆盖“意图已写、Provider 未调用”“Provider 已返回 `img_uuid`、本地未写”“轮询超时、Provider 可能仍在执行”三种场景；重启后分别不重发、按 `img_uuid` 续查、进入 `unknown/需对账`，断言不会再次调用 `generate`。
- **不得把第三方失败折叠成可重试成功**：`detail` 超时或返回不可解析状态时任务必须保持待对账，不能删除任务行后让用户无感重提；测试须用模拟 Provider 断言 `generate` 调用次数，而不是只看 HTTP 200。

### QR-03 微信 `access_token` 服务端化（P0，需解除冻结）

**现象与证据**
- `public/app.js:728` 将微信 `access_token` 写入 `localStorage`。

**实施步骤（解冻后）**
1. 微信 token 只在服务端短期缓存；浏览器只拿操作结果，不持有 token。
2. 删除 localStorage/sessionStorage 中的 token 写入与读取。
3. 服务端缓存加过期、并发刷新锁和失败回退。
4. 日志不记录 token、AppSecret 或完整请求体。

**验收**
- 浏览器存储、网络响应、构建产物中无微信 `access_token`。
- token 刷新并发不会互相覆盖；过期后自动获取一次。

### QR-04 SSO 与测试可复现（P1，需解除冻结）

**现象与证据**
- `src/sso.js:5` 票据消费为进程内 `Map`；重启/多副本丢失。
- 当前调用使用裸 `X-Sub2API-On-Behalf-Of`；主站 S2A-07 后改为短期用户断言。
- **本地异步任务与上游调用不是同一件事**：`POST /api/generate` 命中 `shouldRunGenerateAsync` 时只把任务放进进程内 `generateJobs` Map 并返回 202（`src/qr-app.js:87-104/201-253/936-1001`），30 分钟 TTL 后删除（`:87/162-169`），轮询只读该 Map（`:592-603`）。真正上游调用是同步 `POST /v1/images/edits`，一次请求完成、没有 `taskEndpointTemplate` 轮询（`src/qr-generator.js:262-301/367-477`）。因此“恢复本地任务”与“上游只扣一次”必须分别验收。
- 请求头没有稳定计费键：`qrcodeRequestHeaders` 只返回卫星凭据/用户断言或回退 API Key（`src/sso.js:129-147`），主站中间件不解析 `X-Client-Request-ID` 并生成随机 UUID（`sub2api/backend/internal/server/middleware/client_request_id.go:19-45`）。进程在“上游已成功、响应/本地任务未落盘”窗口崩溃后，用户重提会再次调用 `images/edits`，当前无法证明主站只扣一次。

**实施步骤（解冻后）**
1. 校验 SSO `iss/aud/sub/iat/exp/jti`，TTL ≤ 2 分钟，`aud=qrcode` 精确匹配。
2. 票据消费改为持久化原子表；补并发、重启、多副本测试。
3. 生图表单提交必须携带可跨重试/重启复用的稳定业务键，并由主站按已验明应用凭据 + `qrcode` slug 接收和校验；本地 `jobId` 只能用于本地任务恢复，不能单独当作主站计费键。调用 `images/edits` 前必须先提交 `request_admission=accepted`；若上游返回临时任务 ID 后改用最终键，必须由 `request_admission_alias` 表单跳登记，`(临时键, api_key_id)` 与 `(final_request_id, api_key_id)` 双向唯一、不可改绑；写入失败不得调用上游，别名/usage 失败不得确认成功或换键重提。协议未落地前，读超时/连接中断不得自动重提；必须明确标记“结果不确定/需对账”，或先按业务键查询权威结算状态。只有 `rejected_before_upstream`、`dispatch_state=not_started`（须由写出点事件证明，不得仅凭时间戳为空）且 `funds_effect=none`、`quota_effect=none` 时才可自动重提；`not_seen`/`accepted`/`unknown`/usage 0 行均待对账。此前已产生的本站预留，仅在本地预留对应 0 用量且主站 `funds_effect=none` 时可释放；`quota_effect=changed/unknown` 不阻断本站释放，但不得据此改扣本站钱包。
4. 验证 3 天 Session、生产 Cookie `Secure + HttpOnly`、注销可撤销。
5. 服务端调用主站只使用本应用凭据、slug 和用户断言；缺失失败关闭。
6. 补可重复测试；禁止依赖真实第三方服务做默认测试。
7. 计费只走主站 `qrcode` slug 配置或当前用户余额；不得发送或接受 `X-Sub2API-Payer`、`X-Sub2API-Commission-Rate`。

**验收**
- 同 ticket 并发仅一次成功；重启后重放失败；缺凭据/错 slug 失败关闭。
- 当前仓库未找到覆盖 qrcode/src/sso.js 的 SSO 并发消费/重启重放测试；须新增“两并发仅一条成功、重启后同 jti 拒绝”的可执行测试，不能只靠代码阅读判定通过。
- 生图提交后重启：要么从持久任务/结算行恢复且不再次调用 `images/edits`；要么明确 404 并进入“结果不确定/需对账”，断言不会自动重提。主站已支持稳定计费键时，同一业务键只能有一条权威 usage；未支持时不得声称只扣一次。
- 普通卫星携带付款/抽成头被主站 403；生成记录与 usage 归属当前用户。
- 只带 `X-Sub2API-Commission-Rate`、不带 `X-Sub2API-Payer` 同样被拒绝；非数字、负数、`>=1`、`NaN`、`±Inf` 不得被静默忽略或转成普通用户请求。
- 主站不得静默钳制合法费率：`0.9501`、`0.99`、`0.999` 要么按显式上界计算，要么在扣款前明确 4xx 拒绝；不得“接受 0.99 却按 0.95 扣款”。同一 request_id 重放必须复用首次付款人与费率快照。 Payer 存在时佣金头缺失/为 0 的语义必须两端一致：若 0 表示平台不抽成（Payer 承担 `actual_cost` 全额），必须在接口契约中写死并允许省略头；若不允许省略，Payer 存在而费率缺失/非法时必须 4xx。无论选哪种，不得把 0 解释为 `PayerCost=0`；零扣款只允许来自订阅成功行（`billing_subject=subscription`，含 `ActualCost=0` 的零成本订阅）、`ActualCost=0` 且 `TotalCost=0` 的 `free` 成功行、客户报价 0 但上游 `TotalCost>0` 的余额/订阅免费策略行（不得写 `free`，账号配额仍按 `TotalCost * AccountRateMultiplier` 累计），或未来显式开放的 100% 抽成余额行；必须同时看 `billing_subject` 与 `total_cost`，不能单凭 0 猜来源。当前 `rate>=1` 被拒绝，不得把佣金 0 当成零扣款。
- 用稳定 `request_id` 调 `GET /v1/sub2api/usage?request_id=<id>`：`actual_cost` 等于该 slug 配置的报价（未配置自定义价时等于模型 `actual_cost`；因报价先舍入 6 位、命令再量化 8 位，允许不超过 `5e-7` 的舍入差），`total_cost` 仍是模型/渠道成本；模型/渠道成本不可得时必须显式阻断或标记未归类，不得让 `total_cost=0` 的成功权威行参与统计或对账；命中自定义价时 `rate_multiplier = 1` 且 `billing_mode` 与规则单位一致（`token` / `image` / `video` / `per_request`），不得把按量规则误写为 `per_request`；未命中自定义价且主站为空 setting 键/显式 `mode=model` 时，`rate_multiplier` 才可等于该 Key 的实际倍率；`custom/request/points` 的 `rules=[]` 属配置误用，必须失败关闭，不能靠清空规则回模型价；其他模式未命中必须失败关闭。 另须验证：卫星 SuperKey 未绑组时，主站必须按“用户全部有效订阅”判定：`ListActiveUserSubscriptions(userID)` 返回 0 条走余额，1 条走订阅，2 条及以上请求前显式拒绝，且不写 usage/余额/Key 配额；拒绝码固定为 `MULTIPLE_ACTIVE_SUBSCRIPTIONS`（未映射时至少 403 `billing_error`），不得以订阅 + Payer 错误或任意一条订阅替代多订阅拒绝；请求前预检与后扣必须复用同一请求内订阅快照（不得各自重查；预检后新增/失效订阅不得改变本次账本分支），不得按请求头组、实际调度账号组或订阅 ID 排序任选一条。订阅已命中时 `isSubscriptionBill` 必须为真，且必须由显式账本分支字段表达“未解析/确认无订阅/唯一订阅”，不能继续用 `Subscription=nil` 兼表三态，不得仅因 `apiKey.Group == nil` 或 `apiKey.Group` 非订阅组而落到余额。SuperKey 会跨启用组选号，实际账号组不等于请求组，不能直接套用。平台配额只适用于余额模式：余额模式下按资金主体 `(PayerUserID 或 UserID, 解析出的请求平台)` 与本次 `charged_cost` 累计（余额自付等于 `ActualCost`，代付等于 `PayerCost`）；`Payer == User` 时即为 `(UserID, ActualCost)`。订阅模式走订阅账本，不写 `user_platform_quotas`；不得按 `UserID + ActualCost` 默认记账而让 Payer 额度漏计。平台解析失败时必须显式阻断或记录可对账的未归类消费，不得静默跳过。命中卫星报价时 `api_keys.quota_used`、Key 限流必须按报价（`actual_cost`）累计；账号配额仅对 `APIKey`/`Bedrock` 类型账号按实际 `account_id` 与 `TotalCost * AccountRateMultiplier` 累计，其他类型 `account_quota_cost=0` 且不写账号配额；余额模式下解析出平台后 `user_platform_quotas` 也必须按同一资金主体与 `charged_cost` 累计。另须断言 `/v1/sub2api/usage` 返回本次 typed 五类额度快照与精确金额，包括 `api_key_id`、`billing_subject`、`payer_user_id`、`charged_cost`、`api_key_quota_cost`、`api_key_rate_limit_cost`、`account_quota_cost`、`platform_quota_subject_user_id/platform_quota_platform/platform_quota_cost`、`subscription_cost` 及 `*_usd_nanos`/定点十进制：余额模式自付时 `payer_user_id=user_id` 且 `charged_cost=actual_cost`，代付时 `payer_user_id=PayerUserID` 且 `charged_cost=PayerCost`；订阅模式必须返回 `billing_subject=subscription`、`charged_cost=0`，且 `subscription_cost` 等于本次 `ActualCost`（零成本订阅即 `0`）；`free` 仅 `ActualCost=0` 且 `TotalCost=0`；字段缺失或历史 `NULL` 不得被解释为自付，`charged_cost=0` 必须能与历史 `NULL` 区分。不得用泛化 `quota_subject_user_id` 或 JSON 浮点代替；金额验收比较 nanos/定点，不得先把主站 8 位金额四舍五入到分。冻结期只登记契约，不解冻实现。  另须断言零扣款来源：`billing_subject=subscription` 且 `charged_cost=0` 只表示订阅账本，不得当作余额零扣款；`free` 仅 `ActualCost=0` 且 `TotalCost=0`，五类额度均为 0；其余成功行一律不得以 `charged_cost=0` 作为免扣款理由。另须覆盖失败尝试：后扣失败后，`usage_logs` 不得出现该 `(request_id, api_key_id)` 的零金额成功行，必须写独立 `billing_attempts`（含 `attempt_no/failure_stage/error_code/actual_cost/charged_cost/total_cost/用量/video_duration_seconds/duration_source`）；同键重试成功后才形成唯一真实金额权威行，资金只变化一次。 自有 Provider 路径不得用主站 `/v1/sub2api/usage` 缺失或余额不变证明未重复建单/未重复计费；必须以 Provider 创建次数、Provider 回执 ID 与本地 `(owner, idempotency_key)` 唯一行共同验收。若该路径改走主站 relay，则删除 Provider 侧证明并改用 `X-Client-Request-ID` + 主站权威 usage，不得双轨。
- **usage 命中不是结算证据**：查询必须按 `request_id + 主站 api_key_id`（或主站等价精确过滤）判定；0 行只表示主站暂时不可见/未写入，多行或主站 `api_key_id` 缺失 `NULL` 一律视为不可唯一确认。以上任一情况都不得把任务标为已结算、不得扣本地钱包/额度、不得重试生成新键、不得改用余额差或本地报价补猜，只能保持 `pending`/待对账；只有唯一权威行且 `request_id`、主站 `api_key_id`、付款主体与金额逐项一致时才允许确认。0 行必须结合主站 `request_admission`：仅 `settled` 可确认；只有 `rejected_before_upstream`、`dispatch_state=not_started`（须由写出点事件证明，不得仅凭时间戳为空）且 `funds_effect=none`、`quota_effect=none` 才可重发；`not_seen`/`accepted`/`unknown` 均不得解释为未受理或未扣款，`quota_effect=changed` 也不得作为本站钱包拒释依据。
- **平台配额当前未通过**：目标契约是余额模式按资金主体 `(PayerUserID 或 UserID, 平台)` 与 `charged_cost` 累计，但 `UsageBillingCommand` 尚无平台配额字段，service 层仍按 `p.User.ID + cost.ActualCost` 另写。修复前验收必须标记未通过，不得把 Redis/DB 另写当作已满足；订阅与 `free` 行不写 `user_platform_quotas`。**PayerCost 同精度**：代付金额 `PayerCost=ActualCost×(1-rate)` 必须在仓储扣款、usage `charged_cost` 与平台配额累计前按 8 位 half-away-from-zero 量化，三者使用同一值；当前 `quantizeMonetaryFields` 未覆盖 `PayerCost`（`usage_billing.go:85-91`），第 9 位边界用例修复前必须标失败。
- **订阅行主体必须完整且不得回退余额**：命中行 `billing_subject=subscription` 时，`subscription_id` 必须非空，`subscription_cost` 必须存在且等于该行 `actual_cost`（零成本订阅写 `0`，不得为 `NULL`），`charged_cost=0`；`balance_cost` 必须为 0 且不得同时出现余额实扣或非本人 Payer 实扣。缺主体、缺金额或与余额证据冲突时，只能 `pending`/人工复核，不得按 `charged_cost=0` 确认“未扣款”。`billing_subject=free` 仅限 `actual_cost=0` 且 `total_cost=0`，不得替代缺失的订阅主体。
- **纯文本 token 缺失不得按次**：主站 `custom` 模式若对本项目配置了 `millionTokens` 规则，纯文本调用必须取得可信 token 合计后按 `token` 计价；上游未返回 usage、解析失败或仅图片 token 时，不得静默落 `request` 或模型价，必须失败关闭/待对账；同目标同时有 `token` 与 `request` 时固定优先 `token`。上游明确返回 0 token 可按 `millionTokens` 得 0 金额，但 `billing_mode` 仍为 `token`，须与“用量未知”分开断言。 **当前实现未满足该零用量分支**：`quoteSatelliteBilling` 仍以 token 合计 `>0` 才尝试 `millionTokens`，0 用量会落到 `request`/模型价；修复前该用例只能标为失败/待实现，不得按现网行为验收通过。
- `/v1/sub2api/usage` 当前实现缺口是不返回 `api_key_id` 或 `group_id`，同用户多把 Key 用同一 `request_id` 只能靠行 `id` 区分；这不是接口契约，S2A-08 落地后必须返回 `api_key_id` 并支持按 Key 过滤。在该字段落地前，响应中缺少 `api_key_id` 不得被解释为“当前用户只有一把 Key”或“可以按行 `id` 猜结算”；验收须显式标记为未满足并按 `pending`/人工复核处理。查询固定 `PageSize=20`，同用户大量 Key 可能截断，验收须给出上限/分页语义。
- 本项目仅文本/结构化输入，不要求视频回退；但仍须断言：若上游或代理误传 `VideoCount > 0`，主站不得静默落到 `token`/`request` 规则，必须按 S2A-08 fail closed。
- **只读余额/状态查询不进入计费账本**：本项目存在经 `/api/sub2api/balance` 转发到主站 `GET /v1/sub2api/balance` 的展示/预检调用；该接口只能读取余额，不得生成 usage、占用计费键、扣余额/配额或作为“请求已成功结算”的证据。验收须断言余额查询前后 `usage_logs`/`billing_attempts` 行数、余额、Key/账号/平台额度均不变，且查询失败不得触发重试计费或改变本次模型请求的账本分支。若某次余额查询同时携带了模型结算键，仍只能按只读处理，不得复用该键产生 usage。
- 同一 Key、同一 `request_id` 的**已成功结算**请求重放：`/v1/sub2api/usage` 只返回首次权威记录（first-write-wins），不追加第二行；失败尝试走独立失败审计、不占结算键，成功重试后才形成唯一权威行；同一账本下余额、Key 配额、订阅用量与 usage 行均只变化一次。去重键是 `(request_id, api_key_id)`；同一用户换 Key 使用同一 request_id 会生成第二条记录，不得写成全局“一个 request_id 只一条”。重放命中时不得用本次模型、token、金额、`billing_mode`、订阅或付款人覆盖首次 usage；付款人或费率与首次不一致时，必须返回明确冲突或既有结果并写审计，不得静默换人扣款。代付场景还须复核配额主体：余额、Key 配额、限流、账号配额与平台配额必须由首次资金/额度快照复算，不得重放时改记到 `UserID + ActualCost`。 解冻后还须复核 `/v1/sub2api/usage` 是否返回 `billing_subject`、`payer_user_id/charged_cost`：余额自付应为请求用户与 `actual_cost`，代付应为实际付款人与实扣额；订阅行须返回 `billing_subject=subscription`、`charged_cost=0`，且 `subscription_cost` 等于本次 `actual_cost`（零成本订阅即 `0`）；`billing_subject=free` 仅用于 `actual_cost=0` 且上游 `total_cost=0` 的正常成功行（五类额度均为 0）；客户报价 0 但上游成本 >0 必须走余额/订阅免费策略，不得写成 `free`；完全不计费的旁路没有 usage；字段缺失或历史 `NULL` 不得猜成自付，佣金 0 不得误写为零扣款。 解冻后 `usage` 复核还必须包括 typed 额度快照（`api_key_id`、`billing_subject`、`payer_user_id`、`charged_cost`、`api_key_quota_cost`、`api_key_rate_limit_cost`、`account_quota_cost`、`platform_quota_subject_user_id/platform_quota_platform/platform_quota_cost`、`subscription_cost`）与 `*_usd_nanos`/定点十进制；不得用泛化 `quota_subject_user_id` 或浮点代替，金额比较不得先四舍五入到分。 另须覆盖失败尝试：后扣失败后，`usage_logs` 不得出现该 `(request_id, api_key_id)` 的零金额成功行，必须写独立 `billing_attempts`（含 `attempt_no/failure_stage/error_code/actual_cost/charged_cost/total_cost/用量/video_duration_seconds/duration_source`）；同键重试成功后才形成唯一真实金额权威行，资金只变化一次。此前冻结时只做设计复核，解冻后须按该契约验收，不得以冻结期快照证明已满足。
- **媒体请求缺数量不得按次/按 token 成功**：本项目若存在生图或图片编辑路径，主站 `quoteSatelliteBilling` 只在 `ImageCount>0` 时尝试 `image` 规则；请求已明确为生图但张数为 0 时会落到 `token`/`request`。验收必须覆盖 `ImageCount=0` 的明确生图请求，断言失败关闭/待对账而不是按次成功；视频同理覆盖 `VideoCount=0`、`VideoDurationSeconds>0`。若本项目确无该媒体路径，须在卡内显式写“无此路径”并给出路由/调用证据，不得默认跳过。
- 若主站对该 slug 启用 `custom/request/points` 规则：本卫星实际使用的目标/单位必须在规则中命中；未命中时请求必须失败关闭并返回可定位错误，不得静默按模型价扣费。`points` 模式只允许整数点数，金额按 `点数 × 0.01` 换算；`request` 单位得到 `billing_mode=per_request` 且 `actual_cost = 点数 × 0.01`，`image`/`videoSecond` 分别按图片数/秒数乘点数，`millionTokens` 必须被配置校验拒绝（`satellite_billing.go:114-122/356-359`）。不得把 `per_request` 一律当作固定 1 次请求而不乘 0.01，也不得把 `points` 的 `request` 规则误判为 `custom` 的 token 兜底。
- 本项目的上游生图是同步 `/v1/images/edits`，不是异步任务/轮询/回调；验收必须显式写“无异步上游任务”并引用 `src/qr-generator.js:262-301/367-477`，不得把它误写成 task 轮询。同步调用仍需稳定计费键：同一用户对同一业务请求的重试/重启后重提，只有在主站已接收并校验该键时才能断言只产生一条 usage；否则必须标记为计费结果不确定。
- **本地异步生图任务只存在进程内存，重启即丢，且不能据此推断上游未扣费**：`POST /api/generate` 把任务放入 `generateJobs` Map 并立即返回 202（`src/qr-app.js:87-104/201-253/936-1001`），30 分钟 TTL 后删除（`:87/162-169`）；轮询 `/api/generate/jobs/:jobId` 只读该 Map（`:592-603`）。但上游图片调用是同步 `images/edits`（`src/qr-generator.js:262-301/367-477`），不是可续跑的上游任务。进程重启/崩溃/TTL 过期后本地任务 404、结果不可取，而上游可能已产生费用；用户重提会再次调用主站。解冻后必须把本地任务 ID、状态、用户归属、业务请求键与结算状态持久化，或明确关闭异步生图只允许同步；若保持内存实现，验收必须承认“不支持重启恢复”，并证明 404 时不会因自动重试产生第二次扣费。补验收：异步提交后立即杀进程重启，断言任务可从持久行恢复，或明确 404 且同一业务请求键在主站只有一条权威 usage；没有稳定键时必须断言进入待对账状态。
