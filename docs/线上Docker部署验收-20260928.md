## 实际执行过程

### 1. 核对现状并保留已有改动

先检查本地工作区、线上容器、镜像、Compose 来源、数据挂载、网络、Nginx 和域名。工作区存在用户尚未提交的修改，按当前源码部署，没有执行 reset 或清理用户改动。线上主站和卫星属于不同 Compose 项目，因此没有对根 Compose 执行不加限制的整套重建。

### 2. 先备份，再覆盖源码

1. 创建 `/opt/sub2api_backup/20260928T0315Z`，导出主站 PostgreSQL 全量 SQL。
2. Redis 执行持久化后保存 RDB，并通过 `redis-check-rdb` 检查。
3. 保存主站配置、数据目录、Nginx 配置和容器元数据；对四项主站关键备份计算并验证 SHA256。
4. 保存原线上源码、Livart PostgreSQL dump 和 15 个 SQLite 一致性备份。SQLite 使用数据库备份方式，避免直接复制正在写入的数据库文件。
5. 给旧应用镜像增加备份标签，保留快速切回旧镜像的可能。

最初归档包含正在变化的日志和 Redis AOF，出现文件变化导致的归档失败；删除该不完整归档，重新将稳定配置、数据与单独的数据库快照分开备份。没有把失败的归档当作有效备份。

### 3. 从 Windows 打包、上传并校验

使用 `git ls-files -co --exclude-standard` 收集 13 个项目的当前源码，排除 `.git`、`node_modules`、运行数据、日志、缓存、数据库、`.env` 和备份等内容。初次归档包含 20,806 个文件，约 289.6 MB，并生成逐文件 SHA256 清单。

上传到 `/opt/cc2cx-production/source-20260928.tar.gz` 后，覆盖解压到现有线上源码目录；初次归档的文件哈希检查没有差异。之后修复的源文件以 SFTP 增量上传并重新构建相关应用，所以初次清单不代表最终补丁文件的哈希。

### 4. 构建镜像并分批切换

构建脚本 `/opt/cc2cx-production/build-20260928.sh` 逐项构建并保存独立日志；单个服务失败后继续其他服务，失败项单独修复重试。主站首先构建完成并上线，随后分批切换卫星，所有应用使用 `20260928` 标签。

主构建批次于北京时间 **11:18:22** 开始，**11:45:30** 结束（日志使用 UTC，对应 03:18:22—03:45:30）。AIExcel 单独重试成功；Canvas 在初次构建后因会话和视频身份修复重新构建，最终版本完成后才切换上线。

沿用运行中容器的必要环境配置，生成 release override，避免覆盖源码时丢失服务端凭据。切换使用 `up -d --no-deps --no-build` 和明确服务列表，保留数据库等依赖及数据挂载。

已执行的部署方式如下，均在 Linux 服务器运行：

```bash
# 主站
cd /opt/sub2api-deploy
docker compose -f docker-compose.yml -f docker-compose.talent.yml \
  -f /opt/cc2cx-production/sub2api-release-20260928.yml \
  up -d --no-deps --no-build sub2api

# 卫星与代理站
cd /opt/cc2cxSub2api_all
docker compose --env-file /opt/cc2cx-production/new-apps.env \
  -f docker-compose.online.yml \
  -f /opt/cc2cx-production/release-20260928.override.yml \
  up -d --no-deps --no-build \
  agentapi yibiao aiexcel qrcode ai3d aihuoke-backend aihuoke-frontend \
  screen2code-backend screen2code-frontend aicut canvas ju-backend ju-web livart ppt
```

### 5. 域名、代理与 CORS

核对现有 `/etc/nginx/conf.d/cc2-apps.conf`、`cc2-additional-apps.conf`、`cors.conf` 及共用代理/CORS 片段。已有配置覆盖正式域名、HTTPS、WebSocket 和凭据跨域请求，本次沿用这些有效配置，并通过 `nginx -t` 和实际 HTTPS、预检请求验证，没有声称重新编写了整套 Nginx 配置。

CORS 使用明确的来源域名白名单，返回匹配来源和凭据许可；预检返回 204。不是在凭据请求中设置不兼容的 `Access-Control-Allow-Origin: *`。公开图标和充值链接使用线上域名；容器内部回环地址不等于浏览器访问地址，检查重点是实际浏览器请求不能指向本机 localhost。

### 6. 分层验证与清理

先检查容器与主站健康，再用正常用户身份的短期测试会话检查菜单启动、回调、余额和匿名权限；之后用 Chromium 验证全部 12 个接入站点的页面跳转、异常和请求地址。测试用会话仅临时放在服务器受限文件中，验证结束后删除会话文件和容器内副本。

Canvas 和 Livart 额外验证 Cookie 属性、退出后 401，以及 Livart 使用 Cookie 的 WebSocket 认证。PPT 在最终镜像切换后再单独浏览器验证，避免用旧容器的结果证明新版本。

所有构建结束后清理 Docker 构建缓存和临时测试镜像，保留线上镜像、回退镜像和数据卷。

## 遇到的问题与处理记录

| 现象 | 原因或定位结果 | 实际处理与验证 |
| --- | --- | --- |
| 初次备份归档失败 | 日志/AOF 在归档时仍变化 | 重做稳定配置归档，数据库采用独立快照；校验最终备份 |
| AIExcel 构建找不到 `build/sites-vite-plugin.ts` | 全局 `**/build/` 忽略规则误排除源码插件 | 补传文件；`.gitignore` 增加精确例外；重建上线成功 |
| Yibiao 登录后余额接口 500 | 旧版本存在缺失导入导致的 NameError | 部署本地已有修复，验证余额接口 200 |
| Aicut、Screen2Code 首页和回调 403 | 新镜像中的 Vite 拒绝正式域名 Host | 在 release override 设置 `__VITE_ADDITIONAL_SERVER_ALLOWED_HOSTS` 为对应域名，重建容器；首页、回调及余额恢复 |
| Canvas、Livart 仍将本地认证 JWT 返回浏览器 | 旧 SSO 实现不符合公共层 HttpOnly Session 约定 | JWT 留在 HttpOnly Cookie，前端只接收无认证能力的状态标记；兼容旧会话自然过期 |
| Cookie 登录后需要防止跨源写请求 | 浏览器会自动携带 Cookie | 校验写请求 Origin；Canvas 转发时保留正确公开 Host/HTTPS 信息；三天 TTL、退出和 Cookie 属性测试通过 |
| Canvas JWT 兜底仍为七天 | 默认配置虽为 72 小时，未配置分支仍为 168 小时 | 兜底改为 72 小时，新 Cookie Max-Age 为 259200 秒 |
| Canvas 视频下载返回 503，后台轮询没有上游请求 | 两条链路未叠加任务所属用户的 Sub2API 身份 | 下载和轮询补充用户身份；SSO、流式请求、视频轮询、下载及归属校验回归通过 |
| Livart 改用 Cookie 后 WebSocket 仍依赖客户端 JWT | 原认证消息直接提交 token，来源限制过宽 | 从已认证握手取得用户；限制正式 Origin；真实浏览器返回 `authenticated` |
| Livart 余额可读但充值链接为空 | 运行环境缺少公开 `LINK` | release override 补齐 `https://api.cc2.cx`；验证充值地址为主站 `/purchase` |
| 连续验证后部分 SSO 启动返回 429 | 短时间集中调用触发主站限流 | 保留限流机制，稍后重新验证；最终全部启动接口通过 |
| 浏览器等待 `networkidle` 超时 | 页面可能持续发起后台请求，网络空闲不能稳定作为加载完成条件 | 改用 `domcontentloaded` 加短暂渲染等待，并验证页面内容和实际接口 |
| 中文 Markdown 路径 SFTP 上传失败 | PowerShell 到 Python 的管道把中文路径变成问号 | Python 从目录 glob 定位实际文件，再上传；本地 Markdown 内容保留 UTF-8 |
| Canvas 首次较宽范围测试失败 | 除视频身份缺陷外，还存在模型协议优先级、公共设置断言问题 | 修复本次明确定位的视频身份缺陷；针对性回归通过，其余既存失败保留说明，不宣称全量测试通过 |
| 清理后 Build Cache 不为绝对零 | 还有被引用的基础层，Docker 标记不可回收 | 确认可回收为 0 B；不强删被引用层或生产镜像 |

用户提到的 `Authorization header is required`、`SSO_failed` 按整条菜单链路验证：主站 Cookie 启动、票据回调、必要的 exchange、本地会话和业务接口都覆盖。最终测试未复现这两类错误；不能仅凭首页 200 判断 SSO 已正常。

## 运维与回退注意事项

- 常规重新启动本次发布使用 `/opt/cc2cx-production/deploy-current.sh`；该脚本不重新编译镜像。
- 需要重建时使用本次 build override，再使用 release override 部署；基础 Compose 可能仍含旧标签，不应省略 override。
- 回退镜像前先核对对应容器的 `cc2cx-backup/<container-name>:20260928` 标签、挂载和配置。回退镜像不等于恢复数据库；数据库恢复应在维护窗口明确恢复点后执行，本文未执行数据库回滚，也未做完整恢复演练。
- 不运行 `docker compose down -v`，不清理生产数据卷，不用镜像瘦身替代构建缓存清理。
- 服务端环境文件和容器元数据可能含敏感配置，只在服务器受限目录保存；不要复制到 Git 文档或浏览器。
