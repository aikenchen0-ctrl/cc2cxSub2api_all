# Sub2API 二改说明

更新时间：2026-09-01

本文记录当前定制版本相对于上游 Sub2API 的全部关键改动、运行约束和后续升级要求。后续升级、合并上游代码或重新构建 Docker 镜像时，必须先阅读本文并逐项验证，不得因为同步新版本而覆盖、删除或静默改变本文列出的特性。



后续更新：以当前定制版为基线，只移植官方优化，并且定制行为拥有最高优先级。



## 一、定制版本定位

本项目是以 Sub2API 为基础的定制版中转站，除原有 API 网关、账号管理、计费、订阅、支付和运维能力外，还为 Canvas、QRCode、PPT 子应用提供统一的 Superkey 调用入口。

当前部署方式以 Docker 为主。应用镜像可以独立更新，但 PostgreSQL、Redis、应用数据目录、加密密钥和现有账号数据必须保持连续可用。

## 二、Superkey 机制

### 2.1 用户级唯一 Superkey

- 每个用户使用固定名称 `Sub2API Super Key` 获取唯一 Superkey。
- Superkey 前缀为 `sk-super-`。
- `GET /api/v1/keys/super` 在用户登录后懒创建并复用该用户已有 Superkey。
- 普通自定义 API Key 不得伪造或占用 Superkey 前缀。
- Superkey 仍然经过用户状态、IP ACL、余额、Key 状态、订阅和正常计费校验。

### 2.2 Superkey 不绑定单一分组

Superkey 的设计目标是跨分组调用所有允许的上游，不应固定绑定某个文本组、图片组或视频组。下游请求应根据模型和能力在可用账号中动态选择上游。

兼容旧客户端时，可以接受 `X-Sub2API-Group-ID` 或 `group_id`，但该参数只能作为显式目标分组，不得让前端强制用户选择分组，也不得把 Superkey 永久写入某个分组。

后续修改认证中间件、账号调度、模型路由或分组权限时，必须验证：同一个 Superkey 能分别调用文本、图片和视频能力，且不会因为上一次请求而固定到错误分组。

## 三、子应用入口

### 3.1 Canvas

- Canvas 通过 URL 参数接收 `baseUrl` 和 `apiKey`，使用 `Authorization: Bearer <super-key>` 调用 Sub2API。
- 文本、图片、视频请求均进入 Sub2API 的统一网关，由模型和请求能力决定上游。
- 文本请求保持 OpenAI Responses/Chat Completions 的默认兼容方式，不得因图片或视频适配逻辑改变文本计费。
- Canvas 的默认模型可以被用户本地配置覆盖，排查问题时必须以实际请求中的 `model` 为准。

### 3.2 QRCode

- QRCode 使用 Superkey 调用图片生成和图片编辑能力。
- 图片编辑必须支持 data URL 转 multipart/form-data，并保留参考图片字段。
- 上游协议不一致时，由媒体适配层转换请求和响应；失败必须返回明确错误，不得伪造成功图片。

### 3.3 PPT / Presenton

- PPT 子应用通过 `baseUrl`、`apiKey` 和模型配置调用 Sub2API。
- JSON 和 FormData 请求均可注入 Sub2API 认证及模型信息。
- PPT 的文本生成使用统一文本接口，不能依赖某一个固定上游账号。

## 四、模型与协议适配

### 4.1 文本

支持 OpenAI Chat Completions、OpenAI Responses、Anthropic Messages 和 Gemini generateContent 等协议。协议转换必须保持角色、系统消息、内容块、流式响应和错误信息的语义。

### 4.2 图片

支持 OpenAI-compatible 图片生成与编辑，包括 `gpt-image-1`、`gpt-image-1.5`、`gpt-image-2` 以及文档列出的兼容模型。支持 data URL、multipart/form-data、`data` 响应解包和图片 URL 提取。

### 4.3 视频

支持 OpenAI-compatible 视频创建、状态查询和内容下载，包括文档列出的 Kling、Seedance、Grok 视频模型。视频状态统一归一为 pending、processing、done、canceled、failure 等状态，不能把失败状态当作成功。

### 4.4 计算万物

计算万物本质上是 Sub2API 兼容中转站。除文档明确标注特殊协议的模型外，计算万物列出的文本、图片和视频模型默认按 OpenAI-compatible 方式调用，不得仅凭模型名称包含 `grok`、`kling` 或 `seedance` 就强行切换原厂协议。

## 五、计费与兼容性要求

- 现有文本调用入口、默认请求格式和计费模型必须保持不变。
- 图片、视频适配只能在对应能力入口生效，不得拦截或改写普通文本请求。
- 计费使用用户请求模型、实际映射模型和上游用量的既有链路；协议转换不得重复扣费。
- 上游余额不足、模型不支持、权限错误和网络错误必须真实暴露并记录日志，不得静默降级到另一个模型。
- 不得通过假响应、空图片、空视频或吞掉异常来掩盖上游失败。

## 六、控制面板版本更新策略

当前版本保留版本号展示、GitHub 最新版本检查和“发现新版本”提示，方便管理员了解上游版本变化。

但控制面板不得执行实际程序更新：

- 不显示“立即更新”按钮。
- 不显示或执行版本回滚入口。
- 前端不调用 `/admin/system/update`、`/admin/system/rollback` 或 `/admin/system/rollback-versions`。
- 后端不注册上述会替换程序或列出可回滚版本的变更路由。
- 只保留当前版本读取、最新版本检查和提示展示。
- Docker 镜像只能由管理员手工构建、导入和重建应用容器更新。

## 七、Docker 与数据保护

- 更新应用时只重建 `sub2api` 服务。
- PostgreSQL、Redis、`data/`、`postgres_data/`、`redis_data/` 和 `.env` 必须保留。
- 禁止使用 `docker compose down -v`、`docker volume prune` 或 `docker system prune --volumes`。
- 必须保留数据库连接配置、Redis 配置和加密密钥，否则已有账号凭证可能无法解密。
- 新镜像启动后必须检查容器 healthy 状态和 `/health` 返回 200。
- 启动失败时先检查数据库网络、迁移日志和环境变量，不得删除数据卷强行重建。

## 八、后续版本升级强制流程

每次同步上游新版本或构建新 Docker 镜像前，必须完成以下步骤：

1. 阅读本文和 `二次更新.md`，列出本次上游变更涉及的文件。
2. 检查 Superkey 是否仍为用户级唯一 Key，且没有恢复固定分组绑定。
3. 检查 Canvas、QRCode、PPT 的入口参数、认证头和默认调用协议。
4. 检查文本、图片、视频适配器是否仍按能力分流，计费链路是否未改变。
5. 检查版本面板仍只提示更新，不具备实际更新和回滚动作。
6. 先运行相关单元测试、前端类型检查和生产构建，再构建 Docker 镜像。
7. 在不触碰 PostgreSQL、Redis 数据的前提下更新应用容器。
8. 验证 `/health`、文本最小请求、图片入口和视频入口；任一关键特性失败时停止发布。

## 九、禁止事项

- 禁止把 Superkey 重新绑定到单一分组。
- 禁止要求用户在 Canvas、QRCode、PPT 中手工选择分组。
- 禁止静默将用户选择的模型替换成其他模型。
- 禁止因上游版本更新删除当前子应用适配器。
- 禁止恢复控制面板自动更新、在线回滚或自动拉取官方镜像。
- 禁止未经备份直接修改或清空生产数据库、Redis 和数据卷。

## 十、发布验收记录模板

每次发布应记录：镜像标签和镜像 ID、构建时间、Git/源码版本、测试命令及结果、容器健康状态、`/health` 响应、文本/图片/视频入口验证结果，以及是否确认本文特性未被修改。
