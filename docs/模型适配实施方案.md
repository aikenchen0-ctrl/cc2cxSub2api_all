# Sub2API 模型适配实施方案

## 1. 目标与边界

Sub2API 作为 Canvas、QRCode、PPT 的统一 AI 中转层，重点解决图片和视频模型的协议适配、异步任务管理、计费与跨分组调度。三个子应用只依赖稳定的 Sub2API API，不感知具体供应商。

本轮方案不直接改代码或部署。实施前必须补齐各上游真实 API 文档或脱敏的请求/响应样例；密钥只通过运行时配置注入。

规则：模型未标注特殊平台时，默认使用 OpenAI-compatible profile；只有明确标注 `grok` 的模型才使用 Grok profile；标注 `openai` 的模型使用 OpenAI-compatible profile。模型名称只是目录键，不能据此臆造上游字段。计算万物本身是 Sub2API 兼容中转站，因此其列出的全部图片、视频模型按 OpenAI-compatible 上游处理，不能因为模型名含 `grok`、`kling` 或 `seedance` 就切换到原厂专用协议。

## 2. 外部统一 API 契约

保留现有 OpenAI 风格入口：

- 图片：`POST /v1/images/generations`、`POST /v1/images/edits`。
- 视频：`POST /v1/videos`（兼容 `/v1/videos/generations`），`GET /v1/videos/{id}`，`GET /v1/videos/{id}/content`。
- 可选扩展：`/v1/videos/edits`、`/v1/videos/extensions`，仅在能力目录声明支持时开放。
- 模型发现：`GET /v1/models`，按当前 Superkey 可用账号和能力聚合、去重，不泄漏上游密钥。

图片同步响应统一为 OpenAI image response（`created`、`data[]`，每项 `url` 或 `b64_json`）；视频统一返回内部任务 `id`、标准化 `status`（`queued`/`in_progress`/`completed`/`failed`/`cancelled`）及错误对象。上游原始字段保留在内部日志/任务扩展字段，不直接暴露给客户端。

## 3. 模型能力目录

新增持久化或配置化的 model capability catalog，每个模型至少声明：

| 字段 | 说明 |
| --- | --- |
| `public_model` | 对子应用公开的模型名 |
| `modality` | `image` 或 `video` |
| `operations` | `generation`、`edit`、`image_to_video`、`extension` 等 |
| `protocol_profile` | `openai_compatible`、`grok_media` 或经取证后的专用 profile |
| `async_mode` | `sync`、`polling`、`webhook`（未知时不得猜测） |
| `upstream_model` | 供应商实际模型名，可按 Provider 配置覆盖 |
| `enabled` | 管理端启停开关 |

初始目录：

- 通用图片：`gpt-image-1`、`gpt-image-1.5`、`gpt-image-2`。
- QA API Hub：`gemini-3.1-flash-image`（OpenAI）、`grok-imagine-image-quality`、`grok-imagine-image-2.0`、`grok-imagine-image`、`grok-imagine`（Grok）。
- 一花 Codex：`gpt-image-1`、`gpt-image-1.5`、`gpt-image-2`（OpenAI URL `https://llm.xxttt.com/v1`；Anthropic URL仅作为其文本协议配置，不用于图片适配）。
- 计算万物（Sub2API 兼容中转）：图片 `gpt-image-2`、`grok-imagine-image-1.5`；视频 `grok-imagine-video-1.5`、`kling-v1`、`kling-v1-5`、`kling-v1-6`、`kling-v2-5-turbo`、`kling-v2-6`、`kling-v3`、`kling-v3-omni`、`seedance-2.0`、`seedance-2.0-fast`。上述模型统一绑定 `openai_compatible`，实际 `base_url`、密钥和模型映射由计算万物 Provider 配置提供。

## 4. Provider/Profile 配置

Provider 与模型目录分离。Provider 配置包含 `base_url`、认证方式、端点模板、请求/响应 profile、模型映射、超时和是否允许异步。管理端保存引用关系，密钥使用加密存储或环境变量，不写入日志和前端 URL。

- `openai_compatible`：默认 profile，使用 `/images/generations`、`/images/edits`；视频使用 Sub2API 已定义的 `/videos` 创建、状态查询和 content 下载契约。计算万物作为兼容中转站直接复用此 profile；只需验证其端点、模型映射和响应是否符合契约。
- `grok_media`：复用现有 Grok 图片/视频 handler、模型规范化、状态和 content 代理逻辑。
- 不为计算万物的 Kling/Seedance 模型建立原厂专用 profile。只有未来接入 Kling/Seedance 原厂 API，且用户明确提供其特殊协议时，才另行增加专用 profile。

## 5. Superkey 跨分组动态路由

现有 `ResolveSuperAPIKeyGroup` 会在无显式分组时优先图片组或第一个可用组，这不满足跨分组模型调用。改造为请求感知路由：

1. 鉴权后解析请求模型、端点和 operation。
2. 从 capability catalog 得到 modality、profile 和所需能力。
3. 查询用户可用的活跃分组、账号及其模型映射，过滤平台、能力开关、配额、并发和健康状态。
4. 交给现有 scheduler 选择账号；失败时只在候选集合内按既定 failover 重试，并记录排除原因。
5. 将选中的 group/account/provider/profile 写入请求上下文和内部 usage/task 记录。

Superkey 不接受或保存用户选择的分组；普通 API Key 的显式分组行为保持不变。视频状态/content 请求不带模型，必须依据内部任务记录恢复原始 provider/group/account，不能重新按“第一个组”解析。

## 6. 图片适配器

以现有 `openai_images` 和 `grok_media` 为基础抽象 `ImageAdapter`：解析公共参数（prompt、size、quality、style、背景、输出格式、参考图），执行 provider 请求，归一化响应，返回计费元数据。

- OpenAI-compatible 图片：透传标准字段，保留不支持字段的显式校验和错误。
- Grok 图片：使用现有 Grok 模型规范化与 moderation/权限路径。
- `images/edits` 必须统一 multipart 与 data URL 输入，限制和错误码在网关层保持一致。
- 同步和异步图片接口共用 adapter；异步任务存储内部 task ID、用户、Superkey、provider、group、account、模型和过期时间。

## 7. 视频异步任务适配器

定义 `VideoAdapter` 接口：`Create`、`GetStatus`、`GetContent`，可选 `Edit`、`Extend`。网关只处理公共请求和任务生命周期，adapter 负责供应商字段转换。

统一流程：创建任务返回内部 ID；轮询时按任务绑定的 adapter 查询；完成后由 Sub2API 代理或安全重定向下载；失败映射为标准错误并保留可审计的 upstream request ID。

先迁移/封装现有 Grok 视频逻辑作为基准实现，再通过通用 OpenAI-compatible VideoAdapter 接入计算万物。计算万物每个模型只需验证兼容中转层声明的文生视频、图生视频、时长、比例、分辨率、音频和结果下载能力；不支持的 operation 明确返回 `capability_not_supported`。

## 8. 任务、鉴权与下载安全

任务表至少保存 `task_id`、`user_id`、`api_key_id`、`group_id`、`account_id`、`provider_id`、`public_model`、`upstream_task_id`、状态、时间戳、计费状态和错误摘要。所有状态/content 查询校验任务归属；Superkey 仅能访问本用户任务。结果下载经过鉴权、短期签名或服务端代理，禁止把长期上游凭证放入 URL。

## 9. 计费、配额、并发与审计

沿用现有图片/Grok 视频计费入口，扩展为按 `provider + model + operation + usage` 记录。异步任务在创建、完成、失败、取消四个节点定义计费规则，避免重复扣费。图片/视频并发槽位、用户配额、上游 RPM/并发限制分别记录；所有路由决策、重试和能力拒绝写入审计日志。

## 10. 管理后台

增加 Provider/Profile 管理、模型目录、模型映射、能力开关、价格、健康状态和 fixture 版本视图。Superkey 页面只展示密钥状态和可用模型汇总，不显示分组选择器。变更配置需要版本化、审计和回滚；删除或禁用模型前显示受影响子应用。

## 11. 三个子应用接入约束

### Canvas

继续使用 `/v1/images/generations`、`/v1/images/edits` 和视频创建/轮询/content 三步接口。客户端只发送公开模型名和公共参数；不再为每个供应商写字段分支。视频轮询遇到标准 `failed/cancelled` 直接显示网关错误。

### QRCode

核心图片编辑固定调用 `/v1/images/edits`，使用用户 Superkey 和 Sub2API Base URL。移除对固定默认 key/config 的依赖，错误直接展示网关返回的标准错误。

### PPT

文本继续走 OpenAI-compatible；图片 provider 指向 `/v1/images/generations`。通过 Base URL + Superkey 调用并使用 `/v1/models` 获取可用模型；本方案不声称 PPT 已具备视频入口，后续若增加视频功能再复用统一视频契约。

## 12. 测试矩阵

- 目录：模型去重、映射覆盖、禁用模型、能力不支持错误。
- 路由：Superkey 按图片/视频模型跨组选择；无候选组、配额耗尽、账号故障和 failover。
- 图片：generations/edits、multipart/data URL、OpenAI/Grok 响应归一化、错误和计费幂等。
- 视频：创建、轮询状态映射、content 下载、任务归属、超时、失败/取消、重试不重复扣费。
- Provider fixture：每个真实上游保存成功、参数错误、鉴权失败、限流和结果下载样例；密钥全部脱敏。
- 子应用 E2E：Canvas 图片/视频，QRCode 图片编辑，PPT 文本/图片；桌面和移动端至少各一条主流程。
- 安全：跨用户 task ID、伪造 content URL、日志脱敏、Superkey 不可绑定分组。

## 13. 分阶段实施

### Phase 0：协议取证

收集 QA API Hub、一花 Codex、计算万物的真实 curl、成功/失败/轮询/content 响应，建立版本化 fixture。计算万物重点验证其作为 Sub2API 兼容中转站的公共端点和模型映射，不需要探测 Kling/Seedance 原厂协议。

### Phase 1：能力目录与动态路由

实现 model catalog、Provider/Profile 引用、按模型/operation 的 Superkey 跨组路由，修正 `/v1/models` 聚合和视频任务绑定。

### Phase 2：图片通用适配

统一 OpenAI-compatible 图片、Gemini OpenAI 标注模型、Grok 图片模型的 generations/edits、响应、错误、计费和测试。

### Phase 3：视频框架与 Grok

抽象 VideoAdapter、内部任务表、状态/content 代理；将现有 Grok 视频逻辑接入新接口并完成 Canvas E2E。

### Phase 4：计算万物视频模型

依据通用兼容 fixture 逐模型开启计算万物的能力标签；补齐限流、计费和下载验证。若未来接入原厂 Kling/Seedance，另立项目评估专用协议。

### Phase 5：管理端与三应用验收

上线 Provider/模型管理、Superkey 模型汇总和审计；完成 QRCode、PPT、Canvas 回归后再进行 Docker 构建、迁移和部署验收。

## 14. 风险与待补资料

- 计算万物文档已明确列出视频模型清单；实施时按兼容视频适配器接入。仍需在部署配置中填写其 Base URL、密钥和模型映射，避免与其他 Provider 的同名模型发生路由混淆。
- 同名模型可能在不同 Provider 具有不同能力，必须以 provider mapping 为准。
- 视频结果 URL 的有效期和跨域策略需要上游确认，决定代理还是短期重定向。
- 异步计费规则若不先定，会产生重复扣费或失败任务争议。
- `/v1/models` 聚合结果涉及权限和缓存失效，需在路由改造同时设计。

## 15. 验收标准

1. 使用同一个用户 Superkey，不选择分组即可按模型自动命中正确 Provider/分组；无匹配时返回可诊断错误。
2. 三个图片模型类别均能通过统一图片接口完成成功、失败和计费验证。
3. Grok 视频完成创建、轮询、下载和任务归属闭环；计算万物视频模型按通用兼容 fixture 验证后标记可用。
4. Canvas、QRCode、PPT 不需要供应商专用字段分支即可完成各自已声明流程。
5. `/v1/models`、日志、审计和错误响应不泄漏上游密钥或其他用户任务。
6. 自动化单元、fixture、集成和三应用 E2E 测试通过，Docker 部署后重新执行关键验收。
