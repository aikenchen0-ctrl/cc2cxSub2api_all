## 1. 背景（为什么要改）

部署形态：本实例**没有自有 ChatGPT 号池**。后台「账号」几乎都是指向上游 sub2api 站点的 API Key。

现象：把两张上游渠道禁止调度后，正在用的 Codex 终端重试仍打旧渠道；还有一张可用号，并发不涨。

结论：禁止调度只挡住「以后新选号」，**不会拆已经粘住的 Codex 会话**。用户不能、也不该靠「新开对话」来换号。现有配置、插件、社区二开都解决不了。要网关自己处理。

## 2. 关键事实（下次别再推一遍）

### 调度三层（硬到软）

1. `previous_response_id` → 账号（硬粘，Codex 续聊几乎每次都带）
2. `session_hash`（session-id / conversation_id / prompt_cache_key / 内容种子）
3. 负载均衡

`previous_response_id` 绑的是**更后面那张真实上游号**的服务端状态，不是这张入口 Key。换本地账号 ≈ 换叶账号。

### 加密上下文是什么

- 出现在 Responses / Codex reasoning 第 2 轮及以后：`input` 里的 `reasoning.encrypted_content`，有时还有 compact 的加密块。
- 和 `previous_response_id` 一样，只认产出它的那张叶账号，**解不开、搬不走**。
- **用户可见对话一般不在密文里**。Codex 会把 user/assistant 明文再带一遍。剥密文丢的是内部 thinking 链和 prompt cache，不是聊天记录。

### 池模式（相关但不是这次的改动点）

池模式：出错不把本地入口 Key 标死。选号算法本身不看池模式。  
429/503/529 立刻换本地号，不消耗同账号重试。401/403 才按「同账号重试次数」原地再打。  
重试打的是**同一张本地 Key**，不是上游池里当时那张物理号。

### 官方 / 社区

- PR #2872 sticky_escape：**只逃 session_hash，明确不改 previous_response_id 硬粘**。
- Issue #2991：带着加密上下文换号会 400 解不开。
- Issue #5241：要粘性立刻失效，没落地。
- Linux.do Codex Relay Edition：在**客户端**绕 sub2api 粘死错误号，不是网关方案。
- 没有现成 fork/插件做「停调度后旧会话自动迁号」。

## 3. 实际做了什么

### 产品语义（已实现）

账号变为**手动不可调度**或**临时不可调度**后：

- 下一次选号（含 failover 再进入 `SelectAccount`）立刻离开该账号。
- 禁止对该账号 WaitPlan。
- 「号仍可调度、只是并发满了」的粘性/排队**不变**（BusyKeepsSticky 保留）。
- 进行中的上游 WS **不中途掐断**；Codex 下一发 HTTP / 下一 turn 再选号。

换到另一张号时：

- 普通续聊：丢掉 `previous_response_id` 和带 `encrypted_content` 的 reasoning/compaction item；留下明文消息、summary、已完成工具结果。
- 未完成 `function_call_output`（call_id 盖不全）：**禁止换号**，把错误回给客户端。
- 视频查询等 `ForceStickyAccount`：不因停调度拆粘（媒体状态必须打原号）。

Chat Completions：429/503 立刻换号时清 session 粘性，与 Responses 对齐。

### 代码落点（高内聚）

| 文件 | 职责 |
|---|---|
| `sub2api/backend/internal/service/openai_continuation.go` | 续链政策：能不能换、要不要剥、怎么改 body |
| `sub2api/backend/internal/service/openai_account_scheduler.go` | `stickyAccountNeedsEviction`；session 粘性 / 加权粘性回退跳过不可调度号 |
| `sub2api/backend/internal/handler/openai_gateway_handler.go` | HTTP `/v1/responses` 与 WS 入口：问政策 → `Prepare` → 转发 |
| `sub2api/backend/internal/handler/openai_chat_completions.go` | 立刻换号时 `ClearStickySession` |

核心类型：

- `OpenAIContinuation`：解析一次，记住 previous_response_id、CanMove、有没有加密块。
- `ShouldStrip(hint)`：只看调度结果，不再二次扫 body。
- `OpenAIForwardAttemptState.Prepare`：从不可变 canonical 派生本轮 body；换号、透传边界、同号重试都在这里。
- `SanitizeOpenAISwitchedAccountContinuation`：删 previous_response_id + 整段加密 reasoning/compaction。

## 4. 碰到的问题

1. **停调度 ≠ 拆粘性**  
   `IsSchedulable()` 在粘性命中路径里本来就会 miss，但 Busy 时 WaitPlan 会继续等旧号；加权粘性回退会把旧号再塞回来；请求体里的 `previous_response_id` 和密文换号后还在，新上游 400。

2. **不能「解开密文再换号」**  
   只能剥密文、用明文续。用户体感：不用 `/new`，这一句可能更贵、thinking 重来，对话还在。

3. **工具续链不能静默换号**  
   `function_call_output` 锚在旧 `resp_*`。硬换会出现 `No tool call found`。必须失败给客户端。

4. **同模式换号也要剥密文**  
   旧测试认为 Kiro→Kiro / Bedrock→Bedrock 应保留 reasoning。本实例全是上游 sub，换本地账号就是换叶号，必须剥。已改测试预期。

5. **加权粘性开着时不走 session 硬粘**  
   `StickyWeighted=true` 会跳过 `selectBySessionHash`，改走 `tryFallbackToWeightedSticky`。只改硬粘不够，回退路径也要跳过不可调度号，否则会 WaitPlan 等死号。

6. **session 拆粘后会绑到新号**  
   测试里不要断言 session key 被删光，应断言绑到还开着的号。

7. **本机没有 Go**  
   用 `golang:1.27.0` 容器跑测试。首次拉镜像和下载 module 很慢，要挂 `sub2api-go-mod` 卷。

8. **robocopy 退出码 1 是成功**  
   表示有文件拷过。备份目录空不代表失败，看 `sub2api-bak\sub2api` 在不在。

9. **8080 连不上**  
   当前 Docker 映射是 **18080**，不是文档默认的 8080。`localhost:8080` 拒绝连接是正常的。

10. **进行中的 WS 不重选号**  
    源码注释：「连接内不重选号」。这次刻意不改。停调度后要等 Codex 下一发 HTTP。

2. 把 A（以及其它要停的）禁止调度或临时不可调度。

4. 期望：打到还开着的号；A 并发不再涨；用户能接着聊；这一句可能更贵。
