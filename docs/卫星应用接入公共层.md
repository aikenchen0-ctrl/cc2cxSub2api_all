# 卫星应用接入公共层

给后续 AI / 开发者对接新项目用。**先读完再改代码，不要另发明协议。**

业务分类与部署范围见 **[部署清单.md](部署清单.md)**：卫星应用为 11 个；AgentAPI 是复用本公共协议的代理站，仍受本文鉴权与 Session 约束，但不计入卫星数量；归因探测是 Sub2API 内部模块，随主站部署。

对照表：根目录 `本地链接.txt`。
代码：`sub2api/backend/pkg/satellite/`（环境变量与请求头）。

---

## 1. 目标

用户已登录 Sub2API 后，点左侧菜单进入任意 AI 项目，即可直接使用文本 / 图片 / 视频能力。

- Sub2API 负责登录、计费、跨分组选上游账号。
- 卫星项目独立部署，只负责自己的业务数据和本地会话。
- SuperKey 永远不进浏览器、不进 URL、不能当普通 API Key。
- 本地 / 云端只改 `LINK` 和 `{slug}_link`。

---

## 2. 点击菜单后的链路

```text
用户登录 Sub2API
  → 点左侧项目
  → GET /api/v1/auth/integrations/{slug}/start?next=/
  → 应用专属、2 分钟、一次性 HMAC 票据（身份，不含明文 Key）
  → 卫星 /api/auth/sso/callback?ticket=...
  → 卫星校验 aud/iss/exp/jti，并持久化原子消费票据
  → 卫星建立 3 天本地 Session（生产 Cookie Secure + HttpOnly）
  → 浏览器只带卫星 Session
  → 卫星服务端签发短期用户绑定断言
  → 卫星服务端调 Sub2API /v1：
        Authorization: Bearer <该卫星专属应用凭据>
        X-Sub2API-Satellite: <slug>
        X-Sub2API-User-Assertion: <短期签名断言>
  → 主站验证凭据与 slug 唯一绑定、断言签名/过期/应用
  → 网关内部用该用户 SuperKey，在全部分组里选上游
  → 用量记到该用户，服务端按 slug 配置结算
```

`sk-super-` 出现在 Authorization / x-api-key 里必须 403 `SUPER_KEY_NOT_AN_API_KEY`。

> **当前实现差异**：截至 2026-11-14，主干仍使用共享 SUB2API_APP_CREDENTIAL、共享 SUB2API_SSO_SECRET 和裸 X-Sub2API-On-Behalf-Of。本段是 P0 目标协议，落地见 sub2api/优化任务.md S2A-01/06/07；在 P0 完成前不得对外宣称已完成隔离。

SuperKey 只存在于 Sub2API 服务端：卫星 SSO 不带 Key，控制台 Key 列表不返回 SuperKey 明文，不能当普通 API Key 调用 `/v1`。卫星代调时网关内部取出该用户 SuperKey，并在**全部分组**里选上游（`SuperKeyCrossGroup`）。

> **计费分组边界（2026-11-14）**：跨组选号只决定上游账号，不等于订阅/平台配额的分组口径。卫星 SuperKey 未绑组时，当前中间件不会加载订阅，`QuotaPlatform()` 也可能为空；修复前不得把“已跨组选号”当成“订阅与平台配额已正确计量”。订阅判定口径已冻结为“用户全部有效订阅”：`ListActiveUserSubscriptions(userID)` 返回 0 条走余额，1 条走订阅，2 条及以上在请求前显式拒绝。不得按请求头 `X-Sub2API-Group-ID`、实际调度账号组或订阅 ID 排序任选一条。`RecordUsageInput.Subscription` 必须服从该口径，且 `isSubscriptionBill` 不能继续只由 `apiKey.Group.IsSubscriptionType()` 推导（Anthropic/OpenAI 两条入口均同）；`QuotaPlatform` 是独立的 `(UserID, Platform)` 配额维度，不随订阅组变化。任一项无法唯一确定时 fail closed。

### 2.1 强制条件：Session 身份才允许使用 SuperKey

这是所有卫星项目的共同契约，不能按项目自行放宽：

1. 用户从 Sub2API 左侧菜单进入卫星后，卫星只凭自己的 HttpOnly Session 识别当前用户；SSO ticket 只用于建立该 Session，浏览器不得保存或提交 SuperKey、用户 API Key 或 Sub2API JWT。
2. 卫星服务端每次调用 Sub2API `/v1` 都必须同时发送 该卫星专属应用凭据、`X-Sub2API-Satellite` 和短期用户绑定断言（P0 完成后由 `X-Sub2API-User-Assertion` 承载；裸 `X-Sub2API-On-Behalf-Of` 仅迁移期调试兼容）。这三个值只在服务端请求中出现。
3. 用户断言或应用凭据缺失、Session 无效/过期、凭据与 slug 错配时，必须拒绝请求（401/403/503），**不得**回退到共享 API Key、`.env` 中的 SuperKey、匿名用户或任意默认用户。
4. 普通卫星请求由 Sub2API 验证应用凭据、slug 和用户断言后解析该用户 SuperKey，并通过 `SuperKeyCrossGroup` 从所有启用且可调度的分组选择上游账号；普通 API Key 仍只能使用其绑定分组。AgentAPI 默认 `user_upstream`：模型、余额和 usage 使用当前认证用户映射的主站用户 ID，不使用站长 ID 代付。浏览器使用本站 Session；外部 API 客户端使用 AgentAPI 自有 Key，由服务端校验本站归属后复用上述身份头。注册使用仅部署端持有的主站管理员 API Key 创建普通用户，该密钥不得用于模型调用。AgentAPI 的两种收费模式以 [收费模块](../agentapi/收费模块.md) 为准。
5. 卫星的健康检查、模型列表和文本/图片/视频请求都遵循同一规则。测试夹具可以使用普通测试凭据，但生产配置不得把 `SUB2API_RELAY_API_KEY` 或 `sk-super-*` 作为卫星运行时凭据。

> **计费边界（2026-11-14）**：普通卫星的客户扣费只以主站 `satellite_billing_v1_{slug}` 配置或当前用户余额为权威，只允许覆盖 `ActualCost/BillingMode`，保留 `TotalCost` 用于上游成本统计。客户侧额度必须逐维度区分：`api_keys.quota_used` 与 Key 限流记发起请求的 `APIKey`、金额为 `ActualCost`；账号配额仅对 `APIKey`/`Bedrock` 类型账号按实际 `account_id` 与 `TotalCost * AccountRateMultiplier` 累计（`usage_billing_repo.go:212`），其他账号类型 `account_quota_cost=0` 且不写账号配额，不得要求所有类型都有该额度；`user_platform_quotas` 只在余额模式按资金主体 `(PayerUserID 或 UserID, Platform)` 与 `charged_cost` 累计（自付 `ActualCost`、代付 `PayerCost`），订阅模式不写。不得再用一句“额度都按 ActualCost”混同五类主体。普通卫星不得发送 `X-Sub2API-Payer` 或 `X-Sub2API-Commission-Rate`；主站必须在 S2A-02 中拒绝。AgentAPI 的两种收费模式与费率快照以 [收费模块](../agentapi/收费模块.md) 和 `优化任务-总调度.md` 7.3.1 为准。 付款/抽成头只允许由已验明归属 `agentapi` 的服务端上下文产生；普通卫星携带 `Payer` 或 `Commission-Rate`（包括只带费率、不带 Payer）一律 403，非数字、负数、`>=1`、`NaN`、`±Inf` 不得静默忽略。AgentAPI 本站钱包模式下，主站预检必须按 Payer 检查余额，不能预检 User、后扣 Payer；口径以 `sub2api/优化任务.md` S2A-02 为准。
> **请求身份与扣款身份（2026-11-14）**：卫星服务端调用 `/v1` 时，`X-Sub2API-On-Behalf-Of` 必须是本次请求的终端用户；`X-Sub2API-Payer` 只决定扣款主体，不得替换请求身份。`/v1/sub2api/usage` 当前按 `apiKey.User.ID` 过滤（`gateway_satellite_balance.go:55/68`），因此查询 usage 必须用请求用户身份，不能用 Payer；Payer≠User 时用 Payer 查询返回空列表不等于“usage 尚未可见”。AgentAPI 本站钱包代付必须让流式与非流式使用同一请求身份，否则订阅判定、平台配额与 usage 归属会分裂。
> **usage 查询键（2026-11-14）**：主站把 usage 的 `request_id` 优先写成 `client:<X-Client-Request-ID>`（`gateway_usage_billing.go:206-226`），但 `ClientRequestID` 中间件当前只从 context 读取、缺省生成随机 UUID，并不解析请求头（`middleware/client_request_id.go:19-45`）。卫星若用自己生成的裸 `request_id` 查询，将永远返回空；空列表不得解释为“尚未可见”。卫星计费必须与主站共享同一稳定键：由主站接收并校验 `X-Client-Request-ID`（仅限已验明应用凭据 + slug 的服务端调用），或由主站提供按 `X-Request-ID`/上游任务 ID 的反查接口。

验收时用 `GET /v1/sub2api/usage?request_id=<id>` 核对 `actual_cost`、保留的 `total_cost`、`rate_multiplier`、`billing_mode`，以及 `payer_user_id`/`charged_cost`/`billing_subject` 与 typed 五类额度（`api_key_id`、`account_id`、`subscription_id`、`platform_quota_subject_user_id + platform` 及各自 `*_cost`）；精确金额必须用 `*_usd_nanos` 或定点十进制，不得用 JSON 浮点或先四舍五入到分。具体断言见 `优化任务-总调度.md` 7.3.2。该接口按认证用户过滤，不能用于读取他人账单。 **当前实现缺口**：接口暂不返回 `api_key_id`/`group_id`，同用户多把 Key 同 `request_id` 只能靠行 `id` 区分；S2A-08 落地后必须返回 `api_key_id` 并支持按 Key 过滤，验收不得把当前缺口写成接口契约；固定 `PageSize=20`，大量 Key 可能截断。视频/图片规则的单位尝试顺序是 `video` → `image` → `token` → `request`；有视频数量/时长但无 `video` 规则时必须失败关闭，不能落到 `token` 或 `request`。

### 2.2 Session 生命周期统一约束（AI 必须遵守）

> **AI 执行提醒（不可违反）**：本仓库卫星项目的本地登录 Session/JWT 统一保持 **3 天**。新增功能、修复登录、重构 SSO 或新增卫星时，必须继续使用 3 天，禁止重新引入 7 天、30 天或其他项目自定义的 Session 默认值。

- 3 天 = `3 * 24 * 60 * 60` 秒；必须同时覆盖服务端 Session/JWT 的过期时间、浏览器 HttpOnly Cookie 的 `Max-Age`/`maxAge`，以及续签时长。
- SSO 一次性 ticket 的短时有效期（默认约 2 分钟）是票据安全期限，不是登录 Session 时长，不要把两者混为一谈。
- 本次规则只约束新签发和续签的会话；已有旧会话不强制注销或人为缩短，按其原有过期时间自然结束。
- 修改任一卫星的认证代码后，必须检查该项目的 JWT `exp`、Session TTL、Cookie TTL 是否仍为 3 天，并同步示例配置、Compose 默认值和接入文档。

可供 AI/自动化检查使用的固定事实：

```yaml
satellite_session_ttl_days: 3
satellite_session_ttl_seconds: 259200
satellite_session_scope:
  - aicut
  - aiexcel
  - canvas
  - ju
  - livart
  - ppt
  - qrcode
  - screen2code
  - yibiao
  - ai3d
  - aihuoke
  - agentapi
old_sessions: keep_until_original_expiry
sso_ticket_ttl_is_session_ttl: false
```

### 2.3 卫星余额读取与充值提示

余额也必须由卫星服务端代查，不能从浏览器直接调用 Sub2API 或传递用户 Key：

1. 卫星从当前 HttpOnly Session 取得 Sub2API 用户 ID，以该卫星专属应用凭据、`X-Sub2API-Satellite` 和短期用户绑定断言调用 `GET {SUB2API_RELAY_BASE_URL 或 LINK}/v1/sub2api/balance`。
2. 成功响应为 `{"object":"sub2api.user_balance","balance":0}`；余额端点响应必须带 `Cache-Control: no-store`。Session/身份无效返回 401，卫星凭据或 relay 未配置返回 503。
3. 卫星只向自己的同源 UI 路由返回余额和公开充值地址。`recharge_url` 只能由公开 `LINK` 生成（`LINK` + `/purchase`）；未配置公开 `LINK` 时返回空地址并禁用充值按钮，不能把 Docker 内部 `SUB2API_RELAY_BASE_URL` 暴露给浏览器。
4. 余额 `<= 0` 时由卫星 UI 标红并提示充值；浏览器只携带卫星自己的 HttpOnly Session，不保存或发送上述服务端凭据及 Sub2API 身份头。

## 3. 硬性规则

1. 卫星必须有服务端。纯静态站不能进菜单。
2. 单体必须先改成多用户：本地用户表用 `(identity_provider=sub2api, subject=<Sub2API user id>)`，资源带 `owner_user_id`。
3. 浏览器不出现 SuperKey、Sub2API JWT、模型 API Key。
4. 没有当前用户身份时卫星调模型返回 401，禁止回退到共享 `.env` Key。
5. Sub2API 管理员进卫星仍是普通用户。
6. 不要把卫星合并进 `sub2api/` 进程。
7. 不要为新项目再复制一套 SSO Handler 协议；沿用现有 HMAC 票据 + 公共头。
8. 计费重放必须复用稳定 `request_id`：同一 `(request_id, api_key_id)` 只有首次权威 usage，重放不得用本次快照覆盖金额、模型、订阅或付款人，也不得二次扣款。付款人/费率/订阅归属与请求开始时快照不一致时，必须显式报错或按主站既有结果处理，不得自行改扣。
9. 异步上游任务必须使用稳定任务 ID 派生 `request_id`：创建、多次轮询、完成回调只能结算一次；禁止每次轮询生成新键。任务 ID 必须在返回 `202`/任务句柄前持久化，或由调用方提供已验明的稳定业务键；仅存在内存/Redis 或无计费键的随机任务 ID 不足以证明可恢复，响应丢失后重提不得再次上游建单。无异步上游任务的项目须在验收中显式声明并给出路由证据。
10. 卫星请求的订阅判定必须在服务端请求开始时冻结：预检与后扣复用同一“用户全部有效订阅”快照（唯一订阅 ID、组、窗口与账本分支），不得在两次阶段各自重查；预检后新增/失效订阅不得改变本次扣费账本。
11. 卫星调用主站时的订阅事实必须用显式账本分支表达“未解析/确认无订阅/唯一订阅”，不得把 `Subscription=nil` 同时当作三者；未解析必须拒绝，不能默认余额。
12. usage 返回 `total_cost` 为 0 且本次确实调用模型时，卫星不得把它当正常成本写入统计、差额或对账；必须显式标记未归类并告警。主站模型成本缺失时也可能出现该值，不能用 `actual_cost` 非零反推成本完整。

## 4. 环境变量（必须保留）

来源：`本地链接.txt`。

### 模型地址 `LINK`

所有卫星调大模型都走 Sub2API：

```env
# 本地
LINK=localhost:18080

# 云端
LINK=https://api.cc2.cx
```

无协议的本地值补 `http://`。Docker 容器互访可用 `SUB2API_RELAY_BASE_URL=http://sub2api:8080/v1`，未设则回退 `LINK`。

### 菜单 / SSO 地址 `{slug}_link`

```env
# 本地
aicut_link=http://localhost:5199
aiexcel_link=http://localhost:4173
canvas_link=http://localhost:3522
ju_link=http://localhost:3000
livart_link=http://localhost:8080
ppt_link=http://localhost:8341
qrcode_link=http://localhost:5221
screen2code_link=http://localhost:5173
yibiao_link=http://localhost:8081
ai3d_link=http://localhost:5174
aihuoke_link=http://localhost:3001

# 云端
aicut_link=https://aicut.cc2.cx
# 其余同理：https://{slug}.cc2.cx
```

SSO 回调默认 = `{slug}_link` + `/api/auth/sso/callback`（PPT 为 `/api/v1/auth/sso/callback`）。
只有路径特殊时才设 `{SLUG}_SSO_CALLBACK_URL`。

两端还要相同：

```env
SUB2API_SSO_SECRET=<至少 32 字节>
SUB2API_APP_CREDENTIAL=<卫星调用 /v1 的项目凭证，不是用户 Key>
```

卫星自己的 Session 密钥与 SSO 密钥分开。

## 5. 新项目清单（按顺序做完再挂菜单）

1. **多用户**：本地用户、Session、数据按 `owner_user_id` 隔离。
2. **SSO 接收**：`GET /api/auth/sso/callback`，校验 HMAC 票据 `iss=sub2api`、`aud`（见 `apps.go` 的 Audience，不一定等于 slug）、一次性 `jti`，映射 `sub` 到本地用户，发 HttpOnly Session。
3. **模型调用**：服务端用第 2 节三个头打 `{LINK}/v1/...`，模型只发公开名。
4. **Sub2API**：在 `pkg/satellite/apps.go` 加一行（slug、audience、默认 origin、回调路径）；左侧菜单加一项指向 `/auth/integrations/{slug}/start`。不要新写 `*_sso.go`。
5. **环境**：`{slug}_link`、`LINK`、`SUB2API_SSO_SECRET`、`SUB2API_APP_CREDENTIAL`。Docker 加入 `deploy_sub2api-network`。
6. **验收**：两个 Sub2API 用户数据隔离；用量分别记账；URL 无 Key；用 SuperKey 当普通 Bearer 调 `/v1` 失败。计费验收必须区分首次写入与重放命中：同一 `request_id` 重放只返回首次权威 usage，不追加、不二次扣款，也不得让重放请求的报价/模型/付款人覆盖既有记录。

## 6. SSO 票据

```text
base64url(JSON) . base64url(HMAC-SHA256(payload, SUB2API_SSO_SECRET))
```

必填：`iss=sub2api`，`aud`（注册表 Audience：如 aicut=`openchatcut`、ppt=`presenton`，其余一般等于 slug），`sub`（Sub2API 用户 ID），`jti`，`iat`，`exp`（默认约 2 分钟），安全的站内 `next`。

票据只带身份，不带 SuperKey。新项目不要读 `rk`，用 `sub` 作为 `X-Sub2API-On-Behalf-Of`。

参考：`sub2api/backend/pkg/satellite/apps.go`、`internal/handler/satellite_sso.go`；卫星回调可看 `aiexcel/app/auth-sso.ts`。
