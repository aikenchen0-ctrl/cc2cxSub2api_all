# Sub2API 账号调度方案（大白话版）

本文说明当前版本的账号调度和“遇到错误后切换账号”规则，并与原版本 `C:\Downloads\sub2api-0.2.5` 做对比。

这里的“账号”指系统配置的上游账号。一次请求通常只会实际使用一个账号；只有这个账号被判定为不适合继续服务时，才会换下一个账号。

## 一句话总结

当前方案可以概括为：

> 先从“能用的账号”里挑一个最合适的；请求失败后，先判断是不是账号问题；如果是，就把当前账号记为失败并换号；如果只是短暂抖动，则按规则在原账号重试几次；达到上限后返回错误。

## 一、请求进来后，系统怎样选账号

### 1. 先确定账号池

系统先看以下信息：

- 用户使用的 API Key 属于哪个分组。
- 本次请求要访问哪个平台、哪个模型。
- 请求需要什么能力，例如普通文本、Responses、图片、流式传输等。
- 是否有会话标识（`session_hash`）或上一次响应标识（`previous_response_id`）。

组合分组还会先决定本次请求真正落到哪个目标平台。

### 2. 把明显不能用的账号剔除

以下账号不会进入正常候选池：

- 管理员关闭了账号，或账号已停用、过期。
- 账号正处于限流、过载或临时冷却期。
- 账号配额用尽，或 RPM、会话数、并发槽位已经不允许接新请求。
- 账号不支持本次模型、接口类型、传输方式或图片能力。
- 分组要求隐私设置，但账号还没有完成相应设置。
- 账号不满足分组的计费倍率、利润门槛或其他渠道限制。
- 本次请求已经尝试失败过的账号（失败账号会放进本次请求的排除名单）。

OpenAI/Grok 账号有一个特殊的“错误通道”例外：账号状态显示为 error，但只要账号仍开启调度、没有过期或过载，仍可能进入换号池，用来承接 429/503 等失败后的重试。这个例外不等于账号完全健康，后续仍会再次做实时检查。

### 3. 有会话时尽量保持同一个账号

系统会优先考虑会话粘性：

1. OpenAI Responses 请求带有 `previous_response_id` 时，优先找产生这条响应的账号，避免上下文断裂。
2. 有 `session_hash` 时，优先找这个会话之前绑定的账号。
3. 某些“守护/父账号”场景会强制跟随指定账号。

粘性不是无条件锁死。账号不再支持该模型、进入冷却、配额不足、健康度太差、并发太满或被本次请求排除时，系统会放弃粘性，改选其他账号。

OpenAI 高级调度默认允许粘性逃逸：

- 最近错误率超过约 50%，会暂时跳过这个粘性账号。
- 首 Token 延迟（TTFT）超过约 15 秒，会暂时跳过这个粘性账号。
- 粘性账号并发已满时，当前版本优先转到其他账号，不把长任务一直堵在原账号上。

### 4. 没有合适的粘性账号时，按负载和评分选

普通调度大致按下面的优先级工作：

1. 如果分组配置了模型路由白名单，先在指定的主备账号中选。
2. 在可用账号中优先选择账号优先级较高者（数值越小越优先）。
3. 比较当前负载和等待队列，尽量选更空闲的账号。
4. 条件相同再优先选择更久没有使用的账号，避免总是打同一个账号。
5. 如果开启“尽快用完即将重置的窗口”，会偏向更快重置的账号。

OpenAI 高级调度会把这些因素合成分数：账号优先级、当前负载、等待人数、近期错误率、TTFT；还可以按配置加入配额余量、窗口重置时间、上游成本倍率等因素。默认只从得分靠前的 Top-K 账号里选，Top-K 默认是 7，再按分数加权随机，避免第一名长期成为热点。

如果开启了“订阅账号优先”，会先尝试符合条件的订阅账号池，拿不到可用槽位后再尝试普通账号池。

### 5. 选中后还要抢并发槽

选中账号不代表马上能转发。系统还要抢一个并发槽，并检查会话数量限制：

- 抢到槽位：立即向上游发送请求。
- 账号暂时忙，但允许排队：生成等待计划，等待槽位释放。普通兜底等待默认最长 30 秒，等待队列默认最多 100 个请求。
- 等待队列已满或超过等待时间：本次请求失败，不会无限等待。

## 二、请求成功后怎样处理

请求成功后，系统会：

- 释放本次占用的并发槽。
- 更新账号的成功次数、错误率、TTFT 等运行数据。
- 更新会话粘性和相关缓存的有效期。
- 记录用量和计费信息。

这些运行数据会影响后续请求的评分，所以调度不是固定轮询，而是会随着账号表现变化。

## 三、遇到错误后，当前版本怎样处理

### 1. 先判断“能不能安全重放”

只有在没有产生无法撤回的有效输出时，系统才会自动重试或换号。流式响应已经把有意义的内容发给客户端后，通常不会再换账号拼接，避免客户端收到重复或前后矛盾的内容。

网络连接失败、上游还没返回有效内容、空响应、首 Token 超时等情况，在确认可以安全重放时，才会进入下面的失败处理流程。

### 2. 哪些错误通常会触发换号

当前默认把这些情况视为账号或上游可用性问题：

| 错误情况 | 当前处理 |
| --- | --- |
| 401 认证失败 | 记录账号失败，按规则重试或换号 |
| 402 余额/计费问题 | 记录账号失败并换号 |
| 403 权限、订阅或账号不可用 | 记录账号失败，按规则重试或换号 |
| 405 接口能力不匹配 | 换号 |
| 429 限流 | 优先立即换号 |
| 529 或类似上游过载 | 优先立即换号 |
| 500、502、503、504 等 5xx | 通常换号；某些明确的临时错误会先同号重试 |
| 空响应、流提前结束、首 Token 超时 | 在可以安全重放时换号 |

如果在选号阶段发现整个分组没有任何账号支持该模型，系统会返回“模型不存在/不支持”。至于已经选中的账号在上游返回“模型不存在”的 400，当前版本不会在所有路径上统一触发换号（原版对此做了更明确的账号级识别，见后文对比）。

### 3. 哪些错误不会换号

如果问题明显来自请求本身，换其他账号也不会变好，系统会直接把错误返回给用户，例如：

- 请求参数格式错误。
- 模型上下文超出限制。
- 内容审核或安全策略拒绝。
- 客户端明确要求了上游不支持的功能。
- 已经开始输出有效流内容，无法安全重放的错误。

这类错误不会把账号标记成“坏账号”，也不会因为换号把同一个错误重复放大。

### 4. 同一个账号会不会先重试

当前存在“同账号重试”和“直接换号”两条路径。

#### 直接换号

对 429、503、529，当前版本优先直接换号。这样可以避免请求一直排在一个已经限流或过载的账号上。

换号前会做几件事：

1. 把当前账号加入本次请求的失败名单。
2. 对需要的错误写入临时冷却，避免下一次请求马上又选回它。
3. 对有会话粘性的请求清掉这次会话与该账号的绑定，避免粘性把请求拉回刚失败的账号。
4. 重新建立候选池，选择下一个账号。

#### 同账号重试

只有错误被明确标记为“临时重试可能成功”时，才会在原账号上再试。常见于：

- 池模式账号配置允许的 401/403 等状态。
- 某些短暂的上游处理失败。
- 某些平台的空响应、容量抖动或流空闲错误。

同账号重试次数由账号的 `pool_mode_retry_count` 控制，默认 1 次，最多限制为 10 次；错误本身还可以设置更小的上限或截止时间。默认间隔约 500 毫秒，带有请求级瞬时错误标记时会逐步退避，单次间隔最多约 8 秒。

注意：虽然池模式默认可配置 429，但当前全局策略对 429 优先换号，因此 429 通常不会消耗同账号重试次数。

同账号重试用尽后，系统才会把账号加入失败名单并换号。

### 5. 换号次数上限

换号次数是“本次请求内”的限制，不是账号永久限制。默认值如下：

| 请求路径 | 默认最多换号次数 |
| --- | ---: |
| 普通网关路径 | 10 |
| Gemini/Antigravity 路径 | 3 |
| OpenAI 兼容路径（Responses、Messages、Chat Completions、图片等） | 3 |

可通过网关配置覆盖。达到上限后，系统停止尝试，返回最后一次失败对应的错误；如果候选账号本来就用完，也会直接返回“没有可用账号”。

### 6. 只有一个账号时

如果分组里实际上只有一个账号，系统没有真正的备用账号可切换。部分 503/容量耗尽场景会先做短暂退避，再重新尝试这个账号；仍然失败就返回错误，不会无限循环。

### 7. 请求被客户端取消时

客户端已经断开或取消请求后，系统会停止后续换号，避免为一个没人接收的请求继续消耗上游额度。已发生的用量仍会按可确认的数据记录。

## 四、三个直观例子

### 例 1：A 账号返回 429

1. 请求先选中 A。
2. A 告知“太多请求/限流”。
3. 当前版本不在 A 上等待多次，直接把 A 放入本次失败名单，并清理会话粘性。
4. 从剩余候选中按模型、健康度、负载和优先级选择 B。
5. B 成功则用户无感；所有候选都失败才返回错误。

### 例 2：池模式 A 账号出现短暂 401

1. 错误被账号配置标记为可同号重试。
2. 系统等待约 500 毫秒，在 A 上再试一次（具体次数受账号配置限制）。
3. 重试成功就继续使用 A，不计为换号。
4. 重试仍失败后，A 才进入失败名单并切换到 B。

### 例 3：请求参数本身错误

1. A 返回明确的参数/上下文错误。
2. 系统判断换账号也不会解决。
3. 不重试、不换号，直接把对应错误返回给客户端。

## 五、当前版本与原版 0.2.5 的主要差异

以下是会影响实际调度行为的差异，不是所有代码差异的罗列。

| 对比项 | 当前版本 | 原版 0.2.5 |
| --- | --- | --- |
| 429/503/529 的处理 | 优先立即换号，避免长时间卡在拥堵账号；OpenAI/通用网关会清理会话粘性 | 没有统一的“立即换号”规则；只要错误标记为可重试，可能先在同账号重试 |
| 粘性账号并发已满 | OpenAI 高级调度优先逃逸到负载均衡；普通网关也更快转入其他候选或兜底等待 | OpenAI 调度更倾向给粘性账号生成等待计划；普通网关对粘性账号也更倾向等待（未超等待队列上限时） |
| OpenAI/Grok 的 error 状态账号 | 仍开启调度且满足安全条件时，可作为错误通道候选参与换号 | 主要按 `IsSchedulable` 判断，error 状态账号通常不会进入候选 |
| 分组模型路由 | 通用调度层主要使用 Anthropic 模型路由；OpenAI 主要依靠自己的高级调度和账号级模型映射 | 通用调度层额外支持把 OpenAI 分组模型路由到指定账号列表 |
| OpenAI 兼容接口的“模型不存在”400 | 当前版本不把所有此类 400 统一当成换号信号，需结合具体路径和账号错误规则 | 原版增加了对 OpenAI 兼容账号“模型不存在/不支持”的 400 识别，可直接触发账号 failover |
| 评分中的窗口/配额数据 | 主要使用当前会话窗口和已有字段；相关权重默认关闭 | 原版进一步使用 Codex 5 小时窗口及规范化的 5 小时/7 天配额快照，开启相关权重时排序可能不同 |

## 六、怎样理解这套方案的取舍

- 当前版本更看重“尽快离开明显拥堵的账号”，所以 429/503/529 通常直接换号。
- 同账号重试仍然保留，用来处理很短暂、换号也未必有帮助的抖动，但次数受到严格限制。
- 会话粘性用于保持上下文连续，不是为了牺牲可用性；账号变差时会主动逃逸。
- 账号评分只在“已经合格的候选账号”之间起作用，不能绕过模型能力、配额、权限、冷却和分组限制。
- 换号只对当前请求生效；账号是否在后续请求中恢复，由冷却时间、健康检查和新的运行数据决定。

因此，最简化的理解就是：

> 能用时尽量稳定地用同一个账号；发现限流或过载就快速换号；发现只是短暂抖动就小范围重试；发现是用户请求错误就不折腾账号。
