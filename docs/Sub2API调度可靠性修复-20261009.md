# Sub2API 调度可靠性修复

日期：2026-10-09，香港时间。

## 目标与成立条件

<重表述提示词为问题>客户使用不可控的 Codex、OpenCode 或其他兼容客户端时，如何在本地 Sub2API 内隔离上游故障，在同组存在合格备用且尚未提交不可重放输出时自动换号，让客户保持当前请求和会话，同时不重复工具执行、不丢历史、不用重试洪峰拖慢其他用户？</重表述提示词为问题>

输出前透明恢复 = 可重试故障 AND 同组合格备用 AND 可重放上下文 AND 客户连接仍有效 AND 剩余容量及时间预算足够。

无法承诺的情形 = 全部上游失败 OR 正文/工具动作已交付 OR 上游独占会话状态不可获得 OR 客户端自行断开。

## HMM 建模与取舍

- S0：网关已有切换逻辑，但存在同号重复尝试、粘性账号满载优先排队、前导事件提前提交、错误正文误判成功及会话重建丢信息。
- IFR：客户只使用稳定的本地接口，不感知可恢复的供应故障。
- Sg：输出前同请求透明换号；完整已观察历史支持会话继续；输出后不伪造成功或拼接第二次工具调用。
- 基底约束：客户端已消费的数据和外部工具副作用不可撤销；不同密钥不代表独立故障域；有限容量不能保障无限并发。
- TC：过早发送首包降低延迟，却丢掉早期故障切换机会；增加重试可能提高单请求成功率，却放大共享容量压力。
- PC：同一前导事件既希望立刻可见又希望失败时能撤回。
- 操作子：按语义分离前导与正文；前导有界暂存，正文开始即释放；失败账号在当前请求排除；限流状态先内存生效、后台合并持久化。
- 代偿：每个待首语义请求至多64KiB协议前导，后台2个冷却写入工作协程和64个排队任务；满队列放弃持久化而保留内存保护。

## 实际修改

1. `credentials.fast_failover=true` 的 OpenAI API Key 对可恢复的认证、路径、408、429及5xx等故障直接交同组调度，跳过原池模式的同号重复尝试。未知父响应、客户端参数错误不能简单归为账号故障。
2. 旧调度器的满载粘性账号先尝试同组可用槽位，保留模型、能力、利润、限流与分组资格检查。全部满载才恢复原等待计划；普通账号和OAuth原策略不变。
3. HTTP/SSE兼容适配及原生WebSocket暂存前导，不让故障响应ID和空角色首包提前关闭重试窗口。已输出正文或工具结构后不重放。
4. HTTP 200内嵌错误、畸形JSON、非流式仅usage、错误finish_reason不再误报成功；缺失正常终态不再合成完成。
5. 快速切换账号未配置全局期限时，普通推理首语义预算60秒，高/xhigh/max为120秒；涵盖等待响应头与空前导。开始有效输出后解除该预算。静默故障必须先被检测，不能承诺零时间发现。
6. 429模型冷却立即写入内存，按账号+模型合并后台落库。首个领取者也不等数据库；较晚短期限和旧在途成功不得清除长冷却。
7. 不静默删除未知previous_response_id、远端引用或compaction。完整已观察WS链保留用户、助手、工具调用及结果；第二轮故障重放当前轮，防止重放首轮任务。

## 上线策略与边界

候选使用独立28080端口及独立数据目录，沿用生产数据库和Redis；新数据库池32、旧池256，合计288，数据库上限300、保留槽3。上线时保留旧容器，Nginx平滑切换新请求，旧连接继续排空。审计候选18489单独转发新网关，保留既有留存策略。

首批开启账号60、748、744、745的fast_failover。账号60同时属于17/36组，744同时属于28/32/53组，因此账号级策略也影响其其他组请求；调度仍严格在客户所在组内选择。

重点组53的两个密钥共用 `api.dmxcode.cc`，不能消除供应商整体故障。现有并发额度各19；组36各10。没有擅自把额度改成几百，也没有用500模拟并发宣称供应容量足够。

回退保留旧镜像、容器及入口文件；入口同步器在新网关失去健康时允许新请求回旧端口。它不能挽救已经断开的在途连接，且存在健康检查间隔。
