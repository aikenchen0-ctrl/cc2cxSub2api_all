## 二、项目组成与访问地址

| 项目 | 作用 | 本地地址 |
| --- | --- | --- |
| sub2api | 用户、登录、分组、应用 Key、额度、用量日志及模型请求中转 | http://localhost:18080 |
| screen2code 前端 | 截图/图片输入和代码生成交互 | http://localhost:5173 |
| screen2code 后端 | SSO 会话校验、生成接口及 WebSocket 服务 | http://localhost:7001 |
| PostgreSQL | sub2api 业务数据库 | Docker 内部服务 |
| Redis | 会话、缓存或队列依赖 | Docker 内部服务 |

容器应至少包括 sub2api-dev、PostgreSQL、Redis、screen2code frontend 和 screen2code backend。

健康检查：
- GET http://localhost:18080/health 应返回 HTTP 200。
- 浏览器访问 http://localhost:5173 应能加载页面。
- http://localhost:7001 应能建立后端连接。

## 三、关键配置

### 1. screen2code/.env

```env
BACKEND_PORT=7001
SUB2API_SSO_SECRET=<必须与 sub2api 完全一致的共享密钥>
SCREEN2CODE_AUTH_REQUIRED=true
SUB2API_RELAY_BASE_URL=http://host.docker.internal:18080/v1
SCREEN2CODE_ALLOWED_ORIGINS=http://localhost:5173,http://127.0.0.1:5173
```

不要把真实 SUB2API_SSO_SECRET 写入文档、日志或提交记录。两边密钥必须逐字符一致，修改后需要重启相关服务。

### 2. 前端代理配置

文件 screen2code/frontend/.env.local：

```env
PROXY_CODEGEN_BACKEND=http://backend:7001
```

文件 screen2code/frontend/vite.config.ts 使用 loadEnv(mode, process.cwd(), "")，从而读取不带 VITE_ 前缀的变量。Docker 容器内不能使用 127.0.0.1:7001，应使用服务名 backend:7001。

### 3. sub2api 镜像配置

文件 sub2api/deploy/docker-compose.override.yml 使用当前构建镜像 deploy-sub2api，避免旧的 sub2api:ppt-integration 覆盖最新代码。

## 四、SSO 登录详细流程

1. 用户先登录 sub2api（http://localhost:18080）。
2. sub2api 页面展示左侧菜单“AI识屏转代码”，菜单指向 http://localhost:5173/，通常在新页面打开。
3. sub2api 生成携带用户身份的 SSO 跳转信息。共享密钥只用于两端签名/校验，不暴露给浏览器。
4. screen2code 前端加载后调用自身后端的 /api/auth/me。
5. screen2code 后端使用 SUB2API_SSO_SECRET 校验签名、有效期和用户标识。
6. 校验成功返回 authenticated: true；未登录、签名错误或过期时返回未认证状态。
7. screen2code 后端根据 sub2api 用户身份查找或创建对应的 Screen2Code Application Key，并将 Key 与 user_id、group_id 绑定。
8. 后续生成请求只使用当前用户对应的 Key，不能复用其他用户的 Key。

涉及代码：
- sub2api/backend/internal/handler/screen2code_sso.go
- sub2api/backend/internal/service/api_key_service.go
- screen2code/backend/auth.py
- screen2code/backend/routes/auth.py

## 五、代码生成请求中转流程

1. 用户在 screen2code 页面提交截图、设计图或生成参数。
2. 前端通过 WebSocket/HTTP 将请求发送到 screen2code backend。
3. screen2code/backend/routes/generate_code.py 校验当前登录用户并取得该用户的 Application Key。
4. screen2code backend 按 SUB2API_RELAY_BASE_URL 组装 sub2api 请求，目标为 http://host.docker.internal:18080/v1/responses。
5. 请求携带当前用户对应的 Key 和模型/输入内容，进入 sub2api 的鉴权、分组、额度和模型路由流程。
6. sub2api 校验 Key 是否有效、Key 所属用户和分组是否匹配、账户是否有余额或配额。
7. 校验通过后转发到实际模型供应商，结果按原连接返回 screen2code。
8. 余额不足时返回 INSUFFICIENT_BALANCE，screen2code 将其展示为可识别的生成失败状态。
9. 成功或失败请求按 sub2api 的计费和用量规则记录，避免 screen2code 自行维护不一致的余额数据。

## 六、用户隔离、额度与用量

- 用户身份来源于 sub2api SSO，不以浏览器传入的任意用户名作为可信身份。
- 每位用户使用独立的 Screen2Code Application Key。
- Application Key 绑定 user_id 和 group_id，分组策略由 sub2api 统一管理。
- 请求鉴权同时校验 Key、用户和分组，防止用户之间串用 Key。
- usage 维度使用 user_id + api_key_id，便于按用户、Key 和时间追踪调用量。
- 额度、余额、模型权限和计费结果以 sub2api 为准。
- 删除或禁用用户时，应同步禁用其 Application Key，避免遗留凭证继续调用。

## 八、数据库迁移注意事项

1. 已执行过的迁移文件不要直接改写，否则不同环境的迁移记录与实际结构会不一致。
2. SSO 约束修复使用新增迁移 241_repair_sso_secret_constraints_v2.sql。
3. 发布前确认迁移按编号顺序执行，并检查 PostgreSQL 中的迁移记录。
4. 涉及约束、唯一索引或密钥字段时，先确认已有数据不会违反新约束。
5. 生产环境执行迁移前应备份数据库，并保留回滚方案。

## 十、常见问题排查

### 页面能打开但显示未登录

检查 sub2api 是否已登录、SSO 共享密钥是否一致、浏览器是否携带正确跳转信息，以及 screen2code backend 的 /api/auth/me 响应和日志。

### 前端请求出现 502 或连接 backend 失败

检查 screen2code/frontend/.env.local 是否为 PROXY_CODEGEN_BACKEND=http://backend:7001，并确认 frontend 与 backend 位于同一 Docker 网络。

### 请求没有到达 sub2api

检查 SUB2API_RELAY_BASE_URL、Docker 到宿主机的 host.docker.internal 解析、sub2api 的 /v1/responses 日志，以及请求是否携带当前用户 Application Key。

### 返回 INSUFFICIENT_BALANCE

先确认 sub2api 账户余额、分组额度和模型权限。这通常表示中转链路已打通，不是 screen2code 前端代理故障。

### 修改代码后页面仍是旧版本

确认已重新构建对应镜像并重启容器，检查 compose override 是否仍引用旧镜像标签，同时执行浏览器强制刷新。

## 十一、对接完成标准

1. sub2api 登录后能从菜单打开 screen2code。
2. screen2code /api/auth/me 能识别当前用户。
3. 用户只能使用自己绑定的 Application Key。
4. 生成请求能到达 sub2api /v1/responses 并返回成功或明确业务错误。
5. 余额、配额和 usage_logs 均由 sub2api 正确处理。
6. 服务重启、数据库迁移和常见故障均有可执行的排查路径。
