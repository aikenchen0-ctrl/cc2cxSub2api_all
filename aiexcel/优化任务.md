# AIExcel 优化任务

> 项目：`aiexcel/`（卫星应用）。基线：2026-11-14。
> 全局约束见根目录 `评估报告.md`、`优化任务-总调度.md`；本文件只负责 `aiexcel/` 内落地。

## 1. 项目定位与边界

- 卫星应用，浏览器内解析表格，AI 只生成操作计划；服务端代调主站模型。
- 通过 Sub2API SSO 建立 3 天 HttpOnly Session；浏览器不得接触 SuperKey、应用凭据或 SSO 密钥。
- 本项目只改 `aiexcel/`，不改主站协议、根 Compose 或其他卫星。

## 2. 结论与商用判定

入口和核心流程可用，但**跨平台测试未完成、SSO 重放状态不持久、仓库无 LICENSE**。当前不适合公开商用；须先完成 P0 身份/计费收紧和发布门禁。

## 5. 缺陷清单与补强方案

### AIE-01 Windows 测试脚本失败（P1）

**现象与证据**
- 历史结论称 Windows 下测试脚本失败；本轮未重新执行，不能当作现状。
- 项目含 Node 测试与构建脚本，跨平台路径/命令需要复测。

**实施步骤**
1. 在 Windows PowerShell 与 Linux 容器环境分别执行同一套测试，记录 Node/pnpm 版本。
2. 对路径分隔符、环境变量、脚本 shell 差异做最小修复；不要重写测试框架。
3. 固定锁文件，用 `pnpm install --frozen-lockfile` 验证可复现。
4. 将失败项拆成独立任务卡，不要用跳过测试的方式变绿。

**验收**
```powershell
cd aiexcel
pnpm install --frozen-lockfile
pnpm run test
pnpm run build
```
- Windows/Linux 结果一致；失败项有独立证据。

### AIE-02 SSO 与 AI 代调（P0/P1）

**现象与证据**
- `app/auth-sso.ts:5` 的 `replayed` 为进程内 `Map`；重启后防重放失效。
- Compose 的 `SUB2API_APP_CREDENTIAL`、`SUB2API_SSO_SECRET` 均为 `:-}` 可空，这是当前缺陷。
- 当前调用使用裸 `X-Sub2API-On-Behalf-Of`；主站 S2A-07 后改为短期用户断言。

**实施步骤**
1. 校验 SSO `iss/aud/sub/iat/exp/jti`，TTL ≤ 2 分钟，`aud=aiexcel` 精确匹配。
2. 将票据消费改为持久化原子表（SQLite/Redis），唯一键消费；补并发、重启、多副本测试。
3. 验证 3 天 Session、生产 Cookie `Secure + HttpOnly`、注销可撤销。
4. 服务端调用主站只使用本应用凭据、slug 和主站规定的用户断言；缺失一律 401/503。
5. 主站 S2A-01/06/07 完成后改用专属凭据/派生密钥，测试跨 slug 被拒。
6. 浏览器存储、构建产物、日志不得出现 SuperKey、应用凭据、SSO 密钥。
7. 两个 Compose 变量改为 `:?` 强制，并补服务健康检查；空 Secret 或无健康状态不得启动成功。
8. 计费只走主站 `aiexcel` slug 配置或当前用户余额；不得发送或接受 `X-Sub2API-Payer`、`X-Sub2API-Commission-Rate`。
9. **按 S2A-08 实现受理与别名契约**：调用上游前先提交 `accepted`；本地拒绝先提交 `rejected_before_upstream` 与真实 `funds_effect/quota_effect`，只有双零且 `dispatch_state=not_started` 才可标记可重发；同一请求只建一条 admission（先以临时键建行，最终键只一次 CAS 写入 `final_request_id`；dispatch 前拒绝可保持空，不得伪造），临时键经 `request_admission_alias` 单跳、双向唯一并外键归属该 admission；改绑、二次归属或引用未升级最终键均冲突。usage/反查必须返回完整 `admission_source/funds_effect/quota_effect/dispatch_state/state_version/query_request_id/final_request_id`，`query_request_id` 逐字等于查询键；别名缺失不得返回 `settled`。最终键升级、别名与权威 usage 同事务或同事务 outbox，任一步失败不得确认成功或换键重发；临时键查询别名缺失不得 `settled`，最终键查询唯一 usage 存在须 `settled`。

**验收**
```powershell
cd aiexcel
pnpm run test
pnpm run build
```
- 同 ticket 并发仅一次成功；重启后重放失败；缺凭据/错 slug 失败关闭。
- 当前仓库未找到覆盖 aiexcel/app/auth-sso.ts 的 SSO 并发消费/重启重放测试；须新增“两并发仅一条成功、重启后同 jti 拒绝”的可执行测试，不能只靠代码阅读判定通过。
- Compose 缺任一凭据即渲染/启动失败；携带付款/抽成头被主站 403。
- 只带 `X-Sub2API-Commission-Rate`、不带 `X-Sub2API-Payer` 同样被拒绝；非数字、负数、`>=1`、`NaN`、`±Inf` 不得被静默忽略或转成普通用户请求。
- 主站不得静默钳制合法费率：`0.9501`、`0.99`、`0.999` 要么按显式上界计算，要么在扣款前明确 4xx 拒绝；不得“接受 0.99 却按 0.95 扣款”。同一 request_id 重放必须复用首次付款人与费率快照。 Payer 存在时佣金头缺失/为 0 的语义必须两端一致：若 0 表示平台不抽成（Payer 承担 `actual_cost` 全额），必须在接口契约中写死并允许省略头；若不允许省略，Payer 存在而费率缺失/非法时必须 4xx。无论选哪种，不得把 0 解释为 `PayerCost=0`；零扣款只允许来自订阅成功行（`billing_subject=subscription`，含 `ActualCost=0` 的零成本订阅）、`ActualCost=0` 且 `TotalCost=0` 的 `free` 成功行、客户报价 0 但上游 `TotalCost>0` 的余额/订阅免费策略行（不得写 `free`，账号配额仍按 `TotalCost * AccountRateMultiplier` 累计），或未来显式开放的 100% 抽成余额行；必须同时看 `billing_subject` 与 `total_cost`，不能单凭 0 猜来源。当前 `rate>=1` 被拒绝，不得把佣金 0 当成零扣款。
- 用稳定 `request_id` 调 `GET /v1/sub2api/usage?request_id=<id>`：`actual_cost` 等于该 slug 配置的报价（未配置自定义价时等于模型 `actual_cost`；因报价先舍入 6 位、命令再量化 8 位，允许不超过 `5e-7` 的舍入差），`total_cost` 仍是模型/渠道成本；模型/渠道成本不可得时必须显式阻断或标记未归类，不得让 `total_cost=0` 的成功权威行参与统计或对账；命中自定义价时 `rate_multiplier = 1` 且 `billing_mode` 与规则单位一致（`token` / `image` / `video` / `per_request`），不得把按量规则误写为 `per_request`；未命中自定义价且主站为空 setting 键/显式 `mode=model` 时，`rate_multiplier` 才可等于该 Key 的实际倍率；`custom/request/points` 的 `rules=[]` 属配置误用，必须失败关闭，不能靠清空规则回模型价；其他模式未命中必须失败关闭。 另须验证：卫星 SuperKey 未绑组时，主站必须按“用户全部有效订阅”判定：`ListActiveUserSubscriptions(userID)` 返回 0 条走余额，1 条走订阅，2 条及以上请求前显式拒绝，且不写 usage/余额/Key 配额；拒绝码固定为 `MULTIPLE_ACTIVE_SUBSCRIPTIONS`（未映射时至少 403 `billing_error`），不得以订阅 + Payer 错误或任意一条订阅替代多订阅拒绝；请求前预检与后扣必须复用同一请求内订阅快照（不得各自重查；预检后新增/失效订阅不得改变本次账本分支），不得按请求头组、实际调度账号组或订阅 ID 排序任选一条。订阅已命中时 `isSubscriptionBill` 必须为真，且必须由显式账本分支字段表达“未解析/确认无订阅/唯一订阅”，不能继续用 `Subscription=nil` 兼表三态，不得仅因 `apiKey.Group == nil` 或 `apiKey.Group` 非订阅组而落到余额。SuperKey 会跨启用组选号，实际账号组不等于请求组，不能直接套用。平台配额只适用于余额模式：余额模式下按资金主体 `(PayerUserID 或 UserID, 解析出的请求平台)` 与本次 `charged_cost` 累计（余额自付等于 `ActualCost`，代付等于 `PayerCost`）；`Payer == User` 时即为 `(UserID, ActualCost)`。订阅模式走订阅账本，不写 `user_platform_quotas`；不得按 `UserID + ActualCost` 默认记账而让 Payer 额度漏计。平台解析失败时必须显式阻断或记录可对账的未归类消费，不得静默跳过。命中卫星报价时 `api_keys.quota_used`、Key 限流必须按报价（`actual_cost`）累计。另须断言 `/v1/sub2api/usage` 返回本次 typed 额度快照与精确金额，包括 `api_key_id`、`billing_subject`、`payer_user_id`、`charged_cost`、`api_key_quota_cost`、`api_key_rate_limit_cost`、`account_quota_cost`、`platform_quota_subject_user_id/platform_quota_platform/platform_quota_cost`、`subscription_cost` 及 `*_usd_nanos`/定点十进制：余额模式自付时 `payer_user_id=user_id` 且 `charged_cost=actual_cost`；订阅模式必须返回 `billing_subject=subscription` 且 `charged_cost=0`，不得把订阅未扣资金误判为余额零扣款；若主站对本项目启用代付，则 `payer_user_id` 必须为实际付款人、`charged_cost` 为实际扣款额。字段缺失或历史 `NULL` 不得被解释为自付；`charged_cost=0` 必须能与历史 `NULL` 区分。佣金为 0 表示 Payer 承担全额成本（`charged_cost=actual_cost`），不得误写成 0。余额模式下解析出平台后 `user_platform_quotas` 必须按同一资金主体与 `charged_cost` 累计。不得用泛化 `quota_subject_user_id` 或 JSON 浮点代替；金额验收比较 nanos/定点，不得先把主站 8 位金额四舍五入到分。  另须断言零扣款来源：`billing_subject=subscription` 且 `charged_cost=0` 只表示订阅账本，不得当作余额零扣款；`free` 仅 `ActualCost=0` 且 `TotalCost=0`，五类额度均为 0；其余成功行一律不得以 `charged_cost=0` 作为免扣款理由。另须覆盖失败尝试：后扣失败后，`usage_logs` 不得出现该 `(request_id, api_key_id)` 的零金额成功行，必须写独立 `billing_attempts`（含 `attempt_no/failure_stage/error_code/actual_cost/charged_cost/total_cost/用量/video_duration_seconds/duration_source`）；同键重试成功后才形成唯一真实金额权威行，资金只变化一次。 本项目当前无自有 Provider 现金路径，同步 AI 代调只走主站 relay；不得用主站 `/v1/sub2api/usage` 缺失或余额不变证明未重复建单/未重复计费，幂等验收以 `X-Client-Request-ID` + 权威 usage 为准；不得另建一套 Provider 幂等或双轨验收。
- **usage 命中不是结算证据**：查询必须按 `request_id + 主站 api_key_id`（或主站等价精确过滤）判定；0 行只表示主站暂时不可见/未写入，多行或主站 `api_key_id` 缺失 `NULL` 一律视为不可唯一确认。以上任一情况都不得把任务标为已结算、不得扣本地钱包/额度、不得重试生成新键、不得改用余额差或本地报价补猜，只能保持 `pending`/待对账；只有唯一权威行且 `request_id`、主站 `api_key_id`、付款主体与金额逐项一致时才允许确认。
- **订阅行主体必须完整且不得回退余额**：命中行 `billing_subject=subscription` 时，`subscription_id` 必须非空，`subscription_cost` 必须存在且等于该行 `actual_cost`（零成本订阅写 `0`，不得为 `NULL`），`charged_cost=0`；`balance_cost` 必须为 0 且不得同时出现余额实扣或非本人 Payer 实扣。缺主体、缺金额或与余额证据冲突时，只能 `pending`/人工复核，不得按 `charged_cost=0` 确认“未扣款”。`billing_subject=free` 仅限 `actual_cost=0` 且 `total_cost=0`，不得替代缺失的订阅主体。
- **纯文本 token 缺失不得按次**：主站 `custom` 模式若对本项目配置了 `millionTokens` 规则，纯文本调用必须取得可信 token 合计后按 `token` 计价；上游未返回 usage、解析失败或仅图片 token 时，不得静默落 `request` 或模型价，必须失败关闭/待对账；同目标同时有 `token` 与 `request` 时固定优先 `token`。上游明确返回 0 token 可按 `millionTokens` 得 0 金额，但 `billing_mode` 仍为 `token`，须与“用量未知”分开断言。 **当前实现未满足该零用量分支**：`quoteSatelliteBilling` 仍以 token 合计 `>0` 才尝试 `millionTokens`，0 用量会落到 `request`/模型价；修复前该用例只能标为失败/待实现，不得按现网行为验收通过。
- **配额主体必须与资金主体一致**：本项目不发送 Payer/抽成头，普通请求 `Payer == User`，但验收仍须能证明余额、Key 配额、Key 限流、账号配额与平台配额由同一计费快照复算：Key 配额/限流记在发起请求的 APIKey、金额为 `ActualCost`；账号配额仅对 `APIKey`/`Bedrock` 类型账号按实际 `account_id` 与 `TotalCost * AccountRateMultiplier` 累计（`usage_billing_repo.go:212`），其他账号类型 `account_quota_cost=0` 且不写账号配额；平台配额仅在余额模式按资金主体 `(PayerUserID 或 UserID, 请求平台)` 与 `charged_cost` 累计，订阅模式不写 `user_platform_quotas`。若主站将来对本项目启用代付，须按 S2A-09 冻结的账本事实与 Payer 互斥切换为 Payer 资金主体，并按 S2A-08 落 usage 金额与配额字段；Key 配额主键不变，不得出现“余额按 Payer、额度按 User”的分叉。**实现状态**：`UsageBillingCommand` 尚无平台配额字段，service 层仍按 `p.User.ID + cost.ActualCost` 另写；本条平台配额口径修复前验收必须标记未通过，不得把 Redis/DB 另写当作已满足。**PayerCost 同精度**：代付金额 `PayerCost=ActualCost×(1-rate)` 必须在任何仓储扣款、usage `charged_cost` 与平台配额累计之前按 8 位 half-away-from-zero 量化，三者使用同一量化值；当前 `quantizeMonetaryFields` 未覆盖 `PayerCost`（`usage_billing.go:85-91`），第 9 位为 5 的边界（如 `0.000078125×(1-rate)`）修复前必须标失败，不得只在仓储或 usage 单侧补舍入。
- `/v1/sub2api/usage` 当前实现缺口是不返回 `api_key_id` 或 `group_id`，同用户多把 Key 用同一 `request_id` 只能靠行 `id` 区分；这不是接口契约，S2A-08 落地后必须返回 `api_key_id` 并支持按 Key 过滤。在该字段落地前，响应中缺少 `api_key_id` 不得被解释为“当前用户只有一把 Key”或“可以按行 `id` 猜结算”；验收须显式标记为未满足并按 `pending`/人工复核处理。查询固定 `PageSize=20`，同用户大量 Key 可能截断，验收须给出上限/分页语义。
- 本项目仅文本/结构化输入，不要求视频回退；但仍须断言：若上游或代理误传 `VideoCount > 0`，主站不得静默落到 `token`/`request` 规则，必须按 S2A-08 fail closed。
- **只读余额/状态查询不进入计费账本**：本项目存在经 `/api/sub2api/balance` 转发到主站 `GET /v1/sub2api/balance` 的展示/预检调用；该接口只能读取余额，不得生成 usage、占用计费键、扣余额/配额或作为“请求已成功结算”的证据。验收须断言余额查询前后 `usage_logs`/`billing_attempts` 行数、余额、Key/账号/平台额度均不变，且查询失败不得触发重试计费或改变本次模型请求的账本分支。若某次余额查询同时携带了模型结算键，仍只能按只读处理，不得复用该键产生 usage。
- 同一 Key、同一 `request_id` 的**已成功结算**请求重放：`/v1/sub2api/usage` 只返回首次权威记录（first-write-wins），不追加第二行；失败尝试走独立失败审计、不占结算键，成功重试后才形成唯一权威行；同一账本下余额、Key 配额、订阅用量与 usage 行均只变化一次。去重键是 `(request_id, api_key_id)`；同一用户换 Key 使用同一 request_id 会生成第二条记录，不得写成全局“一个 request_id 只一条”。重放命中时不得用本次模型、token、金额、`billing_mode`、订阅或付款人覆盖首次 usage；付款人或费率与首次不一致时，必须返回明确冲突或既有结果并写审计，不得静默换人扣款。
- **媒体请求缺数量不得按次/按 token 成功**：本项目若存在生图或图片编辑路径，主站 `quoteSatelliteBilling` 只在 `ImageCount>0` 时尝试 `image` 规则；请求已明确为生图但张数为 0 时会落到 `token`/`request`。验收必须覆盖 `ImageCount=0` 的明确生图请求，断言失败关闭/待对账而不是按次成功；视频同理覆盖 `VideoCount=0`、`VideoDurationSeconds>0`。若本项目确无该媒体路径，须在卡内显式写“无此路径”并给出路由/调用证据，不得默认跳过。
- 若主站对该 slug 启用 `custom/request/points` 规则：本卫星实际使用的目标/单位必须在规则中命中；未命中时请求必须失败关闭并返回可定位错误，不得静默按模型价扣费。`points` 模式只允许整数点数，金额按 `点数 × 0.01` 换算；`request` 单位得到 `billing_mode=per_request` 且 `actual_cost = 点数 × 0.01`，`image`/`videoSecond` 分别按图片数/秒数乘点数，`millionTokens` 必须被配置校验拒绝（`satellite_billing.go:114-122/356-359`）。不得把 `per_request` 一律当作固定 1 次请求而不乘 0.01，也不得把 `points` 的 `request` 规则误判为 `custom` 的 token 兜底。
- 本项目若存在异步上游任务/轮询/回调（视频、导出、批处理、WebSocket 结果等），必须用服务端可复用的稳定业务键派生 `request_id`：优先取上游任务 ID，或调用方在提交时已验明的业务幂等键；创建、多次轮询、完成回调只能产生一个结算键。服务端随机生成的本地 `jobId`/`taskId` 若每次重提都会变化，不得当作结算键；若仅在创建后才取得上游任务 ID，必须先持久化创建意图，不能等拿到 ID 再补键。**主站已按 S2A-02 接收并校验 `X-Client-Request-ID` 后**，才可断言最终恰有一条权威 usage / 只扣一次；未落地前必须标记“结果不确定/需对账”，不得每次轮询新生成 `request_id` 或据本地键默认成功。补“同一任务轮询 N 次 + 回调 1 次”只产生一条权威 usage、`/v1/sub2api/usage` 只一条的端到端测试；若本项目无此类路径，须在验收中显式写“无异步上游任务”并给出路由/调用证据。
- 本项目虽无异步上游任务，但 AI 代调是同步付费入口：`app/api/ai/route.ts:38-67` 直接 `POST /chat/completions`，`app/auth-sso.ts:33-43` 的 `satelliteHeaders` 只返回 `Authorization`/`Content-Type`/`X-Sub2API-On-Behalf-Of`/`X-Sub2API-Satellite`，没有 `X-Client-Request-ID`。主站已受理但 Next.js 请求读超时/断连时，客户端重试会再次调用模型；本地没有请求行，无法按原请求查回 usage 或证明未扣费。
- 要求：调用前按 `(user_sub, 业务键)` 持久化 `creating` 意图（业务键可由工作簿摘要 + 用户请求 + 历史窗口摘要派生），把同一键作为 `X-Client-Request-ID` 发送；命中已完成返回原计划，命中进行中返回真实状态或 409，不得再次调用模型。读超时/断连进入 `unknown/需对账`，先按该键查 `/v1/sub2api/usage`；只有主站 `request_admission=rejected_before_upstream`、`dispatch_state=not_started`（须由写出点事件证明，不得仅凭时间戳为空）、`funds_effect=none` 且 `quota_effect=none` 时才可重发；`not_seen`/`accepted`/`unknown`/0 行均只能保持待对账。`activeRequests` 只防同进程并发，不能替代跨重启幂等；同一用户不同请求必须使用不同键，不能因去重而返回旧计划。
- 验收：同一业务键重复提交只产生一条权威 usage、模型调用 1 次；主站已受理但响应丢失后重提返回原计划或待对账，不得再次调用；重启后同键仍命中持久意图；不同工作簿/不同用户相同文本不得互相命中。S2A-02 未落地前只能标记待对账，不得宣称只扣一次。
- **上游 2xx 与本地解析失败必须分账**：当前 `app/api/ai/route.ts:68-75` 在 `response.ok` 后用 `response.json()`、`JSON.parse(text)` 与 `plan.title/operations` 校验；任一失败都会走统一 catch 返回 `500`，但主站可能已完成模型调用并写入 usage。要求持久拆分 `upstream_status`（HTTP 码）、`upstream_request_id`、`usage_state`（`settled/not_found/unknown`）与 `plan_status`（`valid/invalid`）；`plan_status=invalid` 不得改写 `upstream_status=2xx`，不得把它标成“上游未受理”。
- 本地解析失败只能返回可诊断的 `PLAN_INVALID`（或等价业务码）并保留原键与上游请求号；不得自动重发模型、不得生成新 `request_id`、不得据 `500` 自动退款或零扣款。先按原键查 `/v1/sub2api/usage`：有唯一成功行则确认已结算并以 `PLAN_INVALID` 待人工/用户重试“仅解析”，无行且主站 `request_admission=rejected_before_upstream`、`dispatch_state=not_started`（须由写出点事件证明）、`funds_effect=none`、`quota_effect=none` 才可按原键重发；查询 0 行、`not_seen`、`accepted`、`unknown`、`conflict` 均不等同未受理。

### AIE-05 单用户并发限制（P2）

**现象与证据**
- `app/api/ai/route.ts:4` 的 `activeRequests` 是模块级 `Set`；`:43-45` 用它拒绝同用户并发，`:77` 在 finally 删除。
- 该锁只在单个 Node 进程生效；重启后直接清空，多副本各自放行。
- 该路由是同步转发到 `/chat/completions`，没有异步任务状态或后台 worker；因此本卡不要求任务恢复，只要求并发限制真实生效。
- 同步转发不代表重试安全：本卡的全链路验收已要求主站接收并校验稳定计费键；在 S2A-02 落地前，上游超时后的自动重试不得被写成“只扣一次”。并发锁只解决同用户同时提交，不能替代主站计费幂等。

**实施步骤**
1. 把单用户并发计数改为共享原子存储（如 Redis `SET NX` 带 TTL 或数据库唯一键），以 `user.sub + 请求窗口` 为键。
2. 获取失败返回 429 并带明确 `Retry-After`；上游超时、客户端断开、进程退出都必须释放或依赖 TTL 自动过期。
3. 若坚持单进程限制，必须在文档中写明“不支持多副本”，并禁止以该锁宣称全局限流；生产 Compose 固定单副本。

**验收**
- 两个副本同时收到同一用户请求，只有一笔进入上游，另一笔 429。
- 进程在请求中途退出，锁在下一次请求前过期或可恢复，不会永久卡死用户。
- 正常请求完成后可以立即发起下一笔；不得用无 TTL 的永久键。
- 运行 `pnpm run test`，新增并发、重启/过期和多副本用例。

## 6. 全链路验收

- 从主站菜单进入，SSO 成功、Session 3 天、注销可撤销。
- 主站 usage/反查必须返回 `request_admission` 六态（`not_seen`/`accepted`/`rejected_before_upstream`/`settled`/`conflict`/`unknown`）及真实最终键、`admission_source/funds_effect/quota_effect/dispatch_state/state_version/query_request_id/final_request_id`；0 行、`not_seen`、`accepted`、`conflict`、`unknown` 均不得触发自动重发、免费释放或重复扣款，只有 `rejected_before_upstream` 且 `dispatch_state=not_started`（须由写出点事件证明，不能靠时间戳为空、4xx 状态码或本地异常推断）才可重试。自动重发/免费处理还必须 `funds_effect=none`（余额、欠款、订阅用量无资金变化）且 `quota_effect=none`（Key/限流、账号、平台、订阅额度均未写）；本站钱包释放只按本地预留与主站资金效果判断；`quota_effect` 既不是释放前提，也不是拒释前提，不得因主站额度变化改扣本站钱包。`accepted`/`unknown` 表示可能已调上游，必须待对账；已读到唯一成功 usage 必须为 `settled`，不得因冲突态降级为未结算。同一请求只能有一条 admission（先以临时键建行，最终键只一次 CAS 写入 `final_request_id`），临时键与最终键必须经 `request_admission_alias(alias_request_id, api_key_id, admission_id, final_request_id)` 单跳反查同一受理事实，alias 行以外键绑定该 admission，禁止引用尚未升级最终键的行；同一临时键改绑、同一最终键归属第二条 admission、别名引用未升级最终键的 admission、别名缺失或 CAS 失败时不得确认。调用上游前必须先提交 `accepted`（临时键仅作 `admission_key`，最终键未定时不得写可解析别名），提交失败不得调用上游；本地拒绝先提交零效果受理，提交失败只能返回 `unknown`/不可重试；最终键、别名与权威 usage 同事务或同事务 outbox，任一步失败不得确认成功，不得自动换键重发。
- **受理与别名验收必须可执行**：同一临时键并发绑定两个最终键时恰一条成功、另一条 `conflict`；同一请求由临时键建 admission 后改用最终键查询，不得产生第二条 admission，最终键只能一次 CAS 写入；同一最终键被两个临时键/两条 admission 指向时恰一条成功；临时键别名缺失而最终 usage 已存在时，查询必须返回 `unknown`/待对账，不得返回 `settled`；直接查询最终键且唯一 usage 存在时必须返回 `settled`（`admission_source=usage`），不得因别名未写降级；所有查询（含 `usage_count=0`）必须回传完整 `admission_source/funds_effect/quota_effect/dispatch_state/state_version/query_request_id/final_request_id`，且 `query_request_id` 逐字等于查询键；临时键与最终键反查必须命中同一 `state_version`。注入受理写入失败时上游调用计数必须为 0；注入别名或 usage 写入失败时不得返回成功或自动换键重发。
- 表格解析、AI 计划、导出均归属当前用户。
- 余额不足、模型失败、缺凭据有明确错误，不静默回退。
- 跨用户访问、票据重放、重启重放均被拒绝。
