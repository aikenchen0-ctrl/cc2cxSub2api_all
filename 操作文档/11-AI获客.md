# AI 获客测试操作与验收手册

## 1. 文档基线与范围

- 源码核对日期：2026-10-08，依据当前工作区 `aihuoke/ai-hunter-root/`，包含尚未提交的项目更新。这是可执行的测试手册，各用例初始为“未执行”，不是线上/本地已通过的测试结论。
- 本地入口：<http://localhost:3001>；从 <http://localhost:18080> 登录后点击“AI 获客”进入，应用标识 `aihuoke`。
- 覆盖仪表盘、新建任务、自动化队列、挖掘详情、继续挖掘、线索质量、报告导出、邮件审核/发送/回信、持牌找人旁路、设置与用户隔离。
- 记录源码版本、镜像构建时间、浏览器、搜索源与队列消费者状态。运行镜像可能落后当前源码；旧界面应先定位版本差异，不能套用旧文档中的“开始挖掘”按钮。
- P0：主流程、身份隔离和发送控制；P1：异常恢复、关键分支与导出；P2：显示和兼容性。模型、搜索、BetterContact 的付费调用与 SMTP/通知外发分别记录。

## 2. 测试准备与入口

| 项目 | 准备与核对 |
| --- | --- |
| 用户 | A、B 两个测试账号，用独立浏览器配置文件登录；另备匿名窗口 |
| 测试资料 | `QA-product.txt`：虚构开关产品介绍、适用行业、排除条件；不要填真实客户名单、认证、价格或交付承诺 |
| 数量 | 最小主流程设目标线索 2、最大轮数 1、每轮最少新增 1；不用页面默认值做高成本循环 |
| 模型/搜索 | 服务端托管模型默认 `gpt-6-astra`，受 `SUB2API_RELAY_MODEL` 配置影响；搜索源、网站可访问性及额度单独核对 |
| 队列 | 确认 API、队列消费者及模板种子 worker 在实际测试环境可用；仅 API 存活不代表队列能执行 |
| 邮件基线 | AI 邮件生成关闭；在测试环境核对 dry-run 开启、自动发送关闭；隔离真实 SMTP 收件人与外发通知 |
| 邮件专项 | 使用自有测试邮箱与测试收件箱；SMTP/IMAP测试、飞书测试都可能连接外部系统，不能当作纯查看操作 |
| 持牌找人 | BetterContact 单独配置及测试积分；准备受控域名与职位条件，避免无条件购买大批联系人信息 |
| 证据 | 测试前余额、任务数、搜索配置摘要、邮件开关、执行时间；请求证据脱敏，不记录完整密钥和联系人数据 |

直接访问页面可能被登录状态阻断，应通过主站重新进入。页面路由为首页 `/`、`/hunts/new`、`/automation/$jobId`、`/hunts/$huntId`、`/licensed-finder`、`/settings`。不要自行填写托管模型的 API Key 或 SuperKey。

## 3. 登录与仪表盘（HUNT-001，P0）

1. A 从 Sub2API 菜单进入，查看仪表盘的任务、线索和自动化状态。
2. 打开新建任务、持牌找人、设置，再返回仪表盘。
3. 在匿名窗口直接访问受保护接口；B 登录后查看自己的仪表盘。

预期：SSO 后直接可用，菜单对应实际页面，空列表有明确状态；匿名接口拒绝，B 不显示 A 的任务。仪表盘数量与当前用户数据一致；若消费者未运行，保留该状态作为环境阻塞证据。

## 4. 新建任务与自动化队列

### 4.1 最小挖掘任务（HUNT-002，P0，模型/搜索调用）

1. 点击新建任务，输入以下描述：

   > 测试产品是微动开关和旋转开关，寻找美国的电气元件分销商与进口商。排除个人消费者、招聘网站和百科页面。仅收集有官网来源的公司线索，不发送邮件，不编造联系人或认证。

2. 公司官网可留空，或填写自有测试网站。描述、网址、上传资料在当前表单均不是单独必填的前提；完整空表单另做校验用例。
3. 在产品关键词输入 `micro switch` 后按 Enter/加号，再输入一次同词；添加地区 `United States`。最后一个待输入关键词保留在输入框中，不按 Enter。
4. 设目标 `2`、最大轮数 `1`、每轮最少新增 `1`，保持“AI 邮件生成”关闭。
5. 点击一次“提交到队列”，记录跳转的 `/automation/{jobId}`。
6. 核对任务参数，等待消费者领取；挖掘建立后记录 `huntId`，从任务页打开详情。

预期：关键词/地区去重，提交时未确认的输入也纳入；只新增一个 queue job。新任务先排队，不直接作为已完成 Hunt。可观察消费者领取、创建/等待挖掘、加载结果、完成/失败等阶段；开启邮件后还可能有模板种子和 Campaign 阶段。任务参数与表单一致。

页面当前默认值为目标 20、最大轮数 2、最少新增 1；服务端参数上限不同，见边界表。测试报告必须记录实际提交值，不能只写“默认配置”。

### 4.2 资料上传（HUNT-003，P1）

1. 在新建任务通过文件选择器上传 `QA-product.txt`，再上传一份含表格的 PDF/DOCX/XLSX样例。
2. 核对已上传文件列表，移除不需要的文件后提交小任务。
3. 分别测试支持扩展名、损坏文件、空文件及超限文件，不将异常文件提交成大量挖掘。

预期：支持 txt、md、pdf、docx、doc、xlsx、xls、csv、json；上传结果只包含当前用户的文件，删除选择后不应随任务发送。默认单文件上限 50 MB，以实际配置为准；上传成功不等于资料已解析成功，须在执行日志/结果中确认内容被使用。UI 文案含拖放提示，但当前可确认的处理入口是点击选择，拖放需单独实测并记录差异。

### 4.3 队列实时状态与恢复（HUNT-004，P0）

1. 在任务页查看阶段、当前线索数、参数、错误和关联 Hunt。
2. 刷新页面，再短暂断网/恢复，确认仍查看同一 `jobId` 和 `huntId`。
3. 在队列消费者停用的隔离环境提交一次，观察排队状态；恢复消费者后检查领取执行。
4. 仅在已准备的小任务上测试取消；对失败/完成任务的重试另记录新执行。

预期：SSE实时更新，连接失败时通过轮询恢复（任务约 10 秒、结果约 5 秒）；刷新/重连不自动新建任务。排队/运行可取消，失败/完成可重试，操作反馈与后端状态一致。重试可能再消耗模型/搜索额度；取消不能撤回已发送邮件，也不保证已发出的外部请求立即停止。

## 5. 挖掘结果、继续挖掘与导出

### 5.1 核对详情和线索质量（HUNT-005，P0）

1. 打开 `/hunts/{huntId}`，依次检查“概览、线索、AI邮件、邮件日志”。
2. 核对实际轮数、搜索统计、终止原因、原输入与当前线索数量。
3. 抽查至少 2 条或全部少量线索：公司名称、官网、国家、联系人/职位、邮件、电话/社交来源、匹配理由。
4. 点击来源网站人工比对；检查重复公司/域名/邮箱，以及邮箱是验证结果还是推断。

预期：显示的结果来自本次任务，证据链接可追溯。推断信息不得冒充验证事实；没有邮箱也可为有效公司线索。轮数/最少新增阈值可使任务在达到目标之前结束，“完成”不承诺恰好得到目标数量。搜索源不可访问、完全空结果或百科替代商业线索不能仅因状态完成就判功能通过。

### 5.2 继续挖掘（HUNT-006，P1，计费）

1. 在有结果任务点击“继续挖掘”，核对继承线索和公司洞察等提示。
2. 将目标/轮数限制为小值，保持邮件关闭，提交。
3. 记录新的 queue job ID，检查其关联任务、历史线索、已访问网址及新增结果。

预期：创建可追踪的新队列执行，保留已有线索和去重上下文，新增结果不无故重复；来源任务与继续执行关系明确。即使未达到目标，也应解释轮数/阈值或外部失败原因。

### 5.3 报告与 CSV（HUNT-007，P0）

1. 分别下载文本报告 `.txt` 和线索 CSV，记录下载来源、文件名和行数。
2. 用文本编辑器/表格软件打开，核对中文编码、表头、每条来源、空邮箱、逗号/换行/引号字段。
3. 对照页面的唯一线索数与 CSV 数据行，检查不同账号/不同任务不会混入。
4. 在隔离环境模拟服务端导出失败，检查前端本地导出回退及文件内容。

预期：文件真实可用，数据与任务结果一致；即使走本地回退，也要核对完整性，不能仅凭下载提示判定通过。报告不含服务密钥、别人的私密资料或隐藏内部路径。含公式前缀的导出字段应作为表格安全检查项记录，不能靠 CSV 扩展名推定安全。

## 6. 邮件生成、审核与发送专项

### 6.1 草稿与模板种子（HUNT-008，P1，计费）

1. 在隔离测试环境确认 `email_dry_run=true`、`email_auto_send_enabled=false`，记录 SMTP和Campaign实际状态。
2. 新建小任务，开启 AI 邮件生成；填入一条虚构产品模板和语气说明，多条历史模板按空行分隔。
3. 观察模板种子状态、worker、生成的 3 步英文邮件与审核信息。
4. 在“AI邮件”逐条核对称呼、产品事实、来源依据、主题、正文、跟进关系和“需人工复核/可建发送流程”。

预期：邮件与线索对应，没有编造价格、认证、客户案例和邮箱。关闭邮件生成的主流程不应无条件生成邮件。邮件生成开启后消费者可能自动创建并启动 Campaign，不能因为只点了生成就断言绝无发送；以 dry-run、发送开关、审核、实际日志和测试收件箱共同验证。

### 6.2 审核门槛与一次受控发送（HUNT-009，P0，外发专项）

1. 在测试邮箱环境尝试发送未批准/被拒绝的序列，查看拒绝结果。
2. 对已批准且符合发送资格的草稿，核对收件人是自有测试收件箱，再执行一次发送。
3. 对照草稿、Campaign、邮件日志和实际收件箱中的主题/正文、时间、Message ID。
4. 模拟 SMTP不可用、发送窗口/日限额不满足，检查 queued/sent/failed 的区别及重试记录。

预期：审核和发送资格在服务端生效；缺少 SMTP配置或最近成功连接测试时不能误报已发送。dry-run不产生真实邮件，queued 不等于 sent。一次发送不会因重复点击/刷新造成不明重复；失败保留原因。仅审批不等于 SMTP、限额、发送窗口都已满足。

### 6.3 回信与连接测试（HUNT-010，P1，外部服务）

1. 在“设置”核对 SMTP 与 IMAP 状态、最近成功测试时间及对应开关。注意点击连接测试会先保存当前表单。
2. 用测试邮箱完成 SMTP测试；需要回信检测时再配置/测试 IMAP，回复一封本次测试邮件。
3. 执行/等待回信检测，核对匹配到的发送记录、回复计数和邮件日志。

预期：SMTP用于发信，IMAP用于查回信；缺少 IMAP不阻止生成草稿，也不能被当作已完成回信检测。测试失败显示原因且不留下错误成功状态。飞书通知测试作为单独外发用例，仅发往测试渠道。

## 7. 持牌找人旁路（BetterContact）

### 7.1 条件检索（HUNT-011，P1，第三方额度）

1. 打开“持牌找人旁路”，查看 readiness状态；记录是否配置，readiness探测本身不购买联系人。
2. 填受控公司域名、行业、职位、资历、国家、技术条件与筛选理由；最大结果设 2。
3. 保持购买邮箱/电话选项关闭，执行检索，核对结果、来源和空邮箱状态。

预期：旁路与主挖掘图独立，不自动变成 Hunt。结果上限默认 10、允许范围 1–200，以当前接口校验为准；邮箱/电话补全默认关闭。检索本身也可能消耗 BetterContact积分，需分别记录搜索与补全账单。

### 7.2 补全与 CSV（HUNT-012，P1，购买信息专项）

1. 核对当前结果和费用提示，仅在测试预算内点击“补邮箱（花钱）”；执行后记录第三方回执，不假设还会有二次确认。
2. 导出 `licensed-finder-leads.csv`，检查十列：`email,first_name,last_name,company,title,website,linkedin_url,reason,lead_id,qualified_at`。
3. 核对空字段、中文、引号转义、邮箱结果与购买数量。

预期：“补邮箱（花钱）”针对当前结果明确请求邮箱（email=true、phone=false、catchall=false），不是免费刷新；失败有真实原因。CSV格式可供后续工具使用，但导出不自动导入 Instantly、不自动发送、不证明所有邮箱已验证。

## 8. 边界、失败与安全回归

| 用例 | 优先级 | 操作/输入 | 预期结果 |
| --- | --- | --- | --- |
| HUNT-013 数值边界 | P1 | 目标 0/1/10000/10001；轮数 0/1/50/51；最少新增 0/1/100/101；空值/小数 | 服务端范围分别 1–10000、1–50、1–100；无效值明确拒绝，不静默开大任务。上限用校验测试，不实际跑满 |
| HUNT-014 空输入/网址 | P1 | 全空、无效网址、描述-only、重复/待确认关键词 | 记录当前前后端校验一致性；可接受的描述-only不强迫网址；无有效目标应有清楚提示或可解释失败，不编造结果 |
| HUNT-015 文件边界 | P1 | 默认 50MB附近、超限、重复名、中文名、损坏/不支持格式 | 超限按实际配置拒绝并清理未完成上传；解析失败有定位；上传列表和提交文件一致 |
| HUNT-016 搜索/模型故障 | P1 | 在隔离配置模拟超时、额度不足、搜索源不可达 | 保留失败阶段、原始错误和关联ID；不以百科/假线索充数；重试可追溯且可能再次计费 |
| HUNT-017 队列停滞/取消 | P0 | 消费者停用、队列中取消、运行中取消 | 状态与服务端一致，恢复后不执行已取消任务；明确已在途请求/已发邮件不能撤回，不把长期排队标成完成 |
| HUNT-018 用户隔离 | P0 | B访问 A 的 job/hunt/上传文件/邮件/SSE/结果/导出；篡改上传文件ID | 不返回 A 的数据、不执行 A 的任务；常用所有权拒绝为404等，不拘泥单一状态码；文件引用被服务端限制在当前用户目录 |
| HUNT-019 会话与凭据 | P0 | 匿名/过期会话，检查URL、存储、设置响应和错误 | 受保护请求拒绝，主站重入恢复身份；托管SuperKey/第三方完整密钥不在浏览器；设置中秘密字段遮罩，错误不泄密 |
| HUNT-020 发送配置门槛 | P0 | 未通过SMTP/IMAP测试时启用对应开关；未批准/无资格草稿发送 | 前后端均执行门槛；SMTP与IMAP独立，状态不能互相冒充；失败不记作 sent |
| HUNT-021 邮件副作用 | P0 | 生成、取消、重试、继续挖掘、刷新后核对Campaign与收件箱 | 无意外外发/重复外发；dry-run和自动发送设置实际生效；记录每次执行费用及实际投递数 |
| HUNT-022 展示兼容 | P2 | 长公司名/多行正文/无邮箱，1440×900与390×844 | 操作可触达、表格/邮件不覆盖按钮，长内容可滚动查看，空状态明确 |

模型托管模式实际使用 `SUB2API_RELAY_MODEL`（默认 `gpt-6-astra`）；其他配置类中的通用模型默认值不代表该模式请求的模型。抓取脱敏请求/服务端日志核对实际模型和计费归属，不仅看设置页标签。

公共会话约定：新签发/续签的 `aihuoke_session` 和服务端会话均为 3 天（259200 秒），Cookie 为 HttpOnly；SSO ticket 约 2 分钟且只用一次。验证新会话 TTL、重放与过期拒绝；已有旧会话按原有效期自然结束，不为测试强制注销共享用户。

同源 `/api/sub2api/balance` 成功响应应 `Cache-Control: no-store`；专用零余额用户应看到红色充值提示，充值只跳到公开主站 `http://localhost:18080/purchase`。公开 LINK 缺失时禁用充值，不能把 Docker 内部中转地址作为充值链接。模型/搜索调用、BetterContact积分和SMTP投递分别取证；本地支付状态另核对，不进行真实付款。

## 9. 执行记录与清理

每项填写：`用例ID｜未执行/通过/失败/阻塞｜环境/版本｜账号代号｜jobId｜huntId｜阶段｜模型/搜索源｜耗时｜预期｜实际｜证据｜缺陷ID`。未配置队列/搜索源、额度不足、测试邮箱不可用记阻塞，同时记录提示是否合理；有任务状态但结果错误不能判通过。

缺陷至少提供最小输入、操作顺序、两种ID、阶段与错误原文、脱敏请求状态、截图、导出字段/行数对照。邮件问题另附 dry-run/自动发送/审核状态、Campaign ID、实际投递证据。不要在报告中写完整个人邮箱、电话号码、Cookie、ticket或密钥。

执行结束先保存证据，再取消自己尚未执行的队列任务，检查 Campaign和待发邮件，清理自己的测试资料与下载文件。取消任务不撤回已发送邮件；没有页面删除入口的数据由管理员按任务ID处理，不能直接清空共享任务库、邮件库或队列。设置只在隔离环境测试，结束后恢复本次更改并复核开关。
